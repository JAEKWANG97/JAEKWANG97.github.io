## AI가 웹사이트를 쓸 때도 버튼을 찾아야 할까?

사용자가 AI에게 이렇게 요청했다고 해보겠습니다.

> 무선 키보드를 찾아서 가격이 낮은 순서로 보여줘.

사람이라면 검색창에 단어를 넣고 정렬 메뉴를 바꾸면 됩니다. 브라우저를 조작하는 에이전트도 비슷한 일을 할 수 있습니다. 화면이나 DOM을 읽고, 검색창을 찾고, 값을 입력한 뒤, 정렬 메뉴의 의미를 해석하는 방식입니다.

그런데 웹사이트 개발자는 이미 이 기능을 알고 있습니다. 검색어와 정렬 조건을 받아 검색을 실행하는 애플리케이션 로직이 있기 때문입니다.

**그 기능의 이름과 입력 형식을 AI에게 직접 알려주면 어떨까요?**

WebMCP는 웹페이지가 AI 에이전트에 구조화된 도구를 제공하도록 하는 웹 표준 제안입니다. JavaScript로 함수를 등록하거나 HTML 폼에 속성을 추가하면, 에이전트가 페이지의 기능을 더 명시적인 방식으로 사용할 수 있게 합니다.[1]

이 글에서는 WebMCP가 무엇인지 먼저 살펴보고, 상품 검색 하나가 실행되는 과정을 따라가며 동작 원리를 설명합니다. 이어 실제 API 형태와 권한·보안상의 경계를 정리합니다.

2026년 9월 7일 확인한 Chrome 공식 문서를 기준으로 작성했습니다. WebMCP는 논의와 실험이 진행 중이며, 아래 코드는 설명용입니다. 이 글에서 지원 브라우저를 이용한 네이티브 WebMCP 실행 실험까지 수행한 것은 아닙니다.[1]

## Claude Code에 명령하면 화면은 어떻게 바뀔까?

사용자가 Claude Code에 “무선 키보드를 낮은 가격순으로 보여줘”라고 요청하면, WebMCP 도구를 통해 검색이 실행되고 화면의 상품 순서가 바뀝니다.

![사용자가 Claude Code에 가격순 검색을 요청하면 별도 브라우저 연결 계층을 통해 WebMCP 도구가 실행되고 웹페이지의 상품 순서가 바뀌는 전후 비교](./_assets/webmcp/claude-code-webmcp-flow.svg)

여기서는 Claude Code가 사용할 수 있는 도구 연결 계층이 브라우저의 WebMCP 도구를 전달한다고 가정합니다. **Claude Code가 WebMCP를 기본 내장 지원한다는 설명은 아닙니다.** 실제 연결 구현과 지원 여부는 별도로 확인해야 합니다.

### 웹서비스와 브라우저는 각각 무엇을 할까?

웹서비스는 WebMCP 규격에 맞춰 도구의 이름·입력 형식·실행 함수를 등록합니다. Chrome 같은 지원 브라우저는 등록된 도구를 에이전트가 발견하고 호출할 수 있도록 중개합니다.[1][2][4]



따라서 **웹서비스마다 별도 MCP 서버를 만들어야 하는 것은 아닙니다.** 웹서비스는 페이지의 기능을 규격에 맞게 제공하고, 브라우저가 그 기능을 이용할 인터페이스를 제공합니다. 다만 이것은 Chrome이 외부 클라이언트용 MCP 서버를 자동으로 만들어준다는 뜻은 아닙니다. WebMCP와 MCP는 별개의 인터페이스입니다.[4]

그림의 Claude Code처럼 브라우저 밖에서 실행되는 에이전트는 브라우저와 연결돼 있어야 합니다. 이 연결은 에이전트 측 연동의 문제이며, 웹서비스의 WebMCP 도구 등록과 구분됩니다.

이때 바뀌는 것은 웹사이트의 소스 코드가 아니라 사용자가 보고 있는 페이지의 검색 조건과 결과입니다. Claude Code가 HTML이나 React 파일을 수정해 개발 서버 화면을 바꾸는 일반적인 코딩 작업과는 다른 경로입니다.

또한 WebMCP가 화면을 자동으로 다시 그려주는 것은 아닙니다. 사이트가 등록한 검색 함수가 기존 애플리케이션 상태와 UI 갱신 로직에 연결돼 있어야 합니다. 뒤의 코드 예제는 이 중 도구 등록과 결과 반환을 설명하며, 그림 전체를 구현한 완성된 연동 예제는 아닙니다.

## WebMCP는 웹페이지가 제공하는 도구 인터페이스다

WebMCP에서 도구는 에이전트가 호출할 수 있도록 사이트가 공개한 기능입니다. 검색, 폼 작성, 화면 이동, 애플리케이션 상태 변경 등이 도구가 될 수 있습니다.[1][2]

상품 검색 도구라면 다음 정보가 필요합니다.

```text
이름: search_products
설명: 검색어와 정렬 조건으로 상품 목록을 조회한다.
입력: query, sort
실행: 사이트의 검색 로직을 호출한다.
결과: 검색 결과 또는 오류를 돌려준다.
```

에이전트가 화면에서 기능의 의미를 추측하는 대신, 사이트가 이름·설명·입력 스키마를 제공합니다. 명령형 API에서는 이 정보와 실행 함수를 함께 등록합니다.[2]

이 구조가 모든 행동을 정확하게 만들어주는 것은 아닙니다. 사용자의 의도를 해석하고 어떤 도구를 호출할지 선택하는 문제는 남습니다. 다만 검색창의 위치와 정렬 버튼의 모양까지 매번 추론해야 하는 부담을 줄일 수 있습니다.

### 웹사이트 전체가 자동으로 API가 되는 것은 아니다

WebMCP를 켰다고 임의의 사이트 내부 함수를 전부 호출할 수 있는 것은 아닙니다. 사이트가 도구를 등록하거나 폼을 도구로 선언해야 합니다.[1][2][3]

또한 지원하는 브라우저·에이전트 쪽의 연결도 필요합니다. 웹페이지에 속성 몇 개를 넣었다고 모든 AI 클라이언트가 즉시 그 사이트를 사용할 수 있는 것은 아닙니다.[1]

사이트 개발자는 무엇을 공개할지 정하고, 브라우저는 도구를 발견하고 실행할 수 있는 경계를 제공하며, 에이전트는 사용자의 요청에 맞춰 도구를 선택합니다.

## 기존 MCP와는 무엇이 다를까?

이름 때문에 WebMCP를 기존 MCP의 브라우저 전송 방식으로 생각하기 쉽습니다. 하지만 Chrome 공식 비교 문서는 WebMCP가 MCP의 확장이나 대체물이 아니며, MCP에서 영감을 받은 브라우저 API라고 설명합니다.[4]

둘 다 기능을 구조화된 도구로 제공한다는 방향은 같습니다. 차이는 그 기능이 놓인 곳과 사용되는 맥락입니다.[4]

| 구분 | MCP | WebMCP |
| --- | --- | --- |
| 중심 | 외부 시스템의 도구·데이터 연결 | 현재 웹페이지의 기능 연결 |
| 실행 맥락 | MCP 클라이언트와 서버 | 열린 페이지와 브라우저 |
| 사이트 탭 필요 여부 | 특정 웹페이지 탭에 종속되지 않음 | 페이지의 수명과 맥락에 종속 |
| 구현 관점 | 도구 서버와 프로토콜 연결 | JavaScript 등록 또는 HTML 폼 선언 |
| 어울리는 예 | 백그라운드 업무 시스템 조회 | 사용자가 보는 페이지의 검색·폼·상태 조작 |

위 표는 일반적인 사용 형태를 비교한 것입니다. MCP를 반드시 원격 서버라고 볼 필요는 없고, WebMCP 도구가 서버 요청을 하지 않는다는 뜻도 아닙니다.

WebMCP는 웹페이지에서 실행되는 함수가 기존 HTTP API를 호출하는 구조로도 만들 수 있습니다. 그 경우 서버의 업무 로직과 인증·인가 체계는 그대로 필요합니다.

```text
MCP 경로의 예
에이전트 → MCP 클라이언트 → MCP 서버 → 업무 시스템

WebMCP 경로의 예
에이전트 → 브라우저 → 현재 페이지의 도구 → 기존 HTTP API
```

사용자가 열어둔 화면에서 검색 조건을 바꾸는 일에는 WebMCP가 자연스럽습니다. 페이지를 열지 않고 정기적으로 데이터를 모으는 일은 별도 서버 연결 방식이 더 적합할 수 있습니다. 두 기술을 서비스의 서로 다른 접점으로 함께 사용할 수도 있습니다.[4]

## 동작 원리: 등록에서 결과 반환까지

상품 검색을 예로 전체 흐름을 펼쳐보겠습니다. 다음은 역할을 설명하기 위한 논리적 흐름이며, 모든 에이전트 제품이 내부적으로 같은 메시지나 전송 경로를 사용한다는 뜻은 아닙니다.

```text
웹페이지 개발자
  │ 검색 도구의 이름·설명·입력·실행 함수를 정의
  ▼
브라우저의 도구 등록·발견 인터페이스
  │ 현재 문서에서 접근 가능한 도구 정보 제공
  ▼
에이전트
  │ 사용자 요청을 해석하고 도구와 입력 선택
  ▼
브라우저
  │ 도구 실행을 연결
  ▼
웹페이지의 execute 함수
  │ 검색 로직 호출 / 필요하면 서버에 요청
  ▼
검색 결과 + 화면 상태 갱신
  │ 반환값을 브라우저에 전달
  ▼
에이전트
    결과를 읽고 사용자에게 설명하거나 다음 행동 선택
```

### 1. 페이지가 도구를 등록한다

명령형 API에서는 `document.modelContext.registerTool()`에 이름, 설명, 입력 스키마와 실행 함수를 전달합니다.[2]

중요한 점은 등록과 실행이 별개라는 것입니다. 등록은 “이런 기능을 호출할 수 있다”는 안내이고, 실제 검색은 도구가 호출됐을 때 실행됩니다.

### 2. 접근 가능한 도구를 발견한다

현재 공식 API 문서는 `document.modelContext.getTools()`로 호출 문서가 접근할 수 있는 도구 목록을 가져오는 방법을 제공합니다. 기본값은 같은 출처의 문서와 프레임 트리에 등록된 도구이며, 다른 출처의 도구에는 추가 조건이 있습니다.[2]

도구 목록에는 이름, 설명, 입력 스키마, 출처 등의 정보가 포함됩니다.[2] 에이전트 연동 계층은 이 정보를 활용해 모델이 선택할 수 있는 도구를 구성할 수 있습니다. WebMCP 자체가 특정 LLM 공급자나 모델을 지정해주는 것은 아닙니다.

사이트 방문도 여전히 필요합니다. Chrome 문서는 클라이언트나 브라우저가 해당 사이트에 직접 방문해야 호출 가능한 도구를 알 수 있다는 발견상의 한계를 명시합니다.[1]

### 3. 에이전트가 이름과 인자를 선택한다

사용자가 “무선 키보드를 가격순으로 보여줘”라고 요청하면, 에이전트는 예를 들어 `search_products`에 다음 인자를 선택할 수 있습니다.

```json
{
  "query": "무선 키보드",
  "sort": "price_asc"
}
```

이 단계는 자연어 의도를 구조화된 호출로 바꾸는 과정입니다. 스키마는 `sort`에 어떤 값이 허용되는지 알려주지만, 사용자가 정말 가격순을 원했는지까지 보장하지는 않습니다.

### 4. 브라우저가 페이지의 실행 함수로 연결한다

공식 문서는 발견한 도구를 `document.modelContext.executeTool()`에 전달하는 실행 API도 제공합니다. 입력 인자는 유효한 JSON 문자열로 전달하며, 결과는 비동기로 반환됩니다.[2]

페이지의 실행 함수가 서버 API를 호출한다면 네트워크 지연과 오류는 여전히 발생합니다. WebMCP는 클릭 경로를 도구 호출 경로로 바꾸는 것이지, 검색 서버 자체를 없애는 기술은 아닙니다.

### 5. 결과와 화면 상태를 맞춘다

함수는 실제 결과를 반환하고, 사이트가 필요에 따라 화면을 갱신하도록 설계합니다. 반환값만 성공이라고 만들고 화면에는 이전 검색 결과를 남겨두면 사람과 에이전트가 서로 다른 상태를 보고 작업할 수 있습니다.

이것은 애플리케이션 구현상의 책임입니다. “검색이 끝났다”는 문장보다 어떤 조건으로 무엇을 찾았는지 명확한 결과를 주는 편이 다음 판단에 도움이 됩니다.

### 6. 페이지 수명이 끝나면 도구도 사라진다

WebMCP 도구는 열린 페이지의 수명에 묶입니다. 사용자가 사이트를 떠나거나 탭을 닫으면 그 페이지의 도구를 계속 이용하는 상시 서버처럼 동작하지 않습니다.[4]

SPA에서도 화면과 권한이 바뀌면 도구 목록을 함께 관리해야 합니다. 상품 상세 화면을 벗어났는데 이전 상품의 구매 도구가 남아 있지 않도록 하는 식입니다. 현재 명령형 API는 `AbortSignal`을 통한 등록 해제와 도구 목록 변경을 알리는 `toolchange` 이벤트를 안내합니다.[2]

## 구현 방식 1: JavaScript로 도구를 등록한다

명령형 API는 동적인 상태 조작이나 기존 함수와의 연결에 적합합니다.[2] 다음 예시는 외부 서버 없이 작은 상품 목록을 검색합니다. 데이터는 설명을 위해 만든 가상 데이터입니다.

**2026년 9월 1일 갱신된 Chrome 문서의 `document.modelContext` 형태를 기준으로 작성했습니다.** 초기 예제의 `navigator.modelContext`를 현재 코드에 그대로 옮기기보다 대상 브라우저와 문서 버전을 확인해야 합니다.[2]

```javascript
const products = [
  { id: "keyboard-a", name: "무선 키보드 A", price: 59000 },
  { id: "keyboard-b", name: "무선 키보드 B", price: 39000 },
];

function searchProducts({ query, sort }) {
  if (typeof query !== "string" || query.trim() === "") {
    throw new Error("검색어가 필요합니다.");
  }
  if (sort !== "price_asc" && sort !== "price_desc") {
    throw new Error("지원하지 않는 정렬 조건입니다.");
  }

  const results = products.filter((p) => p.name.includes(query.trim()));
  return results.sort((a, b) =>
    sort === "price_asc" ? a.price - b.price : b.price - a.price,
  );
}

if ("modelContext" in document) {
  const lifecycle = new AbortController();

  await document.modelContext.registerTool(
    {
      name: "search_products",
      description: "상품을 검색하고 가격순으로 정렬합니다. 구매하지 않습니다.",
      inputSchema: {
        type: "object",
        properties: {
          query: { type: "string", description: "상품 검색어" },
          sort: { type: "string", enum: ["price_asc", "price_desc"] },
        },
        required: ["query", "sort"],
      },
      annotations: { readOnlyHint: true },
      execute: async (input) => JSON.stringify(searchProducts(input)),
    },
    { signal: lifecycle.signal },
  );

  // SPA 컴포넌트 정리 시 lifecycle.abort()로 등록을 해제할 수 있습니다.
}
```

이 예제는 검색 결과를 반환하는 부분에 집중했습니다. 실제 사이트에서는 사람이 쓰는 검색 UI와 도구가 같은 `searchProducts` 로직을 사용하도록 구성하고, UI 갱신도 공통 경로에서 처리하는 편이 좋습니다.

지원 환경의 같은 문서에서 도구를 수동으로 확인할 때는 다음 형태를 사용할 수 있습니다.[2]

```javascript
const tools = await document.modelContext.getTools();
const tool = tools.find((item) => item.name === "search_products");
if (!tool) throw new Error("검색 도구가 등록되지 않았습니다.");

const result = await document.modelContext.executeTool(
  tool,
  JSON.stringify({ query: "무선 키보드", sort: "price_asc" }),
);
console.log(result);
```

이 코드에는 LLM 호출이 없습니다. 도구의 등록·발견·수동 실행과 자연어를 해석하는 에이전트를 분리해서 볼 수 있습니다. 위 수동 호출을 모델의 도구 선택 결과와 연결하는 부분은 브라우저나 에이전트 클라이언트의 역할입니다.

## 구현 방식 2: HTML 폼을 도구로 선언한다

기존 폼이 있다면 JavaScript로 스키마를 다시 쓰는 대신 선언형 API를 사용할 수 있습니다. `<form>`에 `toolname`과 `tooldescription`을 넣으면 브라우저가 폼과 필드를 구조화된 도구 표현으로 변환합니다.[3]

```html
<form
  action="/search"
  method="get"
  toolname="search_products_form"
  tooldescription="검색어와 정렬 조건으로 상품을 검색합니다."
>
  <label for="query">상품 검색어</label>
  <input id="query" name="query" type="text" required />

  <label for="sort">가격 정렬</label>
  <select id="sort" name="sort" required>
    <option value="price_asc">낮은 가격순</option>
    <option value="price_desc">높은 가격순</option>
  </select>

  <button type="submit">검색</button>
</form>
```

위 코드는 기존 `/search` 경로가 있는 사이트를 가정합니다. WebMCP가 그 서버 경로를 생성해주지는 않습니다.

브라우저는 필드 이름과 필수 여부, 선택 옵션, 설명 등을 바탕으로 입력 스키마를 구성합니다. `toolparamdescription`으로 설명을 보강할 수 있고, 없으면 연결된 label 등을 활용합니다.[3]

```text
HTML form의 toolname → 도구 이름
HTML form의 tooldescription → 도구 설명
필드 name → 입력 속성
required → 필수 입력
select의 option → 선택 가능한 값
label / toolparamdescription → 입력의 의미
```

에이전트가 호출하면 브라우저는 폼을 화면에 드러내고 필드를 채웁니다. 위 예제는 `toolautosubmit`을 넣지 않았으므로 사용자가 제출 버튼을 눌러 완료하는 형태입니다. 자동 제출을 원하면 해당 속성을 추가할 수 있습니다.[3]

검색과 결제를 같은 정책으로 다룰 필요는 없습니다. 검색은 자동 실행하더라도 구매 확정은 사람이 확인하는 경계를 둘 수 있습니다.

### 페이지 이동 없이 결과를 반환하려면?

선언형 API의 `SubmitEvent`에는 에이전트가 유발한 제출인지 구분하는 `agentInvoked`와 결과 Promise를 전달하는 `respondWith()`가 있습니다. `respondWith()` 사용 전에는 `preventDefault()`로 기본 제출을 막아야 합니다.[3]

이 방식은 기존 JavaScript 폼 처리에 도구 결과 반환을 연결할 때 유용합니다. 입력 검증, 서버 오류 처리, 화면 갱신은 여전히 앱이 구현해야 합니다. 자동 제출 속성을 넣었다는 사실만으로 업무가 성공한 것은 아닙니다.

## GPT의 Computer Use, DOM 자동화, WebMCP는 어떻게 다를까?

세 방식 모두 상품을 검색하고 낮은 가격순으로 정렬하는 같은 목표에 사용할 수 있습니다. 차이는 결과보다 **무엇을 관찰하고 어떤 경로로 행동하는가**입니다.

먼저 용어의 범위를 구분해야 합니다. **OpenAI의 Computer Use는 화면 좌표 클릭만을 뜻하지 않습니다.** 현재 공식 가이드는 PyAutoGUI·Playwright 같은 라이브러리를 사용하는 코드 실행 방식과, 구조화된 마우스·키보드 동작을 반환하는 `computer` 도구 방식을 모두 설명합니다. GPT-6 Astra에는 코드 실행 방식을 권장합니다.[6]

따라서 아래 표의 Computer Use는 비교를 위해 **스크린샷·좌표 중심의 사용 방식**으로 좁혀 설명한 것입니다. Computer Use라는 큰 범주 안에 DOM 기반 브라우저 조작이 함께 들어갈 수도 있으므로, 세 항목이 완전히 배타적인 제품 분류는 아닙니다. GPT라는 모델과 그 모델에 연결된 조작 도구도 구분해야 합니다.[6]

| 방식 | 주로 보는 정보 | 행동 경로 | 사이트 측 준비 |
| --- | --- | --- | --- |
| 화면 기반 Computer Use | 스크린샷 | 좌표 클릭·스크롤·키보드 입력 | 사람이 사용하는 화면 |
| DOM 자동화 | 요소 구조·역할·레이블 | 요소를 찾아 입력·클릭 | 조작 가능한 웹 UI |
| WebMCP | 도구 설명·입력 스키마 | 등록된 기능 호출 | 도구 등록과 실행 로직 연결 |

Computer Use의 기본 반복 구조는 모델이 화면을 바탕으로 동작을 제안하고, 실행 환경이 이를 수행한 뒤 새 스크린샷을 돌려주는 방식입니다. 모델이 직접 운영체제의 마우스를 움직이는 것이 아니라 실행 환경이 클릭과 입력을 수행합니다.[6]

```text
Computer Use
화면 캡처 → 검색창 위치 판단 → 클릭·입력
→ 새 화면 확인 → 정렬 메뉴 조작

DOM 자동화
검색 입력 요소 탐색 → 값 입력 → 검색 버튼 클릭
→ 정렬 요소 탐색·선택

WebMCP
search_products 도구 발견
→ query와 sort를 전달 → 결과 확인
```

Computer Use는 사이트가 전용 도구를 등록하지 않아도 사람용 화면을 이용할 수 있습니다. DOM 자동화는 화면 좌표 대신 요소의 구조와 의미를 이용합니다. WebMCP는 사이트가 공개한 기능 계약을 사용하므로 검색창이나 정렬 메뉴를 찾아 조작하는 단계를 줄일 수 있습니다.[1][6]

### 최종 화면은 같을까?

**같은 업무 로직과 화면 갱신 경로로 연결했다면 같을 수 있습니다.** 세 방식 모두 같은 상품 목록을 낮은 가격순으로 보여줄 수 있습니다. WebMCP를 썼다는 이유만으로 다른 결과가 필요한 것은 아닙니다.

```text
Computer Use의 클릭 ─┐
DOM 자동화의 클릭 ───┼→ 공통 검색 로직
WebMCP 도구 호출 ────┘     → 상태·화면 갱신
```

다만 결과의 동등성은 구현에 달려 있습니다. WebMCP 도구가 데이터만 반환하고 UI를 갱신하지 않으면 AI는 검색 결과를 받지만 사용자가 보는 화면은 그대로일 수 있습니다. 버튼 경로에 있던 검증을 도구 경로에서 빠뜨려도 동작이 달라집니다.

이 때문에 실제 버튼과 폼이 정상 작동하는지 확인하려는 UI 테스트를 WebMCP 호출만으로 대체할 수는 없습니다. 도구가 성공해도 버튼이 가려졌거나 입력창이 고장 난 문제는 남아 있을 수 있습니다.

### 어느 하나로 통일할 필요는 없다

사이트가 안정적인 WebMCP 도구를 제공하는 기능에는 그 도구를 사용하고, 도구가 없는 기능에는 DOM이나 화면 조작을 사용하는 구성을 생각할 수 있습니다. 마지막 화면을 시각적으로 확인하는 과정도 별도로 둘 수 있습니다. 이는 가능한 설계이지, 모든 GPT 제품이 이 세 경로를 기본 제공한다는 뜻은 아닙니다.

특히 Computer Use가 로그인이나 결제 화면을 조작할 수 있다는 것과 실행을 허가받았다는 것은 별개입니다. OpenAI 문서는 실행 환경이 실행 제한과 권한 규칙을 적용해야 한다고 설명합니다.[6] WebMCP 역시 뒤에서 설명할 권한·확인 절차가 필요합니다.

## 왜 DOM 조작보다 안정적일 수 있을까?

WebMCP의 이점은 “AI가 더 이상 화면을 볼 필요가 없다”보다 “사이트가 이미 알고 있는 기능의 의미를 명시한다”에 가깝습니다.[1][4]

```text
화면·DOM 기반 경로
검색창 발견 → 입력 → 정렬 메뉴 발견 → 옵션 해석 → 클릭 → 결과 확인

도구 기반 경로
search_products(query, sort) → 실제 결과 확인
```

레이아웃이 바뀌어도 도구의 계약과 연결된 앱 로직이 유지된다면 에이전트가 버튼 위치를 다시 찾을 필요가 줄어듭니다.[4] 하지만 함수 이름이나 인자 의미를 바꾸면 도구 이용 방식도 영향을 받습니다. 유지보수 대상이 없어지는 것이 아니라 UI 조작 절차에서 명시적인 기능 계약으로 옮겨가는 것입니다.

속도 역시 구분해서 봐야 합니다. 화면을 여러 번 읽고 행동하는 횟수는 줄어들 수 있지만, 도구 안의 서버 요청과 실제 업무 처리 시간은 남습니다. 이 글에서는 특정 배수의 속도 개선이나 성공률을 직접 측정하지 않았습니다.

등록되지 않은 기능이나 시각적 확인에는 기존 브라우저 조작이 여전히 필요할 수 있습니다. WebMCP는 기존 UI와 자동화 방식을 전부 대체하기보다 함께 사용할 수 있는 경로입니다.

## 로그인과 권한은 어디에서 처리할까?

WebMCP는 현재 브라우저 탭의 세션과 페이지 맥락을 활용합니다.[4] 이것을 모델에게 세션 쿠키를 그대로 넘겨준다는 뜻으로 읽으면 안 됩니다. 페이지 코드가 기존 권한으로 실행되고 필요한 서버 요청을 보내는 것과, 모델에 비밀값을 제공하는 것은 다른 문제입니다.

서버는 도구에서 온 요청도 검증해야 합니다. 사용자에게 해당 주문을 조회할 권한이 있는지, 입력값이 유효한지, 중복 요청인지 확인하는 기존 책임이 없어지지 않습니다.

### 출처 사이에는 별도의 경계가 있다

Chrome 문서는 WebMCP를 origin-isolated 문서에서 사용할 수 있다고 안내합니다. `document.domain`을 활성화하는 구성에서는 API가 비활성화됩니다. 이는 HTTPS나 COOP·COEP 설정을 하나 넣으면 모든 조건이 해결된다는 식으로 단순화할 내용이 아닙니다.[1]

또한 `tools` Permissions Policy는 기본적으로 `self`입니다. 다른 출처의 iframe에서 도구 등록을 허용하려면 `allow="tools"` 같은 위임이 필요합니다.[1][2]

이 등록 권한과 다른 출처에서 도구를 발견·실행할 권한은 구분됩니다. 등록자가 `exposedTo`로 허용 출처를 지정하고, 발견하는 쪽도 `getTools({ fromOrigins: [...] })`에서 대상 출처를 명시해야 하는 조건이 있습니다.[2]

```text
iframe이 도구를 등록할 수 있는가? → Permissions Policy
다른 출처가 그 도구에 접근할 수 있는가? → exposedTo
어떤 다른 출처의 도구를 찾을 것인가? → fromOrigins
실제 데이터에 접근할 권한이 있는가? → 앱·서버의 인증과 인가
```

읽기 전용 도구도 개인정보를 반환할 수 있습니다. 상태를 바꾸지 않는다는 이유만으로 모든 출처에 공개해도 안전한 것은 아닙니다.[5]

## 구조화된 도구도 프롬프트 인젝션을 없애지는 않는다

상품 리뷰나 고객 메시지를 반환하는 도구에는 외부 작성자의 텍스트가 포함될 수 있습니다. 그 텍스트에 에이전트의 다음 행동을 바꾸려는 지시가 섞이는 문제는 구조화된 호출에서도 남습니다.[5]

현재 문서는 다음과 같은 힌트를 안내합니다.[2][5]

- `readOnlyHint`: 상태를 변경하지 않는 도구임을 표시합니다.
- `untrustedContentHint`: 사용자 작성 내용이나 외부 데이터처럼 신뢰할 수 없는 출력이 포함됨을 표시합니다.
- `consequentialHint`: 구매·송금·삭제처럼 현실의 중대한 결과가 있는 동작임을 표시합니다.

힌트는 브라우저와 에이전트의 판단을 돕는 메타데이터입니다. 서버의 접근 제어와 실제 확인 절차를 대체하는 권한 검사로 취급하면 안 됩니다.

결제나 삭제를 구현한다면 조회와 실행을 분리하고, 실행 직전 대상과 금액·범위를 확인하며, 서버에서 중복 처리를 막는 편이 좋습니다. 이것은 WebMCP의 자동 보장 사항이 아니라 애플리케이션 설계상의 권고입니다.

실행 취소도 롤백과 다릅니다. API는 실행 함수에 취소 신호를 전달하는 방식을 제공하지만, 이미 서버에서 완료된 결제까지 신호 하나로 취소되는 것은 아닙니다. 등록 해제와 진행 중 실행의 취소도 따로 다뤄야 합니다.[2]

## 지금 사용하려면 무엇을 확인해야 할까?

확인한 Chrome 안내는 Chrome 149부터의 origin trial과 로컬 개발용 `chrome://flags/#enable-webmcp-testing`을 소개합니다. 여전히 변경 가능한 제안·실험 단계로 설명되므로 모든 브라우저에서 기본 지원하는 확정 표준처럼 도입하면 안 됩니다.[1]

작게 시작한다면 다음 순서가 좋겠습니다.

1. 로그인이나 결제에 영향을 주지 않는 검색 도구 하나를 고릅니다.
2. 대상 Chrome 버전과 최신 API 문서를 확인합니다.
3. 기존 UI가 사용하는 로직에 도구를 연결합니다.
4. Model Context Tool Inspector로 등록 목록·입력·출력·오류를 확인합니다.[1]
5. 지원하지 않는 환경에서도 기존 폼과 버튼이 정상 동작하는지 확인합니다.
6. 이후 자연어 요청을 연결해 도구 선택과 실제 결과를 확인합니다.

단순한 `"modelContext" in document` 검사는 첫 단계입니다. 구체적으로 사용할 메서드와 대상 브라우저에서의 동작까지 확인해야 합니다. 과거 예제를 참고할 때는 같은 이름의 라이브러리나 이전 실험 API를 현재 브라우저 표준 API와 섞지 않는 것도 중요합니다.

## 마무리

WebMCP는 AI가 사람용 화면의 의미를 전부 추측하게 두는 대신, 사이트가 자신의 기능을 이름·설명·입력 형식으로 알려주는 웹 표준 제안입니다.[1]

동작 원리는 **사이트의 도구 등록 → 접근 가능한 도구 발견 → 에이전트의 선택 → 브라우저를 통한 페이지 코드 실행 → 실제 결과 반환**으로 정리할 수 있습니다.[2]

HTML 폼을 활용하면 기존 화면을 유지한 채 도구를 선언할 수 있고, JavaScript API를 사용하면 동적인 앱 기능과 연결할 수 있습니다.[2][3] 이때 기존 MCP 서버나 HTTP API를 없앨 필요는 없습니다. 각 방식이 맡는 접점이 다르기 때문입니다.[4]

개발자가 새로 고민해야 할 것은 어떤 기능을 어떤 범위로 공개할지입니다. 화면의 버튼을 전부 도구로 옮기는 것보다 사용자의 목적이 분명한 작은 기능부터 연결하고, 실제 결과·권한·확인 절차를 함께 검증하는 편이 좋은 출발점이라고 봅니다.
