## 회사 계정 하나를 여러 서비스가 어떻게 알아볼까?

회사에 사내 위키, 코드 저장소, 업무 관리 도구가 있다고 해보겠습니다. 각 서비스에 계정을 따로 만들면 입사할 때마다 사용자를 등록해야 합니다. 부서가 바뀌면 권한을 바꾸고, 퇴사하면 여러 곳에서 접근을 막아야 합니다.

서비스가 늘어날수록 계정 정보도 흩어집니다. 어느 서비스에는 퇴사한 사람의 계정이 남고, 다른 서비스에는 예전 부서 정보가 남을 수 있습니다.

그래서 사용자와 조직 정보를 한곳에서 관리하고, 여러 서비스가 그 정보를 이용하는 구조를 생각할 수 있습니다.

```text
사내 위키 ────────┐
코드 저장소 ──────┼── 사용자·그룹 정보를 공유
업무 관리 도구 ───┘           │
                            ▼
                      디렉터리 서비스
```

이때 자주 등장하는 이름이 LDAP입니다. “LDAP 로그인”이라는 표현 때문에 인증 기술로만 생각하기 쉽지만, 출발점은 조금 다릅니다.

**LDAP는 디렉터리의 정보를 검색하고 변경하며, 연결의 인증 상태를 설정하는 데 사용하는 통신 규약입니다.** 로그인은 이 기능을 이용하는 대표적인 사례입니다.[1][2]

가상의 회사 `example.com`에서 직원 `jiyun`이 사내 위키에 로그인하는 과정을 따라가 보겠습니다. 제품 설치법보다 각 구성요소가 무슨 역할을 하는지에 집중하겠습니다.

## LDAP는 저장소가 아니라 접근 규약이다

LDAP는 **Lightweight Directory Access Protocol**의 약자입니다. 이름 그대로 디렉터리에 접근하는 프로토콜입니다.[1]

여기서 디렉터리는 파일을 넣는 폴더가 아닙니다. 사용자, 그룹, 조직, 장비 같은 대상을 속성으로 기록하고 찾을 수 있게 만든 정보 체계입니다.

직원 한 명이라면 로그인 이름, 표시 이름, 이메일 같은 속성을 저장할 수 있습니다. 그룹에는 이름과 구성원 정보를 저장할 수 있습니다. 애플리케이션은 이 정보를 LDAP 요청으로 조회합니다.

```text
사내 위키의 LDAP 클라이언트
          │ LDAP 요청과 응답
          ▼
디렉터리 서버
          │ 검색·검증·변경 처리
          ▼
디렉터리 데이터
```

구분하면 세 가지입니다.

- **LDAP:** 클라이언트와 서버가 요청과 응답을 주고받는 규약입니다.
- **디렉터리 서버:** LDAP 요청을 처리하고 정보와 접근 권한을 관리하는 소프트웨어입니다.
- **디렉터리 데이터:** 사용자·그룹 등의 실제 정보입니다.

OpenLDAP는 이런 서버를 제공하는 소프트웨어입니다. Microsoft의 Active Directory Domain Services, 즉 AD DS도 사용자와 컴퓨터 등의 디렉터리 정보를 관리하는 서비스입니다. LDAP라는 규약과 특정 제품을 같은 것으로 보면 안 됩니다.[1][6]

이름에 Lightweight가 붙은 것은 X.500의 기존 디렉터리 접근 방식인 DAP보다 가볍게 접근하려는 역사에서 나왔습니다. 운영이나 보안 설정까지 간단하다는 뜻은 아닙니다.[1]

### 사용자 테이블과는 무엇이 다를까?

관계형 데이터베이스에도 사용자와 그룹을 저장할 수 있습니다. LDAP만 가능한 데이터가 따로 있어서 사용하는 것은 아닙니다.

차이는 여러 클라이언트가 공유할 수 있는 디렉터리 모델과 접근 방식에 있습니다. 디렉터리는 대상을 이름과 속성으로 찾고, 범위를 정해 검색하며, 정해진 스키마와 접근 제어 아래 정보를 공유하는 데 적합합니다.[1]

반면 주문·결제·재고처럼 여러 데이터를 묶어 복잡한 업무 처리를 해야 하는 곳까지 디렉터리로 옮길 이유는 없습니다. LDAP에는 추가·수정·삭제도 있으므로 읽기 전용은 아니지만, 일반적인 업무 데이터베이스와 같은 용도로 보면 곤란합니다.[1][2]

계정은 디렉터리에서 확인하고, 위키 문서와 편집 이력은 위키의 데이터베이스에 저장하는 식으로 역할을 나누면 됩니다.

## 사용자 한 명은 디렉터리에서 어떻게 표현될까?

로그인 흐름을 보기 전에, 서버가 사용자를 무엇으로 식별하는지 알아야 합니다.

LDAP의 정보 단위는 **엔트리(entry)**입니다. 직원 한 명, 그룹 하나가 각각 엔트리가 될 수 있습니다. 엔트리는 속성들의 집합이고, 각 속성은 하나 이상의 값을 가질 수 있습니다.[1]

예를 들어 다음과 같은 디렉터리를 구성할 수 있습니다.

```text
dc=example,dc=com
│
├─ ou=people
│  ├─ uid=jiyun
│  └─ uid=minsu
│
└─ ou=groups
   └─ cn=wiki-editors
```

이런 계층 구조를 **DIT(Directory Information Tree)**라고 부릅니다. 여기서는 `people` 아래에 사람을, `groups` 아래에 그룹을 배치했습니다. 실제 회사의 조직도를 그대로 복제해야 한다는 규칙은 아닙니다.

### DN은 엔트리의 전체 이름이다

`jiyun` 엔트리의 전체 이름은 다음과 같습니다.

```text
uid=jiyun,ou=people,dc=example,dc=com
```

이것이 **DN(Distinguished Name)**입니다. `uid=jiyun`이라는 엔트리를 부모인 `ou=people`과 그 위의 이름까지 이어서 식별합니다.[1]

- `uid`는 사용자 식별에 쓰는 속성입니다.
- `ou`는 organizational unit, 조직 단위를 뜻합니다.
- `dc`는 domain component, 도메인 이름의 구성요소를 뜻합니다.
- `cn`은 common name으로, 사람이나 그룹 등의 이름을 표현할 때 사용합니다.

이 예에서 가장 왼쪽의 `uid=jiyun`은 부모 아래에서 엔트리를 구분하는 **RDN(Relative Distinguished Name)**입니다. RDN을 부모들의 이름과 합치면 DN이 됩니다.

파일의 전체 경로에 비유하면 이해하기 쉽지만, DN은 파일 경로와 문법이 다릅니다. 또 엔트리를 다른 위치로 옮기거나 이름을 바꾸면 DN도 달라질 수 있습니다. 서비스의 영구적인 사용자 식별자가 필요하다면 DN을 무조건 불변 키로 취급하지 말고, 디렉터리가 제공하는 안정적인 식별 속성을 검토해야 합니다.

### 속성은 자유롭게 아무 이름이나 붙이는 것이 아니다

직원 엔트리에는 다음과 같은 정보가 있을 수 있습니다. 디렉터리 데이터를 텍스트로 표현하는 LDIF 형식의 예입니다.

```text
dn: uid=jiyun,ou=people,dc=example,dc=com
objectClass: inetOrgPerson
uid: jiyun
cn: Jiyun Kim
sn: Kim
mail: jiyun@example.com
```

`objectClass`는 이 엔트리가 어떤 종류인지와 어떤 속성이 필수 또는 허용되는지를 결정하는 스키마 규칙에 연결됩니다.[1] 위 예는 사람 정보를 표현하는 구조이며, 비밀번호를 설정하거나 로그인 가능한 계정을 만드는 전체 구성은 아닙니다.

여기서 기억할 것은 두 가지입니다. **DN은 어느 엔트리인지 식별하고, 속성은 그 엔트리의 정보를 담습니다.**

## 검색은 어디서 시작해서 무엇을 찾는지 지정한다

사용자는 로그인 화면에 `jiyun`을 입력합니다. 하지만 애플리케이션은 이 문자열만으로 디렉터리 안의 정확한 DN을 모를 수 있습니다.

그래서 먼저 검색합니다. LDAP 검색은 크게 검색 시작점, 검색 범위, 필터, 반환 속성을 지정합니다.[2]

```text
검색 시작점: ou=people,dc=example,dc=com
검색 범위:   시작점과 그 아래 전체
검색 조건:   (uid=jiyun)
반환 속성:   cn, mail
```

여기서 검색 시작점을 **Base DN**이라고 부릅니다. 앞에서 DN이 엔트리의 전체 이름이라고 했는데, 검색에서는 그 이름을 출발점으로 사용하는 것입니다.

검색 범위도 결과를 바꿉니다.

- **baseObject:** 시작점 엔트리 하나만 검사합니다.
- **singleLevel:** 시작점의 바로 아래 엔트리만 검사합니다.
- **wholeSubtree:** 시작점 자신과 그 아래 모든 깊이의 엔트리를 검사합니다.

예를 들어 `jiyun`이 `ou=engineering,ou=people,...`처럼 한 단계 더 깊은 위치에 있다면, `ou=people,...`을 시작점으로 하는 `singleLevel` 검색에서는 찾지 못합니다. 같은 필터인데 결과가 없을 때는 계정부터 의심하기 전에 시작점과 범위를 확인해야 합니다.

필터는 조건을 표현합니다. `(uid=jiyun)`은 `uid` 값이 조건에 맞는 엔트리를 찾습니다. 사람 엔트리로 제한하고 싶다면 다음처럼 AND 조건을 쓸 수 있습니다.[4]

```text
(&(objectClass=inetOrgPerson)(uid=jiyun))
```

검색 응답에는 일치한 엔트리의 DN과 요청한 속성 중 읽기 권한이 있는 정보가 담깁니다. 응답은 엔트리들과 최종 검색 결과 상태로 구성되므로, 결과가 일부 왔다는 사실만으로 검색이 완전히 성공했다고 단정하면 안 됩니다. 서버의 크기 제한이나 시간 제한도 확인해야 합니다.[2]

로그인 대상 검색에서는 결과가 정확히 한 명인지 확인해야 합니다. 아무도 없거나 여러 명이 나오면 첫 번째 결과를 골라 인증을 계속하는 대신, 검색 조건과 디렉터리 구성을 점검하는 편이 안전합니다.

## 회사 계정으로 로그인할 때 실제로 오가는 것

여기서는 애플리케이션이 사용자 ID와 비밀번호를 받아 LDAP로 확인하는 **search-and-bind 방식**을 보겠습니다. LDAP 인증을 구성하는 유일한 방법은 아니지만, 검색과 인증의 역할을 구분하기 좋은 예입니다.[5]

먼저 결론부터 보면, **비밀번호를 디렉터리에서 가져와 위키가 비교하는 것이 아닙니다.** 위키가 사용자의 자격 증명으로 Bind를 요청하고, 디렉터리 서버가 검증합니다.[5]

```text
사용자
  │ ID와 비밀번호 입력 — HTTPS
  ▼
사내 위키
  │ ① TLS로 보호된 LDAP 연결
  │ ② 조회 계정으로 Bind
  │ ③ ID로 사용자 검색 → DN 확인
  │ ④ 별도 연결에서 사용자 DN·비밀번호로 Bind
  ▼
디렉터리 서버
  │ 인증 결과 반환
  ▼
사내 위키
  │ ⑤ 그룹·접근 정책 확인
  │ ⑥ 위키 로그인 세션 생성
  ▼
사용자에게 로그인 결과 표시
```

### 1. 조회 계정으로 사용자를 찾는다

디렉터리가 익명 검색을 허용하지 않는다면, 위키는 제한된 조회 권한을 가진 서비스 계정으로 접속합니다. 이때 수행하는 Bind는 **위키의 조회 계정을 인증하는 단계**이지, 로그인하려는 직원을 인증하는 단계가 아닙니다.

그 권한으로 `(uid=jiyun)`을 검색하고 다음 DN을 얻습니다.

```text
uid=jiyun,ou=people,dc=example,dc=com
```

조회 계정에는 필요한 사용자·그룹 정보를 읽을 최소 권한만 주면 됩니다. 로그인 기능을 위해 디렉터리 전체 관리자 권한까지 줄 필요는 없습니다.

사용자 DN이 일정한 규칙으로 정해져 있다면 검색 대신 DN 패턴으로 대상을 정하는 구성도 가능합니다. 어떤 방식인지는 애플리케이션과 디렉터리 구조에 따라 달라집니다.[5]

### 2. 사용자 자격 증명으로 Bind한다

**Bind는 LDAP 연결의 인증 상태를 설정하는 작업**입니다. 단순히 TCP 연결을 여는 것과 다릅니다. 이름과 비밀번호를 사용하는 Simple Bind도 있고, SASL을 이용하는 방식도 있습니다.[3]

이 예에서는 찾은 사용자 DN과 사용자가 입력한 비밀번호로 Simple Bind를 요청합니다. 디렉터리 서버는 자격 증명과 적용되는 계정 정책을 검사하고 결과를 반환합니다.

앱이 저장된 비밀번호나 해시를 읽어 직접 비교할 필요는 없습니다. 다만 이 방식에서는 사용자가 입력한 비밀번호를 앱이 받아 LDAP 서버로 전달하므로, 앱의 로그·추적 데이터에 비밀번호가 남지 않도록 해야 합니다.

위 흐름은 조회용 연결과 사용자 인증용 연결을 분리했습니다. Bind가 연결의 인증 상태를 바꾸기 때문에, 여러 요청이 공유하는 조회 연결을 사용자 인증용으로 재사용하면 다음 요청이 어떤 권한으로 실행되는지 혼동할 수 있습니다. 연결 풀을 사용할 때도 이 경계를 유지해야 합니다.

### 3. 인증 성공과 위키 권한을 나눈다

사용자 Bind가 성공하면 자격 증명이 받아들여진 것입니다. 그렇다고 모든 위키 문서를 편집할 수 있는 것은 아닙니다.

위키는 추가로 `wiki-editors` 그룹에 속하는지 확인하고, 그 그룹을 위키의 편집 권한에 연결할 수 있습니다. **인증은 누구인지 확인하는 일이고, 인가는 무엇을 할 수 있는지 판단하는 일입니다.**

디렉터리 서버에도 자체 접근 제어가 있습니다. 하지만 LDAP 데이터를 읽을 권한과 위키 문서를 편집할 권한은 서로 다른 정책입니다.

그룹 구성원 표현 역시 디렉터리 스키마에 따라 다릅니다. 그룹 엔트리가 구성원의 DN을 `member`에 담는 방식도 있고, 다른 속성이나 역방향 멤버십 정보를 사용하는 구성도 있습니다. 모든 서버에서 `memberOf` 하나를 조회하면 중첩 그룹까지 해결된다고 가정하면 안 됩니다.

### 4. 웹 로그인 상태는 애플리케이션이 만든다

LDAP Bind 결과가 브라우저의 로그인 쿠키로 자동 변환되는 것은 아닙니다. 위키가 인증·권한 확인 결과를 바탕으로 자신의 세션을 만들거나 필요한 토큰을 발급하고, 이후 요청에서 그 상태를 검사합니다.

이 구분은 퇴사자 처리에서 중요합니다. 디렉터리 계정을 비활성화해서 다음 로그인을 막더라도, 이미 발급한 위키 세션이 즉시 사라지는 것은 아닙니다. 세션 만료, 접근 시 재확인, 강제 로그아웃 같은 애플리케이션 정책을 함께 설계해야 합니다.

계정 정보의 중앙화와 모든 서비스 세션의 즉시 회수는 같은 기능이 아닙니다.

## LDAP, Active Directory, SSO는 왜 같이 나올까?

셋은 자주 함께 쓰이지만 같은 층위의 용어가 아닙니다.

**LDAP는 디렉터리 접근 규약**입니다. 사용자와 그룹을 찾거나 자격 증명을 확인하는 데 사용할 수 있습니다.

**AD DS는 디렉터리 서비스**입니다. 사용자·컴퓨터·그룹 정보, 인증과 접근 제어, 복제 등 조직의 계정 및 자원 관리 기능을 제공합니다. LDAP 연동을 한다고 해서 AD의 모든 기능을 사용하는 것은 아닙니다.[6]

**SSO(Single Sign-On)는 한 번의 로그인으로 여러 서비스를 이용하는 방식 또는 경험**입니다. 여러 서비스가 같은 LDAP 계정과 비밀번호를 각각 확인한다고 해서 자동으로 SSO가 되는 것은 아닙니다. 계정은 같아도 서비스마다 비밀번호를 다시 입력할 수 있기 때문입니다.

웹 SSO에서는 애플리케이션이 중앙 인증 서비스인 IdP에 인증을 맡기고, OIDC나 SAML을 통해 인증 결과를 받는 구성을 사용할 수 있습니다. 그 IdP가 뒤에서 LDAP 디렉터리와 연동할 수도 있습니다.[7]

```text
웹서비스
   │ OIDC / SAML로 인증 연동
   ▼
중앙 인증 서비스(IdP)
   │ LDAP로 사용자 정보 조회·인증 연동
   ▼
디렉터리 서버
```

이렇게 구성하면 각 웹서비스가 LDAP 사용자 비밀번호를 직접 받아 처리하는 대신, IdP가 제공하는 인증 흐름을 이용할 수 있습니다. MFA와 로그인 정책도 IdP 중심으로 관리할 수 있지만, 디렉터리 연동만으로 이런 정책이 자동 설정되는 것은 아닙니다.

따라서 LDAP와 OIDC를 무조건 경쟁 관계로 볼 필요는 없습니다. 디렉터리 연동과 웹 애플리케이션의 로그인 연동이라는 서로 다른 지점에서 함께 사용할 수 있습니다.

## 연결할 때 놓치기 쉬운 보안 경계

### TLS 연결이 성립한 뒤 자격 증명을 보낸다

Simple Bind 자체는 비밀번호를 암호화하지 않습니다. TLS 등 충분한 보호 없이 이름과 비밀번호를 보내면 안 됩니다.[3]

보통 다음 두 연결 방식을 만나게 됩니다.[8]

- `ldap://` 연결 후 **StartTLS**를 수행해 TLS로 전환합니다. 통상 포트는 389입니다.
- `ldaps://`로 처음부터 TLS 연결을 사용합니다. 통상 포트는 636입니다.

389번 포트를 쓴다고 무조건 평문인 것도, 636번 포트에 연결됐다고 서버 신원 검증까지 올바른 것도 아닙니다. 인증서의 신뢰 관계와 서버 이름을 확인해야 합니다. StartTLS가 실패했는데 평문으로 계속 인증하는 동작도 허용하면 안 됩니다.

사용자와 웹서비스 사이의 HTTPS, 웹서비스와 LDAP 서버 사이의 TLS는 별개의 구간입니다. 로그인 화면에 자물쇠가 표시된다는 사실만으로 LDAP 연결까지 보호되는 것은 아닙니다.

### 빈 비밀번호와 검색 필터를 별도로 검증한다

LDAP의 Simple Bind에는 익명 인증과 비인증 방식도 정의되어 있습니다. 특히 이름이 있지만 비밀번호가 비어 있는 요청이 서버 설정에 따라 비인증 상태로 성공할 수 있으므로, 일반 사용자 로그인에서는 빈 비밀번호를 먼저 거부해야 합니다. Bind 응답의 성공만 보고 사용자가 인증됐다고 처리하면 안 됩니다.[3]

검색 필터에 사용자 입력을 문자열로 그대로 붙이는 것도 위험합니다. 필터에서 `*`, 괄호, 역슬래시 등은 특별한 의미가 있습니다. 예를 들어 별표를 일반 문자로 찾으려는 것과 와일드카드 조건으로 해석하는 것은 다릅니다.[4]

LDAP 라이브러리의 필터 구성·이스케이프 기능을 사용해야 합니다. DN 문자열과 검색 필터는 문법이 다르므로 같은 이스케이프 함수를 아무 곳에나 적용해서도 안 됩니다.

## 로그인이 안 될 때는 어느 단계가 실패했는지 본다

화면에 “로그인 실패”라고 나와도 원인은 하나가 아닙니다. 위에서 본 흐름을 순서대로 나누면 확인할 위치가 드러납니다.

1. **연결 실패:** DNS, 네트워크, 포트, 서버 상태를 확인합니다.
2. **TLS 실패:** 인증서 만료, 신뢰하는 CA, 서버 이름, TLS 설정을 확인합니다.
3. **조회 계정 Bind 실패:** 서비스 계정의 자격 증명과 상태를 확인합니다.
4. **사용자 검색 실패:** Base DN, 검색 범위, 필터, 조회 권한을 확인합니다.
5. **사용자 Bind 실패:** 입력한 자격 증명과 서버가 적용하는 계정 정책을 확인합니다.
6. **인증 후 접근 거부:** 그룹 조회와 앱의 역할 매핑을 확인합니다.
7. **계정 변경 후 접근 지속:** 디렉터리 복제 지연, 그룹 캐시, 앱 세션 정책을 확인합니다.

검색 결과가 없다는 것은 비밀번호가 틀렸다는 뜻이 아닙니다. 인증 성공 후 권한이 없다는 것도 LDAP 서버에 연결하지 못했다는 뜻이 아닙니다.

운영 로그에는 실패 단계를 구분할 수 있는 정보를 남기되, 비밀번호와 불필요한 개인정보는 제외해야 합니다. 외부 로그인 화면에는 계정 존재 여부를 쉽게 추측할 수 있는 상세한 차이를 노출하지 않는 편이 좋습니다.

## 마무리

LDAP를 이해할 때는 “회사 로그인에 쓰는 기술”에서 한 걸음 더 들어가면 구조가 보입니다.

디렉터리는 사용자와 그룹을 엔트리와 속성으로 관리합니다. LDAP는 그 정보를 검색·변경하고 연결의 인증 상태를 설정하는 규약입니다. 애플리케이션은 검색으로 사용자를 찾고, Bind로 자격 증명을 확인한 뒤, 자신의 접근 정책과 로그인 세션을 적용할 수 있습니다.

**사용자를 찾는 것, 자격 증명을 확인하는 것, 서비스 권한을 주는 것, 로그인 상태를 유지하는 것은 서로 다른 단계입니다.** 이 경계를 구분하면 LDAP와 AD, SSO가 왜 함께 등장하는지도 자연스럽게 이해할 수 있습니다.
