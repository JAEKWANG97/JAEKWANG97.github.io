**Software Engineering Is Becoming Factory Engineering**은 에이전트를 더 많이 실행하는 방법보다, 에이전트가 일하는 과정을 어떻게 개선할 것인지 묻는 발표다. 이 글은 발표의 핵심 문제를 먼저 짚고, Warp가 별도로 공개한 구성 사례·벤치마크 실험·제품 문서로 구체적인 작동 방식을 보충한다. 뒤의 자료를 발표에서 모두 설명한 내용처럼 합치지 않는다.

## 1. 발표의 출발점: 사람마다 잘 쓰는 것으로 충분한가

개발자가 노트북에서 여러 에이전트를 실행해도 일을 시작하고 실패를 알아채는 역할은 사람에게 남는다. 조직 전체로 넓히면 모델·스킬·비용·권한과 성공 기준도 제각각이다. Lloyd가 제안하는 전환은 이 과정을 측정하고 수정할 수 있는 시스템으로 만드는 것이다.

그의 조건은 두 가지다. 작업 방식을 코드로 정의하고, 실행 결과를 다음 개선에 되돌려 보내야 한다. 트리거나 에이전트를 모아 놓는 것만으로 개선 과정이 생기지는 않는다.

발표의 구체적인 평가 사례는 **중복 테스트**다. 에이전트가 의미 없는 테스트를 추가한 실행을 찾아 왜 그랬는지 조사한다. 지침이 문제였는지, 기존 테스트를 이해하지 못했는지 검토하고 작업 방식의 변경을 제안한다. 완료 수·비용·사람의 개입 횟수와 특정 실패의 평가는 서로 다른 질문에 답한다.

여기서 점수는 원인을 확정하는 결론이 아니다. 개선 후보를 찾는 신호다. 변경한 설정도 실제 과제로 다시 비교해야 하며, 고객 문제를 해결하는 제품을 만들 책임은 여전히 엔지니어에게 있다. [공식 발표와 전사, 1:04:38·1:14:07 이후](https://ai.engineer/code/2026/talks/zach-lloyd)

> **이 글의 해석:** 개발 과정의 오류를 매번 개인이 수습하는 대신, 같은 종류의 실패가 반복되는 이유를 수정 가능한 대상으로 삼는 관점이다. 다만 잘못된 평가 지표를 최적화하면 잘못된 방향도 더 효율적으로 반복할 수 있다.

## 2. 별도 구성 사례: 코드로 정의한다는 것은 어디까지인가

Warp의 Ben Holmes가 공개한 구성 글은 이 개념을 실제 파일과 역할로 보여 준다. `factory.yaml`에는 저장소, 연결 도구, 실행 환경과 기본 설정을 정의한다. 개별 에이전트는 자신의 모델·실행 환경·도구 접근을 따로 설정한다.

중앙에서 요청을 분배하는 Foreman 옆에는 조사, 구현, 리뷰, 디자인 역할을 둔다. 역할 수 자체가 정답은 아니다. 글에서도 더 단순한 구성을 함께 비교하고 있다고 밝힌다.

자동화 사례는 Sentry의 치명적 오류 알림이다. 이벤트는 조사를 시작하지만, 수신 내용을 신뢰할 지시로 취급하지 않는다. 원인과 확신 정도를 보고하고 명확한 실패일 때 수정 초안으로 이어지도록 범위를 둔다.

실행 환경도 역할에 맞춘다. 모바일 앱 사례에서는 Swift를 컴파일하는 구현 작업만 macOS에서 실행하고, 조정이나 일반 작업은 Linux에서 수행한다. 모든 작업에 비싼 환경을 일괄 배정하지 않는 것이다. [Ben Holmes, 구성과 실행 환경 사례](https://www.warp.dev/blog/software-factory-as-code)

> **이 글의 해석:** 버전 관리 대상이 프롬프트 하나에 머물면 실험을 재현하기 어렵다. 같은 지시라도 접근 가능한 도구와 실행 환경이 달라지면 결과가 달라지기 때문이다. 반대로 설정 파일에 비밀 값 자체를 넣어야 한다는 뜻은 아니다. 변경 가능한 정의와 보안 자격 증명의 저장은 구분해야 한다.

## 3. Lloyd의 별도 설계 글: 실행과 개선은 서로 다른 책임이다

Lloyd가 쓴 **The Factory Stack**은 개방성·부분 도입 가능성·코드 정의를 설계 원칙으로 제시한다. 아래는 그 글의 계층을 역할 중심으로 압축한 것이다.

| 계층 | 맡는 역할 |
| --- | --- |
| 작업 정의 | 에이전트·실행 환경·저장소·트리거·평가 설정을 버전으로 남긴다 |
| 데이터와 맥락 | 실행 이력, 비용·시간, 도구 접근 기록과 필요한 지식을 보관한다 |
| 실행 환경 | 실제 앱을 빌드하고 실행할 수 있는 작업 공간을 제공한다 |
| 추론 | 모델·하네스·추론 제공처를 비교하고 조합할 수 있게 한다 |
| 개선 | 평가, 과거 작업 재실행, 벤치마크와 변경 제안을 지원한다 |
| 작업 조정 | 에이전트를 시작하고 진행 상황·실패 복구·인계를 관리한다 |

이 구분에서 에이전트를 실행하는 기능과 **그 실행 방식이 좋아지는지 알아내는 기능**은 다르다. 모델을 교체할 자유가 있어도 비교할 기록이 없으면 개선을 입증할 수 없다. 실행 이력 역시 저장만 해서는 가치가 생기지 않고 재실행·분석에 연결돼야 한다. 이는 Lloyd의 설계 제안이며 반드시 모든 계층을 한 번에 도입하라는 요구가 아니다. [Zach Lloyd, The Factory Stack](https://www.warp.dev/blog/the-factory-stack)

## 4. 실제 실험: WarpBench는 무엇을 고정했나

Lloyd가 별도로 공개한 **WarpBench** 사례는 내부 과거 작업에서 범위가 다른 30개 과제를 골랐다. 서버와 클라이언트를 포함해 UI, 데이터베이스, 업무 로직 등 서로 다른 작업을 묶었다. 핵심은 같은 질문을 모델에 다시 던지는 데 있지 않았다.

재실행 때 Git을 이용해 원래 코드와 당시 작업 설정을 복원했다. 에이전트 정의와 스킬 같은 조건을 고정하고 구현 모델을 바꾸어 비교했다. 비용·품질 등은 자체 평가기로 확인했다.

실험 자체도 비용이 들었다. 공개 글은 한 실행에 **3시간 46분, 2,130.57달러**가 들었다고 보고한다. 따라서 큰 벤치마크를 무조건 자주 반복하기보다 모델이나 주요 입력이 바뀔 때 수행하고, 특정 질문에는 좁은 과제 묶음을 쓰는 접근을 설명한다.

해당 사례에서 완료 PR당 비용이 대략 **80달러에서 30달러**로 내려갔다고 보고했지만, 이는 Warp의 작업·평가 방식에 대한 자체 결과다. 모든 저장소의 절감률도 아니고 현재 모델 순위도 아니다. 과거 과제의 결과가 미래에도 유지되는지 확인할 필요는 저자 역시 인정한다. [Zach Lloyd, WarpBench 실험](https://www.warp.dev/factories/benchmarks/warpbench)

> **이 글의 해석:** 비교의 핵심은 이름이 유명한 모델을 고르는 일이 아니라, 바꾼 조건과 고정한 조건을 설명할 수 있는가이다. 과거에 쉬웠던 작업만 골랐다면 점수는 좋아도 실제 업무를 대표하지 못한다. 소수 과제에서의 우위와 조직 전체의 운영 성과도 구분해야 한다.

## 5. 제품 문서로 확인한 평가 단위: 과제·설정·반복

현재 공식 벤치마크 문서에서는 한 묶음이 하나의 에이전트를 평가하며, 각 과제에 프롬프트와 성공 기준을 둔다. 한 과제를 한 설정에서 실행한 것이 한 번의 trial이다. 반복 횟수를 늘리면 추가 실행이 생긴다.

실행은 설정과 평가 기준을 보존하므로 이후 과제 정의를 수정해도 과거 결과가 바뀌지 않는다. 막힌 실행은 막힌 상태로 남지만, 확보된 증거를 평가기가 채점할 수 있다. 따라서 **채점 결과가 있다는 사실과 작업이 완료됐다는 사실을 혼동하면 안 된다.**

이 문서는 모델뿐 아니라 하네스와 실행 환경도 비교 대상으로 다루며, 평가기와 반복 횟수가 늘면 비용이 커진다고 설명한다. 발표 당일의 모든 기능을 재현한 자료가 아니라, 조사 시점의 제품 문서라는 점도 구분해야 한다. [공식 Factory benchmarks 문서](https://docs.warp.dev/factories/benchmarks/)

_발표와 별도 1차 자료의 관계를 설명하기 위해 제작한 도식이다. Warp의 원본 슬라이드나 제품 화면을 복제한 그림은 아니다._

> **이 글의 해석:** 운영 기록은 “어디가 불편한가”를 찾고, 통제된 비교는 “이 변경이 도움이 되는가”를 묻는다. 두 질문을 섞으면 새 설정을 적용한 주에 일이 쉬워졌다는 이유만으로 개선을 단정하기 쉽다. 또한 실험 점수가 좋아도 보안·권한이나 되돌리기 조건까지 자동으로 승인된 것은 아니다.

이 관점에서 처음부터 거대한 공장을 만들 필요는 없다. 반복되는 실패 하나에 대해 실행 근거를 보존하고, 변경 후보와 기준 설정을 같은 과제에 비교할 수 있다면 이미 작업 방식을 공학적으로 다루기 시작한 셈이다. 이 마지막 제안은 발표자의 구현 지시가 아니라 자료들을 읽고 내린 해석이다.

## 출처와 한계

- **공식 발표:** 문제 정의와 중복 테스트 평가 사례를 확인했다. 기계 전사의 관련 구간을 읽었으며 원본 영상 전체를 독립적으로 대조하지 않았다.
- **구성·스택·WarpBench 글:** 발표를 보충하는 별도 1차 자료다. 발표에서 모두 설명된 내용으로 취급하지 않았다.
- **제품 문서:** 조사 시점의 평가 단위를 설명하는 자료이며 기능과 형식은 바뀔 수 있다.
- **독립성:** 자료들은 발표자·동료·제품 제공자가 작성한 1차 자료다. 서로 다른 문서이지만 독립적인 제3자 검증은 아니다. 비용과 품질 개선을 재현하지 않았다.
- **내용 범위:** 전체 발표의 번역이나 문장별 재현이 아니라, 발표 주제를 관련 실제 사례로 설명한 글이다. 직접 인용 대신 재서술했으며 도식은 자체 제작했다.
