## 같은 일을 끝내는데 왜 더 많은 호출이 필요한가

**발표 요약:** Philipp Schmid의 *I deleted 90% of my harness (And It Got Better)*는 모델 주변의 도구와 제어 코드를 얼마나 남겨야 하는지 묻는다. 파일 읽기·수정 도구를 각각 호출하는 경로와 Bash에서 여러 변경을 묶는 경로를 비교한다. 후자의 장점은 기능 삭제보다 모델과 도구 사이의 왕복 감소다.

Bash 하나로 시작한 실험에서는 긴 작업의 로그를 파일에 남기고, 계획도 파일로 관리한다. 다만 이미지는 일반 파일 출력으로 보여 줄 수 없어 별도 미디어 도구를 추가한다. 약 350개 과제 비교에서는 점수만 보면 구성이 비슷해 보이지만 토큰과 과제당 비용은 달랐다고 설명한다. 각 과제를 한 번만 실행했으므로 점수 차이는 잡음일 수 있다는 단서도 직접 붙인다.

시연에서는 한 모델이 Python 스크립트로 여러 수정을 묶는 반면 다른 모델은 Bash에서도 작은 작업을 따로 호출한다. 같은 인터페이스를 줘도 묶어서 실행하는 능력은 같지 않았다. 결론은 도구 수만 줄이면 해결된다는 것이 아니라 모델과 실행 구조를 함께 평가해야 한다는 것이다. [공식 발표·전사](https://ai.engineer/code/2026/talks/philipp-schmid)

## 한 도구가 적은 기능을 뜻하지 않는 이유

**해설:** 파일 읽기, 검색, 수정이 각각의 도구로 보이지 않아도 셸에서 같은 기능을 수행할 수 있다. 따라서 도구 개수는 모델에 노출한 인터페이스의 크기일 뿐 실제 능력의 크기가 아니다. 안전성도 같은 이유로 도구 수만 세어 판단할 수 없다.

이 차이는 실험 해석에도 중요하다. 두 하네스를 비교할 때 한쪽이 더 많은 기능이나 다른 실행 환경을 갖고 있다면 결과를 단순히 “도구를 줄인 효과”라고 부를 수 없다. 성공 조건, 모델, 입력, 권한, 실행 환경을 맞춘 뒤 호출 수와 비용을 비교해야 한다.

## 발표자 자신의 Code Mode 글에서 보완되는 부분

**보충 자료:** Schmid의 별도 글은 모델에 `exec(code)`를 제공하고 TypeScript나 Python으로 여러 도구를 연결하는 구조를 설명한다. 입출력 타입을 알면 앞 도구의 결과를 다음 호출로 이어 쓸 수 있다. 병렬 조회, 필터링, 오류 처리도 프로그램 안에서 수행한다. 필요한 결과만 모델에 반환하며 이미지·음성은 전용 출력 경로로 전달한다. 이 설명은 Bash만 제공한 발표 실험과 관련되지만 같은 구현은 아니다. [Schmid: Why Agents Are Soon Only Going to Have 1 Tool](https://www.philschmid.de/code-mode)

![모델이 중간 결과마다 다시 호출되는 구조와 코드 내부에서 처리하는 구조의 비교](/images/ai-engineer-code-2026/philipp-schmid-code-mode.svg)

*개념 비교를 위해 새로 그린 도식이다. 호출 횟수나 비용의 측정 결과를 나타내지 않는다.*

## 중간 결과를 모델에 모두 읽힐 필요가 있는가

**보충 자료:** Anthropic의 별도 MCP 글은 많은 도구 정의와 반복되는 중간 결과를 문맥 비용의 두 원인으로 설명한다. 예로 Drive에서 받은 회의 내용을 Salesforce에 넣을 때 문서가 모델 문맥을 반복해서 통과하는 구조를 든다. 코드 실행 방식에서는 필요한 도구를 찾아 데이터 처리를 실행 환경에서 수행하고 최종적으로 필요한 정보만 반환할 수 있다. [Anthropic: Code execution with MCP](https://www.anthropic.com/research/code-execution-with-mcp)

**해설:** 여기서 구분할 것은 의미를 판단할 데이터와 프로그램이 그대로 운반할 데이터다. 이미 정해진 필드 매핑에 따라 값을 전달하는 작업은 모델이 전체 문서를 다시 생성할 이유가 적다. 반면 어떤 항목이 중요한지 아직 판단하지 못했다면 기계적인 필터가 필요한 근거를 먼저 버릴 수 있다.

따라서 작은 결과만 반환하는 설계에는 관찰 가능성도 필요하다. “성공” 한 줄로 끝내면 빠르지만 일부 실패나 누락을 놓칠 수 있다. 자체 적용 예시로는 성공 수, 실패 수, 재시도 대상, 원본 결과 위치를 함께 남기는 방식이 있다. 이는 발표의 코드나 지표를 재현한 제안이 아니다.

## 비용 실험과 안전 설계는 따로 남는다

성능을 비교할 때는 정답률뿐 아니라 성공한 과제의 비용, 지연시간, 재시도량을 함께 봐야 한다. 실패한 실행이 일찍 끝나 토큰이 적게 든 경우를 효율 개선으로 세면 안 된다.

**자체 평가 예시:** 같은 파일 수정 과제를 두 하네스로 반복 실행하고, 성공 판정에 쓰는 테스트를 고정한다. 각 실행에 모델 버전, 성공 여부, 모델 왕복 수, 입력·출력 토큰, 비용과 시간을 붙인다. 먼저 성공률을 보고 그다음 성공한 실행의 비용 분포를 비교하면, 기능 축소로 일을 덜 하고도 싸졌다고 해석하는 실수를 줄일 수 있다. 이 예시는 발표의 실험 표를 재현한 것이 아니다. 캐시 상태나 모델의 실행 변동도 반복 측정으로 확인할 항목이다.

또한 코드를 실행할 수 있는 환경을 제공했다는 것만으로 비신뢰 코드가 안전하게 격리된 것은 아니다. 파일·네트워크·자격증명 경계와 각 외부 행동의 승인 정책이 필요하다. 모델에 보이는 도구가 하나여도 그 안에서 일어나는 실제 행동은 여러 개다.
