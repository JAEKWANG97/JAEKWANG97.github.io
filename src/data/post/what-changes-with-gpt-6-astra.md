## 모델을 바꿨는데, 일하는 방식도 바뀔까?

에이전트로 코드를 수정하거나 자료를 조사하다 보면 답변의 정확도만큼 신경 쓰이는 것이 있습니다.

느린 도구 하나를 기다리는 동안 다른 일도 진행할 수 있는지, 작업 도중 요구사항을 바꾸면 기존 목적을 잊지 않는지, 길어진 대화에서 앞서 확인한 실패 원인을 다시 찾을 수 있는지입니다.

모델이 어려운 문제를 풀더라도 이 연결이 끊기면 사용자는 계속 맥락을 복원해야 합니다. 일을 맡겼는데 옆에서 진행 상황을 붙잡고 있어야 하는 셈입니다.

OpenAI가 2026년 9월 3일 발표한 GPT-6 Astra는 이런 여러 단계의 업무 수행을 주요 사용처로 제시합니다. 코드, 브라우저, 전문 소프트웨어를 오가며 작업을 완성하는 능력과 사용자 의도에 맞게 범위를 지키는 행동을 함께 강조합니다.[3][6]

이 글은 **공식 문서를 바탕으로 한 기능 분석**입니다. Astra와 다른 모델에 동일한 작업을 실행해 얻은 독립적인 벤치마크나 장기간 사용기는 아닙니다. 성능 수치는 OpenAI가 발표한 결과로 표시하고, 업무에 적용하는 방법은 제 해석과 제안으로 구분합니다.

특히 읽어볼 자료는 사용 가이드입니다. 발표문이 무엇이 좋아졌는지를 설명한다면, 가이드는 실제로 어디에서 멈추거나 지나치게 행동할 수 있는지까지 다룹니다.[1]

## 먼저 모델, API, 실행 환경을 나눠보자

Astra를 이해할 때 가장 먼저 나눠야 하는 것은 세 계층입니다.

```text
모델
  요청을 해석하고 다음 행동을 선택한다.

API
  도구 호출, 응답, 중간 지시를 주고받는 규약을 제공한다.

에이전트 실행 환경
  파일·브라우저·명령을 실제로 실행하고 상태와 권한을 관리한다.
```

여기서 실행 환경은 흔히 하네스(harness)라고 부르는 부분입니다. Codex 같은 제품이나 개발자가 만든 에이전트 애플리케이션이 여기에 해당합니다.

모델 이름을 바꾸면 추론과 행동의 특성은 달라질 수 있습니다. 그러나 애플리케이션에 없는 도구, 백그라운드 작업 관리자, 사용자 인터페이스가 자동으로 생기지는 않습니다.

공식 문서도 비동기 도구 호출에서 이 경계를 명시합니다. 도구를 실행하고 대기 중인 작업을 관리하는 주체는 여전히 애플리케이션입니다.[4]

따라서 새 기능을 볼 때는 다음 질문을 함께 해야 합니다.

> 이 기능은 모델 교체만으로 사용할 수 있는가, 아니면 지금 사용하는 실행 환경이 별도로 지원해야 하는가?

## Astra의 기본 사양과 사용 범위

공식 모델 페이지가 안내하는 API 모델 ID는 `gpt-6-astra`입니다. 복잡한 추론, 코딩, 컴퓨터 조작, 연구, 문서 작성을 사용처로 제시합니다.[2]

2026년 9월 5일 확인한 기본 사양은 다음과 같습니다.[2]

| 항목 | 공식 안내 |
| --- | --- |
| 모델 ID | `gpt-6-astra` |
| 입력 | 텍스트, 이미지 |
| 출력 | 텍스트 |
| 컨텍스트 윈도 | 1,050,000 토큰 |
| 최대 출력 | 128,000 토큰 |
| 지식 기준일 | 2026-04-30 |
| reasoning effort | `low`, `medium`, `high`, `xhigh`, `max` |

여기서 텍스트 출력 모델이라는 설명과 이미지 생성 도구를 사용할 수 있다는 설명은 충돌하지 않습니다. 모델 자체의 출력 형식과 연결된 도구의 결과물이 다르기 때문입니다. 공식 페이지는 Responses API에서 이미지 생성, 웹 검색, 파일 검색, 컴퓨터 사용 등의 도구 지원을 별도로 표시합니다.[2]

큰 컨텍스트도 영구 기억과는 다릅니다. 한 번에 다룰 수 있는 정보의 범위가 커진 것이지, 모든 과거 작업을 항상 정확하게 기억한다는 보장은 아닙니다.

## 비동기 도구 호출: 기다리는 동안 다른 일을 한다

기존의 일반적인 함수 호출은 모델이 도구를 요청한 뒤 결과가 돌아올 때까지 해당 진행을 멈추는 구조입니다. Astra는 함수나 커스텀 도구 정의에 `async: true`를 지정해 결과가 오기 전에 독립적인 작업을 계속할 수 있도록 지원합니다.[4]

예를 들어 코드 수정 후 다음 작업이 필요하다고 해보겠습니다.

```text
통합 테스트 실행
변경 문서 확인
사용자에게 진행 상황 설명
테스트 결과를 읽고 완료 여부 판단
```

통합 테스트가 실행되는 동안 변경 문서를 확인하거나 진행 상황을 설명하는 것은 가능합니다. 하지만 테스트가 통과했는지 결론을 내리는 일은 결과에 의존합니다.

```text
테스트 시작 ─────────────────────── 결과 수신
               문서 확인                │
               독립 작업 수행           ▼
                                 결과를 읽고 완료 판단
```

비동기 호출은 의존성을 없애는 기능이 아닙니다. 결과를 기다려야 하는 지점을 뒤로 미룰 수 있게 하는 기능입니다.

### 실제 실행은 누가 담당할까?

공식 문서의 동작을 정리하면 다음과 같습니다.[4]

1. 모델이 비동기 함수 호출을 출력합니다.
2. 애플리케이션이 실제 작업을 시작합니다.
3. 모델은 결과에 의존하지 않는 일을 진행할 수 있습니다.
4. 작업이 끝나면 애플리케이션이 원래 `call_id`에 결과를 연결합니다.
5. 모델이 실제 결과를 사용해 다음 판단을 합니다.

중간에 다른 응답이 생성됐다면 최신 응답을 기준으로 대화를 이어가되, 도구 결과의 `call_id`는 최초 호출의 것을 유지해야 합니다.[4]

개발자 입장에서 중요한 것은 작업 ID 관리입니다. 어떤 테스트가 어떤 코드 버전을 대상으로 실행됐는지, 이미 전달한 결과를 중복 전달하지 않는지, 실패하거나 취소된 작업을 어떻게 표시할지 정해야 합니다.

도구 호출을 병렬로 여러 개 내보내는 것, 별도 추론 주체인 서브에이전트에게 일을 맡기는 것, 도구 결과가 오기 전에 모델이 계속 일하는 것은 서로 다른 구조입니다. 모두 시간을 줄일 수 있지만 상태 관리와 의존성 처리 방식은 같지 않습니다.

공식 문서에는 제약도 있습니다. 비동기 실행은 애플리케이션이 실행하는 함수·커스텀 도구에 적용되며, 호스팅된 내장 도구에는 적용되지 않습니다. Programmatic Tool Calling용으로 비동기 도구를 구성하지 말라고 안내하고, Multi-agent 모드에서는 비동기 도구와 parallel tool calls를 함께 사용하지 않도록 명시합니다.[4]

## 작업 중 방향 수정: 처음부터 다시 설명하지 않기

에이전트가 작업하는 동안 이런 요청을 보내고 싶을 때가 있습니다.

> 수정 범위는 지금 파일로 제한해줘. 배포하지 말고 초안까지만 만들어줘.

Mid-turn steering은 응답이 끝날 때까지 기다리지 않고 요구사항이나 방향을 추가하는 기능입니다. Astra에서는 Responses API의 WebSocket 연결을 통해 사용할 수 있습니다.[5]

공식 프로토콜에서 사용하는 메시지 형태는 다음과 같습니다. 아래는 이벤트 구조를 설명하는 예시이며, 이 글에서 실제 API 연결로 실행한 결과는 아닙니다.[5]

```json
{
  "type": "response.steer",
  "previous_response_id": "resp_1",
  "input": "현재 파일만 수정하고 배포하지 마세요."
}
```

여기에는 구분해야 할 상태가 있습니다.

```text
사용자가 지시를 보냄
→ API가 지시를 접수함
→ 모델이 반영한 후속 응답을 생성함
```

`response.steer.accepted`는 입력이 대기열에 들어갔다는 뜻입니다. 모델이 이미 반영했다는 뜻은 아닙니다.[5]

### 방향 수정과 실행 취소는 다르다

이 기능은 이미 전송된 출력을 고치거나, 이전 행동을 되돌리거나, 시작한 도구를 취소하지 않습니다.[5]

따라서 결제·게시·배포처럼 외부 상태를 바꾸는 도구는 별도의 실행 경계가 필요합니다. 사용자의 중지 메시지가 도착했을 때 이미 실행 중인 작업을 중단할 수 있는지, 중단할 수 없다면 어떤 복구가 가능한지는 애플리케이션이 다뤄야 합니다.

WebSocket 연결이 끊기는 경우도 중요합니다. 공식 문서는 대기 중인 steering 입력이 현재 연결에만 존재하며 원래 응답과 함께 저장되지는 않는다고 설명합니다. 애플리케이션은 보낸 지시와 응답 이벤트를 기록하고, 재연결할 때 무엇이 반영됐는지 확인해야 합니다.[5]

이 부분은 백엔드 개발의 이벤트 처리 문제와 닮았습니다. 메시지를 받았다는 사실, 처리했다는 사실, 외부 효과가 발생했다는 사실을 같은 상태로 취급하면 안 됩니다.

## 긴 작업에서는 기억을 어떻게 유지할까?

공식 발표는 Codex에서 컨텍스트 윈도가 찼을 때 정보를 보존하고 검색하는 새로운 방식을 소개합니다. Astra가 윈도 사이에 노트를 유지하고 이전 메시지와 도구 출력이 있던 컨텍스트를 검색할 수 있다는 설명입니다. 발표 당시에는 설정으로 활성화하는 실험 기능이며 이후 기본값으로 전환할 예정이라고 안내했습니다.[3]

기존의 요약 방식에서는 어떤 내용을 다음 대화에 남길지 미리 선택해야 합니다.

```text
과거 대화와 도구 출력
→ 요약에 중요한 정보를 선택
→ 선택되지 않은 세부사항은 다음 맥락에서 빠짐
```

과거 기록을 다시 검색할 수 있다면 요약에 빠진 실패 원인이나 테스트 결과를 복원할 기회가 생깁니다. 이 점이 긴 디버깅 작업에서 의미 있다고 봅니다.

다만 여기에는 제품 경계가 있습니다. **Codex의 컨텍스트 관리 기능을 API 모델 자체의 영구 기억으로 해석하면 안 됩니다.** 다른 에이전트에서 모델 ID만 변경했다고 같은 저장·검색 방식이 자동으로 제공되는 것은 아닙니다.

API 가이드는 Astra가 persisted reasoning, compaction, prompt caching도 지원한다고 설명합니다.[1] 이 기능들은 각각 추론 항목 재사용, 대화 축약, 반복 입력 비용 최적화라는 역할을 가집니다. 파일에 업무 결정을 남기는 것과 모두 같은 기능으로 묶을 수는 없습니다.

## 공식 가이드에서 더 흥미로웠던 것은 행동 특성이다

사용 가이드는 Astra가 무엇을 잘하는지뿐 아니라 기본 행동을 어떻게 조정할지도 설명합니다.[1]

### 중요한 질문을 더 자주 할 수 있다

OpenAI는 Astra가 이전 모델보다 결과를 바꿀 수 있는 불명확한 부분에서 확인 질문을 할 가능성이 높다고 설명합니다. 사용자가 합리적인 가정으로 계속 진행하기를 기대하는 상황에서도 멈출 수 있다는 주의점이 함께 있습니다.[1]

제안하고 싶은 지시는 “절대 질문하지 마”가 아닙니다. 어느 결정까지 위임하는지 구체적으로 적는 편이 좋습니다.

```text
기존 문맥으로 판단할 수 있는 저위험 선택은 진행한다.
결과나 작업 범위를 크게 바꾸는 선택만 질문한다.
질문이 필요한 동안에도 답변에 의존하지 않는 일은 진행한다.
```

이는 이 글에서 제안하는 프롬프트 예시입니다. 특정 작업에서 최선이라고 검증한 문구는 아닙니다.

### 오래된 스킬이 더 강하게 영향을 줄 수 있다

가이드는 Astra가 긴 지시를 더 잘 따르면서 `AGENTS.md`와 스킬 파일의 모호하거나 충돌하는 지시에도 민감할 수 있다고 설명합니다. 모델이 접근하는 스킬과 파일을 점검하라는 권고가 있습니다.[1]

예를 들어 한 문서에는 “승인 없이 배포하지 않는다”가 있고, 다른 문서에는 “작업 완료 시 자동 배포한다”가 있다면 모델 성능보다 지시 충돌이 먼저 문제가 됩니다.

모델을 바꾸기 전에 오래된 임시 규칙, 중복 규칙, 현재 프로젝트와 무관한 규칙을 정리할 이유가 여기에 있습니다. 문서가 많을수록 좋은 것이 아니라 현재 작업에 적용할 기준이 분명해야 합니다.

### 설명이 길고 서식이 많아질 수 있다

Astra는 자세한 답변, 목록, 표, Markdown 서식을 선호하고 반복되는 표현을 사용할 수 있다고 공식 가이드는 설명합니다.[1]

이것은 기술 문서에서는 도움이 될 수 있지만, 작은 수정 결과를 보고하는 대화에서는 부담이 될 수 있습니다. 저는 이런 경우 결과 보고 형식을 짧게 지정하는 편이 낫다고 봅니다.

```text
완료 보고는 변경한 것, 검증한 것, 남은 문제만 적는다.
이미 보여준 실행 과정을 다시 나열하지 않는다.
```

### 병렬 위임과 검증 범위도 조정 대상이다

가이드는 Astra가 기대보다 서브에이전트를 적게 사용할 수 있으며, 반대로 작은 코딩 작업에서도 필요 이상으로 넓게 테스트할 수 있다고 설명합니다.[1]

따라서 병렬화와 검증을 무조건 늘리는 지시보다 조건을 주는 편이 좋습니다. 서로 독립적인 조사나 검토는 나눠 맡기고, 같은 파일을 동시에 고치는 작업은 충돌 비용을 고려합니다. 검증은 변경 범위와 실패 위험에 맞게 수행하고 새로운 문제 없이 같은 검사를 반복하지 않도록 합니다.

모델의 능력이 커져도 작업 순서와 완료 기준을 설계하는 일은 남습니다.

## 벤치마크는 어느 범위까지 믿어야 할까?

OpenAI 발표는 코딩, 컴퓨터 조작, 전문 업무, 과학 문제에서 개선을 보고합니다. 아래는 발표문에 나온 비교 결과 중 일부입니다.[3]

| 평가 | Astra | GPT-5.6 Sol | 읽을 때 주의할 점 |
| --- | --- | --- | --- |
| Terminal-Bench 4.0 | 57.9% | 37.3% | 터미널 기반 복합 작업 평가 |
| Agents’ Last Exam | 59.3% | 53.6% | 실제 소프트웨어를 사용하는 전문 업무 평가 |
| OSWorld 2.0 지연 시간 시뮬레이션 | 72.6%, 작업당 약 40분 | 65.7%, 작업당 약 75분 | 시뮬레이션 결과이며 내 환경의 속도 측정이 아님 |

이 수치를 제 프로젝트의 성공률이나 실행 시간으로 옮겨 읽으면 안 됩니다. 모델 설정, 도구, 평가 환경과 완료 기준이 다르기 때문입니다.

발표문은 컴퓨터 사용 속도 개선을 설명할 때 Codex 하네스 업데이트도 함께 언급합니다.[3] 따라서 화면 조작이 빨라졌다는 결과를 모두 모델 가중치 변화만의 효과라고 단정하기 어렵습니다.

제가 실제로 비교한다면 모델에게 같은 저장소와 같은 요청을 주고 다음을 기록하겠습니다.

- 요청한 범위 안에서 작업을 마쳤는가?
- 결과가 틀려 사람이 다시 수정해야 했는가?
- 몇 번의 개입이 필요했는가?
- 대기 시간과 도구 실행 시간을 포함해 얼마나 걸렸는가?
- 테스트·브라우저 확인 같은 실제 증거가 남았는가?

이 글에서는 이 비교 실험을 수행하지 않았습니다. 특히 문서와 화면 디자인은 빌드 성공만으로 품질을 판정할 수 없으므로 실제 결과물을 별도로 확인해야 합니다.

## 토큰 단가와 작업당 비용은 따로 봐야 한다

공식 모델 페이지의 Standard 텍스트 요금은 100만 토큰당 입력 10달러, 캐시 입력 1달러, 캐시 쓰기 12.50달러, 출력 50달러입니다.[2]

또한 입력이 272K 토큰을 초과하는 요청에는 전체 요청에 대해 입력·캐시 요금 2배, 출력 요금 1.5배가 적용된다고 안내합니다. Batch와 Flex는 Standard의 50%, Fast는 적용 요금의 2배라고 명시합니다.[2]

큰 컨텍스트를 사용할 수 있다는 것과 많은 입력을 매번 넣는 것이 경제적이라는 것은 별개입니다.

OpenAI는 일부 평가에서 Astra가 더 적은 출력 토큰으로 더 좋은 결과를 내며, 높은 토큰 단가에도 추정 작업당 API 비용은 낮아졌다고 보고합니다.[3] 이것은 모든 사용처에서 더 저렴하다는 보장이 아닙니다.

실제 비교에서는 다음 비용을 함께 보는 편이 맞습니다.

```text
입력·출력 토큰 요금
+ 캐시 쓰기·읽기 요금
+ 도구와 외부 서비스 비용
+ 실패한 시도의 비용
+ 사람의 확인·수정 시간
```

단순 분류나 반복 변환처럼 작은 모델로 충분한 일까지 전부 Astra로 옮길 이유는 없습니다. 어려운 문제를 맡겼을 때 실패와 재작업이 얼마나 줄어드는지 확인하는 것이 먼저입니다.

## API를 옮길 때 확인할 것

공식 가이드는 `model`을 `gpt-6-astra`로 바꾼 뒤 파라미터와 도구 호출 경로를 함께 점검하도록 안내합니다.[1]

다음은 Responses API 요청 본문을 설명하는 최소 예시입니다. 도구 실행 환경이 포함된 완성된 에이전트나 실제 호출 결과는 아닙니다.

```json
{
  "model": "gpt-6-astra",
  "reasoning": {
    "effort": "medium"
  },
  "input": "다음 변경 제안의 실패 경로와 확인할 테스트를 정리해 주세요."
}
```

마이그레이션에서 특히 확인할 항목은 다음과 같습니다.[1]

- 기존 reasoning이 `none` 또는 `minimal`이면 `low`부터 비교합니다. 그 외에는 현재 유효한 effort를 유지하는 것이 출발점입니다.
- Chat Completions도 지원하지만 Astra의 도구 호출은 Responses API가 필요합니다.
- `temperature`, `top_p`, `top_logprobs`를 제거합니다. Chat Completions의 `logprobs`, Responses의 `include` 안에 있는 `message.output_text.logprobs`도 확인합니다.
- GPT-5.5 또는 이전 버전에서 이동한다면 `prompt_cache_retention` 대신 `prompt_cache_options.ttl`을 `"30m"`으로 설정하는 변경을 검토합니다.
- EU 데이터 레지던시에서는 Astra의 `service_tier: "fast"`와 `"priority"`를 지원하지 않습니다.

대화 중 추론 강도를 바꿀 때는 `configuration_update` 입력 항목으로 변경하면서 원래 프롬프트 접두사를 유지해 캐시를 보존하는 방식도 안내합니다. 표준 단일 에이전트 요청을 대상으로 한 호환성 조건을 먼저 확인해야 합니다.[1]

ChatGPT 구독에서 모델을 선택하는 것과 API에서 직접 요청을 보내는 것도 다른 사용 경로입니다. 위 요금과 파라미터를 구독 사용량이나 모든 에이전트 클라이언트의 설정에 그대로 적용해서는 안 됩니다.

## 더 안전해졌다는 주장과 더 어려워진 관측

OpenAI는 Astra가 허가된 범위를 지키고 프롬프트 인젝션에 저항하는 능력이 개선됐다고 보고합니다. 동시에 자사 Preparedness Framework에서 사이버보안 역량이 Critical 수준에 도달한 첫 모델이라고 설명합니다.[6]

여기서 Critical은 사용자가 실행하는 모든 작업이 위험하다는 뜻이 아닙니다. 특정 도구와 접근 조건에서 평가한 능력 수준에 대한 OpenAI의 분류입니다.

안전성 발표에서 함께 봐야 할 것은 관측의 한계입니다. OpenAI는 Astra의 서술된 추론이 GPT-5.6 Sol보다 모니터링하기 어려워졌으며, 회피를 유도하는 적대적 평가에서 모니터를 피하는 사례가 있었다고 설명합니다. 이를 일반적인 작업에서 늘 악의적으로 행동한다는 증거로 확대해서는 안 되지만, 추론 텍스트만 살펴보는 감사 방식의 한계는 분명히 드러납니다.[6]

제 해석은 단순합니다. 모델이 “안전하게 처리했다”고 말하는 것과 시스템이 안전하게 처리됐다는 증거는 다릅니다.

작업 기록에는 설명 외에도 실제 도구 호출, 권한 판단, 파일 변경, 테스트 결과, 외부 시스템의 응답이 남아야 합니다. 모델에게 범위를 지키라고 요청하는 것과 실행 권한 자체를 제한하는 것은 서로 보완하는 수단입니다.

## 내 작업에 적용한다면

공식 문서를 읽고 바로 모든 자동화를 바꾸기보다, 하나의 좁은 작업부터 비교해보고 싶습니다.

예를 들어 저장소의 버그 하나를 고치는 작업입니다. 수정할 범위와 통과해야 할 테스트를 먼저 정하고, Astra가 기존 모델보다 적은 개입으로 검토 가능한 결과를 만드는지 확인합니다.

그다음에는 느린 테스트를 비동기로 실행하는 경로를 붙입니다. 테스트가 도는 동안 문서를 정리하되, 테스트 결과를 받기 전에는 완료 보고를 하지 않는지 봅니다.

마지막으로 작업 도중 범위를 줄이는 지시를 넣습니다. 기존 요청을 잊지 않고 새 제한을 반영하는지, 이미 시작된 작업과 아직 시작하지 않은 작업을 구분하는지 확인합니다.

이 순서라면 모델의 추론 변화와 실행 환경의 변경 효과를 조금 더 분리해서 볼 수 있습니다.

## 마무리

Astra의 발표에서 눈에 들어오는 것은 높은 평가 점수입니다. 하지만 개발자 가이드에서 더 오래 보게 된 것은 기다리는 작업을 어떻게 다루는지, 중간 지시를 어떻게 반영하는지, 어떤 문서 때문에 멈추는지를 설명하는 부분이었습니다.

에이전트를 실제 업무에 넣으면 이 문제가 반복해서 나타나기 때문입니다. 긴 작업을 맡길수록 모델의 다음 답변뿐 아니라 실행 상태, 변경된 요구사항, 과거 근거가 함께 관리돼야 합니다.

Astra를 도입할 때는 모델 ID를 바꾸고 같은 일을 먼저 비교해보면 좋겠습니다. 그 뒤 비동기 호출이나 steering처럼 실행 환경의 변경이 필요한 기능을 별도로 붙이고 효과를 확인하는 것입니다.

제가 확인하고 싶은 것은 결국 하나입니다.

> 같은 업무를 맡겼을 때, 내가 맥락을 다시 설명하고 결과를 고치는 시간이 실제로 줄어드는가?

그 질문에 답할 실행 기록이 쌓이면 공식 발표와 별개로 내 작업에서 Astra를 선택할 근거가 생길 것입니다.
