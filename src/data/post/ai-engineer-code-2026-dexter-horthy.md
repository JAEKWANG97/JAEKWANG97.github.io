## 구현 담당자가 바뀌어도 개발 과정은 사라지지 않는다

Dexter Horthy는 구현을 에이전트에게 맡겨도 요구사항 판단·검사·배포·피드백은 남는다고 설명한다. 문제는 공장 자체가 아니라 그 과정이 저절로 해결된다고 보는 태도다. [공식 발표](https://ai.engineer/code/2026/talks/dexter-horthy)

발표의 중심 개념은 두 방향의 압력이다. 기능 요청과 장애는 일을 시작시키는 전방 압력이다. 테스트·린트·리뷰는 결과가 기준에 맞도록 되돌려 보내는 역압력이다. 발표자는 사람이 결과를 보기 전에 에이전트가 스스로 고칠 수 있는 문제를 최대한 고치게 하자고 말한다. [발표 전사, 08:21:56 이후](https://www.youtube.com/watch?v=y9JtCCZP2MQ&t=30116s)

아래에서는 12개 항목 전부를 나열하지 않고, 검증 압력과 위험에 맞춘 계획이라는 논점에 집중한다. 이를 발표에 등장하는 코드 진화 평가와 HumanLayer가 공개한 구현 사례로 풀어본다. 별도 글의 사례를 CODE 무대에서 시연한 것처럼 섞지 않고, 어디서 확인한 내용인지 구분한다.

## 1. 첫 번째 과제를 통과한 코드가 다음 과제도 버틸까

발표 초반에 언급된 SlopCodeBench는 한 번의 요구사항으로 프로그램을 완성하는 평가와 다르다. 연구진은 요구사항을 단계적으로 제시하고, 에이전트가 자신이 이전에 만든 코드를 계속 확장하게 한다. 내부 구조를 미리 지정하지 않으므로 앞선 설계 선택이 뒤의 작업에 영향을 줄 여지가 있다. [SlopCodeBench 논문 v2](https://arxiv.org/abs/2603.24755v2)

논문은 기능 통과 여부 외에 복잡도가 특정 부분에 집중되는 현상과 중복·불필요한 코드의 증가를 측정한다. 이 버전은 36개 문제와 196개 체크포인트를 다룬다. 연구진은 품질에 관한 명시적 지시가 초기 상태를 개선해도, 반복 확장에 따른 악화 경향까지 제거하지는 못했다고 보고했다. [같은 논문의 초록과 평가 설명](https://arxiv.org/abs/2603.24755v2)

**읽을 때의 한계:** 이는 해당 평가 환경에서 관측한 결과다. 특정 날짜의 모델 순위를 영구적인 능력 순위로 볼 수 없고, 모든 실제 저장소가 같은 속도로 나빠진다는 뜻도 아니다. CODE 발표에서 언급한 최신 점수와 논문 버전의 점수도 같은 실험으로 합치지 않았다.

**이 글의 해석:** 유지보수성은 코드가 보기 좋은지의 문제에만 머물지 않는다. 다음 요구사항을 넣을 때 기존 기능을 망가뜨리지 않고 바꿀 수 있는지도 포함한다. 그러므로 최초 생성 결과만 보는 평가는 소프트웨어가 살아 있는 동안 치르는 비용의 일부만 본다. Horthy의 문제 제기는 ‘AI 코드가 싫다’가 아니라, 완료를 선언하는 시점이 너무 이른 것 아니냐는 질문으로 읽는 편이 정확하다.

## 2. 역압력은 ‘다시 잘해 봐’라는 말보다 구체적이어야 한다

이 개념의 실제 구현은 HumanLayer의 별도 기술 글에서 확인할 수 있다. Kyle Mistele이 공개한 예제는 에이전트가 멈추려는 시점에 포맷 검사와 TypeScript 타입 검사를 실행한다. 오류가 있으면 그 내용을 에이전트에게 돌려주어 수정을 이어가게 하고, 성공했으면 조용히 끝낸다. 사용자가 모든 실수를 먼저 찾아서 다시 설명하는 방식이 아니다. [HumanLayer의 하네스 엔지니어링 글](https://www.humanlayer.dev/blog/skill-issue-harness-engineering-for-coding-agents)

같은 글에는 검사 출력을 너무 많이 전달해 생긴 실패도 나온다. 전체 테스트의 통과 로그 수천 줄이 문맥을 채우자 에이전트가 원래 작업에서 벗어났다는 것이다. 팀은 성공한 검사 출력을 숨기고 오류만 전달하는 방향으로 바꿨다. 또한 실제 실패를 겪기 전에 이상적인 설정을 모두 만들려 하거나, 매번 긴 전체 테스트를 돌리는 접근은 도움이 되지 않았다고 설명한다. [같은 글의 검증과 시행착오](https://www.humanlayer.dev/blog/skill-issue-harness-engineering-for-coding-agents)

이 사례는 단순히 검사를 많이 넣으라는 조언보다 구체적이다. 검사에는 실행 시간, 출력 크기, 실패 시 다음 행동이 함께 설계되어 있다. **이 글의 해석으로는**, 좋은 역압력은 작업을 무조건 막는 벽이 아니라 잘못된 방향을 알아차리고 고칠 수 있게 하는 피드백이다. 무엇이 틀렸는지 알 수 없는 실패 메시지는 사람과 에이전트 모두에게 추가 조사 비용을 남긴다.

[![작업을 시작하는 압력과 결과를 되돌려 보내는 검증 흐름](/images/ai-engineer-code-2026/dexter-horthy.svg)](/images/ai-engineer-code-2026/dexter-horthy.svg)

*공식 발표와 별도 기술 사례를 구분해 연결한 독자적 설명 도식. 실제 서비스의 구성도는 아니다.*

## 3. 자동화 안에 사람의 판단을 넣는 것은 모순이 아니다

Horthy의 이전 「12 Factor Agents」 글에는 HumanLayer 배포 봇을 바탕으로 한 사례가 있다. 일반 코드가 스테이징 배포와 종단 간 테스트를 수행한 뒤, 제한된 배포 작업을 에이전트에게 넘긴다. 에이전트가 프런트엔드를 먼저 배포하려 하자 사람이 백엔드부터 하라고 수정한다. 에이전트는 그 피드백을 새 순서로 바꾸고, 승인된 작업을 수행한다. 이후에는 다시 일반 코드가 프로덕션 테스트를 실행한다. [12 Factor Agents의 배포 사례](https://www.humanlayer.dev/blog/12-factor-agents)

이 사례에서 모델의 역할은 전체 배포 시스템을 즉흥적으로 재발명하는 것이 아니다. 좁은 작업 범위 안에서 사람의 자연어 피드백을 이해하고 다음 행동을 조정한다. 시작과 종료, 테스트, 승인처럼 고정할 수 있는 부분은 일반 프로그램이 담당한다. 저자는 이런 제한된 에이전트 작업을 더 큰 결정적 흐름 안에 배치하는 접근을 설명한다. [같은 글](https://www.humanlayer.dev/blog/12-factor-agents)

이는 2026년 발표의 ‘12 Factor Factories’ 목록을 옮긴 것이 아니다. 이름이 비슷한 이전 글의 별도 사례다. **이 글의 해석:** 자동화 수준을 판단할 때 사람의 개입 횟수만 세면 중요한 차이를 놓친다. 사람이 반복적인 문법 오류를 지적하는 것과 배포 순서를 결정하는 것은 다른 개입이다. 줄여야 할 것은 사람의 모든 참여가 아니라, 도구가 먼저 잡아 줄 수 있는 문제를 사람이 반복해서 처리하는 비용이다.

## 4. 계획도 검토도 위험에 맞게 배분한다

CODE 발표는 다시 바꿀 가능성과 수정 비용을 곱한 관점으로 계획의 양을 정하자고 제안한다. 버튼 색보다 나중에 바꾸기 어려운 데이터베이스 스키마를 먼저 논의한다는 예가 나온다. 시각적 예시로 합의하고 결정의 이유를 다음 작업자가 되찾게 하자는 설명도 이어진다. [공식 발표 전사](https://ai.engineer/code/2026/talks/dexter-horthy)

**이 글의 해석:** 여기에는 두 종류의 낭비를 함께 줄이려는 관점이 있다. 방향이 틀린 채 구현한 뒤 모두 버리는 낭비와, 작은 변경을 시작하기 전에 지나치게 많은 문서를 만드는 낭비다. 필요한 계획의 양은 산출물의 길이가 아니라, 지금 해결하지 않으면 나중에 비싸지는 불확실성이 얼마나 줄었는지로 판단하는 편이 낫다.

검토도 같은 이유로 한 지점에 몰아넣을 필요가 없다. 문제 정의를 잘못 잡았다면 코드 리뷰보다 앞에서 발견해야 한다. 반대로 구체적인 화면 동작은 실제 결과물을 보아야 판단할 수 있다. 이 문단은 발표에서 착안한 해설이며, 발표자가 제시한 단계별 필수 체크리스트는 아니다.

## 5. 마지막 병목은 읽는 사람에게 넘어갈 수 있다

발표 말미에는 검토하지 않은 긴 출력이 읽는 사람에게 비용을 넘긴다고 지적한다. 보내기 전에 확인하고 상대가 이해할 수 있게 정리하는 책임도 자동화 뒤에 남는다. [공식 발표의 마지막 논점](https://ai.engineer/code/2026/talks/dexter-horthy)

**이 글의 결론:** 소프트웨어 공장을 평가할 때 생성량은 중간 지표다. 요청이 실제로 해결됐는지, 검증되지 않은 출력이 누구의 대기열에 쌓였는지, 다음 변경을 더 어렵게 만들지는 않았는지를 함께 봐야 한다. 에이전트에게 맡길 수 있는 일을 늘리는 것과 결과의 책임을 비우는 것은 같은 일이 아니다.

### 확인 범위

공식 기계 생성 전사, 논문 v2, HumanLayer의 공개 기술 글을 확인했다. 전사 인식 오류 가능성이 있으며 직접 인용은 하지 않았다. SlopCodeBench는 코드 진화를 이해하기 위한 보충 근거이며, 발표 당일의 모든 모델 점수를 검증한 자료로 사용하지 않았다. 배포 봇과 검사 훅은 별도 글의 실제 사례이고, CODE 현장 시연으로 서술하지 않았다. 출처별 요약과 필자의 해석을 분리했다.
