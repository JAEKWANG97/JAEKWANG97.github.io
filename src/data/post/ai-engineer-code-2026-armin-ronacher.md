AI Engineer CODE 2026의 「The Software Atelier」는 자동화를 거부하는 발표가 아니다. 더 강한 도구를 얻었을 때 무엇에 그 힘을 쓸지 묻는다. 아래에서는 발표의 핵심을 먼저 정리하고, 발표자가 별도로 공개한 개발 경험을 연결한다. 뒤의 사례를 모두 무대에서 소개한 것으로 읽어서는 안 된다.

## 1. 발표의 질문: 공장보다 작업실이 먼저일 수 있다

Ronacher는 모델이 개선돼 교정 횟수가 줄어도, 사람이 계속 돌볼 수 있는 프로젝트는 같은 비율로 늘지 않는다고 말한다. 자동화된 오픈소스도 담당자의 관심이 사라지자 중단됐다. 그가 말하는 작업실은 수작업 회귀가 아니다. 에이전트 조작 능력과 소프트웨어 판단력을 함께 써서, 복잡성이 굳기 전에 방향을 고치고 제품의 질을 높이자는 관점이다.

### 오래 실행할수록 중단과 재개를 설계해야 한다

발표 후반은 실행 기반으로 이동한다. 짧은 작업은 사람이 다시 시작할 수 있지만, 밤새 수천 건을 처리할 때는 상태를 보존하며 중단·재개하는 에이전트가 필요하다. 추론을 기다리는 동안 실행 환경도 멈출 수 있어야 자원을 낭비하지 않는다. 이는 완성된 제품의 성능 보고가 아니라 앞으로 해결할 과제다.

### 모든 판단을 큰 언어 모델에 맡길 필요는 없다

코드 모드는 도구들을 JavaScript로 조합하는 방식이다. 그는 고객 지원 요청 3,000건을 예로 든다. 에이전트가 작업 흐름을 만들고, 분류 모델은 각 요청을 처리하거나 고객에게 추가 정보를 요청할지 나눈다. 작업 흐름의 구성과 반복 판단을 분리하는 것이다. 제시한 속도·비용 이점은 발표자의 설명이며 독립적으로 재현한 결과는 아니다. [공식 발표와 전사](https://ai.engineer/code/2026/talks/armin-ronacher)

## 2. 별도 실험: 오래 실행됐다는 사실은 좋은 결과의 증거가 아니다

이 문제의식은 9월의 장시간 코딩 실험 기록에서 더 구체적으로 드러난다. Ronacher는 Python에 새로운 실행·스코프 기능을 넣는 작업을 에이전트가 스스로 조직하도록 두었다. 약 35시간 뒤 그가 내린 평가는, 많은 코드가 생겼지만 쓸 만한 결과도 운영법에 대한 유용한 학습도 얻지 못했다는 것이었다.

그가 공개한 문제는 단순한 문법 오류가 아니었다. 파일을 수정하는 도구 호출이 지나치게 압축돼 사람이 진행 과정을 이해하기 어려웠고, 이러한 스타일이 저장할 테스트 코드에까지 나타났다. 임시 검사용 함수가 실제 구현의 의존성으로 바뀌고, 이름 대신 숫자 위치로 상태를 참조하는 코드도 나왔다. 그의 학습·보상 원인 설명은 추측이므로 모델 내부의 확인된 사실로 받아들일 수 없다. 하지만 읽을 수 있는 실행 기록과 유지할 수 있는 코드가 별개의 평가 대상이라는 관찰은 구체적인 산출물을 근거로 한다. [발표 외 자료: 장시간 코딩 실험](https://lucumr.pocoo.org/2026/9/7/astra-why/)

> **이 글의 해석:** 실패를 “더 오래 돌리면 된다”로 처리하면 원인을 놓친다. 실행 시간은 투입이고, 사람이 이해하며 수정할 수 있는 결과는 산출이다. 둘을 같은 지표로 볼 수 없다.

## 3. 별도 설계 사례: Deser는 더 많은 기능보다 어떤 절충을 택할지 보여 준다

9월에 공개한 Rust 직렬화 라이브러리 Deser 설명은 작업실이라는 비유를 기술적인 선택으로 읽게 한다. 출발점은 기존 Serde가 나쁘다는 판단이 아니라, 안정성을 지키는 기존 설계 안에서 해결하기 어려운 문제였다. 예컨대 중간 버퍼를 거치며 원래 형식의 정보나 오류 위치가 사라지거나, 깊게 중첩된 값이 호출 스택에 부담을 주는 경우다.

Deser는 중첩 처리를 호출 스택에 계속 쌓는 대신, 이벤트와 별도 드라이버를 통해 상태를 관리한다. 그 덕분에 입력을 기다리는 동안 처리를 멈추거나 위치 정보를 유지하는 방향을 택할 수 있다. 대신 자기 기술적이지 않은 형식을 지원하지 않는 선택을 했고, 동적 호출과 힙 관리의 비용도 감수한다. 작성자는 실행 성능이 입력과 형식에 따라 달라진다는 점, 그리고 생태계의 중심인 Serde가 아니라는 사실 자체가 큰 비용임을 인정한다. 만능 대체재를 선언하기보다 개선하려는 문제와 포기하는 범위를 함께 밝히는 사례다. [발표 외 자료: Deser 설계 설명](https://lucumr.pocoo.org/2026/9/29/deser/)

## 4. 더 어려운 일을 시도할 기회와 책임은 함께 커진다

8월의 글에서는 에이전트가 언어 학습과 구현의 마찰을 낮추면서 개발자들이 Rust나 Zig, 디버깅 정보와 저수준 기술처럼 이전보다 어려운 영역을 시도한다고 관찰한다. 그는 이 변화가 조잡한 결과를 늘릴 가능성만 있는 것이 아니라, 작고 빠른 소프트웨어를 원하는 사람을 늘릴 가능성도 있다고 본다. 다만 이것은 현장의 경향에 대한 개인적인 관찰이지 언어별 성능을 비교한 연구는 아니다. [발표 외 자료: Fast and Hard Code](https://lucumr.pocoo.org/2026/8/22/fast-hard-code/)

> **이 글의 해석:** 작업실의 기준은 에이전트 수가 아니다. 해결하려는 불편을 정확히 알고, 구현 과정의 선택을 설명할 수 있고, 결과를 계속 돌볼 사람이 있는가다. Deser의 절충과 장시간 실험의 실패는 그 질문을 서로 다른 방향에서 드러낸다.

## 읽는 범위와 한계

공식 기계 전사와 발표자의 세 글을 확인했다. 전사의 고유명사에는 오인식이 남아 있고 전체 영상과의 대조는 하지 않았다. 추가 사례들은 같은 작성자의 1차 기록으로, 독립적인 제삼자 검증이 아니다. 이 글은 전체 발표를 대체하는 번역이 아니라 핵심 주장과 관련 개발 경험을 연결한 해설이다.
