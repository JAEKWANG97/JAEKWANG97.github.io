## 코드 생산 다음에 오는 문제

**발표 요약:** Sonar의 Andrew Finch는 *Building a Safe Software Factory*에서 구현 자동화 뒤 검토와 운영으로 이동하는 병목을 짚는다. 답으로 제시하는 것은 네 가지 검증 순환이다.

첫째는 PR 검사다. 요구사항 충족, 다른 저장소와 열린 PR의 충돌, 보안과 위험도를 함께 살피고 병합 근거를 남긴다. 둘째는 배포 후 검증이다. 운영 로그·트레이스·지표로 예상한 동작인지 확인한다. 발표자는 이 영역의 자동화를 아직 실험 단계로 설명한다.

셋째는 유지보수다. 병합 뒤 공개된 취약점이나 새 규칙, 서서히 누적된 복잡성은 당시 PR 검사만으로 잡을 수 없다. 코드 전체를 재검사하고 수정 PR을 만든다. 넷째는 지식 갱신이다. 문서와 사업적 결정, 이전 리뷰와 장애에서 배운 내용을 정리해 다른 과정에 공급한다. 사람은 위험한 변경, 증거, 예외 상황, 설계와 제품 의도를 계속 책임진다. [공식 발표·전사](https://ai.engineer/code/2026/talks/andrew-finch)

## 네 번 검사하는 것과 네 종류의 실패를 보는 것은 다르다

**해설:** 이 구조를 “리뷰 에이전트를 네 개 붙인다”로 읽으면 핵심이 사라진다. 같은 코드와 같은 전제를 네 번 검사해도 처음에 없던 정보는 얻을 수 없다. 중요한 차이는 검사 횟수가 아니라 **어느 시점의 어떤 증거를 보는가**다.

예를 들어 PR에서 사용한 테스트 데이터와 운영 환경의 데이터 분포가 다를 수 있다. 이 경우 테스트를 한 번 더 실행하는 일과 실제 서비스 동작을 관찰하는 일은 서로 다른 정보를 준다. 반대로 장애가 없다는 사실만으로 코드에 보안 문제가 없다고 단정할 수도 없다. 아직 악용되지 않은 결함은 정상 운영 지표에 드러나지 않을 수 있기 때문이다.

![변경 시점과 배포 후, 시간 경과, 학습을 구분한 네 검증 순환](/images/ai-engineer-code-2026/andrew-finch-loops.svg)

*발표의 네 순환을 이해하기 위해 재구성한 도식이다. 특정 제품의 구현도나 자동화 수준을 나타내지 않는다.*

## 배포 후 검증에 필요한 독립적인 관찰

**보충 자료:** Google SRE의 모니터링 장은 내부 로그와 지표를 보는 관찰을 white-box, 사용자가 보는 외부 동작을 검사하는 관찰을 black-box로 구분한다. 또한 경보는 단순히 이상해 보이는 현상보다 사람이 실제로 조치해야 할 문제와 연결해야 한다고 설명한다. 이는 Finch가 인용한 자료라는 뜻이 아니라 운영 검증을 이해하기 위한 별도 근거다. [Google SRE: Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/)

**해설:** 이 구분을 적용하면 “배포 성공”의 의미도 명확해진다. 배포 시스템이 새 버전을 실행했다는 신호와 사용자가 원하는 일을 끝낼 수 있다는 신호를 구별해야 한다. 둘을 섞으면 배포 절차의 성공을 제품 동작의 성공으로 착각하기 쉽다.

예를 들어 주문 서비스가 요청에 응답하지만 사용자가 결제를 끝내지 못하는 상황을 가정해 보자. 이때 프로세스가 살아 있다는 신호만으로는 부족하다. 반대로 결제 실패 하나만 보고 즉시 이전 버전으로 되돌리면 외부 결제사의 일시적 장애를 잘못 처리할 수도 있다. 관찰, 원인 판단, 변경 권한은 따로 설계해야 한다. 이 예시는 발표에 나온 사건이 아니라 검증 경계를 설명하기 위한 가정이다.

## 공장은 도구가 아니라 책임을 배치하는 운영 방식

**보충 자료:** Sonar의 별도 설명은 에이전트 소프트웨어 공장을 하나의 제품이 아니라 반복 가능한 전달 체계로 정의한다. 요청이나 사건이 들어오면 검증하고 배포할 수 있는 변경이 나오며, 사람은 의도·제약·수용 기준·승인 정책을 정한다. 팀마다 내부 구조가 같을 필요는 없다. [Sonar: What Is an Agentic Software Factory?](https://www.sonarsource.com/resources/library/what-is-an-agentic-software-factory/)

**해설:** 운영 방식으로 이해하면 처음부터 모든 단계를 자동화해야 할 이유는 없다. 먼저 어떤 변경을 자동으로 처리해도 되는지, 무엇이 근거로 남아야 하는지, 어떤 경우 사람이 개입하는지를 정할 수 있다. 이 결정 없이 에이전트만 추가하면 실패의 소유자가 모호해진다.

또한 기록을 남기는 것과 사용할 수 있는 지식을 만드는 것은 다르다. 오래된 장애 문서가 지금도 유효한지, 예외적인 처방이 일반 규칙으로 오해되지 않는지 확인해야 한다. 자체 적용 제안으로는 각 규칙에 근거, 적용 범위, 마지막 확인 시점을 붙이는 방법이 있다. 이는 발표에서 제시한 문서 양식을 재현한 것이 아니다.

## 이 발표를 과장하지 않고 읽는 법

발표는 완성된 무인 공장의 성능 보고가 아니라 검증 체계에 대한 제안이다. 에이전트가 여러 번 동의하면 안전해진다거나, AI가 운영 변경을 언제나 알아서 결정해도 된다는 결론은 아니다. 기술적으로 자동 실행할 수 있는 일과 조직이 허용한 일도 다르다.

공식 기계 전사에서 네 순환 소개는 03:14:17, 병합 근거는 03:18:04, 배포 후 검증은 03:19:22, 유지보수는 03:20:24, 지식 갱신은 03:21:33에 있다. 시간은 전체 중계 기준이다. 전체 번역이 아니라 제한적인 발표 요약에 독립 자료와 해설을 덧붙였다. 기계 전사의 인식 오류 가능성이 있으며 제품 성능을 재현하지 않았다.
