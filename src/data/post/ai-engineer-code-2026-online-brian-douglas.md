## 에이전트의 자신감으로는 채워지지 않는 경험

코드를 만드는 능력과 그 코드가 팀에 맞는지 판단하는 능력은 같지 않다. 특히 익숙하지 않은 언어에서는 실행되는 결과만으로 안심하기 쉽다. 문법 오류가 없고 자동 리뷰까지 긍정적이라면, 다음 검토자가 발견할 문제를 미리 상상하기가 더 어렵다.

Brian Douglas는 이 간극을 자신의 Rust 작업 경험에서 출발해 설명한다. 발표 제목은 자극적이지만, 여기서 가져갈 주제는 에이전트에게 거친 말을 하자는 것이 아니다. 사람이 결과에 반박한 순간에는 어떤 지식이 드러나는가, 그리고 그 지식을 다음 작업에서 다시 쓸 수 있는가라는 질문이다.

## 실제 사례: Matt는 왜 같은 코드를 받아들이지 않았나

발표자는 에이전트가 만든 Rust 코드에 충분히 반박하지 못해 사람의 PR 리뷰 단계에서 수정 요구를 받는다고 설명한다. 동료 Matt의 지적은 팀의 API 구조, 이미 존재하는 서비스나 라이브러리를 다시 만드는 문제처럼 컴파일만으로 확인하기 어려운 부분에 집중됐다.

그는 에이전트 세션을 수집하고 사람이 반박한 기록에 표식을 붙였다. 팀의 판단이 GitHub 댓글보다 터미널 안에서 오가는 경우도 있었기 때문이다. 이어 그 기록으로 데이터셋을 만들고 후속 학습을 수행한 TwinReview를 시연했다. 목표는 동료의 판단을 참고하는 PR 리뷰였다. 다만 이 데모는 정확도 검증 실험이 아니다. 발표 중 공개 소프트웨어라고 말했다가 민감한 데이터 때문에 TwinReview는 공개하지 않았다고 정정한다. 마지막 권고 역시 바로 학습부터 시작하라는 것이 아니라, 먼저 스킬로 활용해 보라는 쪽이다. [공식 발표와 전사](https://ai.engineer/code/2026/talks/online-brian-douglas)

필자가 읽은 이 사례의 핵심은 정답 코드를 모으는 데 있지 않다. 겉으로는 허용 가능한 코드가 왜 거절됐는지를 모으는 데 있다. 코드 결과물만 저장하면 수정 전후는 비교할 수 있지만, 어느 제약이 그 수정을 요구했는지는 사라질 수 있다.

## 수집 도구와 학습 결과를 구분하기

발표에서 사용하는 Tapes는 TwinReview와 구분해야 한다. Tapes의 공식 홈페이지는 에이전트 세션을 기록해 로컬 Postgres에 보관하는 도구라고 설명하며, 공개 저장소와 Apache-2.0 라이선스를 안내한다. 공개된 수집 도구가 있다는 사실은 발표자의 비공개 데이터나 학습 결과까지 공개됐다는 뜻이 아니다. [Tapes 공식 홈페이지](https://tapes.dev/)

현재 공식 문서에는 세션을 스킬로 바꾸는 더 구체적인 작업 흐름도 있다. 선택한 세션별 후보를 만들고 평가한 다음, 종합한 결과를 새 비공개 리비전으로 남긴다. 생성 완료와 공개는 별도 단계이며, 문서는 한 프로젝트의 가정이 다른 곳으로 따라갈 수 있으니 공개 전에 내용을 검토하라고 안내한다. 이는 현재 제품 문서의 기능 설명이지, 발표 당일 시연 버전과 동일하다는 확인은 아니다. [Tapes 세션 기반 스킬 생성 안내](https://tapes.dev/docs/guides/skills/)

여기서 필자가 중요하게 보는 구분은 세 가지다. 기록이 있다는 것, 재사용할 지침을 만들었다는 것, 그 지침이 새 과제에서도 도움이 된다는 것은 각각 다른 상태다. 세션을 많이 모았다는 이유로 마지막 단계까지 달성했다고 볼 수는 없다.

## 반박을 표식으로 바꿀 때 잃기 쉬운 것

다음은 발표 사례에 대한 필자의 해석이다. 사람이 “이렇게 하지 말라”고 말했다는 사실만 남기면 학습 자료로는 모호하다. 무엇을 대신 해야 하는지, 그 이유가 해당 저장소에만 적용되는지, 이미 합의된 규칙인지 순간적인 선호인지 알아야 한다.

예를 들어 기존 기능을 다시 구현한 변경이라면, “중복 구현”이라는 표식은 출발점일 뿐이다. 재사용할 기존 경로와 그 경로를 선택해야 하는 이유가 있어야 다음 작업의 판단에 도움이 된다. 반대로 한 변경에서 거절된 접근을 모든 상황의 금지 규칙으로 확대하면, 과거의 맥락이 새로운 오류를 만든다. 이것은 Matt의 실제 댓글을 인용한 예가 아니라, 그 사례를 읽으며 도출한 데이터 정리 원칙이다.

동료의 판단을 흉내 내는 도구의 결과를 표시하는 방법도 중요하다. “Matt가 검토했다”와 “Matt의 과거 수정 사례를 참고한 모델이 검토했다”는 전혀 다른 말이다. 후자는 실제 동료의 승인이나 책임을 대신하지 않는다. 검토자는 어떤 근거에서 나온 제안인지 확인할 수 있어야 한다.

## 먼저 재사용하고, 그다음 효과를 확인한다

이 사례에 작은 규모로 접근한다면 모델 학습보다 먼저 할 일은 명확하다. 유용했던 수정 몇 건을 골라, 이유와 적용 범위를 설명할 수 있는지 확인하는 것이다. 설명이 불가능한 사례를 많이 쌓는 것보다, 범위가 분명한 판단을 소수 보존하는 편이 검토하기 쉽다.

그다음에는 기록을 만들 때 보지 않은 변경에서 같은 오류를 찾아내는지 확인해야 한다. 이미 외운 사례를 되풀이하는 것과 새 코드에서 팀의 제약을 이해하는 것은 다르다. 사람의 지적을 얼마나 닮게 말하는지가 아니라, 불필요한 수정 요구 없이 중요한 문제를 찾는지가 평가 대상이어야 한다. 이 문단은 필자의 적용 제안이며, TwinReview가 이런 평가를 통과했다는 주장은 아니다.

Brian의 사례가 남기는 질문은 “리뷰어를 복제할 수 있는가”보다 현실적이다. 팀이 이미 지불한 설명 비용을 매번 처음부터 다시 지불하고 있지는 않은가? 그 비용을 줄이려면 불만의 강도가 아니라 판단의 이유를 남겨야 한다.

### 자료와 한계

공식 웹·ZIP 기계 생성 전사, Tapes 공식 홈페이지와 현재 사용 안내를 확인했다. 비공개 TwinReview, 학습 데이터, 리뷰 결과의 성능을 독립 재현하지 않았다. 전사의 모델명·학습 기법·하드웨어 관련 불명확한 표현은 기술 요구 조건으로 옮기지 않았다. 발표 중 근거가 불분명하다고 언급한 다른 서비스 관련 소문도 제외했다. 실제 사례 요약과 제품 문서 설명, 필자의 해석을 구분했으며 전체 발표의 번역은 아니다.
