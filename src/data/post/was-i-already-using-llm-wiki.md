## 들어가며

안드레 카파시가 공개한 [LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)를 읽으며 가장 먼저 배운 것은 **AI로 노트를 정리하는 것과 지식이 계속 쌓이는 시스템을 만드는 것은 다르다**는 점이었습니다.

저도 옵시디언 Vault에서 Codex와 Hermes를 실행하며 Markdown 파일을 정리해왔습니다. 에이전트가 새로운 문서를 만들고, 기존 문서를 수정하고, 인덱스와 링크를 연결하게 했습니다. 하지만 대부분 그때 필요한 정리 작업을 맡기는 데 가까웠습니다.

LLM Wiki는 여기서 한 걸음 더 나아갑니다. 새 자료와 질문에서 얻은 결과를 기존 문서에 다시 편입하고, 다음 작업이 더 나은 지식 상태에서 시작되게 합니다. 원본과 해석을 나누고, 출처와 충돌을 추적하며, 위키 전체를 반복해서 점검하는 구조도 제안합니다.

이 글에서는 LLM Wiki가 무엇인지, 일반적인 RAG와 무엇이 다른지, 그리고 여기서 배운 방식을 제 옵시디언에 어떻게 적용할 수 있을지 정리해보려고 합니다.

---

## 1. LLM Wiki는 새로운 앱이 아니라 작업 패턴이다

먼저 LLM Wiki는 카파시가 출시한 완성형 서비스 이름이 아닙니다.

카파시가 2026년 4월 공개한 원문은 아이디어를 설명한 Markdown 문서에 가깝습니다. 이 문서를 Codex나 Claude Code 같은 LLM 에이전트에게 전달한 다음, 자신에게 맞는 구조를 함께 만들라는 제안입니다.

그래서 정답처럼 정해진 폴더 구조나 기술 스택도 없습니다. 꼭 Obsidian을 사용해야 하는 것도 아니고, 벡터 데이터베이스를 설치해야 하는 것도 아닙니다. Markdown 파일을 읽고 수정할 수 있는 에이전트와 지식이 계속 남을 저장소가 있으면 시작할 수 있습니다.

카파시는 자신의 사용 방식을 다음과 같이 비유합니다.

> Obsidian은 IDE이고, LLM은 프로그래머이며, Wiki는 코드베이스다.

이 비유를 통해 지식 저장소도 코드베이스처럼 지속적으로 읽고, 수정하고, 점검할 수 있다는 관점을 배웠습니다. 제가 Vault 안에서 Codex와 Hermes로 문서를 탐색하고 수정해온 경험도 이 관점에서 다시 이해할 수 있었습니다.

개발자가 코드를 한 번 생성하고 버리는 것이 아니라 기존 코드베이스를 읽고, 필요한 부분을 수정하고, 테스트하며 계속 관리하듯이 LLM도 지식 문서를 일회성으로 생성하는 것이 아니라 기존 위키에 통합합니다.

사람은 어떤 자료를 넣을지 선택하고, 무엇을 더 알아볼지 질문하며, 결과가 타당한지 판단합니다. 링크 정리, 요약 갱신, 문서 분류 같은 반복적인 유지보수는 LLM이 맡습니다.

## 2. RAG는 매번 찾고, LLM Wiki는 결과를 남긴다

LLM에게 문서를 읽히는 대표적인 방식은 RAG입니다.

문서를 작은 단위로 나누어 저장해두고, 질문이 들어오면 관련된 조각을 검색해 LLM에게 전달합니다. NotebookLM이나 파일을 업로드해서 질문하는 기능도 사용 경험만 놓고 보면 비슷합니다.

```text
질문
→ 관련 문서 조각 검색
→ 필요한 내용을 다시 조합
→ 답변 생성
```

이 방식은 많은 문서에서 필요한 내용을 빠르게 찾을 때 유용합니다. 다만 질문에 답하기 위해 여러 문서를 비교하고 관계를 찾아냈더라도, 그 결과는 대부분 채팅 안에만 남습니다.

며칠 뒤 비슷한 질문을 하면 LLM은 관련 문서를 다시 찾고 관계를 다시 조합해야 합니다. 지식이 축적되기보다 매번 새로 계산되는 셈입니다.

LLM Wiki는 이 지점에서 방향을 바꿉니다.

```text
새로운 자료
→ 핵심 내용 추출
→ 기존 위키 문서 검색
→ 관련 문서 갱신
→ 링크와 충돌 관계 정리
→ 지속되는 Markdown 문서로 저장
```

새로운 자료가 들어오면 LLM은 그것을 검색용으로만 인덱싱하지 않습니다. 기존 개념 문서를 수정하고, 새로운 관계를 연결하며, 과거 주장과 충돌하면 그 사실도 남깁니다. 다음 질문은 이미 한 번 정리된 위키에서 시작할 수 있습니다.

정리하면 RAG는 **질문 시점에 원본에서 답을 찾는 방식**이고, LLM Wiki는 **자료가 들어오는 시점에 지식을 계속 편집해두는 방식**에 가깝습니다.

그렇다고 둘 중 하나만 선택해야 하는 것은 아닙니다. 위키가 커지면 원하는 문서를 찾기 위해 전문 검색이나 벡터 검색을 붙일 수도 있습니다. 차이는 검색 기술 자체보다, 검색과 종합의 결과를 지속적인 지식으로 남기느냐에 있습니다.

## 3. 원본, 위키, 규칙이라는 세 개의 층

카파시가 설명한 구조는 크게 세 층으로 나뉩니다.

```text
knowledge-base/
├── raw/          # 사람이 수집한 원본 자료
├── wiki/         # LLM이 만들고 관리하는 지식 문서
└── AGENTS.md     # LLM이 따라야 할 관리 규칙
```

### Raw sources: 다시 확인할 수 있는 원본

`raw`에는 기사, 논문, 기존 메모, 이미지, 데이터 파일 같은 원본을 보관합니다. 이 자료는 LLM이 읽을 수 있지만 임의로 수정하지 않습니다.

이 구분이 필요한 이유는 단순합니다. AI가 만든 매끄러운 설명과 실제 출처를 분리해야 나중에 주장이 맞는지 다시 확인할 수 있기 때문입니다.

제가 예전에 Vault 전체를 AI에게 정리시킬 때는 원본 메모와 AI가 다듬은 문서의 경계가 선명하지 않을 때도 있었습니다. 정리는 됐지만, 어느 문장이 원래 기록이고 어느 부분이 AI의 해석인지 나중에는 구분하기 어려워질 수 있었습니다.

### Wiki: LLM이 유지보수하는 지식

`wiki`에는 개념 설명, 인물이나 기술에 대한 문서, 비교, 요약, 현재까지의 종합적인 해석이 들어갑니다.

새로운 자료가 들어오면 LLM은 무조건 새 파일부터 만들지 않습니다. 같은 개념을 다루는 기존 문서가 있는지 찾고, 있다면 그 문서를 갱신합니다. 필요하면 여러 문서에 링크를 추가하고 새로운 자료가 기존 주장과 다르면 모순도 표시합니다.

이렇게 하면 위키는 자료별 요약 모음이 아니라, 시간이 지날수록 조금씩 수정되는 현재의 지식 상태가 됩니다.

### Schema: AI를 관리자로 만드는 규칙

마지막은 `AGENTS.md`나 `CLAUDE.md` 같은 규칙 문서입니다.

여기에는 다음과 같은 내용을 적을 수 있습니다.

- 원본 자료는 수정하지 않는다.
- 새 문서를 만들기 전에 기존 문서를 검색한다.
- 중요한 주장에는 출처를 연결한다.
- 충돌하는 주장을 조용히 덮어쓰지 않는다.
- 문서를 수정하면 인덱스와 작업 로그도 갱신한다.
- 대규모 수정 후에는 링크와 출처를 검사한다.

이 규칙이 있어야 LLM이 매번 다른 방식으로 파일을 정리하는 범용 챗봇이 아니라, 같은 기준을 따르는 위키 관리자로 동작할 수 있습니다.

## 4. 자료를 넣고, 질문하고, 다시 점검한다

LLM Wiki의 동작은 `Ingest`, `Query`, `Lint` 세 가지로 정리할 수 있습니다.

### Ingest: 자료를 기존 지식에 편입한다

새로운 글 하나를 저장했다고 가정해보겠습니다.

LLM은 글을 요약한 파일 하나만 만드는 것이 아니라 다음 작업을 함께 수행합니다.

1. 원본을 보존합니다.
2. 기존 위키에서 관련 개념을 찾습니다.
3. 새로 알게 된 내용을 기존 문서에 추가합니다.
4. 필요한 경우 새로운 개념 문서를 만듭니다.
5. 관련 문서 사이의 링크를 갱신합니다.
6. 어떤 문서를 수정했는지 로그로 남깁니다.

자료 하나가 여러 문서를 바꿀 수 있다는 점이 일반적인 요약 작업과 다릅니다.

### Query: 좋은 질문의 결과도 지식으로 남긴다

질문할 때는 먼저 위키의 인덱스를 보고 관련 문서를 찾습니다. 이미 종합된 문서를 바탕으로 답하되, 필요한 경우 원본 출처까지 따라갑니다.

여기서 특히 흥미로웠던 점은 좋은 답변을 다시 위키에 저장할 수 있다는 것입니다.

여러 자료를 비교해서 얻은 결론이나, 질문하면서 새롭게 발견한 연결 관계는 채팅 기록에만 남기기 아깝습니다. 비교표나 분석 문서로 저장하면 다음 탐색의 출발점이 됩니다. 질문하는 행위 자체가 지식 저장소를 성장시키는 셈입니다.

### Lint: 지식도 코드처럼 점검한다

문서가 늘어나면 정리보다 유지보수가 더 어려워집니다.

- 서로 모순되는 문서가 있는가?
- 새 자료가 들어왔는데 과거 주장이 그대로 남아 있는가?
- 아무 문서와도 연결되지 않은 파일이 있는가?
- 여러 곳에서 반복해서 등장하지만 독립 문서가 없는 개념이 있는가?
- 깨진 링크나 출처 없는 주장이 있는가?

LLM Wiki에서는 이런 문제를 주기적으로 검사하는 작업을 `Lint`라고 부릅니다.

AI가 노트를 예쁘게 정리하는 것에서 그치지 않고, 위키 전체의 일관성을 계속 검사한다는 점이 중요합니다.

## 5. LLM Wiki에서 무엇을 배웠나?

LLM Wiki를 통해 제가 가장 분명하게 배운 것은 **개별 정리 작업과 지속적인 지식 관리 시스템의 차이**였습니다.

제가 옵시디언 Vault에서 해오던 작업에는 LLM Wiki와 겹치는 부분이 있었습니다.

- Vault를 Codex와 Hermes의 작업 디렉터리로 사용했습니다.
- Markdown 파일을 AI가 직접 읽고 수정했습니다.
- 대화에서 끝내지 않고 새로운 문서를 Vault 안에 생성했습니다.
- 비슷한 내용을 모아 문서 구조를 정리했습니다.
- 인덱스를 만들고 관련 노트를 연결했습니다.
- 저는 Obsidian에서 변경된 결과를 확인했습니다.

하지만 LLM Wiki를 읽기 전에는 이 작업을 `Raw`, `Wiki`, `Schema`로 나누거나 `Ingest`, `Query`, `Lint`라는 반복 가능한 운영으로 생각하지 못했습니다. 필요할 때 AI에게 정리를 맡기는 것과, 다음 작업을 위해 지식 상태를 꾸준히 개선하는 것은 분명히 달랐습니다.

| 기존에 하던 작업                            | LLM Wiki에서 배운 운영 원칙                        |
| ------------------------------------------- | -------------------------------------------------- |
| Vault 안에서 Codex와 Hermes를 실행한다      | Wiki를 에이전트가 관리하는 코드베이스로 본다       |
| 문서를 직접 생성하고 수정한다               | 자료의 내용을 지속적인 지식 문서로 편입한다        |
| 검색하기 쉽게 인덱싱하고 링크를 연결한다    | 새 자료가 들어올 때 관련 문서 전체를 함께 갱신한다 |
| 원본과 정리된 문서가 섞일 수 있다           | 원본과 LLM이 작성한 위키를 분리한다                |
| 필요할 때 AI에게 질문하고 결과를 문서화한다 | 좋은 질문의 결과도 다시 위키에 편입한다            |
| 요청한 정리 작업이 끝나면 멈춘다            | Ingest, Query, Lint를 반복 가능한 운영으로 만든다  |

그래서 LLM Wiki를 통해 얻은 배움을 이렇게 정리할 수 있습니다.

> LLM Wiki를 통해 옵시디언과 AI를 단순한 기록·정리 도구가 아니라, 지식을 계속 축적하고 발전시키는 시스템으로 활용하는 방법을 배웠습니다.

## 6. 지금 다시 만든다면 무엇을 바꿀까

기존 Vault를 전부 버리고 새로운 도구로 옮길 필요는 없어 보입니다. 오히려 지금 사용하는 옵시디언 구조에 몇 가지 경계를 추가하는 것부터 시작할 수 있습니다.

```text
SecondBrain/
├── Sources/       # 기사, 논문, 원본 메모
├── Resources/     # 종합된 개념과 지식 문서
├── index.md       # 현재 지식의 지도
├── log.md         # Ingest, Query, Lint 기록
└── AGENTS.md      # AI가 따라야 할 관리 규칙
```

제가 다시 적용한다면 다음 규칙부터 추가할 것 같습니다.

1. 원본과 AI가 종합한 문서를 구분합니다.
2. AI가 새 문서를 만들기 전에 기존 문서를 먼저 찾게 합니다.
3. 중요한 사실은 원본 링크를 따라가며 확인할 수 있게 합니다.
4. 질문에서 나온 답은 전부 저장하지 않고, 다시 사용할 가치가 있는 것만 골라 저장합니다.
5. 여러 파일을 바꾼 뒤에는 Git diff로 변경 범위를 확인합니다.
6. 정기적으로 고립된 문서, 깨진 링크, 중복된 개념을 검사합니다.

특히 모든 작업을 완전 자동화하는 것보다 처음에는 자료를 하나씩 넣고 변경된 문서를 확인하는 방식이 안전해 보입니다. 카파시 역시 자료를 하나씩 처리하면서 요약과 변경 내용을 직접 살펴보고, 무엇을 강조할지 안내하는 방식을 선호한다고 설명합니다.

사람이 해야 할 일이 사라지는 것이 아니라 역할이 달라집니다. 직접 폴더를 정리하는 사람에서, 어떤 자료를 믿고 어떤 해석을 남길지 결정하는 편집자에 가까워집니다.

## 7. 유지보수 비용이 정말 사라질까?

LLM은 반복적인 문서 작업에 지치지 않습니다. 여러 문서의 링크를 한꺼번에 갱신하고, 인덱스에 새 항목을 추가하며, 비슷한 개념을 찾는 일도 빠르게 처리합니다.

그렇다고 유지보수 비용이 완전히 0이 되는 것은 아닙니다.

AI가 원본을 잘못 요약하면 그 오류가 여러 문서로 퍼질 수 있습니다. 서로 약하게 관련된 개념을 억지로 연결할 수도 있고, 사람이 쓴 솔직한 메모를 지나치게 매끈한 문장으로 바꿀 수도 있습니다. 개인적인 기록을 외부 모델에 전달할 때는 개인정보 문제도 확인해야 합니다.

그래서 다음 장치가 필요합니다.

- 원본을 수정하지 않는 구조
- 주장에서 출처로 돌아갈 수 있는 링크
- 대규모 수정 전후의 diff 확인
- 변경 이력을 남기는 Git과 작업 로그
- 중요한 문서에 대한 사람의 검토
- AI가 수정해도 되는 영역과 안 되는 영역의 구분

LLM Wiki의 핵심은 사람을 지식 관리에서 완전히 제외하는 것이 아닙니다. 사람이 잘해야 하는 판단과 LLM이 잘하는 반복 작업을 나누는 데 있습니다.

## 마무리

LLM Wiki를 통해 새롭게 배운 것은 AI가 문서를 수정할 수 있다는 사실이 아니었습니다. **AI가 정리한 결과를 다음 작업의 기반으로 남기려면 어떤 구조와 운영 규칙이 필요한가**였습니다.

그동안 저는 옵시디언 Vault 안에서 Codex와 Hermes로 문서를 만들고 수정해왔지만, 이를 지속적인 지식 관리 모델로 설계하지는 못했습니다. LLM Wiki를 보고 나니 다음 질문이 생겼습니다.

> 새로운 자료와 질문이 들어올 때마다, 이전보다 더 나은 지식 구조가 남게 하려면 어떻게 해야 할까?

단순한 인덱싱은 필요한 자료를 다시 찾기 쉽게 해줍니다. LLM Wiki는 여기에서 한 걸음 더 나아가, 찾고 비교하고 연결한 결과까지 지속적인 문서로 남기려고 합니다.

결국 중요한 것은 AI가 노트를 대신 써주는 것만은 아닙니다. 원본은 보존하고, 해석은 갱신하며, 모순과 변경 이력을 추적할 수 있는 구조를 만드는 것입니다.

LLM Wiki는 제가 하던 작업을 확인해준 개념이라기보다, 그 작업을 어떻게 체계화하고 계속 발전시킬 수 있는지 가르쳐준 방법에 가까웠습니다.

앞으로는 제 Vault도 단순한 노트 저장소에 머물지 않도록, 원본과 해석을 구분하고 질문의 결과가 다시 지식으로 쌓이는 구조를 만들어보고 싶습니다.
