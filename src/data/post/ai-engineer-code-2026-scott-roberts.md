검색창에 문장을 끝까지 입력하고, 답변을 읽고, 다시 업무 화면을 찾는다. AI가 있어도 사용자가 여러 번 이동해야 한다면 어디를 바꿔야 할까. Workday의 Scott Roberts는 「Autocomplete for Actions」에서 대화창을 더 잘 만드는 것과 다른 방향을 보여 준다. 다만 먼저 선을 그어야 한다. **발표 속 시연은 합성 데이터를 쓴 실험이며 당시 운영 중인 제품이 아니었다. 출시 여부도 확정하지 않았다.**

## 1. 발표의 두 장면: 입력창에서 업무 카드로, SQL에서 의미 판단으로

첫 시연에서는 휴가를 요청하는 문장을 입력하는 동안 관련 카드가 나타난다. 모델은 먼저 의도를 골라 적절한 카드를 띄우고, 해당 업무를 담당하는 팀이 정한 질문으로 카드 내용을 채운다. 급여 조회, 회의 예약, 사람 찾기도 보여 준다. 카드를 추가할 때는 다른 카드의 선택을 방해하지 않는지 평가하며, 맞는 카드가 없으면 채팅으로 돌아간다.

뒤에서는 DuckDB 함수 안에서 Jev를 호출해 합성 이력서 데이터를 의미에 따라 거르는 실험을 보여 준다. 예를 들어 ML 이력서의 pipeline이라는 단어가 배관 업무 적합성을 뜻하지 않는지 묻는다. 이 시연에서 배관 업무의 점수는 낮았고, 발표자는 117개 레코드를 약 2.3초에 처리했다고 말한다. 작은 시연의 실행 시간이지 대규모 운영 성능이나 실제 채용 판단의 정확도를 입증하는 수치는 아니다. 두 장면을 연결하는 것은 긴 답변 생성이 아니라 짧은 판단을 기존 소프트웨어 안에 넣는 방식이다. [공식 발표와 전사](https://ai.engineer/code/2026/talks/scott-roberts), [합성 데이터·비운영 고지 06:29:06](https://www.youtube.com/watch?v=ZZ19zhYnDKY&t=23346s), [배관 질문 06:35:06](https://www.youtube.com/watch?v=ZZ19zhYnDKY&t=23706s)

## 2. 두 시연을 연결하는 것은 ‘짧은 판단을 어디에 둘 것인가’다

**이 글의 해석:** 업무 카드에서는 판단 결과가 사용자가 보게 될 다음 화면을 정한다. 데이터베이스에서는 행의 비교와 정렬에 영향을 준다. 둘 다 긴 답변을 사용자에게 읽히기보다 기존 소프트웨어의 작은 분기 안에 모델을 넣는다. 하지만 잘못된 판단이 미치는 범위는 같지 않다.

카드 선택이 틀리면 사용자는 다른 화면을 찾거나 질문을 고칠 수 있다. 반면 데이터 필터에서 행이 빠지면 사용자가 그 누락 자체를 모를 수 있다. 따라서 두 시연의 속도가 비슷하게 매력적이더라도 평가 방식까지 같아서는 안 된다. 앞에서는 선택 수정과 입력 보존을, 뒤에서는 누락·미판정·근거를 확인해야 한다.

pipeline과 배관을 구분하는 예시도 범위를 좁혀 읽어야 한다. 단어가 같다는 이유만으로 선택하지 않는다는 것을 보여 주는 작은 점검이지, 사람의 직무 능력이나 채용 적합성을 신뢰할 수 있게 평가했다는 증거가 아니다. 합성 데이터의 한 쿼리와 실제 인사 의사결정 사이에는 검증해야 할 간격이 크다.

## 3. 해석: 업무를 준비하는 것과 실행을 승인하는 것은 다르다

> **이 글의 해석:** 입력 중인 문장에서 유용한 화면을 예측하면 사용자가 메뉴 구조를 알아야 할 부담이 줄어든다. 그러나 사용자가 문장을 고치는 동안 화면도 계속 바뀔 수 있다. 따라서 빠른 예측만으로 좋은 인터페이스가 완성되지는 않는다. 이미 입력한 값을 보존할지, 다른 카드로 바뀔 때 무엇을 설명할지, 예측이 틀렸을 때 어디로 돌아갈지도 설계해야 한다.

특히 날짜와 대상을 미리 채워 놓는 것과 그 상태로 업무를 제출하는 것은 별개다. 이 구분은 발표자의 보안 설계를 확인했다는 뜻이 아니라, 시연을 실제 제품으로 옮길 때 이 글이 제안하는 경계다. 추천 카드에 대한 확률은 사용자의 실행 허락이 아니다.

## 4. 별도 문서: 질문을 순서대로 하지 않아도 되는 경우

TypeSafe의 speculative fan-out 문서는 필요한 질문을 한 요청에 묶고 나중에 코드로 관련성을 결정하는 방식을 설명한다. 고객 문의라면 먼저 종류를 물은 뒤 버그일 때 심각도를 다시 묻는 대신, 종류·심각도·재현 단계 유무를 함께 묻는다. 결제 문의로 분류되면 버그 관련 답은 버린다.

이 방식은 관련 있는 질문에 대한 추가 왕복을 줄인다. 문서는 여러 질문이 병렬로 평가되어 질문 추가가 보통 응답 시간에 미치는 영향이 작다고 설명하지만, 모든 비용이 사라진다는 뜻은 아니다. 또한 각 질문의 답이 반환됐다고 전부 행동에 사용해서는 안 된다. 어떤 결과가 현재 분기에 유효한지는 코드가 결정한다. 이는 Workday의 내부 구현 설명이 아니라, 빠른 판단을 화면 반응에 연결하는 별도의 공개 패턴이다. [발표 외 자료: Speculative fan-out](https://docs.typesafe.ai/patterns/fan-out)

## 5. 별도 문서: 첫 분류가 틀리면 뒤의 정교함도 소용없다

계층 분류 cookbook은 상품 분류처럼 큰 범주에서 작은 범주로 내려가는 문제를 다룬다. 매 단계에서 가장 가능성이 높은 자식 하나만 고르면 초반의 실수를 되돌리기 어렵다. 대안인 빔 탐색은 여러 후보 경로를 유지하며 같은 깊이의 질문들을 병렬로 처리한다.

문서는 경로 점수에 선택 확률의 기하평균을 써서 단순한 곱이 깊은 경로에 불리해지는 문제를 피한다. 노드별 질문은 어디에서 오분류가 발생하는지도 살펴볼 수 있게 한다. 이 자료가 Workday의 카드 선택에 빔 탐색이 사용됐다는 증거는 아니다. 이 글에서는 화면을 먼저 고르고 세부 정보를 채우는 시스템에서, 첫 선택의 오류를 어떻게 관찰할 것인지 생각하기 위한 비교 자료로 읽는다. [발표 외 자료: Hierarchical classification](https://docs.typesafe.ai/cookbooks/hierarchical_classification)

## 6. SQL 안에 넣어도 실패와 불확실성이 없어지지는 않는다

DuckDB의 현재 Python 함수 문서는 `create_function`으로 입력과 반환 타입을 가진 함수를 SQL에서 호출할 수 있다고 설명한다. 행마다 처리하는 방식 외에 Arrow 배열을 묶어서 처리하는 방식도 제공한다. 기본적으로 NULL 입력은 NULL 결과가 되고, 함수 예외는 쿼리를 실패시킨다. 예외를 NULL로 바꾸는 설정도 가능하다. 같은 입력에 같은 결과를 낸다는 가정이 맞지 않으면 그 특성 역시 표시해야 한다.

이 설명은 SQL과 외부 판단 함수를 연결할 때 살펴볼 계약이다. 발표의 함수가 Python이나 Arrow로 구현됐다는 주장은 아니다. 현재 문서는 발표 당시 사용 버전의 동작을 그대로 보장하지도 않는다. [발표 외 자료: DuckDB Python Function API](https://duckdb.org/docs/2.0/clients/python/function)

> **이 글의 해석:** 모델 호출 실패를 조용히 NULL로 바꾼 뒤 결과에서 빠진 행을 “조건에 맞지 않음”으로 읽으면 시스템 장애가 판단 결과로 둔갑한다. 전송할 데이터의 범위, 재시도 비용, 미판정 행의 수를 함께 관찰해야 한다. SQL로 표현이 간단해지는 것과 개인정보 처리나 오류 책임이 간단해지는 것은 다르다.

## 범위와 한계

공식 기계 전사와 TypeSafe·DuckDB의 별도 공식 문서를 확인했다. 실제 고객 이력서나 급여를 사용한 운영 사례로 쓰지 않았으며, 업무 자동화의 효과나 채용 적합성을 독립 검증하지 않았다. 전체 영상과 대조하거나 시연을 재현하지 않았으므로 화면의 세부 동작은 확정할 수 없다. 이 글은 완전한 번역이 아니라 제한된 발표 요약과 기술적 배경을 구분한 해설이다.
