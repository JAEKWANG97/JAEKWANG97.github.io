## 더 유능한 모델이 곧 하나의 작업 방식을 뜻하지는 않는다

Thariq Shihipar는 CODE 2026 발표를 자신의 잘못된 예상에서 시작한다. 에이전트의 도구가 Bash로 수렴하거나, 모델이 잘 쓰는 웹 기술에 작업 방식이 고정될 것이라고 생각했지만 가능한 인터페이스는 더 다양해졌다는 회고다. 이 경험을 바탕으로 그는 모델의 능력이 커지는 것과 사람이 특정 작업 방식에 종속되는 것을 구분한다. [공식 발표](https://ai.engineer/code/2026/talks/thariq-shihipar)

이 발표를 읽을 때 중요한 것은 생산량보다 제작 경험이다. **이 글의 해석으로는**, ‘대신 만들어 줄 수 있다’와 ‘내가 원하는 방식으로 만들 수 있다’는 다른 질문이다. 전자는 위임의 범위를 묻고, 후자는 도구가 사람의 판단을 어떻게 돕는지 묻는다. 코딩 에이전트가 유능해질수록 두 질문을 한데 묶을 필요는 줄어든다.

## 1. 돌을 던지는 기능은 생겼는데, 캐릭터를 모르겠다

발표의 구체적인 사례는 그가 만들던 2차원 대전 게임이다. 캐릭터에게 돌 던지기를 추가해 달라고 하자 에이전트는 돌의 속도와 크기, 충전, 벽과의 충돌 같은 세부 선택도 채워 넣었다. 기능은 동작했지만, 제작자는 캐릭터가 정확히 어떻게 행동하는지 이해하기 어려워졌다. 요청을 보내고 기다리는 동안 집중이 끊기는 문제도 있었다. [발표 전사, 08:48:35 이후](https://www.youtube.com/watch?v=y9JtCCZP2MQ&t=31715s)

그의 실험은 코드의 경계를 바꾸는 것이다. 에이전트가 엔진과 기본 요소를 준비하고, 사람은 읽기 쉬운 행동 코드를 직접 수정한다. 이 코드는 설명 문서만이 아니다. 캐릭터별 행동을 표현하고, 미터 같은 단위를 드러내며, 작성 규칙과 린트로 읽을 수 있는 형태를 유지한다. 사람은 IDE에서 돌의 크기를 바꾸고 플레이한다. 복잡한 기본 요소는 여전히 에이전트에게 부탁한다. 완성된 일반 해법이 아니라 진행 중인 실험이다. [발표의 편집 시연 구간](https://www.youtube.com/watch?v=y9JtCCZP2MQ&t=31955s)

**이 글의 해석:** 여기서 돌의 속도는 구현의 사소한 세부 사항이 아니다. 공격을 피할 수 있는지, 가까이 다가갈 이유가 있는지, 공격이 묵직하게 느껴지는지를 바꾸는 창작상의 선택이다. 이런 선택을 모두 에이전트가 채워 넣으면 요구사항은 빨리 완성될 수 있지만, 만드는 사람은 자신이 고른 적 없는 결정의 묶음을 뒤늦게 이해해야 한다.

따라서 이 사례의 핵심은 사람이 모든 코드를 직접 작성해야 한다는 주장이 아니다. 자주 판단하고 바꾸는 부분을 어디에 둘 것인가의 문제다. 엔진 내부의 복잡성을 감추는 것과 게임의 중요한 선택까지 감추는 것은 구분해야 한다.

*발표의 역할 분담을 설명하기 위해 새로 만든 개념도. 시연 코드나 원본 슬라이드를 복제한 것이 아니다.*

## 2. 취향은 결과를 고르는 감각만이 아니라, 차이를 말하는 능력이다

이 문제는 앞선 Latent Space 인터뷰에서도 나타난다. Shihipar는 게임을 생성할 수 있게 됐어도 재미가 자동으로 생기지는 않는다고 이야기한다. 비행 게임에서 비행기가 입력에 반응하는 느낌은 디자이너가 오랫동안 다듬는 대상이다. 그는 ‘취향’을 소수에게만 주어진 자질처럼 다루는 데 거리를 두고, 여러 시도와 경험을 통해 원하는 것을 알아가며 분야의 언어를 배우는 과정을 강조한다. [본인 인터뷰, 00:18:25 이후](https://latent.space/p/thariq/)

같은 대화에서 디자인을 잘 아는 사람은 참고 화면, 서체, 구성 요소를 더 구체적으로 지정할 수 있지만, 그렇지 않은 사람은 여러 시안을 요청하며 탐색할 수 있다고 설명한다. 모델을 활용해 자신이 아직 모르는 개념을 배우는 것도 중요한 사용 방식이라는 것이다. 이는 CODE 현장 발언을 늘려 적은 것이 아니라 별도 인터뷰에서 확인한 배경이다. [같은 인터뷰의 프롬프팅과 분야 지식 논의](https://latent.space/p/thariq/)

**이 글의 해석:** ‘좀 더 좋게’라는 요청과 ‘발사 준비 동작은 유지하되, 발사 뒤 반응을 빠르게’라는 요청 사이에는 단순한 문장 길이 이상의 차이가 있다. 무엇을 바꾸고 무엇을 유지할지 구분하는 이해가 들어 있다. 직접 작은 수정을 해 보는 편집 공간은 그 이해를 쌓는 데도 도움이 된다. 결과를 평가하는 능력과 요구를 표현하는 능력이 같은 반복 과정 안에서 자라는 셈이다.

## 3. 즉시 바뀌는 화면만으로 충분하지 않은 이유

이 발표를 이해하는 데 비교할 만한 별도 1차 자료는 Bret Victor의 「Learnable Programming」이다. 그는 프로그램을 이해하기 위한 환경이 어휘의 의미, 실행 흐름, 상태를 드러내야 한다고 주장한다. 코드를 수정하면 결과가 즉시 갱신되는 기능만으로 학습과 이해가 해결되지는 않는다는 설명이다. [Bret Victor의 원문](https://worrydream.com/LearnableProgramming/)

그 글의 구체적인 예시는 함수 인자의 뜻과 단위를 주변 데이터에 연결해서 보여 주거나, 움직이는 결과의 시간을 앞뒤로 탐색하게 하는 것이다. 숫자를 무작위로 바꾸며 뜻을 추측하게 하는 대신, 무엇을 조작하는지 이해할 수 있게 만들자는 제안이다. 또한 구체적인 사례를 먼저 이해한 뒤 점진적으로 추상화하는 방식을 설명한다. [같은 글의 어휘·흐름·추상화 절](https://worrydream.com/LearnableProgramming/)

두 자료가 직접적인 계보라는 주장은 아니다. **이 글에서 연결해 보는 지점은**, 사람이 편하게 읽는 표현을 만든다는 목표가 코드 줄 수를 줄이는 목표와 다르다는 사실이다. 짧은 표현이라도 단위나 의미가 숨겨져 있으면 시행착오가 남는다. 반대로 조금 길더라도 어떤 선택이 어떤 결과를 만드는지 드러나면 작업자가 자신의 의도를 더 정확하게 조정할 수 있다.

이 관점에서 행동 편집층은 엔진과 별도로 존재하는 설명 문서여서는 부족하다. 무엇을 바꾸면 실제 동작이 달라지는지 일관되어야 한다. 설명과 실행이 따로 움직이면 사용자는 다시 둘을 맞추는 사람이 된다. 이는 발표를 바탕으로 도출한 설계상의 주의점이며, 시연 프로젝트의 내부 구현을 검증했다는 뜻은 아니다.

## 4. 완벽한 모델이라는 가정과 지금의 모델을 구분하기

발표의 ‘완벽한 모델’은 사고실험이다. 현재의 검증이나 보안 검사가 불필요하다는 뜻이 아니다. [공식 발표 전사](https://ai.engineer/code/2026/talks/thariq-shihipar)

**이 글의 결론:** 모델이 더 잘 만들게 된 뒤에도 남는 일은 잘못된 결과를 잡아내는 것만이 아닐 수 있다. 원하는 느낌을 발견하고, 작은 차이를 시험하고, 그 차이가 왜 좋은지 이해하는 일도 남는다. Shihipar의 게임 사례는 AI 사용자를 결과를 기다리는 감독으로만 상상하지 않는다. 에이전트가 기반 작업을 돕는 동안 사람은 작품을 직접 만지며 바꿀 수 있다. 능력의 향상이 작업 방식의 선택지를 넓히는 방향이다.

### 확인 범위

공식 기계 생성 전사와 별도 인터뷰, Bret Victor의 원문을 확인했다. 화면 속 작은 코드를 검증된 소스 코드처럼 재현하지 않았으며, 게임의 성능이나 생산성 개선 수치를 주장하지 않았다. 발표자의 실험, 다른 시점의 발언, 비교를 위한 외부 자료, 필자의 해석을 구분했다. 직접 인용 없이 출처별 요약 한도 안에서 작성했다.
