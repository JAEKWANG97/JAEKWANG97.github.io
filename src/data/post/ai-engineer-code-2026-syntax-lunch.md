Scott Tolinski와 CJ Reynolds의 점심 세션은 상태 모델, 새 언어, 네이티브 앱, 개발자의 학습을 오가는 대화다. 하나의 실험 결과를 발표하는 형식은 아니다. 이 글은 세션 전체 요약이 아니라 초반의 상태 표현과 설계 경계 논의를 골라 읽는다. 뒤의 언어·플랫폼 논의는 결론으로 묶지 않는다.

## 1. 실제 사례: 이름 붙인 상태와 지켜지는 경계

두 사람은 앱 안의 암묵적인 상태 기계를 찾아보자는 요청에서 출발한다. 로딩·성공·오류 플래그가 흩어지면 원하지 않는 조합이 생길 수 있으므로, 상태와 전이를 명시적으로 표현하는 방향을 논의한다.

대화에는 CLI의 파일 접근을 공통 관리 계층으로 모은 사례도 나온다. 추상화를 만들어도 에이전트가 직접 파일 호출을 추가하면 경계는 무너진다. 이를 금지하는 린트 규칙으로 설계 의도를 유지한다는 설명이다.

다른 주제에서도 판단의 역할이 남는다. 새 언어를 무조건 권하지 않고, 네이티브 전환에서는 기존 테스트가 어떻게 유지되는지 질문한다. 모델이 만든 화면을 맞히는 코너는 오락이지 성능 평가가 아니다. 결과물이 요청을 지키는지, 세부 동작을 돌보는지는 사람이 살펴야 한다. [공식 세션](https://ai.engineer/code/2026/talks/syntax-lunch), [상태 모델 논의 04:12:53](https://www.youtube.com/watch?v=y9JtCCZP2MQ&t=15173s)

## 2. 독립 기술 자료: 상태의 모순과 중복을 줄이기

React 공식 문서는 함께 바뀌는 상태를 묶고, 서로 모순되는 상태와 중복 저장을 피하라고 설명한다. 기존 값으로 계산할 수 있는 정보를 다시 상태에 저장하면 서로 맞춰야 할 값이 늘어난다. 깊은 중첩을 줄이는 것도 갱신 과정의 실수를 줄이기 위한 원칙이다. [Choosing the State Structure](https://react.dev/learn/choosing-the-state-structure)

이 지침은 에이전트가 등장하기 전부터 중요했던 UI 설계 문제를 다룬다. 발표의 모든 논의를 React에 한정하거나 특정 상태 관리 라이브러리가 필수라고 해석할 필요는 없다.

## 3. 해설: 설계는 다음 변경의 선택지를 바꾼다

여기부터는 필자의 해석이다. 명시적인 상태 표현의 가치는 코드가 보기 좋다는 데만 있지 않다. 허용하는 조합과 사건을 좁혀 다음 변경이 지켜야 할 규칙을 드러낼 수 있다는 데 있다.

그러나 상태 이름을 나열한다고 올바른 전이가 자동으로 정해지지는 않는다. 어떤 사건이 현재 상태를 바꾸는지, 오래된 응답은 어떻게 처리할지, 취소 이후 어떤 동작을 허용할지는 별도로 결정해야 한다. 좋은 표현은 판단을 대신하는 것이 아니라 판단할 대상을 분명하게 만든다.

공통 파일 관리 계층도 마찬가지다. 하나의 진입점을 만들면 검사나 정책을 모을 자리가 생기지만, 직접 호출을 계속 허용한다면 약속에 머무를 수 있다. 정적 검사로 지킬 수 있는 규칙과 실행 중 확인해야 하는 규칙을 구분해야 한다. 린트 하나로 모든 안전성을 보장할 수는 없다.

## 4. 별도 공식 자료와 작은 예제로 전이를 읽기

XState 공식 문서는 이벤트가 왔을 때 현재 활성 상태에서 허용된 전이를 찾는다고 설명한다. 조건이 있는 전이는 조건을 통과해야 하며, 가능한 전이가 없으면 상태는 바뀌지 않는다. 상태 이름을 바꿔 쓰는 것만이 아니라 어떤 사건이 어느 상태에서 유효한지 명시하는 방식이다. 이것이 특정 라이브러리를 반드시 도입해야 한다는 뜻은 아니다. [발표 외 자료: XState의 이벤트와 전이](https://stately.ai/docs/xstate/v5/transitions)

**자체 설명 예제:** 한 번에 하나의 요청만 실행하는 화면을 생각해 보자. ‘대기’에서 요청을 시작하면 ‘실행 중’이 되고, 그 상태에서만 성공이나 실패 응답을 받아 각각 ‘완료’나 ‘오류’로 이동한다. ‘완료이면서 실행 중’이라는 조합은 이 예제에서 만들지 않는다. 오류 후 재시도는 다시 ‘실행 중’으로 간다.

다만 오래된 응답을 구별할 요청 ID, 취소, 동시 요청은 이 작은 모델에 없다. 그런 기능이 필요하면 상태와 사건을 추가해야 한다. 그림의 단순함을 실제 앱의 완전한 설계로 오해하지 않는 것이 중요하다. 모델을 명시하면 무엇을 처리하지 않았는지도 더 구체적으로 질문할 수 있다.

## 출처와 한계

공식 웹·ZIP 전사를 대조했다. 대화형 세션의 의견을 단일 실험 결론으로 바꾸지 않았으며, 자동 전사에는 인식 오류가 남을 수 있다. React 문서는 독립적인 기술 근거다. 3절과 4절의 예제·그림은 필자의 해설이며 특정 언어·프레임워크의 우월성을 검증한 결과가 아니다.
