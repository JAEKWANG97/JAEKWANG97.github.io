> AI Engineer CODE 2026 · Kush Agrawal, Duolingo · 2026년 11월 11일 온라인 트랙

테스트 코드를 생성하는 시연은 비교적 짧다. 하지만 생성한 테스트가 빌드되지 않거나, 기존 코드에 가짜 의존성을 넣을 수 없거나, 리뷰받지 못한 채 오래 남는다면 이야기가 달라진다. 파일을 만드는 능력이 곧 테스트 자산을 늘리는 능력은 아니다. MVVM은 화면·화면 상태와 동작·데이터 역할을 나누는 구조이며, 이 사례에서는 테스트하기 쉬운 영역을 먼저 대상으로 삼았다.

Duolingo의 사례에서 눈여겨볼 것은 코드 줄 수보다 그 사이의 운영이다. 무엇을 대상으로 고를지, 반복 실패를 어떻게 분류할지, 언제 사람에게 넘기고 언제 포기할지까지 하나의 흐름으로 연결한다.

## 1. 발표의 전개: 작은 실행에서 실패 패턴을 먼저 찾았다

**이 절은 공식 발표 요약이다.**

Kush Agrawal은 대규모 iOS 코드베이스의 테스트 확대를 설명한다. 초기 두 묶음은 17개 PR 중 8개, 40개 중 19개가 병합됐다. 테스트 프레임워크 혼용, Sendable 제약, 비동기 타이밍, 모킹하기 어려운 의존성이 드러났다. 구체 클래스 대신 프로토콜에 의존하도록 바꾸고 린트로 유지한 사례는 프롬프트 밖의 개선이다.

자동화는 파일 선택, 테스트 생성, CI 수정, 리뷰와 폐기까지 다룬다. CI 수정은 다섯 번으로 제한하고, 리뷰에서 거절된 파일에는 30일의 재선정 대기 기간을 둔다. 사람의 승인을 자동 병합과 구분하며, 실제 소스 변경이나 테스트 약화로 통과시키지 못하도록 제한한다.

발표는 약 8개월 동안 전체 커버리지 11→24%, MVVM 영역 9→59%를 보고한다. 두 수치의 대상은 다르다. 처음에는 Linux에서 iOS 빌드·린트를 확인하지 못해 PR 뒤의 CI 실패를 기다려야 했다. Mac 실행기로 옮겨 생성 단계에서 검사할 수 있게 한 것은 이 지연을 줄이기 위한 변화였다. 코드 줄 수의 전사 불일치는 인용하지 않는다. [실행 환경 문제 04:51:55](https://www.youtube.com/watch?v=ZZ19zhYnDKY&t=17515s)

## 2. 초기 기술 글: PR 하나마다 다음 행동을 결정한다

**이 절은 별도 Duolingo 기술 글의 요약이다. 발표보다 이른 상태를 기록한 자료다.**

기술 글은 Temporal 워크플로가 S3 상태 기록과 GitHub를 통해 대상 선정과 PR 생명주기를 연결한다고 설명한다. 파일의 테스트 적합성·커버리지·크기·모듈 우선순위를 보고, 이미 열린 PR과 기존 테스트, 재시도 대기 조건을 확인한다.

CI가 진행 중이면 기다리고, 통과하면 리뷰어를 배정한다. 충돌한 PR은 닫고, 오래 방치되거나 수정 상한을 넘긴 경우에는 재선정을 지연시킨다. 정해진 형식 수정은 전용 명령으로 처리한다. 초기 250개 PR은 모두 사람의 검토와 승인을 거쳤다.

글의 17주·MVVM 9→30%와 발표의 8개월·9→59%는 같은 시점의 숫자가 아니다. 이 글에서 Mac 실행기는 향후 계획이었으므로 발표 시점의 상태와 혼동하지 않는다.

## 3. 해설: 생성 실패가 코드 구조의 문제를 알려 줄 수 있다

**이하의 설계 판단과 예시는 필자의 해설이다. Duolingo의 추가 구현 사례나 성과가 아니다.**

테스트 생성이 반복해서 실패할 때 프롬프트를 길게 만드는 것이 항상 정답은 아니다. 코드가 외부 의존성을 직접 만들거나 구체 구현에 강하게 묶여 있으면, 사람도 격리된 단위 테스트를 쓰기 어렵다. 에이전트의 실패는 그 구조를 발견하는 신호가 될 수 있다.

필자라면 실패를 문법·프레임워크 사용·환경·설계 제약으로 나누겠다. 단순 형식 오류는 정해진 도구로 수정하고, 테스트 환경이 없어서 검증할 수 없는 문제는 실행 환경을 고친다. 설계 제약은 테스트 PR 안에서 몰래 고치게 하기보다 별도의 변경으로 검토한다.

이렇게 해야 테스트가 통과하기 위해 제품 코드를 바꾸는 상황을 구분할 수 있다. 테스트 가능성을 높이는 리팩터링은 가치가 있지만, 원래 행동을 바꾸어 검사를 통과시키는 것과는 다르다. 목적과 승인 범위를 분리하면 두 작업을 더 명확하게 검토할 수 있다.

*필자가 그린 PR 생명주기다. 생성과 수정의 루프뿐 아니라 기다리기와 포기하기도 정상적인 처리로 포함한다.*

## 4. 해설: 테스트를 더 만드는 것과 검증을 더 잘하는 것은 다르다

커버리지는 실행된 코드의 범위를 보는 데 유용하지만, 어떤 잘못된 행동을 잡는지는 별도 질문이다. 한 줄을 실행해도 결과를 의미 있게 검사하지 않으면 중요한 오류를 놓칠 수 있다. 생성된 테스트의 양이 늘었다는 이유만으로 제품 안전성이 같은 비율로 좋아졌다고 말할 수는 없다.

필자라면 리뷰에서 기대값의 출처를 먼저 묻겠다. 현재 구현을 그대로 흉내 낸 값인지, 요구사항에서 정한 행동인지, 경계 조건과 실패 경로까지 확인하는지 살핀다. 구현의 오류를 테스트가 정답으로 고정하는 일을 피하기 위해서다.

테스트 유지비도 고려해야 한다. 시간에 민감하거나 외부 상태에 의존하는 검사는 이후의 정당한 변경을 자주 막을 수 있다. 그래서 병합 순간의 통과뿐 아니라 이후 불안정성, 수정 빈도, 잡아낸 실제 회귀를 함께 보면 좋겠다. 유용한 테스트 자산은 처음 만드는 비용뿐 아니라 계속 신뢰할 수 있는 비용까지 감당할 수 있어야 한다.

## 5. 해설: 자동화의 중요한 동작은 때로 ‘아무것도 하지 않기’다

CI가 아직 실행 중인데 다시 수정 작업을 보내면 두 실행이 서로의 결과를 덮을 수 있다. 리뷰어가 이미 보고 있는 PR에 자동화가 계속 커밋하면 검토 기준이 움직인다. 오래 실패한 같은 파일을 즉시 다시 선택하면 끝없는 생성과 폐기의 순환이 된다.

따라서 필자라면 생성기와 관리기가 같은 상태 기록을 읽게 하겠다. 무엇을 이미 시도했는지, 다음 행동을 누가 맡고 있는지, 다시 시도할 조건이 무엇인지 일관되게 알아야 한다. 이 기록이 없으면 각 자동화는 자기 작업을 잘하면서 전체로는 서로를 방해할 수 있다.

작은 팀에서는 한꺼번에 많은 파일을 돌리기보다 적은 수의 PR을 실제 리뷰까지 보내는 방식으로 시작하겠다. 병합되지 않는 원인을 먼저 모으고, 해결할 수 있는 반복 실패를 줄인 뒤 처리량을 늘린다. 리뷰 대기열이 밀린다면 생성량을 줄이는 것도 시스템의 올바른 판단이다.

## 마무리

이 발표를 통해 필자가 얻는 결론은 테스트 작성 자동화의 단위가 파일 하나가 아니라 검증된 변경이라는 점이다. 생성, 환경, CI, 리뷰, 폐기가 연결되어야 출력이 자산이 된다. 에이전트가 무엇을 만들 수 있는지뿐 아니라, 무엇을 만들지 말아야 하고 언제 기다려야 하는지도 설계해야 한다.
