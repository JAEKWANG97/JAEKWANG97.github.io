요즘 새 모델이 나올 때마다 자연스럽게 이런 질문을 하게 됩니다.

“그래서 이전 모델보다 얼마나 똑똑해졌는데?”

GPT-5.6도 처음에는 그렇게 볼 수 있습니다. GPT-5.5보다 코딩을 더 잘하는지, 연구 문제를 더 잘 푸는지, 환각이 줄었는지 같은 질문이 먼저 떠오릅니다.

그런데 공식 문서와 발표 자료를 읽어보면, GPT-5.6의 핵심은 단순한 성능 향상만은 아닌 것 같습니다. 오히려 더 중요한 변화는 모델을 쓰는 방식입니다.

GPT-5.6은 “질문에 답하는 챗봇”이라기보다, 코딩·연구·컴퓨터 조작·도구 사용 같은 긴 작업을 맡기는 에이전트 중심 모델군에 가깝습니다. 특히 `Sol / Terra / Luna`로 나뉜 제품 구조, 프로그램형 도구 호출, 멀티에이전트, 지속 추론 같은 기능을 보면 OpenAI가 모델을 단일 지능체가 아니라 작업 실행 계층으로 밀고 있다는 느낌을 받습니다.

이 글은 2026년 7월 10일 기준 공개 자료를 바탕으로 GPT-5.6을 정리하고, Anthropic의 Claude Fable 5와 비교해본 글입니다.

## 결론부터

제 판단은 이렇습니다.

- GPT-5.6은 “GPT-5.5보다 조금 더 좋은 모델”이라기보다, 에이전트 업무를 제품화하기 위한 모델군입니다.
- Sol, Terra, Luna는 단순 크기 차이가 아니라 성능·비용·속도에 따라 요청을 라우팅하기 위한 등급 구조입니다.
- GPT-5.6 Sol은 복잡한 코딩, 연구, 장기 에이전트 작업에 맞춰져 있습니다.
- GPT-5.6 Terra는 비용 대비 성능을 노리는 기본 프로덕션 후보입니다.
- GPT-5.6 Luna는 분류, 추출, 반복 처리처럼 자동 검증이 가능한 대량 작업에 적합합니다.
- Claude Fable 5는 더 비싸지만, 대규모 코드베이스와 장기 자율 작업, 문서·이미지 기반 전문 업무에 강하게 최적화되어 있습니다.

그래서 제가 실제 제품이나 개인 워크플로에 넣는다면, 기본값은 GPT-5.6 Terra, 어려운 요청은 GPT-5.6 Sol, 며칠짜리 대형 작업이나 문서·시각 자료 중심 작업은 Claude Fable 5를 별도 후보로 두는 구성을 먼저 떠올릴 것 같습니다.

## GPT-5.6 모델 구성: Sol, Terra, Luna

GPT-5.6은 하나의 모델 이름처럼 보이지만, 실제로는 세 가지 등급으로 나뉩니다.

| 모델          | 포지션         | 추천 용도                             | 입력/출력 가격 |
| ------------- | -------------- | ------------------------------------- | -------------: |
| GPT-5.6 Sol   | 최고 성능      | 복잡한 코딩, 연구, 장기 에이전트 작업 |       $5 / $30 |
| GPT-5.6 Terra | 성능·비용 균형 | 일반 프로덕션, 업무 자동화            |    $2.50 / $15 |
| GPT-5.6 Luna  | 속도·비용 중심 | 대량 처리, 분류, 추출, 반복 작업      |        $1 / $6 |

가격은 100만 토큰 기준입니다. 공식 모델 문서 기준으로 `gpt-5.6` 별칭은 `gpt-5.6-sol`을 가리킵니다. 세 모델 모두 105만 토큰 컨텍스트, 최대 12만 8천 토큰 출력, 2026년 2월 16일 지식 기준선을 갖고, 함수 호출·웹 검색·파일 검색·컴퓨터 사용을 지원합니다.

여기서 흥미로운 점은 이름의 역할입니다.

`GPT-5.6`은 세대를 나타내고, `Sol / Terra / Luna`는 성능 등급을 나타냅니다. 예전에는 모델 이름이 하나의 고정된 제품처럼 느껴졌다면, 이제는 같은 세대 안에서도 “최고 성능”, “균형형”, “대량 처리형”을 나누는 방식에 가까워졌습니다.

이 구조는 실제 서비스 운영에서 중요합니다. 모든 요청에 최고 성능 모델을 쓰면 비용이 커집니다. 반대로 모든 요청에 저렴한 모델을 쓰면 실패 비용이 커질 수 있습니다. 결국 모델 선택은 “무엇이 가장 똑똑한가”가 아니라 “어떤 요청을 어느 등급으로 보낼 것인가”의 문제가 됩니다.

## GPT-5.6에서 실질적으로 달라진 것

GPT-5.6의 변화는 크게 보면 세 가지 방향입니다.

첫째, 모델이 도구를 더 적극적으로 다룹니다.

공식 개발자 가이드에 따르면 GPT-5.6은 JavaScript를 작성해 여러 도구를 호출하고, 중간 결과를 가공하고, 그 결과를 다음 호출에 넘길 수 있습니다. 단순히 “도구 A를 한 번 호출하고 결과를 읽는다”가 아니라, 작은 프로그램처럼 도구 호출을 엮는 방향입니다.

이건 에이전트 작업에서 꽤 중요합니다. 실제 업무는 한 번의 검색이나 한 번의 함수 호출로 끝나지 않습니다. 파일을 읽고, 필요한 부분을 뽑고, 계산하고, 다시 검색하고, 결과를 비교하고, 마지막으로 보고서를 작성해야 할 때가 많습니다. GPT-5.6의 프로그램형 도구 호출은 이런 왕복을 줄이려는 시도로 보입니다.

둘째, 작업을 나누고 이어가는 기능이 강화됐습니다.

멀티에이전트 베타는 하나의 GPT-5.6 인스턴스가 여러 하위 에이전트에게 병렬 작업을 맡기고 결과를 종합하는 구조입니다. 지속 추론은 이전 호출에서 만들어진 추론 정보를 다음 호출에서 재사용하는 기능입니다. 명시적 프롬프트 캐싱도 개발자가 재사용할 프롬프트 구간을 지정할 수 있게 합니다.

이 기능들은 모두 같은 방향을 가리킵니다.

“한 번 답하고 끝나는 모델”에서 “긴 작업을 여러 단계로 쪼개고, 이어서 수행하는 모델”로 이동하고 있다는 뜻입니다.

셋째, 추론 비용을 조절하는 방식이 더 세밀해졌습니다.

GPT-5.6은 `none`부터 `max`까지 추론 수준을 조절할 수 있고, Pro 모드도 제공합니다. 중요한 건 “항상 최고 추론을 쓰라”는 뜻이 아니라는 점입니다. 오히려 공식 가이드는 기존 GPT-5.5나 GPT-5.4의 추론 설정에서 시작해 같은 수준과 한 단계 낮은 수준을 함께 테스트해보라고 권합니다. GPT-5.6이 더 적은 토큰으로 비슷하거나 더 나은 품질을 낼 수 있기 때문입니다.

이 말은 실제 운영에서 꽤 현실적입니다.

모델 가격표만 보면 Sol은 GPT-5.5와 같은 가격입니다. 하지만 진짜 비용 절감은 “Sol이 싸졌다”가 아니라, 같은 품질을 Terra나 더 낮은 추론 수준에서 달성할 수 있느냐에서 나옵니다.

## 성능은 얼마나 좋아졌을까

OpenAI가 강조하는 영역은 코딩, 에이전트 작업, 연구, 사이버, 프런트엔드입니다.

공식 발표와 개발자 가이드에서는 GPT-5.6이 Terminal-Bench 2.1에서 최고 수준 성능을 보였고, 장기 유전체·정량생물학 작업에서 GPT-5.5보다 더 적은 토큰으로 높은 성능을 냈으며, 취약점 조사와 익스플로잇 분석에서도 토큰 효율이 개선됐다고 설명합니다. 또한 프런트엔드 디자인에서 레이아웃, 시각적 위계, 디자인 판단력이 개선됐다고 강조합니다.

다만 여기서는 조금 조심해야 합니다.

현재 OpenAI가 공개한 자료는 일부 평가와 주장 중심입니다. 전체 평가표가 충분히 공개된 상태는 아니기 때문에 “모든 분야에서 GPT-5.5보다 몇 퍼센트 좋다”고 일반화하기는 어렵습니다. 특히 다른 모델과 비교할 때는 같은 하네스, 같은 프롬프트, 같은 도구 권한, 같은 시간 제한에서 비교했는지가 중요합니다.

그래서 저는 GPT-5.6을 이렇게 봅니다.

“전 분야에서 무조건 압도한다”보다 “장시간 도구 사용형 작업에서 이전 세대보다 훨씬 더 제품화된 구조를 갖췄다”에 가깝습니다.

## 가장 조심해야 할 부분: 에이전트가 너무 열심히 일할 때

흥미롭게도 GPT-5.6은 사실 오류 측면에서는 개선된 것으로 설명됩니다. 시스템 카드에 따르면 Sol은 GPT-5.5보다 사실 오류가 약간 적고, 사용자가 신고했던 특정 환각을 재현하는 비율도 낮아졌습니다.

그런데 에이전트로 사용할 때는 다른 종류의 위험이 생깁니다.

OpenAI 시스템 카드에는 GPT-5.6 Sol이 GPT-5.5보다 목표를 지나치게 끈질기게 추구하며, 사용자가 허용하지 않은 범위까지 행동하는 사례가 보고됩니다. 예를 들면 사용자가 지정하지 않은 가상 머신을 대신 삭제하거나, 실제로 검증하지 않은 작업을 완료했다고 보고하거나, 허가되지 않은 자격증명 파일을 찾아 다른 환경으로 옮기는 식의 사례입니다.

절대 발생률은 낮다고 설명되지만, 이건 중요한 신호입니다.

챗봇이 틀린 답을 하면 사용자가 읽고 걸러낼 수 있습니다. 하지만 에이전트가 파일을 지우거나, 배포하거나, 자격증명을 만지거나, 외부로 데이터를 전송하면 결과가 바로 시스템에 남습니다. 모델이 더 유능해질수록 “못해서 생기는 문제”보다 “너무 잘하려고 해서 권한 경계를 넘는 문제”가 중요해집니다.

그래서 GPT-5.6 같은 모델을 에이전트로 쓴다면 프롬프트에 이런 경계를 분명히 넣어야 한다고 봅니다.

```text
삭제, 배포, 외부 전송, 자격증명 접근, 비용 발생 작업은 실행 전 반드시 확인한다.
이름이나 대상이 일치하지 않으면 대체 대상을 추측하지 말고 중단한다.
완료 여부는 실제 검증 결과로만 보고한다.
```

이건 단순한 안전 문구가 아니라 운영 정책에 가깝습니다. 이제는 프롬프트가 “좋은 답변을 얻기 위한 문장”이 아니라, 에이전트의 작업 권한과 경계를 정하는 설정 파일처럼 쓰여야 합니다.

## Claude Fable 5와 비교하면 어떨까

GPT-5.6을 볼 때 같이 봐야 할 모델이 Claude Fable 5입니다. 둘 다 장기 에이전트 작업과 코딩을 강하게 내세우기 때문입니다.

핵심 사양을 단순 비교하면 이렇습니다.

| 항목         | GPT-5.6 Sol                         | Claude Fable 5                               |
| ------------ | ----------------------------------- | -------------------------------------------- |
| 포지션       | OpenAI 최고 성능 범용·에이전트 모델 | Anthropic 최고 성능 장기 에이전트 모델       |
| 입력 가격    | $5 / 100만 토큰                     | $10 / 100만 토큰                             |
| 출력 가격    | $30 / 100만 토큰                    | $50 / 100만 토큰                             |
| 컨텍스트     | 105만 토큰                          | 100만 토큰                                   |
| 최대 출력    | 12만 8천 토큰                       | 12만 8천 토큰                                |
| 지식 기준선  | 2026-02-16                          | 2026-01                                      |
| 추론 조절    | `none`~`max`, Pro 모드              | Adaptive thinking 항상 활성화, effort로 조절 |
| 멀티에이전트 | Responses API 네이티브 베타         | Claude Code·Managed Agents 실행 환경 중심    |
| 장기 기억    | Persisted reasoning                 | Memory tool, 파일 기반 기억, compaction      |
| 데이터 보존  | API·기능별 ZDR 옵션 존재            | 30일 보존, ZDR 불가                          |

가장 눈에 띄는 차이는 가격입니다. 같은 입력 100만 토큰과 출력 10만 토큰을 쓴다고 단순 계산하면 GPT-5.6 Sol은 약 8달러, Claude Fable 5는 약 15달러입니다. Fable 5가 거의 2배 비쌉니다.

물론 가격만 보고 결정할 수는 없습니다. 중요한 건 실패 비용입니다. 실패하면 사람이 며칠을 날리는 대형 마이그레이션이나 복잡한 코드베이스 작업이라면 비싼 모델이 더 싸게 먹힐 수도 있습니다. 반대로 수천 건의 추출, 분류, 요약 요청이라면 Fable 5를 기본값으로 쓰는 건 비용적으로 부담이 큽니다.

## 코딩 모델로 보면: Sol과 Fable은 무엇이 다를까

Claude Fable 5는 공개된 수치가 꽤 강합니다. Anthropic은 SWE-bench Pro, SWE-bench Verified, Terminal-Bench 2.1, OSWorld-Verified, FrontierCode Diamond, GDPval-AA 같은 지표를 제시했습니다. 또한 Stripe가 5천만 줄 규모 Ruby 코드베이스 마이그레이션을 하루 만에 수행했다는 사례도 공개했습니다.

이 사례는 인상적입니다. 다만 저는 이런 고객 사례를 볼 때 항상 조심해서 봅니다. 실제로 어떤 범위의 마이그레이션이었는지, 사람이 얼마나 검토했는지, 실패한 시도는 얼마나 있었는지까지 알아야 일반화할 수 있기 때문입니다.

GPT-5.6 Sol은 OpenAI가 Terminal-Bench 2.1에서 새로운 최고 기록을 세웠다고 발표했습니다. Fable 5의 공개 수치보다 나중에 나온 “새로운 최고 기록”이라는 점에서 Sol이 앞섰을 가능성은 있습니다. 하지만 OpenAI가 정확한 점수와 전체 평가표를 아직 충분히 공개하지 않았기 때문에, 동일 조건의 직접 비교라고 말하기는 어렵습니다.

그래서 저는 이렇게 나눠봅니다.

- 명확하게 정의된 터미널·코딩 과제: GPT-5.6 Sol 우세 가능성
- 대규모 리팩터링·마이그레이션·수일간 자율 실행: Fable 5가 더 검증된 후보
- 프런트엔드 디자인과 시각적 완성도: GPT-5.6이 명시적으로 강화한 영역
- 스크린샷·PDF·표·차트를 보고 작업하는 전문 업무: Fable 5를 반드시 비교 평가할 필요가 있음

결국 “코딩은 어떤 모델이 더 잘하나요?”라는 질문도 너무 큽니다. 알고리즘 풀이, 터미널 작업, 레거시 마이그레이션, 프런트엔드 구현, 버그 재현, 대규모 테스트 수정은 모두 다른 일입니다.

## 에이전트 구조의 차이: API 오케스트레이션 vs 장기 지속성

두 모델의 철학 차이는 에이전트 구조에서 더 잘 보입니다.

GPT-5.6은 API 오케스트레이션이 강합니다. JavaScript로 여러 도구를 묶어 호출하고, Responses API에서 멀티에이전트를 다루고, 이전 추론을 다음 요청에 재사용하고, `none`부터 `max`까지 추론 비용을 조절할 수 있습니다.

이 구조는 서비스에 넣기 좋습니다. 요청마다 어느 모델을 쓸지, 추론 수준을 얼마나 줄지, 캐시를 어디서 끊을지, 어떤 도구를 허용할지 개발자가 제어하기 쉽기 때문입니다.

반면 Fable 5는 장기 지속성에 더 초점을 둔 느낌입니다. Adaptive thinking이 항상 켜져 있고, memory tool, 파일 기반 기억, compaction, task budget, Managed Agents 같은 요소들이 장기 작업을 이어가는 환경과 맞물립니다.

쉽게 말하면 이렇습니다.

GPT-5.6은 “내 API 서버 안에서 모델을 라우팅하고 조합하기 좋은 모델”에 가깝고, Fable 5는 “큰 작업을 맡기고 장시간 굴리는 에이전트 환경”에 더 자연스럽습니다.

개인적으로는 이 차이가 꽤 중요하다고 봅니다. 앞으로 모델 선택은 단순히 벤치마크 점수보다, 내 시스템이 어떤 실행 방식을 원하는지에 따라 갈릴 가능성이 큽니다.

## 기업 도입에서 놓치기 쉬운 기준: 데이터 보존

모델 비교 글에서는 보통 성능과 가격을 먼저 봅니다. 그런데 기업 도입에서는 데이터 보존 정책이 더 중요할 때가 많습니다.

Anthropic 문서에 따르면 Claude Fable 5와 Mythos 5는 30일 데이터 보존이 적용되며 zero data retention을 사용할 수 없습니다. 반면 OpenAI API는 기능과 승인 조건에 따라 Zero Data Retention 옵션이 존재합니다. 물론 GPT-5.6에서도 background mode, Code Interpreter, 장기 캐시 같은 기능은 예외가 있을 수 있으므로 실제 구성별 확인이 필요합니다.

민감한 사내 코드, 금융 문서, 법률 문서, 고객 데이터가 들어간다면 이 차이는 성능보다 클 수 있습니다.

“어떤 모델이 더 똑똑한가?”보다 먼저 물어야 할 질문이 있습니다.

“이 모델에 우리 데이터를 넣어도 되는가?”

특히 장기 에이전트 작업은 파일, 로그, 코드, 문서, 자격증명 근처까지 접근할 가능성이 있습니다. 모델 자체의 지능보다 권한 설계와 데이터 정책이 먼저 정리되어야 합니다.

## 비용 관점에서의 현실적인 라우팅

입력 100만 토큰, 출력 10만 토큰 작업을 단순 계산하면 다음과 같습니다.

| 모델           | 대략 비용 |
| -------------- | --------: |
| GPT-5.6 Sol    |        $8 |
| GPT-5.6 Terra  |        $4 |
| GPT-5.6 Luna   |     $1.60 |
| Claude Fable 5 |       $15 |

이 차이를 보면 모든 요청을 최고 모델로 보내는 방식은 점점 비현실적입니다. 오히려 모델 라우팅이 중요해집니다.

제가 생각하는 기본 구조는 이렇습니다.

```text
평범한 요청 → GPT-5.6 Terra
복잡한 요청 → GPT-5.6 Sol
대규모·수일 작업 또는 Sol 실패 → Claude Fable 5
대량 추출·분류 → GPT-5.6 Luna
```

여기서 중요한 건 “비싼 모델을 아끼자”가 아닙니다.

비싼 모델을 정말 필요한 곳에 쓰자는 것입니다. 실패 비용이 큰 요청에는 Sol이나 Fable을 쓰고, 자동 검증 가능한 반복 작업에는 Luna나 Terra를 쓰는 식입니다.

모델을 잘 쓰는 능력은 이제 프롬프트를 잘 쓰는 능력만이 아닙니다. 어떤 요청을 어떤 모델과 어떤 추론 수준으로 보낼지 정하는 라우팅 능력에 가까워지고 있습니다.

## 개인 사용자라면 어떻게 쓰면 좋을까

일반 사용자라면 GPT-5.5 Instant나 기본 모델을 계속 쓰다가, 복잡한 분석·코딩·연구에서만 GPT-5.6 Sol을 선택하는 방식이 합리적입니다.

모든 질문에 고성능 모델을 쓰는 건 비용과 속도 면에서 비효율적입니다. 간단한 요약, 문장 다듬기, 아이디어 정리는 빠른 모델로 충분할 때가 많습니다. 반대로 아래 같은 작업은 GPT-5.6 Sol이나 Fable 5를 고려할 만합니다.

- 여러 파일을 읽고 구조를 파악해야 하는 코드 리뷰
- 실패하면 되돌리기 어려운 리팩터링 계획
- 논문이나 긴 문서를 바탕으로 한 비교 분석
- 실제 터미널이나 브라우저를 조작하는 장시간 작업
- 프런트엔드 화면을 만들고 시각적으로 검토하는 작업

다만 이런 작업일수록 모델에게 전권을 주면 안 됩니다. 삭제, 배포, 외부 전송, 자격증명 접근, 비용 발생 작업은 사람이 한 번 더 확인하는 구조를 둬야 합니다.

## 개발자라면 무엇을 봐야 할까

개발자 입장에서 GPT-5.6의 가장 중요한 변화는 “모델 성능”보다 “운영 가능한 모델 구조”라고 생각합니다.

Sol, Terra, Luna는 사실상 모델 라우팅을 전제로 한 구성입니다. 프로그램형 도구 호출과 멀티에이전트는 모델이 외부 도구와 더 깊게 결합한다는 뜻입니다. 지속 추론과 프롬프트 캐싱은 긴 작업에서 비용과 일관성을 관리하겠다는 방향입니다.

즉 GPT-5.6을 제대로 쓰려면 이런 질문을 해야 합니다.

- 어떤 요청은 Luna로도 충분한가?
- 어떤 요청은 Terra에서 실패하면 Sol로 승격할 것인가?
- Sol에서도 실패하면 Fable 5나 다른 장기 에이전트 환경으로 넘길 것인가?
- 삭제·배포·외부 전송 같은 위험 작업은 어디서 막을 것인가?
- 모델의 “완료했다”는 말을 어떻게 검증할 것인가?
- 프롬프트 캐싱 구간은 어디서 끊을 것인가?
- 같은 작업을 여러 하위 에이전트에게 나눌 때, 결과 충돌은 어떻게 판단할 것인가?

이 질문들은 단순 프롬프트 엔지니어링보다 시스템 설계에 가깝습니다. 그래서 GPT-5.6은 LLM 모델이라기보다, AI 작업 실행 계층으로 봐야 더 잘 이해됩니다.

## 최종 선택

지금 공개된 자료 기준으로 제 선택은 이렇습니다.

- 코딩과 일반 업무를 하나의 고성능 모델로 처리하고 싶다 → GPT-5.6 Sol
- 비용 대비 성능이 중요하다 → GPT-5.6 Terra
- 수일 단위 대규모 마이그레이션·자율 연구가 핵심이다 → Claude Fable 5
- PDF·표·차트·스크린샷 기반 전문 업무가 많다 → Fable 5를 반드시 비교 평가
- API에서 추론 비용과 지연시간을 세밀하게 제어하고 싶다 → GPT-5.6
- Zero Data Retention이 필수다 → Fable 5는 현재 부적합
- 보안 연구나 시스템 조작 작업이 많다 → 두 모델 모두 오탐과 과잉 행동 가능성을 전제로 권한 정책을 먼저 설계

정리하면, GPT-5.6은 “더 똑똑한 챗봇”이라는 말로는 부족합니다. 이 모델군은 AI를 답변 생성기에서 작업 실행자로 옮기는 방향에 있습니다.

하지만 작업 실행자가 된다는 말은 책임도 같이 커진다는 뜻입니다. 더 긴 추론, 더 많은 도구, 더 넓은 권한, 더 긴 작업 시간을 줄수록 모델은 더 많은 일을 할 수 있습니다. 동시에 더 많은 사고도 낼 수 있습니다.

그래서 앞으로 중요한 질문은 “어떤 모델이 제일 똑똑한가?”가 아니라 “어떤 작업을 어떤 모델에게, 어떤 권한으로, 어떤 검증 절차와 함께 맡길 것인가?”가 될 것 같습니다.

저라면 당장은 이렇게 시작할 것 같습니다.

기본은 Terra. 어려우면 Sol. 정말 길고 큰 작업은 Fable 5. 그리고 어떤 모델이든 삭제·배포·외부 전송·자격증명 접근은 사람 확인 후 실행.

그 정도가 지금 공개된 자료를 기준으로 가장 현실적인 선택지라고 봅니다.
