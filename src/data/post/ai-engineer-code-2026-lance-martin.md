## 긴 작업을 방해하는 것은 지능만이 아니다

에이전트가 한 번에 풀지 못하는 일을 맡았다고 생각해 보자. 작업자를 늘리면 서로 무엇을 하고 있는지 알아야 한다. 작업 시간이 길어지면 어제 알아낸 사실과 오늘 새로 확인한 사실을 구분해야 한다. 어느 쪽이든 앞선 작업을 다음 작업으로 넘기는 방식이 문제가 된다.

Lance Martin의 「Exploring Claude's Frontier」는 이 문제를 두 갈래로 다룬다. 전반부는 페르마의 마지막 정리를 형식화하는 대규모 에이전트 팀이다. 후반부는 세션 사이에 남긴 기억을 다시 검토하는 작업이다. 발표자는 장기 작업을 수행하는 능력을 협업과 기억이라는 서로 다른 실험으로 살펴본다. [공식 발표와 전사](https://ai.engineer/code/2026/talks/lance-martin)

이 글은 발표의 순서를 따라가되, 실험 조건은 별도로 공개된 연구진의 설명으로 보충한다. 연구진이 보고한 결과와 이 글의 해석을 구분한다. 추가 자료도 대부분 같은 연구팀의 설명이므로, 독립적인 재현 검증으로 취급하지 않는다.

## 1. 페르마의 정리를 새로 발견한 실험이 아니다

먼저 성과의 종류를 정확히 잡아야 한다. 이미 알려진 수학적 증명을 컴퓨터가 검사할 수 있도록 옮기는 형식화와, 알려지지 않은 증명을 발견하는 일은 다르다. Anthropic의 9월 보고서는 전자의 작업을 설명한다. 수십 개 에이전트가 Lean으로 증명을 구성했고, 연구진은 11일이 걸렸다고 보고했다. 초기 시도에서는 프로젝트 상태를 놓쳐 협업이 무너졌지만, Prove2Me를 도입한 뒤 작업이 진전됐다. [9월 형식화 보고서](https://www.anthropic.com/research/formalizing-fermats-last-theorem)

Prove2Me는 정리 사이의 의존 관계를 그래프로 관리했다. 에이전트는 어떤 작은 정리가 아직 증명되지 않았는지 확인하고 다음 일을 고를 수 있었다. 정리와 증명의 파일을 나누어 컴파일 부담을 줄이고, 자연어 설명을 이용해 기존 결과를 찾는 기능도 제공했다. 연구자의 간헐적인 상위 수준 지시도 있었다. 최종 산출물은 Lean으로 검사됐으며, 목표 명제와 일치하는지 확인하는 절차도 거쳤다는 설명이다. [같은 보고서의 방법 설명](https://www.anthropic.com/research/formalizing-fermats-last-theorem)

여기서 중요한 배경은 ‘작은 문제를 푸는 능력’만으로 프로젝트가 완성되지 않았다는 점이다. **이 글의 해석으로는**, Prove2Me는 누가 얼마나 영리한지를 바꾼 장치라기보다, 각자의 진전을 하나의 증명으로 이어 붙일 수 있게 만든 장치에 가깝다. 독립적으로 성공한 작업들이 서로의 전제가 되려면, 무엇이 끝났고 무엇이 남았는지 공동으로 볼 수 있어야 한다.

## 2. 다음 질문: 협업 구조도 에이전트가 만들 수 있을까

발표의 다음 실험은 수학 전용 협업 플랫폼 없이 더 큰 팀이 스스로 작업 구조를 만들 수 있는지 묻는다. 발표자가 강조하는 변화는 전용 도구와 연구자의 풀이 지시를 줄였다는 것이다. 안전장치나 검증 절차까지 없앴다는 뜻은 아니다. 에이전트별 샌드박스와 활동 감시가 남아 있었고, Git과 SQL이 공동 작업의 기반이었다. [발표 전사, 03:50:48 이후](https://www.youtube.com/watch?v=y9JtCCZP2MQ&t=13848s)

11월의 상세 보고서에 따르면 팀은 리더 한 명과 보조 에이전트 999개로 구성됐다. 출발점에는 60개 명제, 간단한 증명 경로, 필요한 정의, 앞선 형식화에서 가져온 47개 보조정리가 있었다. 따라서 아무 수학적 발판 없이 처음부터 모든 것을 만들었다고 읽으면 안 된다. 각 에이전트에는 개별 작업 환경과 Git 브랜치가 있었고, 공유 Postgres 데이터베이스로 작업을 조율했다. [대규모 팀 실험 보고서](https://claude.dev/blog/safely-scaling-multi-agent-teams-with-fable-5-2/)

리더는 공지, 배정, 메모, 하위 작업, 반영된 결과를 위한 테이블을 만들었다. 처음에는 명제별로 인력을 나눴다가 진전에 따라 재배치했다. 후반부에는 어려운 Langlands–Tunnell 정리에 인력을 집중했고, 큰 작업을 다시 작은 작업으로 나누는 트리가 생겼다. 연구진이 보고한 최종 완료 시간은 28.7시간이다. 이 과정에는 실행을 저장 상태에서 다시 시작한 구간도 있었다. [같은 보고서의 실행 결과](https://claude.dev/blog/safely-scaling-multi-agent-teams-with-fable-5-2/)

**이 글의 해석:** 눈여겨볼 부분은 ‘천 개’라는 숫자보다 작업 구조가 실행 중에 바뀌었다는 사실이다. 처음 세운 분할이 최종 분할일 필요는 없다. 어려움이 드러나면 더 나누고, 일이 끝난 작업자는 다른 병목으로 옮길 수 있다. 다만 이것을 일반적인 소프트웨어 프로젝트의 성능 보장으로 확대할 수는 없다. 이 실험은 명확한 목표와 검사 가능한 산출물을 가진 특정 작업이다. 모델, 작업 규모, 초기 자료, 실행 환경이 함께 달라졌으므로 개선을 어느 한 요인의 효과로 단정하기도 어렵다.

## 3. ‘완료 보고’와 ‘검증된 결과’를 분리하는 이유

Lean의 역할을 이해하면 이 실험에서 무엇을 믿을 수 있는지 더 분명해진다. Lean 공식 입문은 증명을 찾는 일과 증명을 검사하는 일을 구분한다. 사람이든 자동화된 도구든 증명을 구성할 수 있지만, 제시한 증명은 형식 체계의 규칙에 맞아야 한다. [Lean 공식 입문](https://lean-lang.org/theorem_proving_in_lean4/Introduction/)

**여기부터는 독자적 설계 해설이다.** 협업 시스템에서 에이전트의 말은 진행 보고이고, 검사를 통과한 산출물은 증거다. 둘을 같은 것으로 취급하면 ‘끝났다고 들은 작업’을 토대로 후속 작업이 시작된다. 잘못된 완료 표시 하나가 여러 작업자의 시간을 낭비하게 만드는 셈이다.

일반 개발에 적용한다면 구현 완료, 테스트 통과, 공유 브랜치 반영을 구분할 수 있다. 모든 프로젝트에 복잡한 상태 관리기를 넣자는 뜻은 아니다. 다음 작업자가 의존해도 되는 시점을 명시하자는 뜻이다. 또한 테스트 통과는 수학적 증명 검사와 같은 보장이 아니다. 실제 개발에서는 요구사항의 누락이나 테스트가 다루지 않은 동작을 따로 검토해야 한다.

## 4. 기억을 많이 남기면 다음 실행이 더 똑똑해질까

발표 후반부는 협업에서 기억으로 옮겨 간다. 세션마다 새로운 문맥에서 시작하더라도 이전 경험을 파일로 읽게 할 수 있다. 하지만 메모가 남아 있다는 것과 그 메모가 도움이 된다는 것은 별개다. 발표에서는 모델에 따라 기록을 남기는 방식이 달랐으며, 게임 진행 중 쌓인 기록과 전략적인 메모를 대비한다. 이어 ‘dreaming’을 통해 기록을 다시 읽고 오류를 고치거나 지식의 표현을 바꾸는 접근을 소개한다. [공식 발표 전사](https://ai.engineer/code/2026/talks/lance-martin)

별도 메모리 연구 글은 포켓몬 레드의 비교를 구체화한다. 각 모델의 한 차례 실행에서 비슷한 진행 단계의 기록을 비교했을 때, 한 모델은 사건별 기록을 대량으로 남겼고 다른 모델은 목표와 전략에 집중했다. 중요한 한계도 있다. 이것은 메모를 줄인 조치만 따로 검증한 실험이 아니라 서로 다른 모델의 실행 비교다. [메모리 연구 글](https://www.anthropic.com/research/components-of-agent-memory)

**이 글의 해석:** 다음 행동을 결정하는 데 필요한 것은 과거의 모든 장면이 아니다. 다시 확인하기 쉬운 현재 상태와, 시행착오를 거쳐 알아낸 규칙은 보존 가치가 다를 수 있다. 예를 들어 화면에서 즉시 읽을 수 있는 값은 오래된 복사본을 유지하는 편이 오히려 혼란을 만들 수 있다. 반대로 실패 원인과 이를 확인한 근거는 다시 얻기 어려울 수 있다. 좋은 기억은 작은 기억이라는 뜻이 아니라, 다음 판단에 필요한 정보를 찾고 검증할 수 있는 기억이라는 뜻이다.

## 5. 잘못된 메모는 같은 실패를 더 오래 유지한다

메모리 연구 글의 인상적인 사례는 달맞이산 주변의 길 찾기다. 에이전트가 포켓몬센터의 위치를 잘못 기록했고, 이를 믿은 뒤 절벽 아래의 이전 경로로 돌아갔다. 잘못된 기록은 산을 이미 통과했다는 판단을 강화했다. 연구진은 dreaming으로 원래 세션 기록과 메모를 대조하게 했고, 위치를 수정한 실행에서는 다시 동굴로 들어가 다음 도시에 도착했다고 설명한다. [사례와 비교 결과](https://www.anthropic.com/research/components-of-agent-memory)

같은 글은 위키를 만드는 실험도 다룬다. 여러 문서를 연결한 표현은 검색을 보조할 수 있었지만, 어떤 과제에서는 뚜렷한 이득이 없었다. 원문보다 더 커진 위키도 있었다. 기억을 가공하는 작업 자체가 항상 성공하는 것은 아니라는 사례다. [메모리 표현 실험](https://www.anthropic.com/research/components-of-agent-memory)

**이 글의 해석:** 이 문제를 단순한 요약으로 풀기는 어렵다. 잘못된 위치를 더 짧게 적으면 짧은 오류가 될 뿐이다. 필요한 것은 원래 관찰로 돌아가서 현재 믿고 있는 내용이 맞는지 확인하는 과정이다. 따라서 기억 시스템에는 적어도 두 가지가 구분되어야 한다. ‘무엇을 믿고 있는가’와 ‘왜 그렇게 믿는가’다.

이 구분은 오래된 개발 메모에도 적용된다. ‘배포는 A 서버에서 한다’라는 한 줄만 남으면 환경이 바뀐 뒤에도 계속 적용될 수 있다. 확인 시점, 적용 환경, 근거가 함께 있으면 재검토 대상을 고르기 쉬워진다. 다만 모든 기억을 매번 다시 검사하면 비용이 커진다. 변경 가능성이 크거나, 자주 사용되거나, 틀렸을 때 피해가 큰 정보부터 검토하는 정책은 이 글에서 제안하는 적용 방식이다. 발표에서 그대로 제시한 운영 규칙은 아니다.

## 두 실험을 함께 읽는 이유

**이 글의 결론은 다음과 같다.** 협업에서는 다른 작업자의 보고를 공동의 프로젝트 상태로 옮긴다. 기억에서는 지난 실행의 관찰을 다음 실행의 판단 근거로 옮긴다. 두 경우 모두 중간 기록이 다음 행동을 움직이기 때문에, 기록을 만드는 기능만큼 기록을 검증하고 고치는 경계가 중요하다.

그렇다고 모든 업무에 천 개의 에이전트나 대규모 위키가 필요하다는 뜻은 아니다. 작은 시스템에서도 질문은 같다. 완료를 누가 판단하는가. 다음 작업자가 어떤 결과를 믿어도 되는가. 이전 판단이 틀렸을 때 어디에서 고치는가. 이 질문에 답하지 않은 채 작업자 수와 기억 용량만 늘리면, 처리량뿐 아니라 혼란을 확대할 수도 있다.

### 자료와 해석의 범위

공식 기계 생성 전사와 공개 연구 글을 확인했다. 전사에는 고유명사와 수식 인식 오류가 있어 기술 명칭과 실험 조건은 연구 글로 보완했다. 숫자는 연구진의 보고값이며 이 글에서 재현하지 않았다. 발표는 2026년 행사 자료의 해당 세션을 기준으로 했으며, 추가 연구 글의 세부 사항을 모두 무대 발언으로 돌리지 않았다. 직접 인용 없이 출처별 제한된 요약과 별도로 표시한 독자적 해설로 구성했다.
