## 수상해 보이는 행동이 곧 공격은 아니다

Roey Ben Chaim의 발표는 클라우드 설정을 읽고 신원 서비스와 인스턴스 메타데이터를 조회하는 사례로 시작한다. 자격 증명을 찾는 공격처럼 보이지만, 그가 제시한 대상은 정상적인 Azure 진단 스킬이다. 어떤 작업이 수행됐는지만이 아니라 왜, 어떤 권한과 맥락에서 수행됐는지를 살펴야 한다는 출발점이다. [공식 발표](https://ai.engineer/code/2026/talks/online-zenity-skills)

이 글은 생중계에서 끊긴 구간이 아니라 공식 14분 30초 교체 영상의 전사를 기준으로 한다. 정적 검사를 무용하다고 선언하는 대신, 문서 검사만으로 알 수 없는 부분이 무엇인지와 실행 관찰에도 어떤 한계가 있는지 구분한다.

## 1. SKILL.md는 실행 전체가 아니라 진입점이다

발표의 보안 리뷰 스킬 시연은 다른 스킬과 원격 지침으로 이어진다. 입구 파일만으로 전체 실행을 알 수 없다는 사례다. 시연의 최종 실행 내용 자체는 악성이라고 제시되지 않았다. [공식 전사](https://ai.engineer/code/2026/talks/online-zenity-skills)

별도 연구인 Trail of Bits의 공개 실험은 이 문제를 더 구체적으로 보여 준다. 연구진은 문서 파일 내부에 지침을 넣거나, 겉으로 보이는 소스와 다른 동작을 가진 바이트코드를 포함한 스킬로 당시 검사 도구의 한계를 시험했다. 또한 외부 패키지 레지스트리 변경을 사내 표준 설정처럼 설명했을 때 LLM 기반 분석기가 이를 안전하다고 판단한 사례를 보고했다. [Trail of Bits의 실험 보고서](https://blog.trailofbits.com/2026/06/03/the-sorry-state-of-skill-distribution/)

이 결과는 연구진이 시험한 당시 구성에 대한 보고다. 모든 스캐너가 항상 실패한다거나 이후 수정도 무의미하다는 주장이 아니다. 보고서 자체도 일부 도구에 개선 사항을 제출했다고 설명한다. 다만 검사 범위 밖의 파일과, 검사 대상이 스스로 주장하는 정당성을 신뢰하는 문제가 각각 존재한다는 근거가 된다. [같은 보고서](https://blog.trailofbits.com/2026/06/03/the-sorry-state-of-skill-distribution/)

**이 글의 해석:** 스킬이 ‘보안팀이 승인했다’고 쓰는 것은 승인 사실의 증거가 아니다. 검사기가 검토해야 할 텍스트와 검사기가 따라야 할 지시를 구분해야 한다. 의존성의 이름이 익숙하다는 이유로 실제 출처를 확인하지 않는 문제도 같은 종류다. 문서가 주장하는 신뢰와 외부에서 확인한 신뢰는 다르다.

## 2. 빈 샌드박스가 조용했다고 안전한 것은 아니다

발표자는 처음에 에이전트와 스킬을 격리 환경에 넣어 실행했지만, 필요한 서비스나 도구가 없으면 중요한 행동에 도달하지 못했다고 설명한다. 이를 보완하기 위해 환경을 준비하는 역할과 다양한 작업 경로를 실행하는 역할을 나눴다. 배포 스킬이라도 설정, 배포, 복구는 서로 다른 경로를 거칠 수 있다. [공식 교체 영상 전사](https://ai.engineer/code/2026/talks/online-zenity-skills)

**이 글의 해석:** 동적 검사는 실행된 경로를 보여 준다. 실행되지 않은 경로의 안전을 자동으로 증명하지는 않는다. 로그인에 실패한 서비스 연동 스킬이나 필요한 프로젝트를 찾지 못한 개발 스킬이 아무 변경도 만들지 않았다고 해서, 정상적으로 준비된 환경에서의 동작까지 확인한 것은 아니다.

따라서 결과에는 탐지 여부만 아니라 테스트가 실제로 어디까지 진행됐는지 필요하다. 작업을 시작했는가, 핵심 기능을 호출했는가, 의존성을 불러왔는가, 특정 분기에서 중단됐는가를 남기면 ‘문제가 없었다’와 ‘문제를 볼 기회가 없었다’를 구별할 수 있다. 이는 발표에서 착안한 평가 결과 해석 방법이다.

## 3. 에이전트가 호출한 도구 아래도 봐야 한다

발표의 후반부는 관찰 범위를 넓힌다. 에이전트 기록에 패키지 설치가 보이더라도 설치 과정에서 생긴 자식 프로세스의 파일 접근이나 네트워크 통신은 그 기록만으로 충분히 알기 어렵다. 연구진은 도구 호출과 함께 프로세스 생성, 파일시스템, 네트워크 활동을 수집하는 방식으로 확장했다고 설명한다. [공식 전사의 관찰 계층 설명](https://ai.engineer/code/2026/talks/online-zenity-skills)

Zenity의 별도 공개 설명도 격리된 환경에서 실제 에이전트가 스킬을 사용하게 하고, 접속 도메인·패키지·파일·명령을 관찰하는 접근을 제시한다. 시험용 자격 증명과 파일을 환경에 배치해 접근 행동을 확인한다는 설명도 있다. 이는 운영 환경의 실제 비밀을 넣고 실행하라는 권고가 아니라 보안 연구용 통제 환경의 구성이다. [Zenity의 AI Total 설명](https://zenity.io/research/ai-total)

해당 설명은 삭제 후 재설치를 유도하는 지속적 지침, 기존 도구의 교체, 실행 시 외부에서 받아오는 내용 등의 조사 사례를 제시한다. 이 글은 그 보고를 독립 재현하지 않았으며, 설치 횟수를 피해자 수로 바꾸거나 발견 비율을 탐지 정확도로 해석하지 않는다. [같은 조사 설명](https://zenity.io/research/ai-total)

## 승인한 대상이 시간이 지나도 같은가

**이 글의 해석:** 원격 자료를 매번 가져오는 스킬에서는 승인 시점과 실행 시점의 내용이 달라질 수 있다. 스킬 본문만 보관하면 다음에 무엇을 읽었는지 비교하기 어렵다. 어떤 버전의 스킬이 어떤 의존성과 설정으로 실행됐는지 남기는 것은 재현뿐 아니라 변경 감지에도 필요하다.

이 관점에서 정적 검사와 실행 관찰은 대체 관계가 아니다. 파일과 출처를 먼저 살피고, 제한된 환경에서 사용 경로를 시험하고, 실제 사용 때도 허용 범위를 유지하는 방식으로 서로 다른 빈틈을 줄인다. 실행 관찰에서 나쁜 행동이 보이지 않았다고 불필요한 권한까지 줄 이유는 없다.

### 자료와 한계

공식 교체 영상의 웹·ZIP 기계 생성 전사, Trail of Bits의 1차 실험 보고서, Zenity의 조사 설명을 확인했다. 보안 업체의 제품 설명과 연구 결과를 독립적인 탐지율 검증으로 취급하지 않았다. 직접 인용·공격 코드·실행 명령은 포함하지 않았고, 출처별 요약 한도 안에서 방어 관점의 해설로 구성했다.
