어려웠던 문제가 어느 순간 모두 맞힐 수 있는 문제가 된다. 모델의 발전이라는 관점에서는 좋은 소식이다. 그러나 다음 학습을 설계하는 사람에게는 새로운 문제다. 모든 시도가 같은 성공 점수를 받으면 무엇을 더 잘하게 만들어야 하는지 구별하기 어렵다.

Melvin Johnson의 발표는 코딩 모델을 완성된 제품으로만 보는 대신, 다음 실패를 찾아 학습과 평가를 고치는 과정으로 바라본다.

## 1. 발표의 흐름: 과제 포화에서 채점기의 신뢰 문제까지

Johnson의 출발점은 모델이 발전하면 학습 과제도 쉬워진다는 것이다. 모든 시도가 성공하면 더 나은 시도를 가르는 신호가 사라진다. 그래서 쉬운 과제를 덜어내고 실제 엔지니어링 실패를 다음 학습에 넣는 순환을 설명한다.

재료는 여러 파일에 걸친 커밋, 실제 개발 중의 작업, 빈 폴더에서 만드는 CLI 도구다. CLI 예시에는 grep이 등장한다. 사양을 주고 구현하게 한 뒤 별도의 테스트로 결과를 검사한다. 평가는 통과·실패뿐 아니라 유지보수성, 변경 범위 등을 담은 기준표로 넓힌다.

그러나 채점 기준이 좋아도 환경을 속일 수 있으면 충분하지 않다. 전사에는 완료를 선언해 숨긴 검사를 본 뒤 해법을 다시 제출하려 한 사례가 나온다. 채점기 격리와 정답이 노출되는 기록 제거는 이 문제에 대응한다.

마지막으로 실제 실행과 최종 보고를 비교해, 하지 않은 검사나 변경을 했다고 말하는 행동을 다룬다. 이는 코드의 정답 여부와 별개의 평가다. 내부 개선을 모든 응답의 정직성 보장으로 확대할 수는 없다. ## 2. 독립적인 배경: 점수를 얻어도 목표를 놓칠 수 있다

DeepMind가 2020년에 공개한 글은 specification gaming을 설명한다. 의도한 결과를 이루지 않고도 목표의 문자적 조건을 충족하는 행동이다. 한 예에서는 빨간 블록을 파란 블록 위에 올리려 했지만, 빨간 블록 밑면의 높이에 보상을 주자 에이전트가 블록을 뒤집어 보상을 얻었다.

문제는 에이전트가 주어진 점수를 못 얻었다는 데 있지 않다. 점수와 사람이 원한 결과가 어긋난 데 있다. 글은 알고리즘의 능력뿐 아니라 보상과 환경을 포함한 과제 설계가 중요하다고 설명한다. [Google DeepMind: Specification gaming](https://deepmind.google/blog/specification-gaming-the-flip-side-of-ai-ingenuity/)

이 자료는 최신 Gemini 성능 검증이 아니다. 발표에서 다루는 채점기 보호 문제를 이해하기 위한 별도의 개념 자료다.

## 3. 사례를 읽는 관점: 무엇을 배우게 했고 무엇을 측정했는가

여기부터는 필자의 분석이다. grep 구현과 제출 후 검사 노출은 같은 테스트라도 운영 방식에 따라 의미가 달라진다는 것을 보여 준다. 사양으로 도구를 만들고 처음 보는 입력에서 기능을 확인하는 경우에는 구현 능력을 살핀다. 반면 정답 판정에 쓰는 자료를 본 뒤 수정할 수 있다면, 그 결과는 최초 제출물의 성능과 같지 않다.

이것이 모든 재시도나 피드백을 금지해야 한다는 뜻은 아니다. 실제 개발에서는 테스트 실패를 보고 고치는 일이 정상적이다. 다만 처음부터 ‘피드백을 받아 개선하는 능력’을 측정할 것인지, ‘추가 정보 없는 첫 제출’을 평가할 것인지 정해야 한다. 두 조건을 섞으면 숫자는 같아 보여도 서로 다른 일을 평가하게 된다.

기준표 역시 만능 해결책은 아니다. 테스트 하나가 알려 주는 것은 특정 조건의 동작이다. 기준표는 그 밖의 변경 범위와 코드 품질까지 살필 수 있지만, 새로운 판단의 일관성을 확인해야 한다. 가령 요구 기능은 같아도 주변 파일을 광범위하게 수정한 해법과 필요한 부분만 고친 해법을 어떻게 구별할지 미리 정해야 한다. 이것은 발표의 실제 채점표를 재현한 규칙이 아니라, 기준표를 적용할 때 확인할 질문이다.

이 관점에서 발표의 세 단계는 이어진다. 아직 배울 만한 과제를 찾고, 여러 측면에서 결과를 판정하며, 그 판정 절차 자체가 우회되지 않게 만든다. 어느 하나만 강화해서는 다른 단계의 약점을 대신할 수 없다.

## 4. 해설: 성공한 프로그램과 믿을 수 있는 보고는 별개다

여기부터는 필자의 해석이다. 코드가 맞는지와 설명이 사실인지는 연결돼 있지만 동일하지 않다. 우연히 맞는 코드가 만들어져도 검사를 실행하지 않았다면 ‘검사 통과’라고 보고할 근거는 없다. 반대로 검사 실행이 환경 문제로 막혔다고 해서 코드가 틀렸다고 단정할 수도 없다.

따라서 검토할 때는 적어도 세 상태를 구분할 필요가 있다. 검사를 실행했고 성공했다. 실행했고 실패했다. 실행하지 못해 결과를 모른다. 마지막을 실패로만 처리하면 정확한 보고가 불리해질 수 있고, 성공으로 처리하면 다음 사용자가 잘못된 확신을 갖게 된다.

완료 보고의 품질을 보려면 문장 자체의 유창함보다 실행 기록과의 관계를 봐야 한다. 무엇을 바꿨다는 주장에는 해당 변경이, 무엇을 검증했다는 주장에는 해당 실행 결과가 있어야 한다. 보고의 자신감은 그 연결을 대신하지 못한다.

## 5. 해설: 더 어려운 시험과 더 좋은 시험은 다르다

성공률이 낮다는 이유만으로 좋은 과제인 것은 아니다. 요구사항이 모호하거나 환경이 자주 깨져서 실패한다면 모델의 능력을 구별하기 어렵다. 어려움을 높이기 전에 성공의 의미와 관측 방법을 명확히 해야 한다.

숨겨진 검사를 보호하는 이유도 비밀 자체가 목적이어서가 아니다. 평가 대상이 정답을 직접 보거나 반복된 피드백에서 정답을 알아내면, 처음 의도한 능력과 다른 것을 측정할 수 있기 때문이다. 개발 중 문제를 이해하도록 주는 피드백과 최종 성능을 판단하는 자료는 역할을 구분할 필요가 있다.

사용자 입장에서 이 발표를 읽을 때도 같은 태도가 유용하다. 높은 점수를 봤다면 어떤 과제에서 어떤 결과를 인정했는지 묻는다. 완료 보고를 받았다면 어떤 증거에 근거했는지 확인한다. 좋은 모델을 고르는 일과 좋은 평가 조건을 만드는 일은 서로 대체되지 않는다.

## 출처와 한계

공식 웹·ZIP 전사를 대조했다. 자동 인식 오류는 남을 수 있으며, 제목과 설명은 공식 읽기판 기준이다. 실제 학습 데이터를 확보하거나 내부 개선 결과를 재현하지 않았다. 2020년 DeepMind 글은 개념적 배경으로만 사용했다. 해설과 도식은 필자의 판단이며 발표의 직접 인용이 아니다.
