> AI Engineer CODE 2026 · Rajath Kotyal, AWS · 2026년 11월 11일 온라인 트랙

코드가 요구사항과 일치한다면 좋은 구현인가. 요구사항이 서로 충돌한다면 이 질문에는 답하기 어렵다. 어느 쪽을 택해도 다른 규칙을 어기기 때문이다. 이런 문제를 테스트 단계에서 발견하면 이미 작성한 코드뿐 아니라 테스트의 기대값까지 다시 결정해야 한다.

이 발표를 읽는 출발점은 에이전트가 명세를 얼마나 잘 따르는지가 아니다. 에이전트에게 준 명세가 애초에 따를 수 있는 것인지, 그리고 그 의미를 팀이 같은 방식으로 이해하는지다.

## 1. 발표의 출발점: 재고가 없으면 주문을 어떻게 처리할까

**이 절은 공식 발표 요약이다.**

Rajath Kotyal은 전자상거래 명세의 충돌로 시작한다. 재고가 없으면 주문을 재고를 확보한 뒤 이행할 주문(backorder)으로 두라는 규칙과, 어떤 주문도 backorder로 두지 말라는 규칙이 함께 있다. 각각 자연스러워도 동시에 만족시킬 수는 없다.

제안한 분석 과정은 자연어 요구를 정리하고 형식 표현으로 옮긴 뒤 SMT 솔버(논리식의 제약을 만족시킬 수 있는지 판정하는 도구)로 제약 관계를 검사한다. 번역 자체의 불확실성도 다룬다. 같은 요구를 여러 번 옮겨 논리적으로 동등한 해석끼리 묶고, 의미가 갈리면 질문하거나 판단을 보류한다. 표현이 달라도 같은 뜻인지 확인하는 단계가 필요한 것이다.

모호함은 모순과도 다르다. 기록을 제거하라는 요청은 삭제인지 표시에서 숨기는 것인지 확정하지 못한다. 솔버가 번역된 표현의 일관성을 확인해도 번역이 원래 의도를 옮겼다는 보장은 없다. 발표의 핵심은 구현 전에 문제를 찾아 사람에게 돌아갈 질문으로 만드는 데 있다.

[공식 발표·전사: Specs have bugs too](https://ai.engineer/code/2026/talks/online-aws-specification-analyzer)

## 2. 제품 문서가 보여 주는 실제 사용 흐름

**이 절은 별도의 Kiro 공식 문서 요약이다. 내부 구현 전체를 검증한 설명은 아니다.**

Kiro의 Analyze Requirements 문서는 요구사항 작성 뒤 설계로 넘어가기 전에 분석하도록 안내한다. 개별 문장뿐 아니라 요구사항 사이의 관계를 살피며, 모순·모호함·상충하는 제약·정의되지 않은 가정·빠진 경계 조건을 대상으로 한다.

결과는 관련 요구사항과 문제 설명, 가능한 수정안을 포함한 질문으로 나온다. 사용자는 제안을 선택하거나 직접 답하고, 의도적인 모호함은 제외할 수 있다. 답을 반영해 requirements.md를 수정하며 이후 다시 분석할 수도 있다. 단순하고 이미 잘 이해한 명세라면 분석을 생략하는 선택도 허용한다.

이 문서는 질문을 해결하는 작업 흐름을 확인해 준다. 그러나 발표에서 설명한 번역·솔버 구성의 모든 세부가 제품의 현재 구현과 동일하다는 증거는 아니다.

[Kiro 공식 문서: Analyze Requirements](https://kiro.dev/docs/specs/analyze-requirements/)

## 3. 해설: ‘모순 없음’과 ‘결정 완료’를 구분해야 한다

**이하의 예시·분류·적용 순서는 필자의 해설이다. 발표자의 추가 발언이나 Kiro의 실제 명세가 아니다.**

명세에서 발견한 문제를 전부 ‘불명확함’이라고 부르면 해결 책임이 흐려진다. 필자라면 적어도 세 가지로 나누겠다.

첫째는 동시에 참일 수 없는 규칙이다. 이때 필요한 것은 문장을 매끄럽게 고치는 일이 아니라 어느 규칙을 수정할지 결정하는 일이다. 둘째는 한 문장이 서로 다른 구현을 허용하는 경우다. 이때는 가능한 해석을 나란히 놓고 고르면 된다. 셋째는 어떤 상황의 규칙이 아예 없는 경우다. 이 경우 기존 문장 하나를 자세히 설명해도 빈칸은 남는다.

![자연어 명세의 논리 검사와 업무 의도 확인을 분리한 개념도](/images/ai-engineer-code-2026/rajath-kotyal.svg)

*필자가 그린 검토 절차다. 솔버의 통과 결과를 곧바로 업무 승인으로 연결하지 않은 것이 핵심이다.*

## 4. 해설: 여러 번 번역해도 ‘다수결이면 정답’은 아니다

같은 요구를 여러 번 해석했을 때 결과가 갈린다면 유용한 경고 신호가 된다. 하지만 모두 같은 해석을 했다는 이유만으로 그 해석이 맞다고 결론 내릴 수는 없다. 같은 전제나 용어 오해를 공유하면 반복해서 같은 방향으로 틀릴 수 있기 때문이다.

그래서 필자는 일치율을 업무 담당자의 승인을 대신하는 점수로 쓰지 않겠다. 질문할 우선순위를 정하는 신호로 쓰겠다. 돈, 권한, 데이터 삭제처럼 잘못된 해석의 비용이 큰 항목에는 해석이 안정적이어도 별도의 예시 확인이 필요하다.

확인 방법은 추상적인 “이 명세가 맞습니까?”보다 구체적인 입력과 결과를 보여 주는 편이 낫다. “기록을 지운다는 것은 저장된 데이터를 삭제한다는 뜻입니까, 화면에서 숨긴다는 뜻입니까?”라고 물으면 담당자는 실제 정책을 결정할 수 있다. 답을 받은 뒤에는 문서만 고치지 말고 그 사례를 검증 기준에도 남겨야 한다. 그래야 다음 구현자가 같은 질문을 다시 추측하지 않는다.

## 마무리

이 발표를 통해 필자가 다시 보게 된 것은 코드 생성 이전의 책임이다. 구현을 빠르게 할수록 잘못된 전제도 빠르게 확산된다. 먼저 의미를 정하고, 표현된 규칙의 관계를 검사하고, 그 결정이 테스트까지 이어지게 만드는 일이 필요하다. 논리 검사는 그 과정의 강력한 도구지만 무엇을 원하는지 결정하는 주체는 아니다.
