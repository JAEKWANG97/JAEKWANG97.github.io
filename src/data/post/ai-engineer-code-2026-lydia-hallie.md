## 발표의 출발점: 사람이 빠진 자리는 빈자리로 남겨 둘 수 없다

**발표 요약:** Lydia Hallie의 *Rethinking Claude Code Best Practices*는 짧은 세션에 매번 개입하던 개발자가 여러 장시간 세션을 관리하게 되는 변화에서 시작한다. 사람이 맡던 판단을 모델, 실행 도구, 환경 중 무엇이 대신할지 정해야 한다는 문제다.

오래된 강한 지침을 계속 쌓기보다 코드만으로 알 수 없는 정보를 남기자고 제안한다. 예로 코드에 드러나지 않는 레거시 의존성을 든다. 이어 권한 판단과 실행 중 격리를 구별한다. `npm test`를 승인해도 그 안의 의존성이 비밀 파일을 읽지 못한다는 보장은 없다. 셸 샌드박스 밖에서 실행되는 MCP와 훅도 따로 고려해야 한다.

검증 사례는 인증 API 이전이다. 같은 요청에도 기존 API를 남기거나, 신규 로그인만 바꾸거나, 모든 사용자를 로그아웃시키는 결과가 나올 수 있다. 따라서 완료 조건을 중간 검사로 바꾸고 실제 결과를 확인한다. 필수 검사는 훅과 CI에 둔다. 격리된 실행 컴퓨터를 버릴 수 있어도 이미 전송한 메시지와 커밋은 남는다. [공식 발표·전사](https://ai.engineer/code/2026/talks/lydia-hallie)

## 왜 테스트 명령이 핵심 사례인가

**해설:** 이 사례는 “AI가 위험한 명령을 선택할 수 있다”는 설명보다 한 단계 더 나아간다. 선택한 명령이 업무상 필요하고 표면상 정상이어도, 실행되는 코드 전체를 승인 화면 하나에서 파악할 수는 없다. 사람이 승인했는지와 실행 환경이 안전한지는 별도 질문이다.

테스트를 막으면 결과 검증을 할 수 없다. 그렇다고 테스트에 컴퓨터 전체의 권한을 줄 필요는 없다. 개발을 계속할 수 있는 범위와 지켜야 할 자원을 나누는 것이 해결의 출발점이다. 아래 그림은 이 구분을 설명하기 위해 새로 그렸다. 실제 Claude Code 내부 구성도를 복제한 것은 아니다.

## 별도 자료로 확인하는 두 방어선

**보충 자료 1: 실행 중 경계.** Anthropic의 샌드박싱 설명은 파일시스템과 네트워크를 함께 제한한다. 명령이 시작한 프로그램과 하위 프로세스에도 운영체제 수준의 제한을 적용한다. 파일 접근만 제한하거나 네트워크만 제한하는 것으로 충분하지 않다는 설명이다. 클라우드 Git 연동에서는 별도 프록시가 저장소와 브랜치를 검사한 뒤 인증을 처리한다. 이는 2025년 공개된 설계 설명이며 모든 환경의 현재 기본 설정이 동일하다는 뜻은 아니다. [Anthropic 샌드박싱 설명](https://www.anthropic.com/research/claude-code-sandboxing)

**보충 자료 2: 행동 전 판단.** Auto mode 기술 설명은 유용한 일을 하려다 권한을 넘어서는 행동도 위험으로 다룬다. 예컨대 모호한 브랜치 정리 요청을 원격 브랜치 삭제로 넓히거나, 인증 실패 뒤 다른 자격증명을 찾아 쓰는 경우다. 분류기는 사용자의 요청과 실제 도구 호출을 중심으로 판단하며 에이전트의 해명과 도구 결과를 제외한다. 그러나 위험 행동을 놓치는 사례가 남으므로 중요한 인프라에 대한 신중한 사람 검토를 그대로 대체한다고 보지 않는다. [Anthropic auto mode 기술 설명](https://www.anthropic.com/research/claude-code-auto-mode)

**해설:** 두 자료는 같은 안전장치를 다른 이름으로 부르는 것이 아니다. 행동 판단은 요청의 의도와 범위를 해석한다. 격리는 실행 프로세스가 접근할 자원을 제한한다. 전자가 틀렸을 때 후자가 피해 범위를 좁힐 수 있지만, 허용된 외부 서비스에서 일으킨 모든 효과까지 되돌려 주지는 않는다.

## 인증 이전 사례가 드러내는 또 다른 경계

**해설:** 인증 코드를 새 API로 바꾸는 데 성공했다는 말과 사용자가 기대한 이전을 완료했다는 말은 다르다. 컴파일 성공은 전자를 일부 확인할 수 있어도 기존 사용자의 세션이 유지되는지까지 자동으로 증명하지 않는다.

이 차이를 실무에 적용한다면, 구현 방법을 길게 지시하기 전에 “무엇을 바꾸고 무엇을 유지할 것인가”부터 정하는 편이 낫다. 다음은 발표에서 제시한 체크리스트가 아니라 그 문제에 대한 자체 적용 예시다.

- 바꿀 것: 인증 요청이 사용하는 API.
- 유지할 것: 이전 과정에서 보존해야 하는 사용자 상태.
- 확인할 것: 새 로그인과 기존 세션을 각각 어떤 검사로 판정할지.
- 멈출 지점: 검사 실패 또는 승인받지 않은 외부 변경이 필요한 순간.

테스트 자체를 만들었다는 보고도 완료 증거와 같지 않다. 어떤 입력으로 실행했고 어떤 결과가 나왔는지를 남겨야 한다. 한편 검사 통과가 곧 요구사항의 완전성을 뜻하지도 않는다. 빠뜨린 요구사항은 테스트에도 없을 수 있다. 사람의 검토를 모든 명령 승인에서 요구사항과 증거의 검토로 옮기더라도, 판단 책임 자체가 사라지는 것은 아니다.

## 읽을 때 구분해야 할 범위

이 글은 발표의 주요 문제와 두 사례를 제한적으로 요약하고 별도 기술 자료로 보완한 해설이다. 전체 녹취의 번역이나 제품 설정 안내서가 아니다. 실제 권한 정책과 샌드박스 범위는 사용하는 버전·환경에서 확인해야 한다. 특히 “샌드박스를 켰다”를 “모든 연동과 외부 효과가 격리됐다”로 읽어서는 안 된다.

공식 자료는 현장 기술 문제 뒤 별도로 녹화한 영상의 기계 전사다. 제품명과 버전 표기의 인식 오류 가능성이 있어 여기서는 불확실한 모델 번호를 옮기지 않았다. 핵심 확인 구간은 지침 정리 03:12, 테스트 실행과 격리 07:15~09:22, 인증 이전과 검증 11:12~13:21이다. [발표자 재녹화 영상](https://www.youtube.com/watch?v=vlfCjWuv4es)
