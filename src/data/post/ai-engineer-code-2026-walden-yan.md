코딩 에이전트가 수정안을 만들었다. 이제 테스트하려고 보니 데이터베이스가 비어 있고 외부 서비스 키가 없으며, 실행 안내는 지난달 화면을 설명한다. 사람은 코드를 검토하기도 전에 환경 복구부터 시작한다. 이 경우 병목은 코드 생성 능력이 아니다. 일을 시작하고 끝내는 데 필요한 조건이 사람의 기억에 남아 있다는 점이다.

Walden Yan의 발표는 이런 관점에서 읽을 만하다. 에이전트의 성능표보다 팀과 작업 환경을 어떻게 바꾸었는지에 주목하면, 자기 팀에서 먼저 고칠 지점도 달라진다.

## 1. 발표의 실제 사례: 고객 영상에서 검증 영상까지

Cognition의 Yan은 같은 기간 병합 PR이 40배, 엔지니어 인원이 2.7배가 되었다고 보고한다. 작은 팀이 고객 문제 전체를 맡고, 오류 영상을 받은 에이전트가 수정 후 동작 영상까지 돌려주는 사례를 설명한다. 숫자와 품질 평가는 회사 자체 보고이며 고객 가치의 인과적 측정은 아니다.

그 아래에는 Docker Compose와 모의 외부 서비스로 단일 VM에 구성한 실행 환경이 있다. 최신 코드 스냅숏을 매시간 만들고 테스트 안내도 유지한다. 실행 기록에서 반복 작업을 찾아 스크립트로 바꾸는 개선도 소개한다. 이후에는 p99 지연시간처럼 지속적으로 측정할 목표를 맡기는 방향으로 확장한다. Android 유지 작업은 발표 당시 아직 출시 전이며, 자율 탐색이 모든 사람의 승인을 없앤다는 주장도 아니다.

## 2. 별도 운영 기록에서 확인되는 준비 작업

Cognition은 2026년 2월 글에서도 작업 전에 코드베이스를 탐색해 목표를 좁히는 과정, 오류 접수 후 관련 코드와 변경 이력을 조사하는 절차, 최근 병합 내용을 살피는 정기 디자인 시스템 점검을 소개했다. 읽기 전용 데이터베이스와 로그를 조사에 활용한다는 설명도 있다. 이는 11월 발표의 수치를 독립 검증한 자료가 아니라, 같은 회사가 다른 시점에 공개한 운영 기록이다. [How Cognition Uses Devin to Build Devin](https://cognition.com/blog/how-cognition-uses-devin-to-build-devin)

여기서 읽을 수 있는 변화는 요청의 입구만 대화형으로 만든 것이 아니라는 점이다. 아래 해설에서는 이 운영 방향을 ‘문제를 푸는 과정’과 ‘다음 문제를 더 쉽게 풀게 만드는 과정’으로 구분한다.

## 3. 해설: 두 종류의 완료를 구별하자

아래는 필자의 해석이다. 사용자 문제를 해결하는 것과, 다음 문제를 더 쉽게 해결할 환경을 남기는 것은 다른 성과다. 수정 코드와 회귀 검사는 전자에 속한다. 반복되던 준비 절차를 줄이는 작업은 후자에 속한다. 후자를 보지 않으면 같은 조사를 반복하면서도 활동량만 늘었다고 만족할 수 있다.

## 4. 기술 배경: 실행 중인 컨테이너와 준비된 서비스는 다르다

Docker 공식 문서는 Compose가 기본적으로 컨테이너의 실행 상태를 기다릴 뿐, 애플리케이션이 요청을 받을 준비가 되었는지까지 기다리는 것은 아니라고 설명한다. 의존 서비스의 준비 상태가 필요하면 healthcheck와 `service_healthy` 같은 조건을 사용한다. [Docker Compose 시작 순서 문서](https://docs.docker.com/compose/how-tos/startup-order/)

이는 발표 사례를 이해할 때도 중요한 경계다. 실행 환경을 하나로 모았다는 사실만으로 검사 준비가 끝난 것은 아니다. 데이터, 계정, 서비스 준비 상태가 맞아야 제품 동작을 확인할 수 있다. 반대로 healthcheck 통과가 전체 업무 흐름의 정확성을 증명하지도 않는다. 준비 상태 검사와 제품 동작 검사는 서로 다른 질문이다.

모의 서비스 또한 실제 외부 서비스와의 호환성을 모두 보장하지 않는다. 빠른 독립 검사와 제한된 통합 검사의 역할을 구분해야 한다. 이 구분은 Docker 문서와 발표 사례를 연결한 필자의 해설이며, Cognition의 검증 범위를 직접 확인한 결과는 아니다.

## 5. 지속 목표는 ‘계속 일하라’와 다르다

필자의 관점에서 장기 작업에는 성공 기준과 함께 중지 기준이 필요하다. 지연시간을 줄이면서 오류율이나 비용을 악화시키지 않았는지, 어느 변경에 사람의 승인이 필요한지 알아야 한다. 모델이 다음 실험을 고를 수 있다는 것과 모든 실험을 허용한다는 것은 다르다.

이 발표를 자기 팀에 가져올 때 먼저 물을 질문은 세 가지다. 작은 수정 하나를 새 환경에서 검증할 수 있는가. 실패했을 때 코드 문제와 환경 문제를 구별할 기록이 있는가. 같은 준비 작업이 반복될 때 다음 실행의 비용을 줄일 담당이 있는가.

에이전트에게 더 긴 지시를 주기 전에 이 조건을 갖추는 편이 중요할 수 있다. 자율성을 높인다는 목표가, 사람이 보이지 않는 준비 작업을 계속 대신해 준다는 뜻이 되어서는 안 된다.

## 출처와 한계

공식 개별 전사와 공식 ZIP 전사를 대조했다. 자동 인식 오류는 남을 수 있다. 발표 요약은 제한된 핵심 사례이며 전체 번역이 아니다. Cognition 글은 당사자 보고, Docker 문서는 별도의 기술 근거다. 해설과 그림은 필자의 재구성이며 실제 도입 실험을 주장하지 않는다.
