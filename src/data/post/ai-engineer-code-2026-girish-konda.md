> AI Engineer CODE 2026 · Girish Konda · 2026년 11월 11일 온라인 트랙

여러 에이전트에게 일을 나눠 주면 서로의 빈틈을 메워 줄 것처럼 보인다. 그러나 모두 같은 잘못된 정보를 읽었다면 결론이 일치하는 것은 놀라운 일이 아니다. 일을 맡긴 뒤 응답이 끊겼을 때도 마찬가지다. 답이 없다는 사실은 아무것도 하지 않았다는 뜻이 아니다.

이 발표가 흥미로운 지점은 이런 문제를 모델의 성격이나 지시문 작성 요령으로만 설명하지 않는다는 데 있다. 작업을 나누고, 공유 상태를 읽고, 외부 시스템을 바꾸는 순간 조정해야 할 문제가 생긴다. 그 조정의 결과가 자연어 문장으로 돌아온다고 해서 문제 자체가 사라지지는 않는다.

## 1. 발표의 사례: 같은 결론이 같은 작업을 뜻하지 않는다

**이 절은 공식 발표 요약이다. 사례마다 실제 프로젝트 경험과 설명용 가정을 구분한다.**

Konda의 설명용 사례에서는 확인하지 않은 ‘오류율 80% 감소’ 문장을 다른 에이전트들이 읽고 반복한다. 세 결과의 일치는 세 관측이 아니라 한 추측의 재사용이다. 또 오류 건수가 줄어도 요청 수까지 줄면 오류율은 그대로일 수 있으므로 조정자가 수치를 다시 계산해야 한다고 설명한다.

실제 mcp-pacemaker 경험에서는 첫 실행 다운로드가 늦어 정상 서버를 고장으로 오인했다. 다른 경우에는 서버가 죽은 뒤 타임아웃이 원래 종료 원인을 덮었다. 따라서 타임아웃은 확정 실패가 아니라 결과를 모르는 상태로 다룬다. PR 생성 후 응답을 잃는 예에서도 무조건 재시도하지 않고 외부 효과부터 확인한다.

또 여러 서버가 동시에 패키지 관리자를 실행하며 공유 캐시 충돌을 일으켰다고 한다. 개별 요청보다 동시 실행 수의 문제였다. SAFE는 출처·버전·시점이 있는 읽기, 최대 한 번의 효과를 지향하는 실행 규율, 제한된 병렬 작업 예산, 명시적 결과 상태를 묶는다. 단일 조정자를 전제로 한 개인 제안이며 진실성·정확히 한 번 실행·자동 복구를 보장하지 않는다. [공식 발표·전사](https://ai.engineer/code/2026/talks/online-subagent-distributed-systems)

**해설:** 여기서 세 문제의 처방은 다르다. 같은 추측을 반복한 답에는 출처 확인이, 응답을 잃은 변경에는 효과 조회가, 캐시 충돌에는 동시 실행 제어가 필요하다. ‘에이전트에게 더 주의하라고 말하기’만으로 해결되지 않는 이유다.

*실제 경험과 설명용 사례를 구분해 재구성한 도식. SAFE 구현 명세가 아니다.*

## 2. 보조 자료: 연결이 살아 있는 것과 일이 복구된 것은 다르다

**이 절은 발표자 측 공개 프로젝트의 별도 설명이다. SAFE 전체를 구현하거나 검증했다는 뜻은 아니다.**

mcp-pacemaker는 에디터나 CLI 수명과 MCP 서버 수명을 분리하는 로컬 브리지다. 공개 README는 클라이언트가 재접속할 때 기록된 세션 ID로 새로운 서버와 다시 연결할 수 있다고 설명한다. 동시에 임의의 도구 상태나 TCP 연결까지 복원하는 것은 아니라고 명시한다.

이 제한은 중요하다. 연결 복구, 작업 상태 복구, 외부 변경의 복구를 하나의 ‘재개’로 뭉뚱그리지 않아야 한다. 해당 저장소는 그중 연결과 프로세스 수명 관리의 근거이며, 모든 에이전트 작업의 안전성을 입증하는 자료는 아니다.

## 3. 해설: ‘하지 못함’과 ‘했는지 모름’을 나눠야 한다

**이 절은 필자의 해석이다.**

결과 전달의 목적은 결론을 더 그럴듯하게 만드는 일이 아니라, 다음 작업이 어떤 전제에서 진행해도 되는지 알리는 일이다. 검사를 하지 못한 경우, 검사 결과가 부정적인 경우, 외부 실행은 시도했지만 효과를 확인하지 못한 경우는 각각 다른 다음 행동을 요구한다.

모든 미완료를 실패 한 가지로 합치면 이미 일어난 변경을 반복할 수 있다. 반대로 모든 부분 결과를 성공으로 합치면 남은 일을 건너뛸 수 있다. 그래서 조정자가 상태와 조사 범위, 근거, 확인된 외부 효과를 별도로 확인하는 편이 낫다. 문장 끝에 불확실하다는 경고만 붙이고 다음 단계를 그대로 실행하면 경계로 작동하지 않는다.

또 병렬 작업 수는 에이전트의 수만으로 정할 수 없다. 서로 다른 작업도 같은 패키지 캐시나 외부 API를 사용할 수 있기 때문이다. 충돌하는 자원 단위로 한도를 두어야 하는지는 실제 실행 경로에서 확인할 문제다. 더 많은 작업자를 만드는 것과 독립된 실행 환경을 만드는 것은 다르다.

## 마무리

이 발표를 읽고 필자가 먼저 바꾸고 싶은 것은 에이전트의 수가 아니라 결과 전달 방식이다. 무엇을 읽었는지, 어디까지 했는지, 외부에 무엇이 생겼는지, 무엇을 모르는지 알 수 있어야 다음 작업을 안전하게 이어 갈 수 있다. 협업은 답변 여러 개를 모으는 일이 아니라, 서로 다른 실행 사이에서 근거와 책임을 잃지 않는 일이다.
