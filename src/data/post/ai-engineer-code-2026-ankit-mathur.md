병렬 에이전트를 늘리는 일은 모델 호출을 늘리는 일만이 아니다. 같은 데이터와 파일을 만지는 작업자들이 서로의 실험을 망치지 않도록 해야 한다. Databricks의 Ankit Mathur는 「The Rise of the Agent Workforce」에서 탐색 능력에 맞는 인프라를 이야기한다.

## 1. 실제 출발점: 고장 난 파이프라인을 어디에서 시험할까

Mathur는 운영 데이터 파이프라인이 고장 난 상황을 든다. 원인을 찾으려고 운영 환경에서 코드를 바꾸고 재실행하면 데이터에 영향을 줄 수 있다. 팀은 테이블·실행 자원·권한을 함께 분기해 에이전트가 다른 가설을 시험하게 했다. 상류 파이프라인을 수정하고 다시 실행하는 조사도 그 격리된 환경에서 시도한다. 단순히 코드를 여러 벌 만드는 문제와 다르다. [발표 2:51:09부터](https://www.youtube.com/watch?v=ZZ19zhYnDKY&t=10269s)

### 작업 기억도 그대로 합치면 안 된다

팀의 기억에는 개별 에이전트가 발견한 내용을 바로 공통 사실로 삼을지라는 문제가 있다. 발표자는 별도 분기에서 기억을 제안하고 검토하는 방향을 설명한다. 또 데이터베이스만 나누고 원래 파일이 따라오지 않으면 조사 맥락을 잃었다고 한다. 변경된 부분만 새로 기록하는 copy-on-write는 이런 분기의 기반이다. 보안 조사에서도 대화·기억·저장을 나눠 가설을 병렬 탐색하며, 조사 대상 서비스의 분기는 가능한 경우에 한정한다. 모든 외부 효과가 자동 격리된다는 뜻은 아니다. [기억 2:55:42부터](https://www.youtube.com/watch?v=ZZ19zhYnDKY&t=10542s) · [파일 2:58:13부터](https://www.youtube.com/watch?v=ZZ19zhYnDKY&t=10693s) · [보안 조사 3:00:43부터](https://www.youtube.com/watch?v=ZZ19zhYnDKY&t=10843s)

**해설:** 이 흐름에는 두 가지 경계가 있다. 실험의 변경이 다른 실험에 영향을 주지 않는 경계, 실험 중 생긴 판단을 팀의 공통 지식으로 받아들이는 경계다. 상태를 복제하는 기능만으로 두 번째 문제가 해결되지는 않는다.

## 여기서부터는 별도 제품 문서로 보는 구현 범위

아래 자료는 앞의 발표 사례 자체를 재현한 기록이 아니다. 공개된 데이터베이스 기능과 개발 예제로, 어떤 부분을 실제로 구성할 수 있고 무엇은 별도 책임인지 확인한다.

## 2. 현재 Lakebase 문서: 공유하는 것은 과거이지 변경 권한이 아니다

Lakebase 브랜치 문서는 생성 시 부모의 데이터와 스키마를 이어받되 기반 저장 공간을 공유한다고 설명한다. 자식에서 바꾼 부분만 새롭게 기록한다. 자식의 변경은 부모에 영향을 주지 않고, 부모의 이후 변경도 자동으로 자식에 나타나지 않는다. 데이터베이스와 Postgres 역할 상태 역시 분기 범위에 들어간다.

여기에는 중요한 비대칭이 있다. 부모의 현재 상태로 자식을 초기화하는 기능과 자식 변경을 부모에 반영하는 일은 다르다. 후자에는 일반적인 마이그레이션 도구가 필요하다. 또한 물리적으로 데이터를 공유한다는 사실이 모든 브랜치가 같은 비용이라는 뜻은 아니다. 현재 문서는 만료되는 브랜치와 영구 브랜치의 저장 요금 기준을 구분한다. 구조의 효율성과 청구 정책은 따로 확인해야 한다. [발표 외 자료: Lakebase 브랜치 문서](https://docs.databricks.com/aws/en/oltp/projects/branches)

## 3. 별도의 실제 구현 예: 코드 작업 폴더와 데이터 브랜치를 짝짓기

10월에 공개된 개발 워크플로는 발표의 주제를 구체적인 구성으로 보여 준다. Git worktree로 코드 디렉터리를 나누고, 체크아웃 훅으로 에이전트마다 데이터베이스 브랜치를 만든다. PR을 열면 별도의 임시 브랜치에 마이그레이션을 적용하고 미리보기 앱을 연결하며 스키마 차이를 검토한다.

중요한 점은 임시 데이터베이스 전체를 운영에 합치는 방식이 아니라는 것이다. 코드와 마이그레이션 지시를 승격하고 시험 브랜치는 정리한다. 문서는 민감한 운영 정보를 그대로 복제하지 않도록 미리 준비한 데이터에서 시작하는 선택도 설명한다. 이 사례는 파일 전체와 모든 외부 시스템을 자동 복제하는 완성형 탐색 환경이 아니라, 코드와 데이터베이스를 함께 격리하는 개발 예제다. [발표 외 자료: 코딩 에이전트와 Lakebase](https://www.databricks.com/blog/lakebase-and-agentic-sdlc-branching-databases-coding-agents)

## 4. 임시 환경의 종료도 설계에 들어간다

브랜치 관리 문서는 자동 만료를 제공한다. 만료 시 연결된 데이터와 계산 자원이 삭제되므로, 검토에 필요한 결과를 남기는 일과 임시 실행 환경을 정리하는 일은 구분해야 한다. 이것은 현재 데이터베이스 기능 설명이며, 발표의 모든 파일·기억이 같은 수명으로 관리된다는 뜻은 아니다. [발표 외 자료: 브랜치 관리](https://docs.databricks.com/aws/en/oltp/projects/manage-branches)

> **이 글의 해석:** 좋은 분기는 두 질문에 답한다. “무엇이 같은 출발점을 공유하는가?”와 “무엇이 아직 공유돼 있어 실험 밖에 영향을 주는가?”다. 데이터베이스를 분기했어도 공용 파일, 외부 API, 메시지 전송은 별도 경계다. 여러 가설을 안전하게 비교한다는 목적은 복제 기능 하나가 아니라 이 경계를 정확히 그릴 때 달성된다.

## 범위와 한계

공식 기계 전사와 Databricks의 기술 글·현재 문서를 확인했다. 발표의 비전, 공개 예제, 현재 제품 기능을 구분했으며 전체 영상 대조나 실환경 실행은 하지 않았다. 전사 인식 오류가 남아 있고, 공급자의 구조 설명이 독립적인 성능·보안 검증을 대신하지 않는다.
