## 첫 결과가 빨리 생길수록, 첫 결과를 의심해야 한다

Ishaan Dey의 「Judgement is the last job」는 제품을 빨리 만들 수 있게 됐을 때 판단이 어디에 남는지 묻는다. Antigravity 개발 경험을 바탕으로, 여러 방향을 실제로 만들어 보고 배울 기회가 커졌지만 먼저 나온 그럴듯한 결과를 그대로 받아들이기 쉬워졌다고 지적한다. [공식 발표](https://ai.engineer/code/2026/talks/ishaan-dey)

발표의 제품 판단은 추상적인 취향론에 머물지 않는다. 요청을 언제 에이전트에게 전달할지, 사용자가 만든 확장 기능을 어디까지 제품에 반영할지, 여러 작업을 관리하는 화면에 어떤 정보를 남길지가 사례다. 이 글은 그 세 질문을 중심으로 읽고, Antigravity의 공개 개발 기록으로 배경을 보충한다.

## 1. 예전 모델을 위해 만든 대기열이 아직 필요한가

발표에서 Dey는 모델 능력의 변화에 따라 제품의 제약을 재검토한다. 짧은 지시를 차례대로 처리하던 환경에서는 입력을 대기열에 넣는 방식이 자연스러울 수 있다. 그러나 더 긴 작업과 비동기 사건을 다루는 에이전트에게는 사용자의 의도를 지금 전달하고, 위임하거나 나중으로 미루는 판단을 맡기는 방식도 생각할 수 있다. [발표 전사, 06:14:30 전후](https://www.youtube.com/watch?v=y9JtCCZP2MQ&t=22470s)

**이 글의 해석:** 여기서 대기열을 없애라는 일반 규칙을 읽어서는 안 된다. 사용자의 의도를 전달하는 시점과 실제 행동을 실행하는 시점은 다르다. 지금 새 요청을 알게 하는 것과 지금 모든 작업을 중단시키는 것은 동일하지 않다. 중요한 질문은 기존 인터페이스의 제한이 여전히 사용자를 보호하는지, 아니면 과거 모델의 한계만 보존하는지다.

이 질문에는 반대 방향의 위험도 있다. 아직 안정적으로 수행하지 못하는 능력을 전제로 인터페이스를 만들면 사용자는 모델의 실패를 떠안는다. 제품 팀은 미래가 어떻게 될지 예상하는 일과, 현재 무엇을 안전하게 맡길 수 있는지 확인하는 일을 분리해야 한다. 이는 발표의 문제의식에서 도출한 해설이지, 특정 작업에 대한 권한이나 승인 절차를 없애자는 제안이 아니다.

## 2. 별도 팀 실험: 자율성 뒤의 조율 구조

발표의 협업 기능을 이해하는 보충 자료로 Antigravity 팀의 운영체제 제작 기록을 볼 수 있다. 팀은 FreeDoom을 실행하는 최소한의 운영체제를 에이전트들이 만들었다고 보고했다. 그러나 현대 운영체제와 같은 완성도는 아니며, 여러 기능과 품질상의 한계를 직접 열거했다. 높은 수준의 요청이 짧았다는 사실도 전체 구성이 단순했다는 뜻은 아니었다. 팀은 역할과 조율에 상당한 설정이 필요했다고 설명한다. [Antigravity 팀의 실험 기록](https://antigravity.google/blog/google-antigravity-built-an-os)

그 구성에는 요구를 정리하는 역할, 작업을 분해하고 배정하는 역할, 구현자, 리뷰어, 결함을 찾는 역할이 나뉘어 있었다. 오래된 진행 상태를 감지해 멈춘 작업을 다시 시작하고, 문맥이 차면 인계 파일로 후속 에이전트가 이어받게 하는 장치도 있었다. 첫 시도에서 이전 실행 기록을 참고한 문제가 발견되어 통제를 추가했다는 설명도 포함된다. [같은 기록의 구성과 시행착오](https://antigravity.google/blog/google-antigravity-built-an-os)

이것은 CODE 발표의 모든 시연을 검증하는 자료가 아니라, 앞서 공개된 팀 협업 실험의 배경이다. 결과를 독립적으로 재현한 자료도 아니다.

**이 글의 해석:** 사용자가 접하는 요청 창이 단순해져도 내부의 조율 문제가 없어지는 것은 아니다. 겉으로는 한 번의 지시였더라도 상태 유지, 정지 감지, 결과 검토가 따로 있을 수 있다. 따라서 모델이 좋아졌으니 모든 조율을 제거할 수 있다는 결론과, 모델이 좋아졌으니 사람이 보던 조율의 일부를 시스템이 맡을 수 있다는 결론을 구분해야 한다.

## 3. 확장 기능은 사용법을 발견하는 장소가 된다

Dey는 개인 대시보드, 팀의 데모 협업 도구, 과학 분야 플러그인처럼 사용자가 제품 위에 만든 사례를 소개한다. 에이전트 군집 기능도 플러그인에서 시작해 더 중심적인 기능으로 발전했다고 말한다. 확장 기능을 추가 기능 목록이 아니라 새로운 작업 방식을 발견하는 통로로 보는 대목이다. [공식 발표의 확장성 구간](https://www.youtube.com/watch?v=y9JtCCZP2MQ&t=22528s)

**이 글의 해석:** 제품 팀이 사용자의 모든 작업을 미리 설계하기는 어렵다. 확장할 수 있는 공간을 두면 사용자는 자기 업무의 구체적인 문제를 먼저 풀어볼 수 있다. 그렇다고 인기 있는 확장 기능을 모두 기본 화면에 넣으면 제품은 다시 복잡해진다. 어떤 요구가 반복되는지, 그 요구가 특정 팀의 사정인지, 더 많은 사용자에게도 같은 형태로 유용한지 판단하는 단계가 남는다.

이 문단은 사례에서 얻은 제품 설계 해석이다. 플러그인이 만들어졌다는 사실만으로 일반 사용자에게도 같은 효과가 검증된 것은 아니다.

## 4. 관리 화면의 개선은 로그를 더 넣는 일이 아닐 수 있다

발표의 마지막 사례는 에이전트 관리 화면이다. ‘더 좋게’ 만들어 달라고 하면 차트와 색상, 제어 항목, 도구 호출 정보가 늘어날 수 있다. Dey는 여러 에이전트를 보는 사용자가 당장 알아야 할 의미 있는 상태를 간결하게 전달하는 방향을 제시한다. [발표 전사, 06:17:35 이후](https://www.youtube.com/watch?v=y9JtCCZP2MQ&t=22655s)

이 방향은 초기 제품 소개의 설명과도 연결된다. Antigravity 팀은 모든 도구 호출을 보여 주는 방식과 설명 없이 최종 코드 변경만 보여 주는 방식의 양극단을 지적했다. 대신 작업 단위의 진행 상태와 계획, 스크린샷, 브라우저 녹화 같은 산출물을 통해 사용자가 내용을 확인하도록 설계했다고 밝혔다. 텍스트나 이미지의 해당 부분에 피드백을 남기는 방식도 설명했다. [초기 제품 소개의 신뢰와 피드백 설계](https://antigravity.google/blog/introducing-google-antigravity)

공식 Artifacts 문서는 이런 산출물을 에이전트의 작업과 진행을 전달하는 구조화된 결과물로 설명한다. 사용자는 모든 도구 호출을 실시간으로 따라가는 대신 중요한 단계에서 계획과 변경을 검토하고, 필요한 경우 구체적인 피드백으로 방향을 바꿀 수 있다. [Artifacts 공식 문서](https://antigravity.google/docs/artifacts)

**이 글의 해석:** 이 사례에서 ‘덜 보여 준다’는 말은 근거를 없앤다는 뜻이어서는 안 된다. 우선순위를 정해서 현재 판단에 필요한 내용을 먼저 보여 주고, 더 알아야 할 때 증거로 내려갈 수 있게 만드는 것이다. 요약만 있고 결과물이 없으면 검증이 어렵다. 반대로 로그만 있으면 지금 무엇을 결정해야 하는지 찾는 일이 사용자의 몫이 된다.

## 빨리 만드는 능력을 어디에 쓸 것인가

**이 글의 결론:** 첫 번째 시안이 빨리 생겼다면, 절약한 시간을 더 많은 장식에 쓸 수도 있고 서로 다른 방향을 비교하는 데 쓸 수도 있다. Dey의 발표는 후자를 지향한다. 이전 모델 때문에 생긴 제한을 재검토하고, 사용자 확장에서 새 사용법을 배우고, 관리 화면이 실제로 판단을 쉽게 만드는지 살핀다.

제품 판단은 기능을 추가하는 순간에만 필요하지 않다. 무엇을 삭제할지, 무엇을 기본값으로 만들지, 무엇을 상세 화면으로 옮길지를 결정할 때도 필요하다. 생산이 쉬워졌다는 사실은 그 선택을 대신해 주지 않는다.

### 자료와 해석의 범위

공식 기계 생성 전사와 Google의 제품 소개·실험 기록·공식 문서를 확인했다. 발표의 제안을 보편적으로 검증된 UX 원칙으로 확대하지 않았으며, 별도 운영체제 실험을 상용 수준의 운영체제 완성으로 표현하지 않았다. 제품 문서에는 발표 이후 변경이 반영될 수 있어 현재 기능 안내가 아니라 개념을 확인하는 보충 자료로 사용했다. 직접 인용 없이 출처별 요약과 필자의 해석을 분리했다.
