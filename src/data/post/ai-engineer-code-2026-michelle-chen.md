## 처음의 인프라 가설이 다시 의미를 얻기까지

**발표 요약:** Michelle Chen의 *cloudflare is a neolab*는 Cloudflare가 왜 모델을 직접 만들게 됐는지 설명한다. 분산 인프라에 작은 모델을 놓으면 네트워크 지연의 중요성이 커질 것이라는 초기 가설이 있었다. 그러나 시장은 큰 모델로 향했고, 회사도 이를 제공하는 방향으로 확장했다. 이후 빠른 결정·추출 모델이 등장하면서 원래 인프라의 강점을 활용할 여지가 다시 생겼다.

시연은 CI 빌드 실패를 조사하는 에이전트다. 40개 도구를 매번 LLM에 전달하는 대신 Clef가 후보를 줄이고, Clairic이 PR 번호와 로그의 오류·관련 위치를 추출한다. 코드는 API를 실행하고 큰 LLM은 남은 판단과 작업을 맡는다. 모든 단계에 큰 모델을 호출하는 흐름과 비교해 왕복과 문맥을 줄이려는 구성이다.

발표자는 이를 LLM 대체가 아니라 보완으로 설명한다. 시연의 호출 수와 시간 비교는 예시이며 일반적인 품질 동등성을 입증하는 평가가 아니다. [공식 발표·전사](https://ai.engineer/code/2026/talks/michelle-chen)

## 추출과 결정은 같은 작업이 아니다

**보충 자료: Clef.** 공식 출시 문서에서 Clef는 입력 상태와 타입이 정해진 질문을 받아 허용된 답의 확률을 반환하는 결정 모델이다. 정해진 선택지 중 고르기, 예·아니오, 순서가 있는 평가 기준 등이 대상이다. 자유 문장을 생성한 뒤 다시 파싱하는 방식과 구분된다. 회사가 공개한 속도 비교는 해당 평가 조건의 자체 결과다. [Cloudflare Clef 출시 문서](https://developers.cloudflare.com/changelog/post/2026-10-01-clef-workers-ai/)

**보충 자료: Clairic.** 공식 설명은 문서에서 값을 추출하는 일과 값의 추정·계산을 함께 다룬다. 타입이 있는 값, 원문 구간, 누락 가능성, 신뢰도 등을 반환하도록 설계됐다. 예시 고객 이메일에서는 금액과 세금을 더하고 날짜 차이를 계산하며, 존재하지 않는 추적 번호에는 `null`을 반환한다. 추정은 단일 숫자뿐 아니라 구간으로 표현할 수 있다. 이는 공급자의 기능 설명과 예시이며 모든 실제 입력에서 정확하다는 뜻은 아니다. [Cloudflare Clairic 소개](https://blog.cloudflare.com/clairic-extraction-model/)

![추출, 선택, 개방형 추론을 나누고 검증 경계를 표시한 자체 도식](/images/ai-engineer-code-2026/michelle-chen-routing.svg)

*발표와 제품 문서를 바탕으로 재구성한 역할 비교다. 제품별 성능 우열을 나타내지 않는다.*

## 시연에서 줄인 것은 모델의 크기만이 아니다

**해설:** 이 흐름은 같은 질문에 작은 모델을 대신 호출하는 방법과 다르다. 도구 선택, 입력값 추출, API 실행, 결과 해석을 서로 다른 작업으로 본다. PR 번호를 이미 얻었다면 API 호출을 결정적인 코드로 처리할 수 있다. 로그에서 좁힌 근거는 최종 판단을 담당하는 모델에 전달한다. 각 단계가 다음 단계에 넘기는 정보가 무엇인지 정해져야 가능한 분업이다.

따라서 속도의 원인을 하나로 환원해서는 안 된다. 가벼운 호출의 응답 시간, 큰 모델을 오가는 횟수, 뒤 단계가 읽어야 할 문맥의 양이 동시에 달라진다. 시연에서 전체 시간이 줄었다고 해서 각각의 기여도를 알 수 있는 것은 아니다. 어느 요인이 효과를 냈는지 확인하려면 나머지 조건을 고정한 비교가 필요하다.

반대로 추출 단계에서 관련 로그를 버리면 뒤의 모델은 빠르게 잘못된 답에 도달할 수 있다. 자체 적용이라면 추출 결과와 원본 로그의 연결을 남기고, 근거가 부족할 때 원본을 다시 읽는 경로를 두겠다. 문맥을 줄인다는 목표와 증거를 잃지 않는다는 목표를 함께 다루는 것이다. 이 검증 경로는 발표에서 확인한 구현이 아니라 이 글의 제안이다.

## 형식이 맞는 답과 내용이 맞는 답

**해설:** 정해진 타입의 값을 받으면 후속 프로그램이 다루기 쉬워진다. 그러나 유효한 숫자라고 해서 올바른 금액인 것은 아니며, 허용된 선택지라고 해서 적합한 선택인 것도 아니다. 스키마는 표현의 범위를 제한하고 정답 검증은 내용의 타당성을 확인한다.

이 때문에 확신이 낮거나 입력에 값이 없을 때의 경로가 중요하다. 없는 필드를 억지로 채우지 않고 보류할 수 있어야 한다. 또한 원문에서 직접 읽은 값과 모델이 계산하거나 추정한 값은 구분해 전달해야 한다. 같은 숫자로 표현되더라도 근거의 종류가 다르기 때문이다.

## 도구를 먼저 줄이는 설계에 남는 위험

**해설:** 앞 단계가 도구 후보를 잘 고르면 뒤 단계의 비용을 줄일 수 있다. 반대로 꼭 필요한 도구를 제외하면 큰 모델은 잘못된 선택 범위 안에서만 일하게 된다. 빠른 분류기의 정확도는 최종 결과와 별개가 아니라 그 결과의 조건이다.

따라서 이 방식을 평가한다면 빠른 모델의 평균 지연만 재는 것으로 부족하다. 전체 작업의 완료 시간, 잘못 제외한 후보, 보류·재시도 비율, 최종 성공률을 함께 봐야 한다. 무엇을 잘못 선택했을 때 다시 돌아갈 수 있는지도 확인해야 한다. 이는 발표에 나온 벤치마크 절차가 아니라 구조를 적용할 때의 검증 제안이다.

대규모 모델을 더 적게 부른다는 사실만으로 비용이 줄었다고 결론 내리지도 않는다. 추가 모델 호출과 네트워크, 오류 복구가 새 비용이 된다. 중요한 비교는 같은 성공 조건을 만족하는 전체 흐름이다.

## 출처와 표현상의 주의

공식 발표 페이지와 기계 전사에는 제품명 표기가 흔들린다. 이 글은 Cloudflare 제품 원문을 기준으로 **Clef**, **Clairic**을 사용했다. 핵심 구간은 초기 가설 00:44:35~00:46:36, 작은 모델의 재등장 00:48:02 이후, 개발 작업 시연 00:54:00~00:57:54다. 시간은 전체 중계 기준이다.

System One과 System Two는 이 발표와 제품 문서가 역할을 설명하는 표현이다. 인간의 사고 과정을 동일하게 구현했다는 검증으로 읽지 않는다. 전체 번역 대신 제한적 요약과 별도 제품 자료, 해설을 구분했으며 시연 결과를 독립 재현하지 않았다. 특히 현장 설명과 사전 실행 설명에서 LLM 호출 수가 다르게 언급되므로 단일한 확정 벤치마크로 합치지 않았다.
