대표가 코딩 에이전트를 쓰기로 결정하면 회사도 바로 달라질까. Quinn Slack의 발표는 권한이 있어도 조직 변화는 간단하지 않았다는 경험에서 출발한다. 기존 고객과 역할, 일하는 방식이 이미 다른 제품을 중심으로 짜여 있었기 때문이다.

## 1. 발표: 채용할 수 없었던 팀이 일하는 방식을 바꾸다

Slack은 Sourcegraph 안에서 Amp 팀을 만들었지만, 대표 권한만으로 기존 조직을 바꾸기는 어려웠다고 설명한다. 분사 과정에서는 약 1년 동안 채용과 주식 보상에 제약이 생겨 21명이 다른 방식으로 일해야 했다. 작은 팀은 목표인 동시에 주어진 조건이었다.

그들은 필수 PR 단계를 없애고 에이전트 스레드 안에서 협업했다. 잦은 배포의 위험은 작은 변경부터 관찰하는 방식으로 다뤘다. 먼저 로그를 넣어 이해가 맞는지 확인하고, 구·신 시스템의 결과를 나란히 비교한 뒤 다음 변경으로 넘어간다. 고객 문제도 수정에서 끝내지 않고 영향받은 다른 사용자를 찾아 알리는 순환으로 이어 간다.

발표의 논리는 ‘리뷰를 지우면 빨라진다’보다 넓다. 조직의 전달 단계, 작업 도구, 고객 피드백을 함께 바꿨다는 경험담이다. 소규모 팀의 경험이지 다른 조직에서도 같은 결과를 보장하는 비교 실험은 아니다. [공식 발표](https://ai.engineer/code/2026/talks/quinn-slack), [조직 제약 08:01:21](https://www.youtube.com/watch?v=y9JtCCZP2MQ&t=28881s), [관찰하며 배포하기 08:04:07](https://www.youtube.com/watch?v=y9JtCCZP2MQ&t=29047s)

## 2. 별도 1차 자료: PR 대신 남긴 통제는 무엇인가

Amp의 Will Dollman은 2026년 8월 글에서 주 브랜치 직접 반영을 별도로 설명했다. 반영 권한을 업무에 맞게 제한하고, 서명된 커밋을 요구하며, 자동 검사와 커밋부터 배포까지의 기록을 남긴다고 한다. 커밋은 작업한 Amp 스레드와 연결된다. 따라서 주 브랜치 사용은 이 글에서 확인한 사실이며, 발표 전사만으로 추정한 내용이 아니다.

이 자료가 중요한 이유는 검토 단계 하나를 빼는 것과 다른 통제 수단을 설계하는 것이 다르기 때문이다. 저자는 작은 고신뢰 팀의 방식을 큰 조직 전체에 그대로 적용하라고 주장하지 않는다. 이는 회사가 공개한 운영 설명이며, 이 글이 감사 결과나 현재 준수 상태를 독립적으로 확인했다는 뜻도 아니다. [발표 외 자료: Amp의 변경 통제](https://ampcode.com/notes/thats-not-soc-2-compliant)

Amp의 현재 운영 원칙은 변경 전에 기존 방식을 이해하고, 검증·되돌리기가 가능한 작은 단위로 반영하며, 반영한 사람이 결과를 책임지는 방향을 제시한다. 고객에게 왜 필요한지 먼저 설명하고 실제로 사용하며 고친다는 원칙도 포함된다. 이런 공개 원칙은 발표를 이해할 보충 자료이지 조직 전체가 매번 그대로 행동한다는 외부 검증은 아니다. [발표 외 자료: How We Build](https://ampcode.com/how-we-build)

## 3. 기술 배경: 코드를 배포하는 것과 기능을 켜는 것은 다르다

Pete Hodgson의 Feature Toggles 글은 기능 플래그로 실행 경로를 선택하는 방법을 설명한다. 내부 사용자나 일부 사용자에게 먼저 새 기능을 켜고 결과를 관찰할 수 있다. 동시에 플래그는 검사 조합과 유지 복잡성을 늘리므로 수와 수명을 관리해야 한다고 지적한다. [Feature Toggles](https://martinfowler.com/articles/feature-toggles.html)

이 자료는 Amp의 내부 구현을 확인하는 근거가 아니다. 배포가 반드시 모든 사용자에게 한꺼번에 새 동작을 노출하는 사건일 필요는 없다는 기술적 배경이다. 두 과정을 분리하면 ‘배포 빈도가 높다’는 표현도 좀 더 정확히 읽을 수 있다.

## 4. 해설: 짧은 피드백이 성립하려면 누군가 결과를 봐야 한다

여기부터는 필자의 해석이다. 배포 횟수가 많다는 것만으로 학습 속도가 빠르다고 말하기 어렵다. 바뀐 결과를 관찰하지 않거나 여러 변경을 한꺼번에 섞어 원인을 구별하지 못한다면, 반복은 늘어도 이해는 늘지 않는다.

작은 변경은 관찰 가능한 질문과 연결될 때 유용하다. 어떤 가정이 맞는지 확인하고, 결과가 나쁘면 다음 단계를 멈출 수 있어야 한다. 로그가 있다는 사실보다 필요한 질문에 답할 로그가 있는지가 중요하다.

관찰에도 비용과 위험이 있다. 기록에 민감한 정보를 남기지 않는지, 실제 사용자를 대상으로 한 변화가 되돌릴 수 있는지 검토해야 한다. 배포 속도를 위해 이런 검토를 없애면 빠른 실험이 아니라 빠른 위험 확대가 될 수 있다.

## 5. 해설: 넓은 책임과 무제한 권한은 다르다

고객 문제를 처음부터 끝까지 맡는 방식은 부서 사이의 전달을 줄일 수 있다. 그러나 누가 무엇을 결정할 권한이 있는지는 여전히 중요하다. 문제의 원인을 조사하는 권한, 제품을 바꾸는 권한, 고객에게 보상하는 권한은 같지 않다.

에이전트가 여러 단계를 수행할 수 있다고 해서 모든 단계를 자동 승인할 필요는 없다. 작업의 맥락을 이어 주되, 결과가 중요한 결정 앞에는 적절한 승인 지점을 남길 수 있다. 자율성과 책임의 연결은 경계가 없다는 뜻이 아니다.

따라서 이 발표를 도입 지침으로 읽기보다 조직을 점검하는 질문으로 읽는 편이 낫다. 지금의 대기 단계는 어떤 위험을 줄이기 위해 존재하는가. 그 목적을 더 빠른 다른 방식으로 충족할 수 있는가. 없앴을 때 누가 결과를 알아차리고 책임질 것인가.

이 질문 없이 리뷰 단계만 제거하면 발표에서 강조하는 짧은 학습 순환은 남지 않고, 통제만 사라질 수 있다.

## 출처와 한계

공식 웹·ZIP 전사를 대조했다. 자동 인식 오류는 남을 수 있다. 운영 방식은 발표자의 경험이며 비교 실험으로 검증하지 않았다. 기능 플래그 자료는 별도의 기술 해설이고 Amp의 사용 여부를 주장하지 않는다. 마지막 두 절은 필자의 해석이며 그림은 발표의 관찰 순환을 단순화했다. 별도 회사 자료는 현재 확인한 공개 설명이다.
