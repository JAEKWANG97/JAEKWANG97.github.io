## 1. 사람보다 빠른 것과 기다릴 만한 것은 다르다

Natalie Serrino의 **What will you build when AI is 10× faster?**는 슬라이드를 고치는 에이전트에서 시작한다. 결과는 유용하지만 한 차례 수정에 약 2분이 걸린다. 사람의 노동을 줄여도 사용자의 생각이 이어지는 속도에는 못 미칠 수 있다는 문제다.

이어 느린 접속 환경의 이메일과 Token Mint Factory 게임을 보여준다. 게임의 목표는 빠른 개별 응답, 높은 총생산량, 정해진 시간 안의 생산량으로 달라진다. 같은 자원도 목표에 따라 운영 방식이 달라진다.

해결 방향으로는 모델의 작업을 서로 다른 가속기에 나누는 Gimlet의 접근을 소개한다. 장치 간 이동 비용보다 작업 배치의 이득이 커야 한다. 마지막에는 추론을 빠르게 만들수록 도구 호출이 새로운 병목으로 드러난다는 점을 짚는다. 속도를 평가할 단위는 토큰 하나를 넘어 사용자가 결과를 확인하고 다음 수정을 시작하는 전체 과정이다.

이것이 발표의 논리다. 아래에서는 이 흐름을 이해하는 데 필요한 성능 개념을 별도 자료와 계산으로 풀어본다. **발표 요약, 보충 자료, 필자의 해설을 구분했으며 전체 녹취의 번역은 아니다.** [공식 발표·전사](https://ai.engineer/code/2026/talks/natalie-serrino)

## 2. 응답시간은 화면의 사용 방법을 바꾼다

**보충 자료:** Jakob Nielsen의 응답시간 지침은 약 0.1초를 즉각적인 반응, 약 1초를 생각의 흐름을 유지할 수 있는 구간, 약 10초를 대화에 주의를 유지하는 구간으로 설명한다. 더 오래 걸리는 작업에는 진행 상태를 알려야 한다. 이 값들은 모든 작업에 적용하는 SLA가 아니라 인터랙션 설계의 참고 기준이다. [NN/G: Response Times](https://www.nngroup.com/articles/response-times-3-important-limits/)

**해설:** 여기서 AI 기능을 두 종류로 나누면 차이가 선명해진다.

- **함께 수정하는 기능:** 사용자가 문장을 바꾸고, 결과를 보고, 다시 고친다. 한 번의 대기가 짧아야 여러 번 시도할 수 있다.
- **맡겨 두는 기능:** 사용자가 큰 작업을 넘기고 다른 일을 한다. 짧은 응답보다 완료 알림, 취소, 중간 방향 변경이 중요할 수 있다.

같은 30초라도 두 기능에서 의미가 다르다. 전자에서는 매번 생각을 끊는 시간이 된다. 후자에서는 충분히 받아들일 수 있는 처리 시간일 수 있다. 따라서 “사람이 직접 하면 10분인데 AI는 30초”라는 비교만으로 UX가 좋아졌다고 판단하기 어렵다. 사용자가 기다리는 동안 무엇을 해야 하는지도 설계해야 한다.

## 3. 처리량과 지연시간은 서로 다른 질문이다

**해설:** 처리량은 일정 시간 동안 얼마나 많은 일을 끝냈는가를 묻는다. 지연시간은 요청 하나가 얼마나 오래 걸렸는가를 묻는다. 서버 전체가 바쁘게 일한다는 사실만으로 사용자 한 명의 대기가 짧아지는 것은 아니다.

가상의 서비스가 요청 열 개를 모아서 처리한다고 하자. 묶어서 처리하면 자원을 효율적으로 쓸 수 있다. 하지만 첫 번째 요청은 나머지 요청이 모일 때까지 기다린다. 총처리량이 좋아지면서 일부 요청의 응답은 느려질 수 있다. 반대로 들어온 요청을 즉시 처리하면 대기는 줄어도 자원을 충분히 묶어 쓰지 못할 수 있다.

팀이 결정해야 할 것은 추상적인 “최고 성능”이 아니라 **어떤 조건에서 무엇을 최적화할 것인가**다.

| 서비스의 목적 | 먼저 볼 지표 | 함께 지켜야 할 조건 |
| --- | --- | --- |
| 사용자가 결과를 보며 연속 수정 | 요청별 완료 시간, 긴 대기의 비율 | 정답률·비용·취소 가능 여부 |
| 밤새 대량 문서 처리 | 시간당 완료 문서 수 | 아침 마감 시각·재처리율 |
| 고객 문의 자동 분류 | 제한시간 내 처리 비율 | 오분류율·보류 처리 경로 |

이 표는 발표의 게임을 그대로 옮긴 것이 아니라 서비스 목표를 정하기 위한 자체 예시다. 세 경우 모두 “평균 토큰 생성 속도”만으로는 성공 여부를 정할 수 없다. 특히 평균이 좋아져도 일부 사용자의 긴 대기가 늘었다면 대화형 제품에는 퇴보일 수 있다.

## 4. 하드웨어를 섞는다는 것은 작업의 성질을 나눈다는 뜻이다

**보충 자료:** Gimlet의 Cerebras 협업 글은 GPU 중심 시스템의 총처리량과 개별 사용자 응답속도 사이에 타협이 있다고 설명한다. Cerebras의 대용량 온칩 SRAM과 메모리 대역폭을 토큰 생성처럼 메모리 집약적인 작업에 활용하고, 서로 다른 가속기의 강점을 결합하겠다는 접근이다. 이는 공급자가 설명한 설계 방향과 성능 주장이지 이 글에서 재현한 비교 실험은 아니다. [Gimlet의 이기종 추론 설명](https://gimletlabs.ai/blog/cerebras-announcement)

**해설:** “GPU보다 좋은 장치를 찾는다”로만 이해하면 중요한 조건을 놓친다. 한 작업의 여러 단계가 같은 자원을 같은 방식으로 쓰는지부터 봐야 한다. 계산이 많은 단계와 데이터를 자주 읽는 단계는 서로 다른 제약을 가질 수 있다.

다만 작업을 나눈 순간 비용도 생긴다. 결과를 다음 장치로 보내고, 두 단계의 실행 순서를 맞추고, 중간 데이터를 보관해야 한다. 앞 단계가 너무 빨라지면 뒤 단계의 대기열이 늘어날 수도 있다. 따라서 비교 대상은 각 장치의 최고 속도가 아니라 **전송과 대기를 포함한 전체 완료 시간**이다.

## 5. 추론 10배 개선이 전체 작업에 미치는 영향

**해설·자체 계산:** 다음 수치는 원본 시연의 측정값이 아니다. 병목 이동을 설명하기 위해 전체 100초 중 추론이 80초, 도구가 20초인 직렬 작업을 가정한다. 두 부분의 겹침은 없고, 작업량과 도구 성능은 바뀌지 않는다고 둔다.

추론만 10배 빨라지면 다음과 같다.

```text
기존:      추론 80초 + 도구 20초 = 100초
추론 개선: 추론  8초 + 도구 20초 =  28초
전체 개선 배수: 100 ÷ 28 ≈ 3.57배
도구 시간 비중: 20 ÷ 28 ≈ 71.4%
```

추론은 10배 빨라졌지만 전체 작업은 약 3.57배 빨라진다. 이제 도구가 대부분의 시간을 차지한다. 처음에는 추론이 문제였고, 개선 뒤에는 도구가 문제다. 어느 쪽이 “진짜 병목”인지 영구적으로 정할 수 없는 이유다.

![추론과 도구의 시간을 같은 눈금으로 비교한 자체 계산 예제](/images/ai-engineer-code-2026/natalie-serrino-bottleneck.svg)

*모든 막대는 동일한 시간 눈금을 사용한다. 발표 자료를 복제한 그림이 아니라 위 가정으로 계산한 설명용 도식이다.*

같은 가정에서 추론 시간을 0초로 줄여도 도구의 20초는 남는다. 전체 개선의 상한은 5배다. 이 수치는 모델 기술의 한계가 아니라 **이 예제에서 바꾸지 않은 작업이 만든 한계**다. 도구도 개선하거나 실행 구조를 바꾸면 상한은 다시 달라진다.

일반식으로 표현하면 다음과 같다.

```text
개선 후 시간 = 개선하지 않은 시간 + 개선 대상 시간 ÷ 개선 배수
```

이 계산은 순차 실행이라는 가정을 가진다. 실제 서비스에서 일부 작업이 겹쳐 실행된다면 단순 합계 대신 완료까지 이어지는 가장 긴 의존 경로를 봐야 한다. 요청 로그에 각 단계의 시작·종료와 선행 조건을 남겨야 이 차이를 구별할 수 있다.

## 6. 에이전트는 요청 하나보다 긴 실행 단위를 가진다

**보충 자료:** Gimlet·UIUC·Intel 연구를 소개한 글은 에이전트를 독립적인 모델 요청들의 묶음으로만 보면 놓치는 것이 있다고 설명한다. 작업마다 모델 호출 횟수와 누적 문맥 크기가 달라진다. 기존 문맥의 KV 캐시가 유지되면 앞부분의 재계산을 줄일 수 있지만, 동시 작업으로 메모리 압박이 생겨 캐시가 밀려나면 그 이점이 줄어든다. 연구의 측정 조건을 벗어난 모든 서비스에 같은 비율이 적용된다는 뜻은 아니다. [Inside Agentic AI Workloads](https://gimletlabs.ai/blog/inside-agentic-ai-workloads)

**해설:** 사용자가 보는 것은 여러 호출이 이어진 하나의 작업이다. 첫 호출이 빨라도 뒤에서 탐색을 반복하거나 같은 파일을 다시 읽으면 최종 완료는 늦어진다. 모델의 한 번 응답 성능과 에이전트가 작업을 끝내는 효율은 분리해서 측정해야 한다.

## 정리: 빨라진 뒤에 가능해지는 작업까지 생각한다

이 발표가 흥미로운 이유는 속도를 인프라 숫자에만 가두지 않기 때문이다. 대기가 줄면 사용자가 시도할 수 있는 수정 횟수가 달라진다. 작업을 맡겨 놓는 인터페이스를 함께 편집하는 인터페이스로 바꿀 여지도 생긴다.

다만 그 가능성을 판단하려면 경계를 분명히 해야 한다. 개별 요청의 지연시간과 시스템 처리량을 구분한다. 추론과 도구 호출을 구분한다. 한 호출의 속도와 전체 과제의 완료 시간을 구분한다. 그리고 최적화가 끝났다고 생각한 시점에 다시 측정한다.

**현재의 가장 큰 대기를 줄이면, 다음 대기가 보인다.** 그 과정을 반복하면서 사용자가 실제로 활용할 수 있는 결과까지의 시간을 줄이는 것이 실용적인 출발점이다.
