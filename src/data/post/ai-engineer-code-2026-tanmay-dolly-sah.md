> AI Engineer CODE 2026 · Tanmay Sah·Dolly Sah · 2026년 11월 11일 온라인 트랙

에이전트가 코드를 고치고 테스트도 통과했다. 그런데 외부 시스템에 요청을 보낸 뒤 응답이 끊겼다. 같은 요청을 다시 보내면 될까. 요청이 실패한 것이 아니라 응답만 사라진 것이라면, 두 번째 요청은 이미 끝난 일을 한 번 더 만들 수 있다.

이 발표는 업무를 수행하는 능력과 실패에서 회복하는 능력을 분리한다. 저장소의 변경을 되돌렸다는 사실만으로 외부 효과까지 원상 복구됐다고 말할 수 없는 이유도 여기에서 출발한다.

## 1. 발표의 질문: 코드 밖에 남은 효과를 어떻게 다룰까

**이 절은 공식 발표 요약이다.**

발표는 코드·릴리스·외부 API·설정·알림이 함께 바뀌는 작업을 제시한다. Git의 되돌리기는 이 전체를 복구하지 않는다. 티켓 생성이 반영됐지만 응답이 유실된 사례에서는 단순 재시도가 중복 효과를 만든다.

UndoBench는 정상 수행과 장애 상황의 복구를 분리해 평가한다. 실패가 변경 전인지, 일부 변경 중인지, 반영 후 응답 전인지에 따라 필요한 대응이 달라진다.

EvoUndo는 에이전트가 실행 틀을 바꾸는 자기 수정의 복구 가능성을 다룬다. 변경 전 상태의 증거가 없으면 무엇으로 돌아가야 하는지 알 수 없고, 복구 표현이 부족하면 올바른 설명을 주어도 필요한 동작을 나타내지 못한다. 예시는 제한 시간을 바꾸기 전에 원래 값을 저장하고, 시험 환경에서 변경과 복구를 실행한 뒤 독립 검증자가 원래 상태와 대조하는 흐름이다. 능력이 좋아져도 복구 검사를 통과하지 못하면 변경을 채택하지 않는다. 복구를 배포 뒤의 사후 대책이 아니라 변경을 받아들이는 조건으로 옮긴다. ## 2. 원 연구에서 구분해야 할 숫자와 조건

**이 절은 두 논문의 공개 초록에서 직접 확인한 범위다. 논문 전체를 독립 재현한 결과가 아니다.**

UndoBench의 고정된 응답 유실 실험은 2,880개의 쌍, 즉 실행 5,760회를 보고한다. 정상 수행은 83.54%, 조건부 복구 성공은 46.72%였다. 분모가 다른 지표이므로 단순히 같은 성공률의 전후 비교로 읽으면 안 된다. 여러 단계 중 일부가 반영된 경우에는 호출별 멱등성만으로 충분하지 않았고, 반영 후 응답 전 실패에서는 상태 확인과 서버 측 멱등성이 도움이 됐다.

[UndoBench 원 논문](https://arxiv.org/abs/2610.05622)

EvoUndo는 600개 과제에서 능력은 개선됐지만 복구 검증에는 실패한 변경 197개를 분석한다. 정확한 상태 위치 정보가 도움을 준 38/48과 더 풍부한 복구 표현을 사용한 142/143은 서로 다른 조건의 부분집합이다. 합산해 전체 개선율처럼 쓸 수 없다. 더 많은 진단 정보가 항상 더 좋은 결과를 만들지도 않았으며 일부 상호작용은 모델에 따라 달랐다.

[EvoUndo 원 논문, v2](https://arxiv.org/abs/2608.28363v2)

## 3. 해설: 실패를 세 위치로 나누면 대응이 달라진다

**이하의 예시와 절차는 필자의 해설이다. 논문의 모든 환경을 재구성하거나 보편적 보장을 제시하는 것이 아니다.**

아무 변경도 일어나기 전이라면 원래 요청을 다시 수행하는 것이 적절할 수 있다. 그러나 일부 단계가 반영됐다면 남은 단계만 실행할지, 이미 반영한 효과를 보상할지 판단해야 한다. 모든 변경이 끝난 뒤 응답만 잃었다면 다시 실행하는 대신 완료 사실을 확인해야 할 수 있다.

같은 네트워크 오류가 이 세 경우 모두에서 나타날 수 있다. 따라서 오류 메시지 하나만 보고 대응을 결정하는 구조는 충분하지 않다. 어느 단계까지 실제 효과가 생겼는지 관측할 수 있어야 한다.

필자라면 요청 식별자와 외부 객체의 식별자를 구분해 남기겠다. 요청을 보냈다는 기록은 처리됐다는 증거가 아니다. 반대로 객체가 생성됐음을 확인하면 응답이 없었더라도 다음 행동을 달리 선택할 수 있다. 시스템이 제공하는 조회·중복 방지 기능이 이 구분을 실제 제어로 바꾸는 기반이다.

![변경 전·부분 반영·반영 후 응답 유실을 구분하는 복구 판단 도식](/images/ai-engineer-code-2026/tanmay-dolly-sah.svg)

*필자가 구성한 판단 틀이다. 각 칸은 자동 실행 지시가 아니라 상태를 확인한 뒤 검토할 선택지다.*

## 4. 해설: 복원과 보상은 같은 말이 아니다

가상의 설정 값을 바꿨다가 원래 값으로 돌리는 경우에는 이전 값이 필요하다. 하지만 이미 발송된 알림은 설정을 되돌린다고 사라지지 않는다. 정정 알림을 보낼 수는 있어도 받는 사람이 최초 알림을 보지 않았던 상태로 돌아가는 것은 아니다.

필자라면 복구 계획을 작성할 때 원상 복원이 가능한 효과, 별도 보상이 필요한 효과, 되돌릴 수 없어 확인과 대응이 필요한 효과를 나누겠다. 모든 변경에 ‘undo’라는 이름을 붙이면 차이가 가려진다.

동시에 발생한 다른 사람의 변경도 고려해야 한다. 에이전트가 기록한 옛 값으로 무조건 덮어쓰면 그 사이의 정당한 수정까지 지울 수 있다. 이전 값을 알고 있다는 것만으로 복원이 안전해지는 것은 아니다. 현재 상태가 자신이 바꾼 결과와 일치하는지, 다른 변경이 끼어들었는지도 확인해야 한다.

이 때문에 복구는 예외 처리 코드 몇 줄보다 넓은 설계다. 실행 전 남겨야 할 정보, 실행 후 얻어야 할 증거, 사용할 수 있는 보상 동작, 사람이 결정해야 하는 경계를 함께 정해야 한다.

## 5. 해설: 정상 성공률과 복구 성공률을 따로 시험하자

업무 자동화를 평가할 때 정상적인 입력과 성공 경로만 반복하면 중요한 문제가 보이지 않는다. 필자라면 안전한 시험 환경에서 효과가 반영되기 전, 단계 중간, 반영 뒤 응답 전에 장애를 주입해 보겠다. 그 후 최종 상태뿐 아니라 효과가 몇 번 발생했는지도 확인하겠다.

결과가 겉보기에는 같아도 중간에 외부 알림을 두 번 보냈다면 사용자에게는 다른 경험이다. 최종 파일 내용만 비교하는 검사로는 이런 차이를 놓칠 수 있다. 어떤 관측을 복구 성공의 기준으로 삼을지 먼저 정해야 한다.

자기 수정 시스템에서는 변경을 만든 에이전트의 설명과 별개로 복구 결과를 확인할 경로를 두겠다. 변경자가 자신의 성공 기준까지 바꾸면 좋은 점수와 안전한 변경이 분리될 수 있기 때문이다. 그리고 모든 환경에서의 복구를 주장하기보다 어떤 상태·효과·장애를 시험했는지 범위를 명시하겠다.

## 마무리

이 발표가 던지는 질문은 단순하다. 일을 해낼 수 있다는 사실만으로, 잘못됐을 때 안전하게 수습할 수 있다고 믿어도 되는가. 필자의 답은 별도로 확인해야 한다는 것이다. 재시도, 상태 확인, 복원, 보상, 중단을 서로 다른 선택지로 설계해야 에이전트의 행동을 끝까지 책임질 수 있다.
