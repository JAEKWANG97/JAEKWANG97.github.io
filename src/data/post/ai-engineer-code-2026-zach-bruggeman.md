## 의심에서 시작한 공동 디버깅

**발표 요약:** Ramp의 Zach Bruggeman은 *How to build an agent that builds the culture*에서 Inspect를 개인 코딩 도구보다 공동 작업 공간으로 설명한다. 각자 설정과 개선을 반복하면 비용이 누적되고 지식이 고르게 퍼지지 않는다. 공통 기반을 개선하면 다른 사람도 같은 이득을 얻는다.

핵심 사례는 Inspect 자체의 버그 조사다. 에이전트는 관측용 계측 코드가 오류 원인이라고 했고 개발자들은 의심했다. 같은 공개 세션에서 라이브러리 코드를 더 조사하자 `fetch` 응답 본문을 읽거나 취소하지 않는 구체적 문제가 드러났다. 응답 본문을 명시적으로 취소하도록 exporter를 고친 뒤 오류가 더 보이지 않았다고 발표자는 설명한다. 당시 Cloudflare 환경에서 관찰한 문제이지 모든 `fetch` 사용의 일반 진단은 아니다. 중요한 변화는 신고자가 수정 완료 통보만 받은 것이 아니라 조사에 참여하고 후속 아이디어를 내게 됐다는 점이다.

또 다른 사례는 기존 PR 트리거를 활용해 동료들이 만든 Review Buddy다. 새 검토 기능을 제품팀이 먼저 완성해 제공한 것이 아니라, 사용자가 기존 부품을 조합하면서 제품팀의 방향을 넓혔다. [공식 발표·전사](https://ai.engineer/code/2026/talks/zach-bruggeman)

## 원인 후보와 확인된 설명 사이

**해설:** 위 사례에서 AI의 첫 답변을 바로 믿지 않았다는 점을 놓치면 안 된다. 의심은 도구 도입을 방해하는 감정이 아니라 다음 확인 질문을 만드는 출발점이었다. “계측 코드가 문제”라는 넓은 주장과 실제 코드의 특정 동작을 지목하는 설명은 검증 가능성이 다르다.

또한 수정 후 오류가 보이지 않았다는 보고는 그 조사에서 얻은 결과다. 이를 모든 환경에서 같은 오류가 같은 원인으로 발생한다는 규칙으로 일반화해서는 안 된다. 버그 해결 기록을 재사용할 때는 당시 환경과 관찰 조건이 함께 있어야 한다.

![혼자 얻은 결과를 전달하는 흐름과 함께 증거를 확인하는 흐름의 비교](/images/ai-engineer-code-2026/zach-bruggeman-evidence.svg)

*발표 사례에서 읽은 협업 구조를 재구성한 그림이다. 실제 사고 로그나 제품 화면은 아니다.*

## 제품 설명에서 확인되는 공동 세션의 역할

**보충 자료:** Ramp의 Inspect 출시 글은 동료가 세션에 들어와 맥락을 추가하고 제약을 알려 주거나 접근법을 조정할 수 있다고 설명한다. 작업은 팀의 개발 환경에서 수행하며 시각적 검증과 리뷰를 거친 PR로 돌아온다. 더 나은 조사·테스트·리뷰 방식을 발견하면 다른 사람도 쓰는 에이전트나 자동화로 만들 수 있다는 방향이다. 채택은 강제보다 공유 세션에서 동료의 사용을 보는 방식으로 확산됐다는 회사 설명도 있다. [Ramp: Introducing Inspect](https://ramp.com/blog/introducing-inspect)

## 세션이 새로운 검토 자료가 될 때

**해설:** 코드 차이만 보면 무엇이 바뀌었는지는 알 수 있지만 어떤 대안을 버렸는지까지 알기는 어렵다. 대화와 실행 결과가 연결돼 있으면 검토자는 가정과 증거를 확인할 수 있다. 그렇다고 긴 대화 전체를 읽어야 한다면 검토 비용이 다시 커진다.

자체 적용 제안은 세션 링크만 던지는 대신 핵심 주장에 해당하는 증거 위치를 연결하는 것이다. 어떤 입력으로 재현했는지, 어떤 수정이 원인 후보를 다뤘는지, 어떤 확인이 남았는지를 짧게 정리한다. 세션 원문은 그 설명을 확인하는 자료로 남긴다. 예컨대 ‘오류 수정 완료’라는 문장만 쓰지 않고, 최초 가설과 반론, 수정한 동작, 배포 후 관찰을 각각 연결하면 다음 사람이 같은 의심을 처음부터 반복할 필요가 줄어든다. 이것은 발표에서 제시한 PR 양식이 아니라 협업 원리를 적용한 편집 제안이다.

공유의 범위도 따로 정해야 한다. 사내 공개 세션이 유용했다는 사례는 모든 대화와 자격증명을 전 직원에게 공개하라는 권고가 아니다. 코드 접근권, 고객 데이터, 인사 정보처럼 별도 경계가 필요한 내용은 공동 작업 도구에서도 보호해야 한다.

## 확인 범위

이 발표의 중심은 샌드박스 구현이나 모델 성능 순위가 아니라 팀이 함께 일하는 방식이다. 회사 자체의 사용률이나 코드 생산량을 독립적인 생산성 증명으로 옮기지 않았다. 핵심 구간은 공통 기반 07:52:02, 검증 근거 공유 07:56:16, 텔레메트리 조사 07:57:00~07:59:53, Review Buddy 08:01:26이다. 전체 중계 기준이며 기계 전사 오류가 있을 수 있다. 원문 전체 번역이 아닌 제한적 요약과 해설이다.
