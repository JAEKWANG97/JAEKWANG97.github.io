## 도구를 잘 쓰고 있는 걸까, 도구의 빈틈을 메우는 걸까

명령 하나를 실행한 뒤 에이전트가 `grep`, `head`, `tail`을 붙인다. 그것으로 부족하면 짧은 Python 코드까지 작성한다. 이 모습을 능숙한 셸 사용으로 볼 수도 있다. 그러나 같은 가공을 매번 반복한다면 다른 질문이 필요하다. 도구가 애초에 필요한 정보를 돌려주지 않는 것은 아닐까?

Ayush Bhardwaj의 발표는 이 질문을 CLI 설계 문제로 가져온다. 중요한 것은 에이전트에게 출력 전체를 더 열심히 읽게 하는 일이 아니다. 명령 이후에 반복되는 수작업이 무엇을 요구하는지 읽는 일이다.

## 실제 사례: 과거 대화에서 필요한 부분만 찾고 싶었다

발표자는 자신의 코딩 에이전트 세션 검색 도구를 사용하는 호출 기록을 살폈다. 에이전트는 긴 세션을 받은 뒤 검색어 주변이나 특정 메시지만 남겼다. 필요한 것은 대화 전체가 아니라, 과거에 어떤 문제를 어떻게 해결했는지 보여주는 구간이었다. 의존성 보고서와 테스트 출력에서도 비슷한 축약이 나타났다.

그는 이를 관련 구간 선택, 필요한 필드 선택, 여러 대상의 일괄 조회라는 개선 방향으로 묶었다. 출력 글자 수만 자르는 것과 필요한 메시지를 고르는 것은 다르다. 아무 효과가 없어진 옵션도 스킬에 남아 있자 계속 호출됐다. 지침을 고친 뒤 관찰한 두 세션은 그 옵션을 쓰지 않고 새 옵션을 시도했다. 작은 관찰이므로 일반적인 효과 크기로 볼 수는 없다. 그래서 사용 지침도 갱신하고, 과거 호출과 별도 검증 과제로 변경을 평가하자고 제안한다. 이 관찰은 발표자 자신의 사용 기록에 기반한다. 모든 에이전트의 행동 비율을 측정한 연구는 아니다. ## 짧은 출력보다 먼저 지켜야 할 것: 실패의 의미

발표는 테스트 결과를 잘라 보는 과정에서 실패 정보가 사라질 수 있다는 점도 짚는다. 실패 요약과 전체 로그 위치를 제공하되 종료 상태를 보존하는 방향이다. [공식 전사, 발표 구간 1:46:46–1:59:04](https://www.youtube.com/watch?v=y9JtCCZP2MQ&t=6406s)

이 문제의 한 부분을 직접 확인하기 위해 아래의 무해한 Bash 예제를 실행했다. 발표자가 사용한 명령은 아니며, 실제 테스트 도구의 동작을 재현한 것도 아니다.

```bash
bash -c 'false | cat; printf "default=%s\n" "$?"'
bash -c 'set -o pipefail; false | cat; printf "pipefail=%s\n" "$?"'
```

실행 결과는 각각 `default=0`, `pipefail=1`이었다. 앞의 `false`는 실패한다. 뒤의 `cat`은 정상 종료한다. 첫 실행에서는 파이프라인 상태만 보면 앞의 실패를 놓친다. 두 번째 실행에서는 이 예제의 실패가 상태에 반영된다.

여기에는 서로 다른 두 문제가 있다. 하나는 셸이 어떤 종료 상태를 돌려주는가이고, 다른 하나는 모델에게 전달한 출력에 실패 원인이 남아 있는가이다. `pipefail`을 켠다고 잘려 나간 오류 설명이 복구되지는 않는다. 반대로 오류 문장을 남긴다고 프로세스 상태가 자동으로 수정되지는 않는다. 자동화가 다음 단계를 결정하려면 둘 다 필요하다.

따라서 출력 최적화를 평가할 때는 “토큰이 얼마나 줄었나”만 보면 안 된다. 같은 실패 사례를 넣었을 때 에이전트가 여전히 실패를 알아차리고, 필요한 근거에 도달하며, 다음 행동을 올바르게 선택하는지도 확인해야 한다. 이는 위 실험으로부터 도출한 평가 관점이지, 발표 도구의 검증된 성능 수치가 아니다.

## 이미 존재하는 설계 사례: GitHub CLI의 필드 선택

이 문제를 전혀 새로운 인터페이스 발명으로 볼 필요는 없다. GitHub CLI는 사람이 읽는 기본 출력과 별도로 `--json`을 통해 필드를 선택하도록 한다. JSON 결과에 `--jq` 필터를 적용할 수도 있다. 이 필터를 쓰기 위해 별도 jq 설치가 필요하지는 않다. [GitHub CLI 공식 출력 형식 문서](https://cli.github.com/manual/gh_help_formatting)

예를 들어 PR 번호와 제목만 필요한 상황을 설명하는 명령은 다음과 같다. 여기서는 실제 계정이나 저장소에 실행하지 않았다.

```bash
gh pr list --json number,title
```

필자가 이 사례에서 강조하고 싶은 것은 JSON 자체가 아니다. 모든 필드를 JSON으로 쏟아 내는 것과 필요한 두 필드를 요청할 수 있는 것은 다르다. 형식이 기계 친화적이어도 범위가 과도하면 읽기 비용은 남는다. 반면 선택 가능한 필드가 있으면 호출하는 쪽이 원하는 정보의 계약을 명시할 수 있다.

세션 검색 도구라면 같은 질문이 메시지 범위에 적용된다. “앞에서 몇 글자”는 위치에 따른 절단이다. “일치한 메시지와 앞뒤 문맥”은 찾으려는 근거에 따른 선택이다. 둘을 같은 축약 기능으로 취급하면 정작 중요한 맥락을 잃기 쉽다.

## 읽고 남는 결론

이 발표를 계기로 바꿔 볼 만한 리뷰 대상은 CLI 설명서보다 실제 호출 뒤쪽이다. 에이전트가 반복해서 추가하는 가공 코드를 모으면, 도구가 직접 맡아야 할 책임의 후보가 보인다. 다만 모든 파이프를 없애는 것이 목표는 아니다. 조합 가능한 작은 도구는 여전히 유용하다. 반복되는 가공이 필요한 정보를 선택하는지, 실패를 감추는지부터 구분해야 한다.

짧아진 출력이 좋은 출력인 것은 아니다. 다음 판단에 필요한 사실을 남긴 출력이 좋은 출력이다.

### 자료와 한계

공식 기계 생성 전사와 GitHub CLI 공식 문서를 확인했다. 전사에는 인식 오류가 남아 있을 수 있으며, 영상 화면의 세부 UI를 독립적으로 판독하거나 발표자의 도구를 재실행하지 않았다. Bash 예제만 별도로 실행해 결과를 확인했다. 발표 사례의 요약, 다른 제품의 문서상 기능, 필자의 설계 해석은 구분했다. 전체 발표의 번역이나 대체 전사는 아니다.
