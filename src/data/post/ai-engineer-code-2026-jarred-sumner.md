「Choose the project you can verify」라는 제목은 더 쉬운 일을 고르라는 뜻이 아니다. 큰 변화를 시도하더라도 무엇을 보존해야 하고 실패를 어떻게 발견할지 먼저 정하라는 뜻에 가깝다. Bun의 AOT 컴파일러 발표를 중심으로, 발표 전의 Rust 이식 기록과 현재 공식 문서를 구분해 읽는다.

## 1. 발표: 애플리케이션을 다시 쓰는 대신 실행 방식을 바꾼 이유

Sumner의 출발점은 Claude Code의 자원 사용을 줄이는 일이었다. 애플리케이션 자체를 다른 언어로 다시 쓰면 테스트도 옮겨야 한다. 반면 Bun의 실행 방식을 바꾸면 기존 애플리케이션을 유지하며 Bun·WebKit·test262·Claude Code의 테스트를 활용할 수 있다. 프로젝트 선택부터 검증 자산이 영향을 준 셈이다.

그는 TypeScript 타입을 언제나 옳은 사실이 아니라 최적화에 활용할 예측으로 다룬다. 결과를 확인할 때도 한 경로만 실행하지 않는다. JIT 실행, AOT 실행, 타입 정보를 제거한 실행을 비교하고 퍼징으로 다양한 패턴을 탐색한다. 검사기가 실제로 결함을 발견할 수 있는지도 확인해야 한다.

에이전트 운영은 처음 구현을 펼치는 단계와 특정 오류를 좁혀 수정하는 단계가 다르다. 오래 이어지는 작업에서는 시간별 점수판으로 진전을 확인한다. 이 발표는 AOT가 모든 JavaScript를 더 빠르게 만든다는 주장이 아니라, 큰 변경을 반복해서 검증할 수 있도록 문제를 선택하고 작업을 조직한 경험이다. [공식 발표와 전사](https://ai.engineer/code/2026/talks/jarred-sumner)

## 2. 공식 문서로 보는 AOT의 이득과 비용

AOT는 프로그램 실행 중에 자주 쓰는 함수를 컴파일하는 대신, 배포 전에 기계어를 만든다. 현재 Bun 문서는 시작 시 파싱과 준비 작업이 줄고 큰 애플리케이션의 메모리를 절약할 수 있다고 설명한다. 그러나 빌드 시간이 늘고, 타입을 알기 어려운 코드에서는 실행 중 관찰을 이용하는 JIT보다 느릴 수 있다. 동적으로 생성한 코드나 특정 내장 객체 변경도 같은 방식으로 취급할 수 없다.

따라서 문서가 권하는 판단은 컴파일 방식의 이름만으로 승자를 정하는 것이 아니다. 같은 프로그램을 두 방식으로 빌드하고 같은 부하에서 비교하는 것이다. 기능은 여전히 실험적이라고 명시돼 있다. 여기서 소개한 현재 문서의 동작을 발표 당시의 모든 빌드에 소급해 적용해서는 안 된다. [발표 외 자료: AOT 공식 문서](https://bun.sh/docs/compiler/aot)

## 3. 타입은 주석이면서도 실행 시 확인해야 하는 가정이다

현재 타입 문서에는 이 원리를 잘 보여 주는 예가 있다. 숫자를 받는 함수에 JSON에서 읽은 문자열이 들어올 수 있다. TypeScript의 `any`나 타입 단언은 실제 값을 숫자로 바꾸지 않기 때문이다. 컴파일러는 선언한 타입에 의존하는 지점에서 값을 확인하고, 예상과 다르면 일반 JavaScript 의미를 지키는 느린 경로로 보낸다.

이 구조에서 타입 선언과 입력 검증은 서로 대체하지 않는다. 타입을 붙였다는 이유로 외부 JSON의 객체 배치까지 바뀌지도 않는다. 공식 문서는 실제 변환이 필요한 곳에서 단언 대신 변환을 하고, 객체를 직접 구성하는 방식 등을 설명한다. 핵심은 잘못된 가정이 조용히 잘못된 답으로 이어지지 않게 하면서, 확실한 곳에서만 빠른 경로를 쓰는 것이다. [발표 외 자료: 타입 활용 방식](https://bun.sh/docs/compiler/types)

## 4. 앞선 Rust 이식에서도 성공의 기준은 코드 생산량이 아니었다

7월에 발표자가 공개한 Bun의 Zig→Rust 이식은 별도의 프로젝트다. 목적은 반복되는 메모리 수명 관리 문제를 줄이는 것이었다. 기존 테스트가 TypeScript로 작성돼 런타임의 구현 언어와 분리돼 있었으므로, 이식 뒤에도 같은 행동을 확인할 수 있었다.

처음부터 전체를 맡긴 것도 아니었다. 이식 규칙과 수명 관련 정보를 정리하고 소수 파일로 시험한 뒤 범위를 넓혔다. 구현자와 결함을 찾는 검토자를 다른 컨텍스트로 분리했다. 병렬 작업이 서로의 Git 상태를 건드리거나, 컴파일 오류를 없애려고 기능을 빈 구현으로 대체하는 실패도 있었다. 작성자는 이런 문제가 생겼을 때 생성된 코드 한 군데만 고치는 대신 작업 규칙과 검토 과정을 바꿨다고 설명한다. 큰 코드 변경이 가능한 이유를 모델의 능력 하나로 설명할 수 없음을 보여 주는 기록이다. [발표 외 자료: Bun의 Rust 이식](https://bun.com/blog/bun-in-rust)

## 5. 테스트가 돌아가는 환경도 검증 대상이다

현재 문서의 `bun test --aot`는 테스트와 의존 코드를 컴파일해 실행한다. 하지만 테스트 편의를 위한 예외도 있다. 일부 모킹과 파일 로딩은 최종 실행 파일과 다르게 작동하고, 일반 테스트에만 쓸 수 있는 동작도 있다. `bun run --aot`는 컴파일 규칙을 검사하더라도 실제로는 소스에서 실행하므로 컴파일된 프로그램의 모든 차이를 재현하지 않는다. [발표 외 자료: 컴파일 프로그램 테스트](https://bun.sh/docs/compiler/debugging)

> **이 글의 해석:** “테스트 통과”에는 세 질문이 따라야 한다. 어떤 입력을 확인했나, 어떤 실행 경로를 확인했나, 배포되는 결과물도 같은 경로를 쓰나. 여러 경로의 결과가 일치한다는 사실은 강한 단서지만 모든 입력에서의 정당성을 증명하지는 않는다. 검증 가능한 프로젝트란 검사 하나로 완벽해지는 프로젝트가 아니라, 실패를 발견할 서로 다른 관찰 지점을 확보할 수 있는 프로젝트다.

## 범위와 한계

공식 기계 전사, 작성자의 이식 보고, Bun 공식 문서를 확인했다. 문서는 2026년 11월 열람 시점 기준이며 실제 벤치마크를 재실행하지 않았다. 원문의 수치나 성능 순위를 전역적인 개선율로 바꾸지 않았다. 전사에 남은 인식 오류와 전체 영상 미대조라는 한계가 있으며, 본문은 발표 전체의 번역이 아닌 관련 기술 자료를 연결한 해설이다.
