## 먼저 복잡하게 만들었다가, 다시 단순해졌다

**발표 요약:** Lovable 공동창업자 Fabian Hedin의 *What it takes to set intelligence free*는 2023년의 단순한 초기 제품에서 출발한다. 이후 전문 에이전트들이 대화하는 정교한 구조를 만들었지만 제품이 나빠졌고, 2024년 말에는 다시 단순한 흐름으로 돌아갔다. 발표자는 모델 역량이 달라진 지금 다중 에이전트에 재도전한다고 설명한다.

발표는 장시간 작업의 조건을 런타임, 컴퓨터, 검증으로 나눈다. 작업 이력은 계속 추가되는 기록이고 모델에 전달하는 문맥과 분리한다. 같은 과거에서 이력을 분기할 수 있지만 Git처럼 이력들을 병합하지는 않는다. 실행 프로세스도 이력과 분리해 배포 중 교체할 수 있다. 잦은 배포와 보안 업데이트가 고객의 장시간 작업을 끊어서는 안 되기 때문이다.

컴퓨터는 디스크뿐 아니라 메모리와 실행 상태를 체크포인트로 저장한다. 복제 뒤 쓰기가 발생한 메모리만 따로 복사하는 방식 등으로 병렬 실행 비용을 줄인다. 검증은 빌드·타입·브라우저 오류를 확인하는 내부 과정과 실제 사용·전환 등의 외부 피드백으로 나눈다. [공식 발표·전사](https://ai.engineer/code/2026/talks/fabian-hedin)

## 에이전트의 수명과 프로세스의 수명은 다르다

**해설:** 오래 일하는 에이전트를 “프로그램을 오랫동안 끄지 않는 것”으로 만들면 배포, 장애, 모델 변경이 모두 예외가 된다. 반대로 진행 상태를 복구할 수 있다면 어떤 실행자가 다음 단계를 처리하는지는 교체 가능한 요소가 된다.

여기서 기록과 실행 환경도 같은 것이 아니다. 어떤 결정을 내렸는지 저장해도 실행 중인 서버와 파일 상태가 자동으로 복원되지는 않는다. 반대로 컴퓨터를 복원해도 사용자가 방금 바꾼 목표를 모델이 알고 있다는 보장은 없다. 서로 다른 상태를 각각 관리해야 하는 이유다.

## 기술 글로 확인하는 수신함과 작업 이력의 차이

**보충 자료:** Lovable의 *Inside Chats*는 들어온 메시지를 저장하는 수신함과 실제로 처리한 내용을 기록하는 작업 이력을 분리한다. 외부 발신자는 수신함에 쓰고, 에이전트는 실행 시작과 반복 경계에서 이를 자신의 이력에 받아들인다. 깨우기 신호는 메시지 본문이 아니며, 수신함에 먼저 저장된 내용이 기준이다. 따라서 메시지 전달, 작업 이력, 실행 시점은 같은 개념이 아니다. 한 이력에는 하나의 기록자가 있고, 바쁜 에이전트에 신호가 다시 와도 두 번째 실행을 중복 시작하지 않는다. 문맥은 이력으로부터 그때 필요한 형태로 구성한다. [Lovable: Inside Chats](https://lovable.dev/blog/how-lovable-agents-work-together)

![메시지 도착, 처리 이력, 모델 문맥, 교체 가능한 실행자를 구분한 도식](/images/ai-engineer-code-2026/fabian-hedin-state.svg)

*공식 그림의 복제가 아니라 상태의 역할을 나누어 그린 설명도다.*

**해설:** 이 설계에서 “받았다”와 “처리했다”가 다른 상태라는 점이 중요하다. 실행 중 새 요청이 들어와도 지금까지 실제로 처리한 순서를 바꾸지 않고 다음 경계에서 받아들일 수 있다. 문제를 조사할 때도 요청의 도착 시간뿐 아니라 어떤 판단 이전에 반영됐는지를 물을 수 있다.

다만 기록의 영속성이 외부 효과의 중복 방지를 자동으로 보장하지는 않는다. 예를 들어 외부 API는 성공했는데 그 결과를 기록하기 전에 실행자가 멈춘 상황을 가정할 수 있다. 복구 후 재호출할지 확인할지는 별도 설계가 필요하다. 이 예시는 Lovable에서 실제 사고가 났다는 주장이 아니라 복구 설계에 남는 일반적 질문이다.

## 단순한 사용자 경험을 위해 좁힌 문제

**보충 자료:** 공동창업자 Anton Osika의 별도 글은 새 애플리케이션 생성에 집중하고 기술 스택을 제한한 결정도 설명한다. 실행 환경과 라이브러리를 알면 실패를 관찰하고 공통 개선을 여러 프로젝트에 적용하기 쉽다. 반복 오류는 짧은 지식 파일로 정리하고 관련 항목을 검색해 문맥에 넣었다. 예를 들어 존재하지 않는 아이콘 이름을 만들어 내는 문제에 대응하는 지침이다. 지속되는 개발 서버와 점진적 타입 검사도 수정 후 확인 시간을 줄이기 위한 선택이었다. [Lovable: How we built Lovable](https://lovable.dev/blog/how-we-built-lovable-and-why-we-keep-rebuilding-it)

**해설:** 이 경험을 임의의 기존 코드베이스에 그대로 적용할 수 있다고 보면 안 된다. 공통 스택과 통제된 환경에서 얻은 이점은 다양한 환경을 지원해야 하는 도구와 조건이 다르다. 배울 것은 특정 구조의 보편적 우월성이 아니라, 자신이 통제할 수 있는 범위 안에서 피드백을 빠르게 만들었다는 점이다.

## 이 발표에서 남는 질문

다중 에이전트를 도입할 때 먼저 물어야 할 것은 몇 개를 띄울 수 있는지가 아니다. 실행자가 바뀌어도 작업을 이어갈 수 있는지, 새 메시지가 언제 반영되는지, 결과가 잘못됐음을 얼마나 빨리 알 수 있는지가 더 구체적인 질문이다.

공식 전사의 핵심 구간은 초기 실패 07:26:42~07:29:34, 런타임 07:34:53~07:40:29, 컴퓨터 체크포인트 07:40:32 이후, 검증 07:45:13 이후다. 전체 중계 기준이며 기계 인식 오류가 있을 수 있다. 이 글은 제한적인 발표 요약에 별도 회사 기술 글과 해설을 덧붙였다. 공개된 운영 규모나 성능 수치를 독립 검증하지 않았으며, 회사 사례를 모든 제품의 권장 구조로 일반화하지 않았다.
