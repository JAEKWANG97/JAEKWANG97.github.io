## 올해 더 많이 해 보기로 한 사람의 연말 회고

Simon Willison의 「2026 in LLMs」는 모델 출시 목록보다 개인적인 사용 경험에 가깝다. 그는 코딩 에이전트가 일상 도구가 된 순간, 더 큰 목표를 오래 추구할 수 있게 된 변화, 생성한 게임을 실제로 재미있게 느낀 경험을 세 번의 전환점으로 묶는다. [공식 발표](https://ai.engineer/code/2026/talks/simon-willison)

그의 새해 계획도 달라졌다. 예년에는 프로젝트를 줄이겠다고 다짐했지만, 이번에는 에이전트의 도움으로 더 야심 차게 시도하기로 했다. 발표 시점에는 동시에 진행하는 일이 많아져 부담스럽다고 인정한다. 쉬운 구현을 맡길 수 있게 된 것이 곧 일의 부담이 사라졌다는 뜻은 아니었다. [발표 전사, 08:32:43 이후](https://www.youtube.com/watch?v=ZZ19zhYnDKY&t=30763s)

이 글은 회고 전체를 기술 연표로 재구성하지 않는다. 실제 작업이 어떻게 달라졌는지 보여 주는 두 사례를 본인의 별도 글로 보충하고, 마지막의 업무 부담 문제로 돌아간다. 공식 읽기 자료도 검증하지 않았다고 밝힌 보안 사건과 정책 일화는 사실로 확정해 옮기지 않았다.

## 1. 질문을 잘 쓰는 것에서, 필요한 관측을 연결하는 것으로

발표에 등장하는 생활 속 문제는 정리하지 않은 상자가 가득한 방의 간헐적인 삐 소리다. Willison은 상자를 모두 뒤지는 대신 여러 기기의 마이크를 이용해 소리의 위치를 찾는 도구를 만들었다고 설명한다. 여기서 목표는 코드 생성 자체가 아니라 실제 소리가 나는 곳을 찾는 것이다. [공식 발표의 소리 탐색 사례](https://ai.engineer/code/2026/talks/simon-willison)

그가 공개한 별도 글에는 시행착오가 더 자세하다. Beep Locator는 Python 서버와 브라우저 기반 녹음을 연결하고, 여러 기기가 WebSocket으로 측정값을 전달하는 구조다. 기기끼리 소리를 내어 위치를 추정하는 초기 방식은 만족스럽지 않았다. 그래서 사람이 지도 위에 대략적인 위치를 지정하는 모드를 추가했다. [Beep Locator 제작 기록](https://simonwillison.net/2026/Nov/9/mysterious-beeps/)

그다음에는 손뼉을 쳐서 위치 추정을 시험하는 기능, 녹음된 소리를 다시 듣는 기능, 찾던 소리를 표시하는 기능이 들어갔다. 목표 소리를 확인한 뒤 반복 관측을 모아 위치를 좁혔고, 그는 약 40cm 범위로 추정된 상자 더미에서 오래된 일산화탄소 감지기를 찾았다고 보고했다. 이는 개인 실험의 결과이며 안전 설비를 대체하는 도구나 일반적인 측위 정확도 보장은 아니다. [같은 제작 기록](https://simonwillison.net/2026/Nov/9/mysterious-beeps/)

이 프로젝트에서는 모델이 찾은 2007년 BeepBeep 연구도 참고했다. 또한 청취 기기에 새 코드를 전달하는 구조 덕분에, 장치를 둔 채로 측정 방식과 구현을 계속 바꿀 수 있었다. 핵심은 모델에 마이크 데이터와 실행 결과를 살펴볼 통로를 제공했다는 데 있다. [같은 글의 구현 설명](https://simonwillison.net/2026/Nov/9/mysterious-beeps/)

**이 글의 해석:** 이 사례를 ‘AI가 소리를 들었다’로만 줄이면 실제 설계가 사라진다. 장치에서 신호를 모으고, 잘못된 가정을 수정하고, 사람이 알아볼 수 있는 검사 방법을 넣는 과정이 있었다. 특히 손뼉 테스트는 프로그램이 무언가 그럴듯한 점을 지도에 찍는 것과 현실의 위치를 제대로 반영하는 것을 구분하는 수단이었다.

모델의 추론 능력만 높이는 것과, 추론할 관측값을 마련하는 것은 다른 개선이다. 이 사례는 후자를 함께 보여 준다. 실제 문제를 해결하려면 에이전트가 자신의 변경이 어떤 결과를 냈는지 볼 수 있어야 한다.

## 2. 게임처럼 보이는 것과 다시 하고 싶은 것은 다르다

발표의 게임 이야기는 외형과 경험을 구분한다. 그럴듯한 게임이 만들어져도 짧게 실행한 뒤 흥미가 떨어질 수 있다. Willison은 전략 게임을 더 재미있게 만들어 달라고 요청한 뒤, 장시간의 반복 작업을 거쳐 자신이 재미있다고 느끼는 결과가 나왔다고 말한다. 이 판단은 사용자의 체험이며 보편적인 재미의 척도는 아니다. [공식 발표의 게임 구간](https://www.youtube.com/watch?v=ZZ19zhYnDKY&t=31477s)

그의 10월 글은 성공을 단일한 과정으로 묶지 않는다. Tree Appreciator는 두 나무의 차이를 찾는 작은 게임으로, 그는 추가 요청 없이 마음에 드는 결과를 얻었다고 설명한다. 반면 판타지 RPG Emberwick에는 플레이 테스트와 수정이 더 필요했다. 다른 이야기 사건 때문에 인물이 이동해 버려 퀘스트를 완료할 수 없는 문제 등이 있었다. [게임 제작 회고](https://simonwillison.net/2026/Oct/28/vibe-game-development/)

Battle Drones는 작동하지만 재미가 부족했던 전략 게임에서 출발했다. 이후 조정과 확장을 거쳤고, Willison은 이 프로젝트를 특히 성공적으로 평가한다. 같은 글에서 호박 농장 게임은 귀엽고 개인적인 아이디어를 담았지만, 아직 게임 규칙에 만족하지 않는다고도 썼다. 모든 생성물이 같은 수준으로 성공했다는 기록이 아니다. [같은 글의 프로젝트별 평가](https://simonwillison.net/2026/Oct/28/vibe-game-development/)

**이 글의 해석:** 이 사례들을 함께 보면, 단순한 요청 한마디가 항상 충분하다는 결론보다 결과를 다시 경험하는 일이 중요하다는 결론이 더 유용하다. 어떤 작업은 첫 결과가 충분하고 어떤 작업은 끝까지 진행해 봐야 문제가 드러난다. 화면이 아름다운 것, 조작이 가능한 것, 이야기의 다음 단계로 넘어갈 수 있는 것, 다시 하고 싶은 것은 서로 다른 확인 항목이다.

게임을 더 재미있게 만들라는 요청은 새로운 방향을 열 수 있다. 다만 이 사례에서 ‘재미있다’의 근거는 제작자의 플레이 경험이다. 이 글이 직접 게임을 평가하거나 보편적인 재미를 검증한 것은 아니다.

## 3. 에이전트가 강해져도 사람이 덜 피곤해지지 않는 이유

Willison은 별도의 짧은 글에서도 코딩 에이전트의 잠재력을 제대로 쓰려면 상당한 지식과 규율이 필요하며, 소프트웨어 엔지니어링이 오히려 더 어려워진다고 느낀다고 적었다. 이는 노동 생산성 연구가 아니라 숙련 개발자의 자기 보고다. [2026년 9월의 본인 메모](https://simonwillison.net/2026/Sep/24/harder/)

**이 글의 해석:** 앞의 사례에서 줄어든 것은 모든 일이 아니다. 직접 작성해야 하는 코드의 양이 줄면서 소리 측정 도구나 여러 게임처럼 이전에는 시작하지 않았을 프로젝트가 가능해졌다. 하지만 무엇을 만들지, 무엇이 제대로 작동하는지, 어디까지 개선할지는 계속 정해야 한다.

도구가 구현 부담을 낮추면 선택 가능한 일의 수가 늘어난다. 그때 절약된 시간이 휴식으로 갈 수도 있고, 새로운 프로젝트로 갈 수도 있다. 후자를 계속 선택하면 총부담은 줄지 않는다. 따라서 ‘코딩이 쉬워졌다’와 ‘내 일이 쉬워졌다’는 동시에 참일 필요가 없다. 발표의 즐거움과 피로는 서로 모순되는 감정이 아니라, 작업 범위가 넓어진 결과로 함께 나타날 수 있다.

## 성능표 밖에서 무엇이 바뀌었는가

이 회고에서 가져갈 만한 변화는 도구가 놀라운 출력을 한 번 만들었다는 사실만이 아니다. 현실의 관측을 연결하고, 실패한 가정을 바꾸고, 사용 경험을 다시 확인하는 작업까지 시도할 수 있게 됐다는 점이다. 반대로 무엇을 성공으로 볼지와 어디에 시간을 쓸지는 여전히 중요하다.

**이 글의 결론:** 더 유능한 에이전트가 생기면 야심을 키울 수 있다. 다만 새로 가능해진 일과 지금 책임질 일을 같은 목록으로 만들 필요는 없다. Willison의 발표가 흥미로운 이유는 발전을 반기면서도 그 발전이 개인에게 남기는 판단과 부담을 숨기지 않기 때문이다.

### 자료와 한계

공식 기계 생성 전사와 본인의 공개 제작 기록을 확인했다. 같은 제작자의 다른 글은 상세한 1차 설명이지만 독립 재현 검증은 아니다. 소리 위치의 수치는 보고값이고 게임의 재미는 주관적 평가다. 발표의 모델 출시 연표와 보안 사건 전체를 검증한 글은 아니며, 확인하지 않은 혐의나 법적 표현은 제외했다. 직접 인용 없이 출처별 제한된 요약과 별도 해석으로 작성했다.
