창작 도구의 기능이 많아질수록 모든 사용자에게 더 좋은 제품이 될까. Brandon Thomas의 발표에는 반대 방향의 요구가 나온다. 특정 작업을 하는 사람에게는 기능을 더하는 것보다 필요 없는 복잡성을 지우는 일이 중요할 수 있다. 코딩 에이전트와 오픈소스가 만나는 지점도 여기에 있다.

## 1. 발표의 흐름: 소유의 문제에서 작업 화면의 문제로

Thomas가 말하는 오픈소스는 코드를 무료로 배포한다는 이야기만은 아니다. 사용자가 자신에게 맞게 도구를 바꿀 수 있어야 한다는 주장이다. 초기 웹에 대한 회상도 이 문제의식으로 이어진다. 그의 개인적 경험을 웹 전체의 역사와 동일시할 필요는 없다.

구체적 장면은 마이크로드라마 제작 현장이다. 스튜디오 안에서 역할마다 필요한 도구와 작업 순서가 다르므로, 기존 API를 이용해 담당자에게 맞는 화면을 만든다. 범용 앱의 모든 기능을 복제하기보다 해당 작업에서 쓰지 않는 복잡성을 줄이는 방향이다.

이어 Photoshop을 닮은 초기 구현이 등장한다. 익숙한 조작 방식을 활용하지만, 원래 제품의 전체 기능을 구현했다고 주장하지는 않는다. 이 구분이 중요하다. 발표의 사례는 빠른 시작을 보여 주며, 완전한 대체품의 검증은 아니다.

개발 과정에서는 화면·기능·데이터·도구를 나누되, 백엔드와 API, 스키마처럼 영향이 큰 결정은 사람에게 남긴다. 이후 공개하겠다는 자동화 도구의 계획도 이미 공개된 결과와 구별해야 한다. ## 2. 공개 저장소가 보여 주는 ‘통제’의 구체적인 의미

ArtCraft 공개 저장소의 설명은 이미지·영상 생성에서 화면 구성과 카메라, 인물의 배치 등을 사용자가 조절하는 방향을 강조한다. 2D 레이어를 구성하거나 3D 장면에서 물체를 배치한 뒤 생성하는 식이다. 프롬프트로 아이디어를 탐색하되 캔버스와 장면 도구로 원하는 부분을 구체화한다. [ArtCraft 공식 저장소](https://github.com/storytold/artcraft)

이는 생성 모델을 선택하는 기능만으로 사용자의 의도가 충분히 표현되지는 않는다는 제품 관점을 보여 준다. 다만 이 저장소는 ArtCraft의 공개 상태를 확인하는 근거이지, 발표에서 언급한 다른 모든 앱이 완성·공개되었다는 증거는 아니다. 설치·실행이나 기능 재현 실험도 이번 글에서는 하지 않았다.

## 3. 사례를 읽는 관점: 화면을 줄이면 무엇이 달라지는가

이 절은 발표의 사례에서 출발한 필자의 분석이다. 마이크로드라마 스튜디오와 Photoshop 형태의 초기 구현은 서로 다른 문제를 다룬다. 전자는 특정 역할의 작업 경로를 줄이는 문제이고, 후자는 이미 익힌 조작 방식을 새 도구에서도 사용할 수 있게 하는 문제다. 두 사례를 모두 ‘AI로 앱을 복제했다’로 묶으면 사용자가 얻는 이점이 사라진다.

가령 한 담당자가 장면의 배치를 정하고 다른 담당자가 최종 이미지를 만든다고 가정하자. 이 가정은 발표의 실제 운영을 재현한 것이 아니라 비교를 위한 예시다. 첫 담당자에게 필요한 것은 모든 생성 설정이 아니라 배치 결과를 다음 담당자에게 넘기는 확실한 방법일 수 있다. 화면이 단순해져도 전달한 정보가 사라지거나 해석이 달라진다면 업무는 단순해지지 않는다.

따라서 이 사례를 검증할 질문은 버튼 수가 아니다. 담당자가 입력한 결과가 다음 단계까지 보존되는가, 잘못 전달했을 때 되돌릴 수 있는가, 다른 도구에서도 같은 결과를 읽을 수 있는가다. 이런 질문을 통과한 작은 화면이라면 범용 앱보다 기능이 적어도 목적에 더 잘 맞을 수 있다.

## 4. 해설: 편집할 수 있다는 것과 유지할 수 있다는 것은 다르다

여기부터는 필자의 해석이다. 오픈소스의 가치는 반드시 모든 사용자가 코드를 읽는 데 있지 않다. 자신의 작업을 바꿀 선택지가 생기는 데도 있다. 하지만 에이전트가 변경을 작성할 수 있다는 사실만으로 유지 비용이 사라지지는 않는다.

역할에 맞게 화면을 줄인 경우에도 파일을 잃지 않고 저장하는지, 다른 도구로 전달할 수 있는지, 원래 프로젝트 업데이트와 충돌하는지 확인해야 한다. 겉으로 보이는 버튼을 줄이는 작업과 내부 동작을 안전하게 삭제하는 작업은 다르다. 사용하지 않는 것처럼 보인 기능이 파일 호환성이나 다른 작업의 전제일 수도 있다.

그래서 공통 기능과 사용자별 화면을 구분한 그림은 단순히 ‘모듈화하면 좋다’는 의미가 아니다. 무엇을 바꿀 때 누구의 작업이 영향을 받는지 판단하기 위한 구분이다. 같은 데이터 형식을 공유하는 여러 도구라면, 화면 변경보다 데이터 형식 변경의 파급이 클 수 있다.

## 5. 해설: 익숙한 모양과 완성도는 다른 평가 축이다

기존 앱과 비슷한 화면은 첫 사용의 부담을 줄일 수 있다. 그러나 화면이 익숙하다는 사실만으로 파일 호환성, 색상 처리, 정밀도, 성능까지 같다고 판단해서는 안 된다. 발표의 빠른 초기 구현을 읽을 때도 이 경계가 중요하다.

반대로 기존 제품의 모든 기능을 따라잡지 못했다는 이유만으로 특정 작업에 쓸모없다고 단정할 필요도 없다. 평가 단위는 실제로 끝내려는 작업이어야 한다. 어느 작업을 어디까지 완료할 수 있으며, 어떤 단계에서는 다른 도구로 넘겨야 하는지 밝혀야 한다.

Thomas의 발표를 읽고 남는 질문은 ‘상용 앱을 얼마나 빨리 복제할 수 있나’보다 ‘사용자가 자신의 제작 과정을 어디까지 바꿀 수 있나’다. 그 가능성은 매력적이지만, 수정 가능한 도구에도 호환성·검증·유지의 책임은 남는다.

## 출처와 확인 범위

공식 개별 웹 전사와 ZIP 전사를 대조했고, ArtCraft 저장소의 공개 설명을 별도로 확인했다. 자동 전사에는 인식 오류가 남을 수 있다. 발표자 주장과 제품 설명은 제한적으로 요약했으며, 3~5절과 도식은 필자의 해석이다. 미완성 구현을 완전한 대체품으로, 미래 공개 계획을 현재 상태로 바꾸지 않았다.
