## 들어가며

저는 무언가를 개발할 때 전체를 파악하려는 편이었습니다.

새로운 코드베이스를 만나면 파일을 하나씩 열어보고, 데이터가 어디에서 들어와 어디로 흘러가는지 따라가고, 사용한 라이브러리가 내부에서 어떻게 동작하는지도 이해하려고 했습니다. 그래야 제가 만든 것을 책임질 수 있다고 생각했습니다.

AI 에이전트를 본격적으로 쓰기 시작하면서 이 방식이 흔들렸습니다.

지금은 어려운 문제를 주고 여러 접근을 시도하게 할 수 있습니다. 에이전트는 코드베이스를 탐색하고, 가능한 원인을 세우고, 프로토타입을 만들고, 테스트와 벤치마크를 반복한 뒤 결과를 정리해줍니다.

그러다 이런 생각이 들었습니다.

> 비용이 큰 탐색과 실험은 AI가 하고, 나는 최종 보고를 받은 뒤 결정하면 되는 것 아닐까?

바로 다음 질문도 따라왔습니다.

> 그렇다면 나는 AI가 만든 모든 코드를 이해해야 할까? 결과와 근거만 판단할 수 있으면 되는 걸까?

처음에는 둘 중 하나를 골라야 한다고 생각했습니다. 전부 이해하거나, 결과만 보거나. 그런데 여러 개발자의 글과 실제 AI 작업 방식을 살펴보니 그 사이에 더 현실적인 기준이 있었습니다.

## 코드 생성 비용이 달라졌다

예전에는 접근 방법 세 개를 비교하는 것 자체가 부담이었습니다.

```text
접근 A 구현 -> 실패 원인 확인
접근 B 구현 -> 테스트와 디버깅
접근 C 구현 -> 성능 측정
세 결과 비교 -> 최종 결정
```

시간이 부족하면 가장 그럴듯한 방법 하나를 골라 진행할 수밖에 없었습니다. 다른 접근은 머릿속으로만 비교하거나 문서에서 본 결과를 믿었습니다.

AI 에이전트는 이 비용을 크게 낮췄습니다. 같은 문제를 서로 다른 방향으로 시도하게 하고, 실패한 접근까지 기록하게 할 수 있습니다. 사람이 한 가지 구현을 붙잡고 있는 동안 여러 에이전트가 탐색과 실험을 나눠 수행하는 것도 가능합니다.

Mitchell Hashimoto는 [My AI Adoption Journey](https://mitchellh.com/writing/my-ai-adoption-journey)에서 에이전트에게 라이브러리 조사와 여러 방향의 실험을 맡긴 경험을 설명합니다. 바로 배포할 코드를 기대한 것이 아니라, 자신이 놓친 가능성을 발견하기 위한 탐색이었습니다. 다음 날 사람이 결과를 읽고 쓸 만한 방향을 선별했습니다.

이 방식에서 AI는 정답을 대신 결정하는 존재가 아닙니다. 탐색할 수 있는 범위를 넓혀주는 실행팀에 가깝습니다.

```text
사람: 문제와 평가 기준을 정한다
  ↓
AI: 여러 가설과 접근 방법을 만든다
  ↓
AI: 구현·테스트·실험을 반복한다
  ↓
AI: 성공·실패·근거·한계를 비교해 보고한다
  ↓
사람: 증거를 검토하고 선택한다
```

여기까지 보면 사람의 역할이 줄어든 것처럼 보입니다. 실제로 반복 구현에 쓰는 시간은 줄어듭니다. 하지만 다른 병목이 생깁니다.

AI가 열 개의 접근을 실험해도, 무엇이 좋은 결과인지 판단할 사람이 없으면 결정할 수 없습니다.

## 병목이 나라는 말의 의미

AI가 빨라질수록 사람의 판단 속도는 상대적으로 느려집니다. 그래서 "결국 병목은 사람"이라는 말이 나옵니다.

처음에는 이 병목도 제거해야 한다고 생각하기 쉽습니다. AI가 가설을 세웠다면 평가까지 맡기고, 가장 높은 점수를 받은 구현을 자동으로 배포하면 더 빠를 것 같습니다.

그런데 평가 기준까지 같은 AI에게 넘기면 이상한 순환이 생깁니다.

```text
AI가 구현한다
-> AI가 자신이 만든 기준으로 평가한다
-> AI가 성공했다고 보고한다
```

테스트가 통과했는데 요구사항을 잘못 이해했을 수도 있습니다. 벤치마크 수치는 좋아졌지만 운영 복잡도가 너무 커졌을 수도 있습니다. 코드상으로는 맞지만 실제 사용자의 업무 방식과 충돌할 수도 있습니다.

사람이 맡아야 하는 건 모든 실험의 노동이 아니라 이런 질문입니다.

- 우리가 실제로 해결하려는 문제는 무엇인가?
- 반드시 지켜야 하는 사용자와 업무의 제약은 무엇인가?
- 성능, 복잡성, 안정성 중 무엇을 우선할 것인가?
- 어떤 증거가 있어야 결과를 믿을 수 있는가?
- 실패했을 때 감당할 수 있는 범위는 어디까지인가?
- 실제 서비스에 적용해도 되는가?

병목이 사람이라는 말은 사람이 모든 작업을 직접 해야 한다는 뜻이 아닙니다. 사람이 개입할 지점을 값비싼 판단으로 좁혀야 한다는 뜻에 가깝습니다.

탐색 비용은 AI가 부담하고, 선택의 책임은 사람이 부담합니다.

## 그렇다면 코드는 어디까지 이해해야 할까

여기서 제 고민이 다시 시작됐습니다.

최종 판단을 제가 한다면 AI가 만든 코드를 전부 읽어야 할까요? 모든 함수와 라이브러리의 내부 동작까지 알아야 제대로 판단했다고 말할 수 있을까요?

여러 개발자의 의견을 찾아보니 "모든 줄을 이해해야 한다"와 "테스트만 통과하면 된다" 사이에서 기준을 나누고 있었습니다.

Simon Willison은 [Not all AI-assisted programming is vibe coding](https://simonwillison.net/2025/Mar/19/vibe-coding/)에서 프로덕션 코드에 엄격한 기준을 둡니다. AI가 작성했더라도 사람이 읽고 테스트한 뒤 다른 사람에게 무엇을 하는 코드인지 설명할 수 있어야 한다는 입장입니다. 반면 피해가 작고 쉽게 버릴 수 있는 프로토타입에서는 코드를 거의 들여다보지 않는 방식도 쓸모가 있다고 봅니다.

Addy Osmani는 [Software Factories, Light and Dark](https://addyo.substack.com/p/software-factories-light-and-dark)에서 `comprehension debt`, 즉 이해 부채를 이야기합니다. 코드가 생성되는 속도와 사람이 시스템을 이해하는 속도의 차이가 계속 벌어지면 테스트가 통과해도 위험할 수 있다는 것입니다. 아무도 시스템의 경계와 설계 이유를 설명하지 못하는 상태가 뒤늦게 드러날 수 있습니다.

반대로 Thorsten Ball은 [Surely not all code's worth it](https://registerspill.thorstenball.com/p/surely-not-all-codes-worth-it)에서 모든 코드가 같은 양의 관심을 받을 필요는 없다고 말합니다. 일회성 데이터 변환, 임시 디버깅 도구, 폐기할 프로토타입처럼 수명이 짧고 피해 범위가 작은 코드는 AI에게 맡겨도 됩니다. 거기에 아낀 시간을 오래 남을 코드에 쓰는 편이 낫다는 이야기입니다.

Kent Beck의 경험도 흥미로웠습니다. 그는 [Augmented Coding: Beyond the Vibes](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes)에서 자신이 충분히 알지 못했던 Rust와 B+ 트리 프로젝트에 AI를 활용했습니다. 시작 전에 모든 걸 알 필요는 없었습니다. 하지만 AI가 복잡성을 쌓도록 내버려 둔 초기 시도는 막혔고, 이후 설계에 직접 개입하며 중간 결과를 확인했습니다.

이 의견들을 보고 나니 제가 과거에 했던 방식이 틀렸다기보다, 모든 코드에 같은 깊이의 이해를 요구한 것이 문제였다는 생각이 들었습니다.

## 이해의 깊이는 위험·수명·학습 목적에 따라 달라진다

제가 지금 세운 기준은 세 가지입니다.

### 오래 남고 실패 비용이 큰 코드는 깊게 이해한다

운영 데이터, 개인정보, 동시성, 트랜잭션, 스키마 마이그레이션처럼 잘못됐을 때 복구 비용이 큰 영역은 직접 파고들어야 합니다.

이런 코드에서는 다음 질문에 답할 수 있어야 합니다.

- 핵심 불변조건은 무엇인가?
- 데이터가 어느 경계를 통과하는가?
- 실패하면 어떤 상태가 남는가?
- 관찰할 로그와 지표가 있는가?
- 어떻게 되돌릴 수 있는가?
- 이 설계를 선택한 이유는 무엇인가?

모든 줄을 암기하라는 뜻은 아닙니다. 장애가 났을 때 AI에게 다시 물어보는 것 외에는 아무 방법이 없는 상태를 피해야 한다는 뜻입니다.

### 반복 구현은 구조와 증거를 이해한다

익숙한 프레임워크의 API 구현, 충분한 테스트가 있는 반복 수정, 영향 범위가 제한된 리팩터링은 모든 줄을 같은 밀도로 읽지 않아도 됩니다.

대신 변경된 경계와 검증 증거를 봅니다.

```text
어디가 바뀌었는가?
기존 동작을 무엇으로 보존했는가?
어떤 테스트가 실패했고 왜 수정됐는가?
새로운 예외 경로는 무엇인가?
성능이나 복잡도는 어떻게 달라졌는가?
```

Charity Majors는 [AI demands more engineering discipline. Not less](https://charity.wtf/p/ai-demands-more-engineering-discipline)에서 사람이 육안으로 모든 출력을 검토하는 방식보다, 필요한 행동과 허용할 수 없는 실패를 명시하고 테스트·리플레이·관측 장치로 검증하는 방식에 무게를 둡니다.

사람의 이해를 없애는 것이 아니라 머릿속의 이해를 반복 가능한 검증 장치로 꺼내놓는 것입니다.

### 저위험 실험은 결과만 받아도 된다

쉽게 버릴 수 있고 실패해도 피해가 작은 코드는 AI가 거의 전부 수행해도 괜찮습니다.

- 일회성 데이터 비교
- 라이브러리 후보 조사
- 아이디어 검증용 프로토타입
- 임시 로그 분석 도구
- 여러 알고리즘의 성능 비교

이 영역에서 모든 구현을 읽느라 시간을 쓰면 AI를 사용하는 이점이 줄어듭니다. 대신 실험 조건과 결과가 재현 가능한지만 확인합니다.

## 어려운 문제를 AI에게 맡기는 방식

예를 들어 Kafka consumer의 지연이 갑자기 커졌다고 가정해보겠습니다.

예전의 저는 consumer 코드부터 DB 호출, Kafka 설정까지 전부 읽으려고 했을 것 같습니다. 지금은 먼저 AI에게 가능한 원인을 나누고, 운영 환경을 변경하지 않는 범위에서 각각 검증하게 할 수 있습니다.

```text
가설 A: DB 쓰기가 병목이다
가설 B: 특정 partition에 이벤트가 몰렸다
가설 C: consumer rebalance가 반복된다
가설 D: batch와 poll 설정이 현재 트래픽에 맞지 않는다
```

AI는 로그와 메트릭을 살펴보고, 로컬에서 부하 테스트를 만들고, DB 호출을 대체했을 때 처리량이 어떻게 달라지는지 비교할 수 있습니다.

제가 받고 싶은 보고서는 "A가 정답입니다"가 아닙니다.

```text
가설: DB 쓰기 병목

관찰
- 전체 처리 시간 중 DB 호출 비중이 가장 컸다.

실험
- DB 호출을 대체하자 처리량이 증가했다.

반증 가능성
- 실제 DB lock과 connection pool 대기는 아직 구분하지 못했다.

남은 위험
- 운영 트래픽과 로컬 부하 패턴이 다르다.

다음 결정
- 운영 변경 전 query latency와 pool wait metric을 추가로 확인한다.
```

이런 형태라면 AI가 비싼 탐색을 대신하면서도, 제가 근거와 한계를 보고 다음 행동을 결정할 수 있습니다.

## 업무 완료와 학습은 같은 방식으로 하면 안 된다

여기에는 주니어 입장에서 놓치기 쉬운 문제가 하나 있습니다.

AI가 탐색과 구현을 모두 수행하면 업무는 빨라지지만, 그 과정에서 얻던 기술 형성은 줄어듭니다. Hashimoto도 자신의 글에서 기초가 약한 주니어의 기술 형성 문제를 걱정한다고 적었습니다.

그래서 저는 작업의 목적을 먼저 구분하려고 합니다.

```text
업무 완료가 목적일 때
- AI가 탐색·구현·실험을 넓게 수행한다.
- 나는 평가 기준, 위험, 증거, 최종 판단에 집중한다.

학습이 목적일 때
- 내 가설을 먼저 적는다.
- 중요한 실패는 직접 디버깅한다.
- AI의 접근과 내 판단을 비교한다.
- 마지막에는 내 말로 설명한다.
```

모든 업무를 학습 과제로 만들면 느려집니다. 반대로 모든 학습을 AI에게 위임하면 결과물은 쌓여도 제 판단 기준은 자라지 않을 수 있습니다.

저에게 필요한 건 AI를 적게 쓰는 규칙이 아니라, 직접 통과할 경험을 고르는 기준이었습니다.

## 앞으로 적용할 기준

앞으로 어려운 문제를 만났을 때 먼저 짧게 적어보려고 합니다.

```text
이 작업의 목적은 무엇인가?
무엇을 좋은 결과로 볼 것인가?
절대로 허용하면 안 되는 실패는 무엇인가?
내가 직접 이해해야 할 핵심 경계는 어디인가?
AI에게 맡길 탐색과 실험은 무엇인가?
결과를 믿기 위해 어떤 증거가 필요한가?
```

그다음 AI에게 여러 접근을 실험하게 합니다. 최종 보고에서는 성공한 방법만 보지 않고 실패한 방법, 반증되지 않은 가정, 남은 위험까지 확인합니다.

그리고 위험이 크거나 오래 운영할 코드, 제가 지금 배우려는 핵심 부분은 직접 파고듭니다. 쉽게 버릴 실험과 반복 작업은 과감하게 맡깁니다.

## 마무리

예전에는 모든 것을 알아야 책임질 수 있다고 생각했습니다. 그 태도 덕분에 코드와 시스템을 보는 기본적인 감각을 만들 수 있었습니다. 그래서 과거의 방식이 틀렸다고 생각하지는 않습니다.

다만 AI가 탐색과 구현 비용을 크게 낮춘 지금, 모든 세부를 같은 깊이로 이해하려는 방식은 오래 유지하기 어렵습니다.

제가 내린 결론은 이해를 포기하는 것이 아닙니다.

> AI는 비용이 큰 탐색과 실험을 맡고, 나는 문제·평가 기준·핵심 경계·증거·운영 결과를 소유한다.

쉽게 버릴 코드는 결과만 봐도 됩니다. 오래 남을 코드와 실패 비용이 큰 경로는 설명하고 복구할 수 있을 만큼 이해해야 합니다. 학습이 목적이라면 효율이 조금 떨어지더라도 일부 실패를 직접 통과해야 합니다.

결국 모든 코드를 이해하는 개발자가 되려는 것보다, **어디를 깊게 이해해야 하는지 판단할 수 있는 개발자**가 되는 편이 지금의 제 역할에 더 가까운 것 같습니다.
