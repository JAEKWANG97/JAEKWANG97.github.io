## 들어가며

최근 AI 에이전트의 활용 방법에 관해 대화하다가 문득 이런 질문이 생겼습니다.

> API 명세, ERD, ADR 같은 문서를 계속 관리하면서 프로젝트를 진행하는 방식도 있을까?

처음에는 이 질문을 단순한 문서화 방법에 관한 것으로 생각했습니다. 그런데 제가 진행하고 있는 별찌 프로젝트를 다시 살펴보니, 이미 여러 종류의 문서를 코드와 함께 관리하고 있었습니다.

```text
PRODUCT.md
API.md
ERD.dbml
ADR
운영 문서
AGENTS.md
Linear 이슈
PR 템플릿
```

문서가 많다는 사실보다 더 흥미로웠던 점은, 이 문서들이 AI 에이전트의 작업 방식에도 영향을 주고 있었다는 것입니다.

에이전트는 `AGENTS.md`를 읽고 어떤 문서를 우선해야 하는지 확인합니다. API를 바꿀 때는 API 명세를 참고하고, 구조나 정책을 바꿀 때는 관련 ADR을 찾아봅니다. 작업 범위는 Linear 이슈에서 확인하고, 완료 전에는 PR 템플릿과 테스트 규칙을 따릅니다.

이 모습을 보면서 문서를 조금 다르게 보게 됐습니다.

문서는 개발이 끝난 뒤 남기는 보고서만이 아니었습니다. 사람과 에이전트가 다음 작업을 시작할 때 읽는 **프로젝트의 기억**에 가까웠습니다.

이번 글에서는 별찌 프로젝트의 실제 구조를 바탕으로, API 명세·ERD·ADR·`AGENTS.md`가 각각 무엇을 기억하고 어떻게 연결되는지 정리해보려고 합니다. 아직 완성된 모범 사례라기보다, 직접 운영해보며 잘된 부분과 부족한 부분을 함께 돌아보는 글입니다.

## 코드는 현재 모습을 보여주지만 이유까지 설명하지는 않는다

AI 에이전트에게 저장소를 맡기면 코드는 꽤 잘 읽습니다. 컨트롤러를 보고 엔드포인트를 찾고, 설정 파일을 보고 서버 포트를 확인하고, 테스트를 읽어 현재 기대 동작을 파악합니다.

그런데 코드만으로는 답하기 어려운 질문이 있습니다.

- 왜 이 기술을 선택했을까?
- 검토했지만 사용하지 않기로 한 대안은 무엇일까?
- 이 API 응답 형식을 유지해야 하는 이유는 무엇일까?
- DB 스키마를 바꾸면 어떤 클라이언트가 영향을 받을까?
- 현재 구조는 임시 POC인가, 앞으로도 지켜야 하는 방향인가?
- 이전 결정을 바꾸어도 되는 조건은 무엇일까?

예를 들어 저장소에서 PostgreSQL이나 Spring Modulith를 발견하는 것과, 왜 그 기술을 선택했고 어떤 대안을 버렸는지 이해하는 것은 다른 일입니다.

코드는 보통 **무엇이 구현되어 있는지**를 보여줍니다. 반면 프로젝트를 안전하게 변경하려면 **왜 그렇게 되어 있는지**도 알아야 합니다.

사람끼리 오래 협업했다면 이 맥락이 회의나 경험으로 남아 있을 수 있습니다. 하지만 새 팀원이나 AI 에이전트에게는 그런 암묵지가 없습니다. 메신저에서 한 번 합의하고 끝낸 결정은 다음 작업에서는 사실상 사라진 정보가 될 수 있습니다.

그래서 에이전트에게 일을 맡길수록 중요한 판단을 저장소 안에 남겨야 한다는 생각이 들었습니다.

```text
코드        현재 구현을 기억한다
테스트      지켜야 할 동작을 기억한다
API 명세   시스템 사이의 계약을 기억한다
ERD        데이터 구조를 기억한다
ADR        선택의 이유를 기억한다
AGENTS.md   에이전트가 이 기억을 찾는 방법을 알려준다
```

문서를 많이 만드는 것이 목적은 아닙니다. 코드에서 알 수 없는 정보를 필요한 위치에 남기는 것이 핵심입니다.

## 문서마다 서로 다른 질문을 맡긴다

프로젝트 문서가 복잡해지는 가장 쉬운 방법은 하나의 문서에 모든 내용을 넣는 것입니다.

`README.md` 하나에 제품 설명, 기술 스택, API 명세, DB 구조, 배포 명령, 과거 결정까지 전부 넣으면 처음에는 편합니다. 하지만 프로젝트가 바뀔수록 같은 정보가 여러 문단에 반복되고, 어디를 고쳐야 하는지 알기 어려워집니다.

별찌는 문서를 역할에 따라 나누고 있습니다.

```text
docs/product/       제품 요구사항과 단계별 범위
docs/engineering/   API, ERD, 인프라, 기술, 데이터 소싱
docs/decisions/     ADR
docs/operations/    협업, 배포, 법률, 운영 절차
docs/team-logs/     최근 작업 맥락
```

각 문서는 다음과 같은 질문에 답합니다.

| 문서             | 답해야 하는 질문                               |
| ---------------- | ---------------------------------------------- |
| 제품 문서        | 누구의 어떤 문제를 왜 해결하는가?              |
| Linear 이슈      | 지금 무엇을 어디까지 구현하는가?               |
| API 명세         | 클라이언트와 서버가 지켜야 할 계약은 무엇인가? |
| ERD·마이그레이션 | 데이터를 어떤 구조로 저장하는가?               |
| ADR              | 왜 이 선택을 했고 어떤 대안을 포기했는가?      |
| 운영 문서        | 배포·장애·협업 상황에서 어떻게 행동하는가?     |
| `AGENTS.md`      | 에이전트는 어떤 작업에서 어떤 문서를 읽는가?   |

이렇게 역할을 나누면 정보가 충돌했을 때 무엇을 우선해야 하는지도 정할 수 있습니다.

별찌의 `AGENTS.md`에는 실제로 다음과 같은 우선순위가 있습니다.

```text
1. 현재 Linear 이슈의 완료 조건
2. CONTRIBUTING.md와 PR 템플릿
3. 팀 운영 문서와 최근 작업 기록
4. 관련 ADR
5. 엔지니어링 문서
6. 제품 문서
```

오래된 전체 설계 문서에는 미래 기능이 포함되어 있을 수 있지만, 지금 구현할 범위는 현재 Linear 이슈가 더 정확할 수 있습니다. 반대로 이슈에 적혀 있지 않은 장기적인 기술 제약은 ADR에서 찾아야 할 수 있습니다.

중요한 것은 “항상 이 문서가 절대적으로 우선한다”가 아니라, 서로 다른 문서가 담당하는 시간과 범위를 구분하는 것입니다.

## ADR은 선택의 결과보다 선택의 이유를 남긴다

ADR은 Architecture Decision Record의 약자입니다. 이름 그대로 중요한 아키텍처 결정을 한 건씩 기록하는 문서입니다.

별찌의 `docs/decisions/`에는 데이터·검색 스택, Spring Modulith, OCI 인프라, 자체 OAuth, POC 우선 개발, Turborepo 같은 결정을 다룬 ADR이 있습니다.

보통 ADR은 다음 내용을 담습니다.

```text
상황: 왜 결정이 필요했는가
결정: 무엇을 선택했는가
근거: 왜 이 선택이 적절하다고 판단했는가
대안: 무엇을 검토했고 왜 선택하지 않았는가
결과: 이 결정으로 어떤 제약과 비용이 생기는가
상태: proposed / accepted / superseded / deprecated
```

여기서 특히 중요한 부분은 대안과 상태라고 생각합니다.

과거에 Elasticsearch를 사용하지 않기로 했더라도 상황이 바뀌면 다시 검토할 수 있습니다. 이때 이전 문서를 조용히 수정하면 당시 왜 그런 결정을 내렸는지 사라집니다. 대신 새로운 ADR이 이전 ADR을 `superseded`했다고 표시하면 결정의 흐름을 보존할 수 있습니다.

```text
과거 상황에서 내린 결정
→ 새로운 조건 발생
→ 새 ADR 작성
→ 이전 ADR을 superseded 처리
```

이 구조는 AI 에이전트에게도 유용합니다.

에이전트가 현재 코드만 읽으면 과거에 버린 대안을 다시 제안할 수 있습니다. 하지만 ADR을 읽으면 “이 방법은 이미 검토했고, 이런 이유로 채택하지 않았다”는 사실을 알 수 있습니다. 반대로 재검토 조건이 충족됐다면 기존 결정을 무조건 지키는 대신 새 ADR 초안을 제안할 수도 있습니다.

다만 에이전트가 ADR의 상태까지 임의로 확정하게 해서는 안 된다고 생각합니다.

```text
에이전트: 상황 정리, 대안 조사, proposed ADR 초안 작성
사람: 트레이드오프 판단, 합의, accepted 승인
```

에이전트는 결정을 위한 자료와 초안을 만들 수 있지만, 비용과 책임이 따르는 최종 결정은 사람이 가져가는 편이 안전합니다.

## AGENTS.md는 모든 문서를 넣는 창고가 아니라 라우터다

에이전트에게 프로젝트 정보를 전달하려고 하면 `AGENTS.md` 하나에 모든 내용을 넣고 싶어집니다.

하지만 제품 요구사항, API 전체 명세, DB 테이블, 배포 절차, 코딩 규칙을 모두 한 파일에 넣으면 금방 길어집니다. 매 작업마다 필요하지 않은 내용까지 컨텍스트에 들어가고, 일부 내용이 바뀔 때마다 같은 파일을 계속 수정해야 합니다.

그래서 `AGENTS.md`는 지식 창고보다 **문서 라우터**에 가깝게 사용하는 편이 좋았습니다.

예를 들면 다음과 같습니다.

```text
API 변경
→ API 명세와 인증 규칙 확인
→ 관련 API·보안 ADR 확인

DB 변경
→ Flyway migration 확인
→ ERD와 데이터 관련 ADR 확인

배포 변경
→ 인프라 문서와 Runbook 확인
→ 배포 관련 ADR 확인

작업 완료 전
→ 테스트 실행
→ git diff 확인
→ PR 템플릿의 영향 범위 작성
```

에이전트가 모든 문서를 매번 읽는 것이 아니라, 변경하려는 영역에 맞는 문서를 선택하게 하는 것입니다.

별찌에서는 `AGENTS.md`가 다음과 같은 안정적인 규칙을 담당합니다.

- 작업 범위는 현재 Linear 이슈에서 확인한다.
- API 변경은 API 규약을 따른다.
- 아키텍처·정책 변경은 관련 ADR을 참조하거나 새 ADR을 작성한다.
- 사용자 행동이 바뀌면 관련 문서를 함께 수정한다.
- 작업을 완료하기 전에 테스트와 Git 상태를 확인한다.
- PR 본문은 저장소의 템플릿을 따른다.

이 규칙들이 있으면 매번 긴 프롬프트로 프로젝트 운영 방식을 다시 설명할 필요가 줄어듭니다.

저는 이 구조를 다음과 같이 이해했습니다.

```text
문서      = 프로젝트의 기억
AGENTS.md = 기억을 찾는 지도
테스트·CI = 기억이 실제 코드에서 지켜지는지 확인하는 장치
```

## 별찌는 어디까지 하고 있었을까

대화를 나눈 뒤 실제 별찌 저장소를 다시 확인해봤습니다.

잘되어 있는 부분은 생각보다 분명했습니다.

- 제품·엔지니어링·의사결정·운영 문서가 역할별로 구분되어 있었습니다.
- 중요한 기술과 제품 결정이 ADR로 남아 있었습니다.
- `accepted`, `proposed`, `superseded` 상태를 구분하고 있었습니다.
- `AGENTS.md`가 정보의 우선순위와 작업별 참고 문서를 알려주고 있었습니다.
- PR 템플릿에서 API, DB 스키마, 환경 변수, 문서 영향을 확인하고 있었습니다.
- Flyway migration, Hibernate schema validation, Springdoc OpenAPI처럼 일부 문서는 실행 가능한 설정과 연결되어 있었습니다.

즉, 별찌는 이미 단순히 문서를 모아두는 프로젝트보다 **문서를 참고해 사람과 에이전트가 작업하는 프로젝트**에 가까웠습니다.

하지만 완전한 Living Documentation이라고 부르기에는 부족한 부분도 있었습니다.

가장 작은 예는 개발 서버 주소였습니다. `API.md`에는 개발 주소가 `http://localhost:3000`으로 적혀 있었지만, 실제 Spring Boot 설정의 서버 포트는 `8080`이었습니다. `3000`은 웹 애플리케이션 주소에 가까웠습니다.

```text
API.md             http://localhost:3000
application.yaml   server.port: 8080
```

문서를 꼼꼼하게 만들었더라도 코드와 자동으로 비교하지 않으면 이런 차이가 생길 수 있다는 뜻입니다.

DB도 비슷합니다. 별찌에는 사람이 읽고 시각화하기 좋은 `ERD.dbml`과 실제 DB 변경에 사용하는 Flyway migration이 함께 있습니다. 하지만 둘 사이의 차이를 CI가 자동으로 검사하지는 않습니다.

```text
Flyway migration 변경
→ 실제 DB 구조는 바뀜
→ ERD를 깜빡하면 문서는 이전 상태로 남음
```

ADR에도 모듈 경계와 운영 원칙이 기록되어 있지만, 모든 결정이 테스트나 정적 검사로 강제되는 것은 아닙니다. 에이전트가 문서를 읽지 않거나 잘못 해석해도 일반 테스트는 통과할 수 있습니다.

이 경험에서 얻은 가장 중요한 교훈은 이것이었습니다.

> 문서가 없는 것만큼이나, 실제 코드와 맞지 않는 문서도 위험하다.

에이전트는 제공된 컨텍스트를 활용합니다. 그런데 그 컨텍스트가 오래됐다면 더 자신 있게 잘못된 방향으로 갈 수도 있습니다.

## 문서를 작성하는 것에서 검증하는 것으로

문서를 프로젝트의 기억으로 사용하려면 각 정보의 원본을 명확하게 해야 합니다.

예를 들어 API 관련 정보를 컨트롤러, Markdown, Swagger, 프론트엔드 타입에 각각 따로 작성하면 어느 것이 진짜인지 알기 어렵습니다.

프로젝트마다 선택은 다를 수 있지만, 별찌에서는 다음과 같은 방향을 생각해볼 수 있습니다.

```text
API의 실행 계약
원본: Springdoc이 생성하는 OpenAPI
설명 문서: API.md
검증: contract test와 OpenAPI diff

DB 구조
원본: Flyway migration
설명 문서: ERD.dbml
검증: migration test와 schema drift check

아키텍처 결정
원본: accepted ADR
현재 구조 요약: engineering 문서
검증: Modulith·ArchUnit 같은 구조 테스트
```

여기서 모든 설명 문서를 자동 생성해야 한다는 뜻은 아닙니다.

사람이 작성한 문서에는 코드에서 생성하기 어려운 맥락과 이유가 필요합니다. 반면 엔드포인트 목록, 필드 이름, 실제 DB 컬럼처럼 코드와 정확히 일치해야 하는 정보는 가능하면 실행 가능한 원본에서 가져오거나 자동으로 비교하는 편이 안전합니다.

```text
사람이 기록해야 하는 것
- 문제 상황
- 대안
- 선택 이유
- 트레이드오프
- 운영상 판단

자동으로 검증하기 좋은 것
- API path와 schema
- DB table과 column
- 문서 내부 링크
- 모듈 의존성
- 테스트와 빌드 결과
```

문서 작성의 다음 단계는 더 많은 문서를 만드는 것이 아니라, 문서가 여전히 맞는지 확인하는 루프를 만드는 것입니다.

---

## 처음부터 모든 문서를 만들 필요는 없었다

별찌에는 문서 관리의 반대쪽 교훈도 있습니다.

초기에는 제품과 기술을 꼼꼼하게 준비하면서 짧은 기간에 많은 Linear 이슈, ERD 테이블, ADR, 운영 문서가 만들어졌습니다. 하지만 실제로는 아직 핵심 기술 가능성을 확인하는 POC 단계였습니다.

결국 ADR 0014를 통해 방향을 다시 정리했습니다.

> 처음부터 production-ready 구조를 완성하려 하지 말고, 핵심 가설을 작은 POC로 검증한 뒤 점진적으로 확장한다.

이 결정은 문서가 중요하다는 주장과 충돌하지 않습니다. 오히려 어떤 문서를 언제 만들어야 하는지 알려줍니다.

작은 프로젝트를 시작한다면 처음부터 수십 개의 문서가 필요하지 않습니다. 저는 다음 정도로 시작해도 충분하다고 생각합니다.

```text
README.md
- 프로젝트 목적과 실행 방법

AGENTS.md
- 에이전트의 작업·검증 규칙과 문서 지도

API 명세
- 프론트엔드와 백엔드 사이의 현재 계약

DB migration
- 실행 가능한 데이터 구조의 원본

ADR
- 되돌리기 어렵고 여러 작업에 영향을 주는 결정만 기록
```

그리고 반복해서 문제가 생길 때 문서를 추가합니다.

- API가 자주 어긋나면 contract test를 붙입니다.
- DB를 이해하기 어렵다면 ERD를 추가합니다.
- 같은 논쟁이 반복되면 ADR을 남깁니다.
- 배포 실수가 반복되면 Runbook을 만듭니다.
- 에이전트가 같은 실수를 반복하면 `AGENTS.md`나 테스트를 보강합니다.

이 방식이 문서를 위한 문서화를 피하면서도 프로젝트의 중요한 기억을 남기는 현실적인 방법에 가깝다고 느꼈습니다.

---

## 마무리

처음에는 문서를 개발이 끝난 뒤 정리하는 기록이라고 생각했습니다.

그런데 AI 에이전트와 프로젝트를 진행하면서 문서의 역할이 조금 다르게 보이기 시작했습니다. 에이전트는 코드를 빠르게 읽고 수정할 수 있지만, 우리가 왜 그런 결정을 내렸는지는 자동으로 기억하지 못합니다.

그래서 API 명세는 시스템 사이의 계약을 기억하고, ERD와 migration은 데이터 구조를 기억하고, ADR은 선택의 이유를 기억합니다. `AGENTS.md`는 에이전트에게 그 기억을 언제 찾아야 하는지 알려줍니다.

```text
API 명세   = 무엇을 약속했는가
ERD        = 데이터를 어떻게 바라보는가
ADR        = 왜 이 선택을 했는가
AGENTS.md  = 작업할 때 무엇을 먼저 읽는가
테스트·CI  = 그 약속과 결정이 실제로 지켜지는가
```

다만 문서가 많다고 자동으로 좋은 프로젝트가 되는 것은 아니었습니다. 실제 코드와 맞지 않는 문서는 에이전트에게 잘못된 컨텍스트를 줄 수 있습니다. 별찌에서도 API 주소나 ERD 동기화처럼 수동 관리의 한계가 보였습니다.

그래서 앞으로는 문서를 더 많이 만드는 것보다 다음 세 가지를 먼저 생각해보려고 합니다.

1. 이 정보의 원본은 무엇인가?
2. 에이전트는 어떤 작업에서 이 문서를 읽어야 하는가?
3. 코드와 문서가 어긋났을 때 어떻게 발견할 것인가?

AI 에이전트 시대의 문서는 설명을 위한 부가물이 아니라, 다음 작업의 입력이 됩니다.

좋은 문서는 에이전트에게 정답을 대신 알려주는 문서가 아닙니다. 사람이 내린 결정과 검증 기준을 잊지 않고 다음 작업까지 전달하는 문서에 더 가깝다고 생각합니다.
