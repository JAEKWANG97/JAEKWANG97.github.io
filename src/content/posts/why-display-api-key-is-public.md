## 들어가며

최근에 쇼핑몰 상품 검색 API를 붙이는 작업을 하다가 `DISPLAY_API_KEY`라는 값을 봤습니다.

상황은 이랬습니다. 특정 쇼핑몰의 검색 페이지에서는 상품 목록을 잘 보여주고 있었고, 브라우저 네트워크 탭을 보면 내부적으로 상품 검색 API를 호출하고 있었습니다. 그런데 그 API를 직접 호출하려고 하니 그냥 요청만 보내서는 동작하지 않았습니다.

요청 헤더에 이런 값이 필요했습니다.

```http
DISPLAY-API-KEY: ...
```

처음에는 조금 이상하게 느껴졌습니다.

“API key라고? 그럼 비밀키 아닌가?”

그런데 검색 페이지 HTML을 확인해보니, 이 값은 페이지 안에 그대로 들어 있었습니다. 브라우저에서 볼 수 있는 값이었던 겁니다. 이름은 `API_KEY`인데 공개되어 있는 상황이었습니다.

그래서 자연스럽게 이런 질문이 생겼습니다.

> 검색에 필요한 `DISPLAY_API_KEY`는 왜 공개되어 있을까?

이번 글은 그 질문에 대한 정리입니다. 결론부터 말하면, 이런 키는 보통 서버 비밀키라기보다 **브라우저가 쓰는 public client key**에 가깝습니다.

## 프론트엔드가 직접 API를 호출하면 값은 공개될 수밖에 없다

웹페이지가 동작하는 방식을 생각해보면 이유는 단순합니다.

사용자가 쇼핑몰 검색 페이지에 들어가면 브라우저는 HTML, CSS, JavaScript를 내려받습니다. 그리고 그 JavaScript가 다시 상품 검색 API를 호출해서 상품 목록을 가져옵니다.

흐름을 단순화하면 이렇습니다.

```text
브라우저
→ 검색 페이지 HTML/JS 다운로드
→ JS가 상품 검색 API 호출
→ 상품 목록 렌더링
```

만약 상품 검색 API가 `DISPLAY_API_KEY` 헤더를 요구한다면, 브라우저의 JavaScript는 그 값을 알고 있어야 합니다. 브라우저가 알아야 하는 값은 결국 사용자도 볼 수 있습니다.

브라우저 개발자 도구를 열면 네트워크 요청 헤더도 볼 수 있고, 내려받은 HTML이나 JavaScript 안의 설정값도 볼 수 있기 때문입니다.

즉, 프론트엔드에서 직접 쓰는 값이라면 “완전히 숨기는 것”은 불가능합니다.

그래서 이런 값은 애초에 서버 비밀키처럼 설계하면 안 됩니다.

## 그럼 왜 API key라는 이름을 붙일까?

이 지점이 헷갈립니다. `API_KEY`라는 이름만 보면 보통 비밀키를 떠올립니다.

예를 들어 서버에서 결제 API를 호출할 때 쓰는 secret key, 관리자 API를 호출할 때 쓰는 token, OAuth client secret 같은 값은 절대 노출되면 안 됩니다. 이런 값이 유출되면 결제, 개인정보, 관리자 기능 같은 민감한 작업이 위험해질 수 있습니다.

그런데 브라우저에 공개되어 있는 `DISPLAY_API_KEY`는 성격이 다릅니다.

이런 값은 대체로 “비밀번호”라기보다는 “클라이언트 식별자”에 가깝습니다.

예를 들면 이런 용도로 쓸 수 있습니다.

- 이 요청이 PC 웹에서 온 요청인지 구분하기
- 모바일 웹, 앱, PC 웹 같은 채널을 나누기
- API gateway에서 특정 display API만 허용하기
- 키 단위로 rate limit을 걸기
- 로그에서 어떤 클라이언트가 호출했는지 추적하기
- 무키 요청이나 엉뚱한 클라이언트의 요청을 걸러내기

즉, `DISPLAY_API_KEY`는 “이 사용자가 누구인가?”를 증명하는 값이라기보다, “이 요청이 어떤 클라이언트 흐름에서 온 것인가?”를 표시하는 값에 가깝습니다.

비유하면 집 열쇠라기보다는 입장 스티커에 가깝습니다.

스티커는 눈에 보입니다. 누구나 볼 수 있습니다. 하지만 그 스티커 하나만으로 금고를 열 수 있으면 안 됩니다. 공개되어도 되는 값이라면, 공개되어도 안전한 범위의 API에만 권한이 있어야 합니다.

## 공개 client key와 서버 secret key는 역할이 다르다

이 둘을 구분하는 게 중요합니다.

공개 client key는 브라우저나 앱에 포함될 수 있습니다. 대표적으로 이런 것들이 있습니다.

```text
Google Maps browser API key
Firebase web config apiKey
Sentry DSN
Kakao/Naver JavaScript SDK app key
Stripe publishable key
Algolia search-only API key
```

이 값들은 노출되는 것을 전제로 설계됩니다. 대신 권한이 제한되어 있거나, origin 제한, rate limit, 도메인 제한 같은 보호 장치와 함께 사용됩니다.

반대로 서버 secret key는 절대 클라이언트에 내려가면 안 됩니다.

```text
결제 secret key
관리자 API token
DB password
개인정보 조회 권한이 있는 access token
OAuth client secret
```

이런 값은 서버 안에서만 사용해야 합니다. 브라우저에 들어가는 순간 유출된 것으로 봐야 합니다.

그래서 어떤 값을 봤을 때 중요한 질문은 “이름에 key가 들어가냐?”가 아닙니다.

더 중요한 질문은 이것입니다.

> 이 키로 무엇을 할 수 있는가?

상품 목록 조회처럼 이미 공개된 데이터를 읽는 정도라면 public client key일 수 있습니다. 하지만 사용자 정보 조회, 주문 생성, 결제, 관리자 작업이 가능하다면 절대 공개되면 안 됩니다.

## 검색 API에서 이런 키를 쓰는 이유

그럼 상품 검색 API에서 굳이 이런 키를 요구하는 이유는 무엇일까요?

가장 현실적인 이유는 운영상의 제어입니다.

공개 상품 검색 API라고 해도 아무 요청이나 무제한으로 받아들이고 싶지는 않을 겁니다. 검색은 비용이 드는 작업입니다. 검색 인프라, 캐시, 랭킹, 로그 적재, 추천 시스템과 연결될 수도 있습니다.

그래서 서비스는 요청을 어느 정도 분류하고 싶어합니다.

```text
이 요청은 PC 웹 검색 화면에서 온 요청인가?
모바일 앱에서 온 요청인가?
외부 봇처럼 보이는 요청인가?
어떤 키에서 트래픽이 많이 발생하고 있는가?
특정 클라이언트만 허용해야 하는 API인가?
```

`DISPLAY_API_KEY` 같은 값은 이 분류에 도움을 줍니다.

물론 이것만으로 강한 보안이 되지는 않습니다. 공개된 값이기 때문입니다. 하지만 보안은 보통 하나의 장치로만 이루어지지 않습니다.

실제로는 여러 신호를 함께 봅니다.

```text
DISPLAY_API_KEY
Origin
Referer
User-Agent
Cookie/session
요청 파라미터
rate limit
서버 측 권한 체크
```

이 중 `DISPLAY_API_KEY`는 요청을 구분하는 하나의 힌트로 볼 수 있습니다.

## 하드코딩하지 않고 런타임에 읽는 이유

이번 작업에서는 이 값을 코드에 직접 박아두지 않았습니다.

대신 검색 페이지를 먼저 요청하고, 그 페이지 안에 있는 runtime 설정에서 `DISPLAY_API_KEY`를 읽은 다음 상품 검색 API를 호출하는 방식으로 처리했습니다.

흐름은 이렇습니다.

```text
1. 검색 페이지 요청
2. HTML 안의 DISPLAY_API_KEY 추출
3. 상품 검색 API 호출 시 헤더에 포함
4. 검색 결과를 공통 상품 후보로 변환
```

이렇게 한 이유는 간단합니다.

첫째, 공개 키라고 해도 외부 서비스의 값을 우리 저장소에 하드코딩하고 싶지는 않았습니다. 값이 바뀌면 코드 수정이 필요하고, “외부 서비스 키를 코드에 박아두었다”는 찝찝함도 생깁니다.

둘째, 실제 웹 클라이언트가 쓰는 최신 값을 따라가는 편이 더 자연스럽습니다. 서비스가 키를 바꾸면 페이지에 내려오는 값도 바뀔 가능성이 높습니다. 그러면 우리도 페이지에서 다시 읽으면 됩니다.

셋째, 이 API는 공식적으로 제공된 외부 개발자 API라기보다 웹 클라이언트가 사용하는 내부 display API에 가깝습니다. 이런 API는 계약이 안정적이지 않을 수 있습니다. 그래서 특정 키 값을 전제로 삼는 것보다, 현재 페이지의 runtime 설정을 읽는 방식이 조금 더 유연합니다.

## 그래도 조심해야 하는 부분

그렇다고 이런 방식을 아무 생각 없이 써도 된다는 뜻은 아닙니다.

공개 client key를 사용하는 내부 API는 언제든 바뀔 수 있습니다.

예를 들어 이런 일이 생길 수 있습니다.

- 키 이름이 바뀐다
- HTML 구조가 바뀐다
- API 요청 body가 바뀐다
- 헤더 정책이 바뀐다
- Origin이나 Referer 검사가 강화된다
- rate limit이 강해진다
- 특정 요청 패턴이 차단된다

특히 공식 API 문서가 없는 경우라면 더 조심해야 합니다. 지금 동작한다고 해서 안정적인 계약이라고 볼 수는 없습니다.

그래서 이런 provider를 붙일 때는 실패를 전제로 설계하는 편이 안전합니다.

예를 들어 여러 검색 provider를 함께 사용하는 구조라면, 하나의 provider가 실패해도 전체 비교 검색이 죽지 않게 해야 합니다.

```text
Naver 실패 → Musinsa/W Concept 결과는 계속 사용
W Concept 실패 → Naver/Musinsa 결과는 계속 사용
특정 provider 오류 → 전체 /api/compare 오류로 번지지 않게 처리
```

이렇게 해두면 외부 사이트 구조가 바뀌어도 서비스 전체 장애로 이어질 가능성을 줄일 수 있습니다.

## 이 경험에서 다시 확인한 것

이번에 `DISPLAY_API_KEY`를 보면서 다시 느낀 건, 키라는 이름만 보고 바로 판단하면 안 된다는 점이었습니다.

처음에는 “왜 API key가 공개되어 있지?”라는 생각이 들 수 있습니다. 저도 그랬습니다. 하지만 웹 프론트엔드가 직접 API를 호출하는 구조라면, 브라우저가 써야 하는 값은 공개될 수밖에 없습니다.

중요한 건 공개 여부 자체보다 역할입니다.

- 이 값은 사용자를 인증하는가?
- 민감한 작업을 할 수 있는가?
- 읽기 전용 공개 데이터에만 접근하는가?
- 도메인, origin, rate limit 같은 제한이 있는가?
- 유출되었을 때 어떤 피해가 가능한가?

이 질문에 따라 public client key인지, 숨겨야 하는 secret인지가 갈립니다.

`DISPLAY_API_KEY`는 이름은 key지만, 실제 역할은 공개 클라이언트 식별자에 가깝습니다. 그래서 HTML에 포함되어 있는 것이 이상한 일은 아닙니다.

다만 이것을 사용하는 쪽에서는 착각하지 않아야 합니다.

“공개되어 있으니 마음대로 써도 된다”가 아니라,
“공개되는 것을 전제로 한 제한된 키이고, 언제든 정책이 바뀔 수 있다”에 가깝습니다.

## 마무리

이번 질문을 한 문장으로 정리하면 이렇습니다.

> `DISPLAY_API_KEY`가 공개되어 있는 이유는 브라우저가 직접 써야 하는 public client key이기 때문이다.

그리고 백엔드 입장에서 더 중요한 정리는 이것입니다.

> key라는 이름보다 중요한 것은 그 key로 무엇을 할 수 있느냐다.

브라우저에 공개되는 키는 공개되어도 안전한 범위 안에서만 동작해야 합니다. 반대로 서버 secret은 절대 클라이언트에 내려가면 안 됩니다.

이번 작업은 단순히 외부 검색 API를 하나 붙이는 일이었지만, 그 안에서 프론트엔드 API, public key, rate limit, provider failure isolation 같은 주제를 함께 다시 생각해보게 됐습니다.

이런 작은 의문을 그냥 넘기지 않고 구조로 정리해두면, 다음에 비슷한 API를 만났을 때 조금 더 차분하게 판단할 수 있을 것 같습니다.
