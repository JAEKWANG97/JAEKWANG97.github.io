## 들어가며

이전 글에서는 서비스에서 생긴 데이터가 어디로 흘러가는지 큰 그림을 봤습니다.

운영 DB에 데이터가 생기고, 그 데이터가 분석이나 리포트, 추천, 검색, ML, RAG 같은 곳에서 다시 쓰이려면 데이터 파이프라인과 분석 저장소가 필요하다는 이야기였습니다.

그 글의 마지막에서 다음에는 `Data Warehouse / Data Lake / Lakehouse`를 더 쪼개서 보겠다고 했습니다.

이번 글은 그 후속편입니다.

전체 지도에서 보면 이번 글은 “Storage” 영역을 다룹니다.

```text
Source -> Ingestion -> Storage -> Processing -> Metadata -> Query -> Consumption
                          ↑
                       이번 글
```

질문은 단순합니다.

> 분석에 쓸 데이터는 어디에 저장해야 할까?

이 질문에 대한 대표적인 답이 `Data Warehouse`, `Data Lake`, `Lakehouse`입니다.

처음에는 세 단어가 비슷하게 느껴집니다. 전부 데이터를 저장하는 곳처럼 보입니다. 그런데 각각이 나온 배경과 잘하는 일이 다릅니다.

저는 이 셋을 이렇게 구분하면 이해하기 편했습니다.

```text
Data Warehouse
  = 분석하기 좋게 정리된 데이터 창고

Data Lake
  = 다양한 원본 데이터를 넓게 담아두는 저장소

Lakehouse
  = Lake의 유연성과 Warehouse의 관리 기능을 합치려는 시도
```

이 글에서는 각각을 따로 보고, 왜 다음 개념이 필요해졌는지 흐름으로 정리해보겠습니다.

---

## 1. 먼저 운영 DB와 분석 저장소를 구분해야 한다

Data Warehouse나 Data Lake를 보기 전에 먼저 운영 DB와 분석 저장소를 구분해야 합니다.

서비스를 만들면 보통 데이터는 운영 DB에 먼저 저장됩니다.

예를 들어 쇼핑몰 서비스라면 이런 데이터가 있습니다.

- 회원 정보
- 상품 정보
- 주문 정보
- 결제 상태
- 배송 상태
- 장바구니

이 데이터는 서비스가 정상적으로 동작하기 위해 필요합니다.

사용자가 결제 버튼을 눌렀을 때 주문이 정확히 생성되어야 하고, 재고가 차감되어야 하고, 결제 상태가 바뀌어야 합니다.

이런 운영 DB는 보통 `OLTP` 성격을 가집니다.

`OLTP`는 Online Transaction Processing입니다.

쉽게 말하면:

> 서비스에서 발생하는 작은 단위의 거래를 빠르고 정확하게 처리하는 시스템

반면 분석은 성격이 다릅니다.

예를 들어 이런 질문을 생각해볼 수 있습니다.

- 지난 3개월 동안 카테고리별 매출은 어떻게 변했을까?
- 신규 가입자는 7일 뒤에도 남아 있을까?
- 어떤 검색어가 구매 전환으로 이어질까?
- 사용자 행동 로그를 기반으로 추천 모델을 만들 수 있을까?
- 매일 아침 비즈니스 지표 리포트를 만들 수 있을까?

이런 질문은 많은 데이터를 읽고, 묶고, 비교하고, 집계해야 합니다.

운영 DB에서 이런 분석 쿼리를 계속 실행하면 서비스 성능에 영향을 줄 수 있습니다.

그래서 보통 운영 DB와 분석 저장소를 분리합니다.

```text
운영 DB
  = 서비스 요청 처리

분석 저장소
  = 많은 데이터를 읽고 분석
```

Data Warehouse, Data Lake, Lakehouse는 모두 이 “분석 저장소”를 어떻게 만들 것인가에 대한 답입니다.

## 2. Data Warehouse는 분석하기 좋게 정리된 창고다

Data Warehouse는 이름 그대로 데이터 창고입니다.

하지만 아무 데이터나 막 쌓아두는 창고는 아닙니다.

Data Warehouse는 **분석하기 좋게 정리된 데이터 저장소**에 가깝습니다.

예를 들어 회사에 여러 시스템이 있다고 해보겠습니다.

```text
주문 DB
회원 DB
상품 DB
결제 시스템
마케팅 광고 플랫폼
고객 문의 시스템
```

각 시스템에는 필요한 데이터가 따로 있습니다.

그런데 경영진이나 데이터 분석가는 이런 질문을 하고 싶습니다.

```text
이번 달 신규 고객의 구매 전환율은?
광고 캠페인별 매출 기여도는?
카테고리별 재구매율은?
고객 등급별 평균 주문 금액은?
```

이런 질문에 답하려면 여러 시스템의 데이터를 모아서 일관된 형태로 정리해야 합니다.

Data Warehouse는 이런 분석을 위해 데이터를 모델링합니다.

대표적으로 다음과 같은 형태가 나옵니다.

```text
fact_order
dim_user
dim_product
dim_date
```

`fact`는 실제로 발생한 사건이나 수치에 가까운 테이블입니다.

예를 들면 주문, 결제, 클릭, 매출 같은 것입니다.

`dimension`은 분석 기준이 되는 설명 정보에 가깝습니다.

예를 들면 사용자, 상품, 날짜, 지역, 카테고리 같은 것입니다.

이렇게 정리해두면 분석 쿼리를 작성하기 쉬워집니다.

```sql
SELECT
  d.month,
  p.category,
  sum(f.order_amount) AS revenue
FROM fact_order f
JOIN dim_date d ON f.date_id = d.date_id
JOIN dim_product p ON f.product_id = p.product_id
GROUP BY d.month, p.category;
```

Data Warehouse의 핵심은 “분석하기 좋은 구조”입니다.

그래서 보통 다음 특성이 중요합니다.

- 데이터가 어느 정도 정제되어 있다.
- 스키마가 명확하다.
- 비즈니스 지표를 계산하기 좋다.
- SQL 분석에 적합하다.
- 대시보드와 리포트에 자주 연결된다.

대표적인 Data Warehouse 계열 제품으로는 Snowflake, BigQuery, Redshift 같은 것들이 있습니다.

전통적으로는 Teradata, Oracle DW 같은 시스템도 있었습니다.

## 3. Data Warehouse의 장점과 한계

Data Warehouse의 장점은 분명합니다.

분석하기 좋습니다.

데이터가 잘 정리되어 있고, 스키마가 명확하고, 비즈니스 기준에 맞춰 모델링되어 있기 때문입니다.

대시보드나 리포트에는 특히 잘 맞습니다.

예를 들어 매출, 주문 수, 고객 수, 전환율 같은 지표를 안정적으로 계산해야 한다면 Data Warehouse가 좋습니다.

하지만 한계도 있습니다.

가장 큰 한계는 유연성입니다.

Warehouse에 넣기 전에 보통 데이터를 정리하고 모델링해야 합니다. 그런데 모든 데이터의 사용처를 미리 알기는 어렵습니다.

예를 들어 이런 데이터가 있다고 해보겠습니다.

- 클릭 이벤트 원본 로그
- 검색어 로그
- 서버 access log
- 모바일 앱 이벤트
- JSON 형태의 실험 로그
- 이미지나 문서 파일

이런 데이터는 당장 어떤 분석 모델로 정리해야 할지 모를 수 있습니다.

그래도 나중에 추천, 검색 품질 개선, 이상 탐지, ML 학습, RAG 등에 쓸 수 있습니다.

문제는 Warehouse 중심으로만 생각하면, 정제되지 않은 다양한 원본 데이터를 폭넓게 담아두기 어렵다는 점입니다.

그래서 Data Lake라는 개념이 중요해집니다.

## 4. Data Lake는 원본에 가까운 데이터를 넓게 담는 곳이다

Data Lake는 이름 그대로 데이터 호수입니다.

Warehouse가 정리된 창고라면, Lake는 다양한 데이터를 넓게 받아들이는 저장소에 가깝습니다.

Data Lake에는 이런 것들이 들어갈 수 있습니다.

- 운영 DB에서 추출한 데이터
- 서버 로그
- 클릭 이벤트
- 앱 이벤트
- JSON 파일
- CSV 파일
- Parquet 파일
- 이미지, 문서, 음성 같은 비정형 데이터

Data Lake의 핵심은 유연성입니다.

처음부터 모든 스키마와 분석 목적을 확정하지 않아도 됩니다.

원본에 가까운 데이터를 먼저 저장해두고, 나중에 필요한 목적에 맞게 가공할 수 있습니다.

예를 들어 사용자 행동 이벤트를 생각해보겠습니다.

지금 당장은 단순히 “일별 클릭 수”만 보고 싶을 수 있습니다.

하지만 나중에는 같은 로그를 다음 용도로 다시 쓰고 싶을 수 있습니다.

- 추천 모델 학습
- 검색 랭킹 개선
- A/B 테스트 분석
- 이상 행동 탐지
- 사용자 여정 분석
- 세션 기반 WAU 계산

이런 경우 원본 이벤트를 너무 빨리 버리거나, 특정 리포트 형태로만 집계해두면 나중에 다시 활용하기 어렵습니다.

Data Lake는 이런 문제를 해결합니다.

> 일단 원본에 가까운 데이터를 보존하고, 필요할 때 다시 가공할 수 있게 하자.

## 5. Data Lake의 장점과 한계

Data Lake의 장점은 유연성입니다.

다양한 데이터를 담을 수 있고, 나중에 여러 목적에 맞게 다시 처리할 수 있습니다.

또한 보통 object storage나 분산 파일 시스템 위에 구축되기 때문에 많은 데이터를 비교적 저렴하게 저장할 수 있습니다.

예를 들어 클라우드에서는 이런 조합이 자주 나옵니다.

```text
AWS S3
Google Cloud Storage
Azure Data Lake Storage
HDFS
```

하지만 Data Lake에도 큰 문제가 있습니다.

정리 없이 계속 쌓기만 하면 나중에 찾기 어렵고, 믿기 어려워집니다.

이런 상태를 흔히 `Data Swamp`라고 부릅니다.

호수가 아니라 늪이 되는 것입니다.

예를 들어 Data Lake에 파일은 많은데 다음을 모른다고 해보겠습니다.

- 이 데이터는 어디서 왔는가?
- 누가 만든 데이터인가?
- 어떤 스키마인가?
- 중복은 없는가?
- 최신 데이터인가?
- 어떤 partition이 누락됐는가?
- 이 데이터를 써도 되는가?

이러면 데이터는 저장되어 있지만 실제로 쓰기 어렵습니다.

결국 Data Lake도 관리가 필요합니다.

파일만 쌓는 것이 아니라, metadata, schema, partition, 품질 검증, 접근 제어, lineage가 필요합니다.

이 고민이 Lakehouse로 이어집니다.

## 6. Lakehouse는 왜 나왔을까?

Lakehouse는 Data Lake와 Data Warehouse의 장점을 합치려는 접근입니다.

아주 단순하게 말하면:

```text
Data Lake의 저렴하고 유연한 저장 방식
  +
Data Warehouse의 테이블 관리와 신뢰성
```

을 함께 가져가려는 시도입니다.

Data Lake는 다양한 데이터를 담기 좋지만, 관리가 약하면 Data Swamp가 됩니다.

Data Warehouse는 분석하기 좋지만, 원본 보존과 유연성 측면에서 부담이 있을 수 있습니다.

Lakehouse는 이 사이에서 나온 개념입니다.

핵심 질문은 이것입니다.

> Data Lake 위의 파일들도 Warehouse처럼 신뢰할 수 있는 테이블로 다룰 수 없을까?

이 질문에서 Iceberg, Delta Lake, Hudi 같은 table format이 등장합니다.

이들은 단순히 Parquet 파일을 저장하는 것보다 더 많은 기능을 제공합니다.

- table schema 관리
- schema evolution
- ACID transaction
- snapshot
- time travel
- upsert/delete
- partition evolution

즉 Lakehouse는 “파일은 Lake에 두지만, 사용 경험은 Warehouse처럼 만들고 싶다”는 방향에 가깝습니다.

## 7. Warehouse, Lake, Lakehouse를 비교하면

세 개념을 표로 보면 조금 더 정리됩니다.

| 구분        | Data Warehouse                | Data Lake                      | Lakehouse                           |
| ----------- | ----------------------------- | ------------------------------ | ----------------------------------- |
| 핵심 목적   | 정제된 분석                   | 원본/다양한 데이터 저장        | Lake 위에서 신뢰 가능한 테이블      |
| 데이터 형태 | 구조화 데이터 중심            | 구조화/반구조화/비정형         | 주로 파일 기반 테이블               |
| 스키마      | 미리 설계                     | 느슨하거나 나중에 적용         | 테이블 포맷이 관리                  |
| 장점        | SQL 분석, 리포트, 지표        | 유연성, 원본 보존, 저렴한 저장 | 유연성과 신뢰성의 절충              |
| 단점        | 유연성 부족, 비용 부담        | 관리 안 하면 Data Swamp        | 운영 복잡도, 도구 이해 필요         |
| 예시        | BigQuery, Snowflake, Redshift | S3, GCS, ADLS, HDFS            | Iceberg, Delta Lake, Hudi 기반 구조 |

여기서 중요한 건 셋 중 하나만 정답이라고 보는 것이 아닙니다.

현실의 데이터 플랫폼은 이 개념들이 섞여 있습니다.

예를 들어:

```text
원본 로그는 Data Lake에 저장한다.
정제된 분석 테이블은 Data Warehouse에 둔다.
대규모 이벤트 테이블은 Lakehouse table format으로 관리한다.
```

이런 식으로 목적에 따라 조합할 수 있습니다.

## 8. 쇼핑몰 이벤트 로그로 다시 생각해보기

예를 들어 쇼핑몰 서비스에서 사용자 행동 로그가 생긴다고 해보겠습니다.

```text
사용자가 상품을 조회했다.
장바구니에 담았다.
구매했다.
검색어를 입력했다.
상품을 제거했다.
```

이 이벤트를 어디에 둘 수 있을까요?

먼저 원본 이벤트는 Data Lake에 저장할 수 있습니다.

```text
s3://data-lake/raw/events/
  dt=2026-05-23/
```

이 데이터는 원본에 가깝습니다. 나중에 여러 용도로 다시 쓸 수 있습니다.

그 다음 Spark 같은 처리 엔진으로 이 데이터를 정리할 수 있습니다.

```text
raw events
  -> sessionized events
  -> daily partitioned parquet
```

이렇게 만들어진 데이터는 분석하기 좋은 테이블이 됩니다.

Hive Metastore나 Glue Catalog에 등록하면 SQL로 조회할 수 있습니다.

```sql
SELECT count(DISTINCT user_id)
FROM sessionized_events
WHERE dt BETWEEN '2026-05-01' AND '2026-05-07';
```

그리고 매출 리포트나 핵심 KPI처럼 자주 쓰는 지표는 Data Warehouse 쪽에 모델링할 수도 있습니다.

```text
fact_order
dim_user
dim_product
```

만약 Data Lake 위에서 테이블 변경, schema evolution, snapshot 관리까지 필요해지면 Lakehouse table format을 고려할 수 있습니다.

이렇게 보면 Warehouse, Lake, Lakehouse는 따로 외울 단어가 아니라 데이터 활용 단계에 따라 자연스럽게 등장합니다.

## 9. 백엔드 개발자 입장에서 왜 중요할까

백엔드 개발자는 보통 운영 DB와 API를 먼저 다룹니다.

하지만 서비스가 커지면 백엔드가 만든 데이터는 분석과 ML, 검색, 추천으로 흘러갑니다.

이때 Data Warehouse, Data Lake, Lakehouse의 차이를 알면 시스템을 보는 시야가 넓어집니다.

예를 들어 이벤트 로그를 설계할 때도 질문이 달라집니다.

단순히:

> 로그를 남긴다.

가 아니라:

> 이 로그는 나중에 어디에 저장되고, 어떤 partition 기준으로 관리되고, 어떤 분석이나 모델 학습에 쓰일 수 있을까?

를 생각할 수 있습니다.

또 포트폴리오를 설명할 때도 달라집니다.

예를 들어 “상품 클릭 이벤트를 남겼습니다”보다 다음 설명이 더 설득력 있습니다.

> 상품 클릭 이벤트를 운영 DB와 분리된 분석 흐름으로 볼 수 있도록 설계했고, 원본 이벤트는 Data Lake에 보존한 뒤, Spark batch로 세션화된 Parquet 테이블을 만들 수 있다고 생각했습니다. 자주 조회하는 지표는 Data Warehouse나 mart 형태로 모델링할 수 있습니다.

아직 실제 회사 규모의 데이터 플랫폼을 운영해보지 않았더라도, 이런 관점이 있으면 백엔드 경험과 데이터 엔지니어링 경험이 이어집니다.

## 10. 세 개념을 한 문장으로 정리하면

저는 이렇게 기억하려고 합니다.

```text
Data Warehouse
  = 분석하기 좋게 정리된 데이터 저장소

Data Lake
  = 다양한 원본 데이터를 유연하게 담는 저장소

Lakehouse
  = Data Lake 위에서 Warehouse처럼 신뢰 가능한 테이블을 만들려는 구조
```

조금 더 이야기처럼 말하면 이렇습니다.

> Warehouse는 “잘 정리된 분석 창고”이고, Lake는 “다양한 데이터를 넓게 담는 원본 저장소”이고, Lakehouse는 “Lake에 쌓인 파일을 더 믿을 수 있는 테이블처럼 다루려는 시도”입니다.

이 차이를 이해하면 데이터 엔지니어링 용어들이 조금 덜 따로 놀게 됩니다.

Spark, Hive, Parquet, Iceberg 같은 구현체도 이 흐름 안에서 볼 수 있습니다.

```text
Data Lake에 파일이 쌓인다.
Spark가 그 파일을 처리한다.
Parquet과 partition으로 분석하기 좋게 저장한다.
Hive Metastore가 파일을 테이블처럼 설명한다.
Iceberg/Delta/Hudi는 Lakehouse table format으로 더 강한 테이블 기능을 제공한다.
```

이렇게 이어집니다.

## 마무리

이 글에서는 Data Warehouse, Data Lake, Lakehouse를 저장소 관점에서 정리했습니다.

중요한 질문은 이것이었습니다.

> 분석에 쓸 데이터는 어디에 저장해야 할까?

정리하면:

- 정제된 지표와 리포트 중심이면 Data Warehouse가 잘 맞습니다.
- 다양한 원본 데이터를 넓게 보존하려면 Data Lake가 필요합니다.
- Lake의 유연성을 유지하면서 테이블 신뢰성과 관리 기능을 강화하려면 Lakehouse가 등장합니다.

다음으로는 데이터를 저장소에 넣기 전과 후의 차이를 볼 수 있습니다.

즉 `ETL`과 `ELT`입니다.

데이터를 저장하기 전에 먼저 바꿀 것인가, 일단 저장한 뒤 저장소 안에서 바꿀 것인가.

이 질문을 이해하면 데이터 파이프라인이 어떤 방식으로 설계되는지 조금 더 선명해집니다.
