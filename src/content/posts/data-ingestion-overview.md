## 들어가며

이전 글에서는 분석용 데이터를 어디에 저장할지 봤습니다.

운영 DB만으로는 분석, 리포트, 추천, 검색, ML, RAG 같은 요구를 모두 감당하기 어렵기 때문에 `Data Warehouse`, `Data Lake`, `Lakehouse` 같은 분석 저장소가 필요하다는 이야기였습니다.

그런데 저장소가 있다고 해서 데이터가 저절로 들어오지는 않습니다.

운영 DB에 있는 주문 데이터, 애플리케이션에서 남긴 로그, 사용자가 클릭한 이벤트, 외부 API에서 받아온 데이터, 누군가 업로드한 CSV 파일은 모두 어딘가에서 생깁니다. 그리고 분석 저장소에서 쓰려면 그 데이터를 어떤 방식으로든 가져와야 합니다.

이번 글은 그 지점을 다룹니다.

전체 지도에서 보면 이번 글은 `Ingestion`, 즉 수집 영역입니다.

```text
Source -> Ingestion -> Storage -> Processing -> Metadata -> Query -> Consumption
              ↑
           이번 글
```

질문은 단순합니다.

> 데이터는 어떻게 분석 환경으로 흘러들어올까?

이 질문을 이해하면 `Batch`, `Streaming`, `CDC`, `Event`, `File Upload` 같은 단어가 조금 덜 따로 놀기 시작합니다.

이 단어들은 서로 완전히 다른 세계의 개념이라기보다, **데이터를 가져오는 방식의 차이**에 가깝습니다.

---

## 1. Ingestion은 데이터를 가져오는 입구다

`Ingestion`은 말 그대로 데이터를 먹어 넣는다는 뜻입니다.

데이터 엔지니어링에서는 보통 여러 Source에서 생긴 데이터를 분석 환경으로 가져오는 단계를 말합니다.

예를 들어 쇼핑몰 서비스를 생각해보겠습니다.

서비스 안에서는 계속 데이터가 생깁니다.

- 회원가입이 발생한다.
- 사용자가 상품을 조회한다.
- 검색어를 입력한다.
- 장바구니에 상품을 담는다.
- 결제를 한다.
- 배송 상태가 바뀐다.
- 리뷰를 작성한다.

이 데이터는 처음에는 각각 다른 곳에 생길 수 있습니다.

```text
운영 DB
애플리케이션 로그
사용자 행동 이벤트
외부 광고 플랫폼 API
CS 시스템
CSV 파일
```

이때 Ingestion의 역할은 이 데이터를 분석 환경으로 가져오는 것입니다.

```text
여러 Source
  -> Ingestion
  -> 분석 저장소
```

여기서 중요한 점은, 수집은 단순히 “복사”가 아니라는 것입니다.

데이터를 얼마나 자주 가져올지, 어떤 단위로 가져올지, 실패하면 어떻게 재처리할지, 중복은 어떻게 처리할지, 순서는 중요한지 같은 문제가 함께 따라옵니다.

그래서 Ingestion을 이해할 때는 도구 이름보다 먼저 이런 질문을 보는 편이 좋습니다.

- 데이터는 얼마나 자주 필요할까?
- 데이터가 늦게 들어와도 괜찮을까?
- 데이터가 중복으로 들어오면 문제가 될까?
- 데이터 순서가 중요할까?
- 원본 시스템에 부담을 주지 않을 수 있을까?
- 실패했을 때 다시 가져올 수 있을까?

이 질문에 따라 수집 방식이 달라집니다.

## 2. 배치 수집: 일정한 간격으로 모아서 가져오기

가장 이해하기 쉬운 방식은 배치 수집입니다.

배치 수집은 데이터를 실시간으로 계속 가져오는 것이 아니라, 일정한 시간 단위로 모아서 가져오는 방식입니다.

예를 들면 이런 식입니다.

```text
매일 새벽 2시
  어제 주문 데이터를 가져온다

매시간 정각
  지난 1시간의 로그 파일을 가져온다

매주 월요일
  외부 광고 플랫폼의 성과 데이터를 가져온다
```

배치 수집은 현실에서 아주 많이 쓰입니다.

모든 데이터가 실시간일 필요는 없기 때문입니다.

예를 들어 매일 아침 보는 매출 리포트라면, 어제까지의 데이터가 정확하게 들어오는 것이 더 중요할 수 있습니다. 1초 늦게 들어오는지 10분 늦게 들어오는지는 큰 문제가 아닐 수 있습니다.

배치 수집은 보통 이런 경우에 잘 맞습니다.

- 일간 리포트
- 월간 정산
- 주기적인 통계 집계
- 외부 API에서 주기적으로 가져오는 데이터
- 파일 단위로 전달되는 데이터

장점은 단순합니다.

구현과 운영이 상대적으로 이해하기 쉽고, 실패했을 때 특정 기간을 다시 처리하기도 좋습니다.

예를 들어 “2026년 5월 23일 데이터 수집이 실패했다”면, 그 날짜의 데이터를 다시 가져오면 됩니다.

```text
2026-05-22 OK
2026-05-23 실패 -> 다시 수집
2026-05-24 OK
```

다만 단점도 있습니다.

데이터가 어느 정도 늦게 들어옵니다. 매일 새벽에 수집한다면 오늘 낮에 발생한 이벤트는 내일 새벽이 되어서야 분석 저장소에 들어올 수 있습니다.

그래서 배치 수집은 보통 **정확성과 단순함이 중요하고, 아주 빠른 반영이 필요하지 않은 경우**에 잘 맞습니다.

## 3. 이벤트 수집: 발생할 때마다 흘려보내기

반대로 어떤 데이터는 발생하자마자 빠르게 흘러가야 합니다.

예를 들어 사용자의 행동 이벤트를 생각해보겠습니다.

- 상품 클릭
- 검색어 입력
- 장바구니 담기
- 구매 버튼 클릭
- 페이지 이탈

이런 이벤트는 하나하나가 작지만 굉장히 많이 발생합니다.

그리고 어떤 경우에는 빠르게 활용하고 싶을 수 있습니다.

- 실시간 대시보드
- 이상 징후 탐지
- 실시간 추천
- 사용자 행동 기반 알림
- 검색/추천 품질 개선을 위한 빠른 피드백

이럴 때는 데이터를 일정 시간 모아서 가져오는 것보다, 발생하는 즉시 이벤트로 흘려보내는 방식이 어울립니다.

```text
사용자 행동
  -> 이벤트 발생
  -> 수집 시스템
  -> 저장소 또는 처리 시스템
```

이벤트 수집에서 중요한 것은 “계속 들어오는 데이터”를 안정적으로 받는 일입니다.

데이터가 갑자기 많이 들어와도 버틸 수 있어야 하고, 일시적으로 뒤쪽 시스템이 느려져도 이벤트를 잃어버리지 않아야 합니다.

그래서 이벤트 수집을 이야기하다 보면 나중에 `Kafka` 같은 도구가 자연스럽게 등장합니다.

하지만 지금 단계에서는 도구 이름보다 문제를 먼저 보는 게 좋습니다.

핵심은 이것입니다.

> 계속 생기는 작은 데이터 조각들을 어떻게 잃어버리지 않고 안정적으로 받을 것인가?

이 질문이 이벤트 수집의 출발점입니다.

## 4. CDC: 운영 DB의 변경 사항을 따라가기

운영 DB에 이미 중요한 데이터가 쌓이고 있다면, 그 변경 사항을 분석 환경으로 가져오고 싶어집니다.

예를 들어 주문 테이블이 있다고 해보겠습니다.

```text
orders
- id
- user_id
- status
- total_price
- created_at
- updated_at
```

주문이 생성되고, 결제 상태가 바뀌고, 배송 상태가 바뀝니다.

분석 저장소에서도 이 변화를 알고 싶다면 어떻게 해야 할까요?

가장 단순한 방법은 주기적으로 DB를 조회하는 것입니다.

```sql
SELECT *
FROM orders
WHERE updated_at >= '2026-05-24 00:00:00';
```

이런 방식도 많이 쓰입니다.

하지만 운영 DB를 계속 직접 조회하면 부담이 될 수 있고, `updated_at`이 정확히 관리되지 않으면 놓치는 데이터가 생길 수도 있습니다.

그래서 등장하는 방식 중 하나가 `CDC`입니다.

`CDC`는 Change Data Capture의 줄임말입니다.

말 그대로 데이터의 변경 사항을 잡아내는 방식입니다.

```text
운영 DB 변경
  -> 변경 로그 감지
  -> 분석 환경으로 전달
```

CDC의 핵심은 “현재 테이블 전체를 다시 읽는 것”보다 “무엇이 바뀌었는지”를 따라가는 데 있습니다.

예를 들면:

- 주문이 새로 생성되었다.
- 결제 상태가 `READY`에서 `PAID`로 바뀌었다.
- 회원 정보가 수정되었다.
- 상품 가격이 변경되었다.

이런 변경 이벤트를 잡아서 분석 환경으로 전달할 수 있습니다.

CDC를 이해할 때도 도구 이름보다 문제를 먼저 보면 됩니다.

> 운영 DB에 생긴 변경 사항을 운영 시스템에 큰 부담을 주지 않고 어떻게 따라갈 것인가?

이 문제에 대한 구현체로 나중에 `Debezium` 같은 도구가 나옵니다.

## 5. 파일 수집: 데이터가 파일로 오는 경우

모든 데이터가 DB나 이벤트로만 들어오는 것은 아닙니다.

현실에서는 파일로 전달되는 데이터도 많습니다.

- 외부 업체가 매일 CSV 파일을 준다.
- 광고 플랫폼 리포트를 엑셀로 내려받는다.
- 로그가 시간 단위 파일로 쌓인다.
- Kaggle 같은 곳에서 공개 데이터셋을 CSV로 받는다.
- 사내 다른 팀이 S3 같은 저장소에 파일을 올려둔다.

파일 수집은 단순해 보이지만, 실제로는 여러 문제가 있습니다.

예를 들어 매일 파일이 하나씩 들어온다고 해보겠습니다.

```text
orders_2026-05-22.csv
orders_2026-05-23.csv
orders_2026-05-24.csv
```

이때 생각해야 할 것이 많습니다.

- 파일 이름 규칙은 안정적인가?
- 파일이 완전히 업로드된 뒤에 읽는가?
- 같은 파일이 두 번 들어오면 어떻게 할 것인가?
- 일부 행이 깨져 있으면 전체를 실패시킬 것인가?
- 컬럼이 추가되거나 사라지면 어떻게 할 것인가?
- 과거 파일을 다시 처리할 수 있는가?

파일 수집은 특히 재처리와 잘 어울립니다.

파일은 특정 시점의 입력 데이터가 비교적 명확하게 남아 있기 때문입니다.

예를 들어 데이터 처리 로직에 버그가 있었다면, 원본 파일을 다시 읽어서 결과를 새로 만들 수 있습니다.

이 관점은 데이터 엔지니어링 과제에서도 중요합니다.

Kaggle의 `2019-Oct.csv`, `2019-Nov.csv` 같은 파일을 받아서 Spark Application으로 처리하는 과제는, Source가 파일 형태로 주어진 경우라고 볼 수 있습니다.

```text
CSV 파일
  -> Ingestion
  -> Storage
  -> Processing
  -> Query
```

여기서 CSV 파일은 단순한 예제 파일이 아니라, “외부에서 들어온 원천 데이터”의 역할을 합니다.

## 6. 수집 방식은 하나만 쓰지 않는다

현실의 데이터 시스템은 보통 한 가지 수집 방식만 쓰지 않습니다.

서비스의 성격에 따라 여러 방식이 함께 쓰입니다.

예를 들어 쇼핑몰이라면 이런 식일 수 있습니다.

```text
주문/회원 데이터
  -> 운영 DB 변경 사항을 수집

클릭/검색/노출 이벤트
  -> 이벤트로 수집

광고 성과 데이터
  -> 외부 API에서 매일 배치로 수집

정산 데이터
  -> 파일로 전달받아 수집
```

각 데이터는 생기는 방식도 다르고, 필요한 속도도 다르고, 실패했을 때 복구하는 방식도 다릅니다.

그래서 Ingestion을 이해할 때는 “어떤 도구가 제일 좋은가?”보다 먼저 “이 데이터는 어떤 성격인가?”를 봐야 합니다.

저는 보통 이렇게 구분하면 이해하기 쉽다고 느꼈습니다.

| 데이터 성격                                   | 어울리는 수집 방식 |
| --------------------------------------------- | ------------------ |
| 하루에 한 번 정확히 보면 되는 데이터          | 배치 수집          |
| 계속 발생하고 빠르게 반영하고 싶은 데이터     | 이벤트 수집        |
| 운영 DB의 변경을 따라가야 하는 데이터         | CDC                |
| 외부에서 정해진 형식으로 전달되는 데이터      | 파일 수집          |
| 외부 서비스에서 주기적으로 받아야 하는 데이터 | API 수집           |

물론 실제 시스템에서는 이 경계가 딱 잘리지 않습니다.

예를 들어 운영 DB 변경도 CDC로 거의 실시간에 가깝게 가져올 수 있고, 이벤트도 나중에 파일로 쌓아서 배치 처리할 수 있습니다.

중요한 것은 정답을 외우는 것이 아니라, 데이터의 성격과 요구사항을 보고 수집 방식을 선택하는 것입니다.

## 7. 좋은 Ingestion은 재처리를 생각한다

데이터 수집에서 자주 놓치기 쉬운 것이 있습니다.

처음 한 번 잘 가져오는 것보다, 실패했을 때 다시 가져올 수 있는 구조가 더 중요할 때가 많습니다.

데이터 파이프라인은 실패할 수 있습니다.

- 외부 API가 일시적으로 실패한다.
- 네트워크가 끊긴다.
- 파일이 늦게 업로드된다.
- 중복 데이터가 들어온다.
- 스키마가 갑자기 바뀐다.
- 처리 코드에 버그가 있다.

그래서 수집 단계에서는 복구 가능성을 같이 생각해야 합니다.

예를 들어 배치 수집이라면 날짜 단위로 다시 실행할 수 있어야 합니다.

```text
2026-05-23 수집 실패
  -> 2026-05-23 범위만 다시 수집
```

파일 수집이라면 원본 파일이 남아 있어야 다시 처리할 수 있습니다.

이벤트 수집이라면 어디까지 읽었는지, 다시 읽을 수 있는지, 중복을 어떻게 처리할지 고민해야 합니다.

CDC라면 변경 로그를 어디까지 반영했는지 추적해야 합니다.

이런 장치가 없으면 장애가 났을 때 “어디부터 다시 해야 하지?”가 됩니다.

반대로 재처리를 염두에 둔 수집 구조는 운영할수록 가치가 커집니다.

데이터 엔지니어링에서 자주 나오는 `idempotent`, `checkpoint`, `offset`, `partition`, `backfill` 같은 단어들도 결국 이 문제와 연결됩니다.

> 실패해도 다시 실행할 수 있는가?

이 질문은 Ingestion뿐 아니라 뒤의 Processing 단계에서도 계속 중요해집니다.

---

## 8. Ingestion 다음에는 Processing이 온다

Ingestion은 데이터를 가져오는 단계입니다.

하지만 데이터를 가져왔다고 해서 바로 쓸 수 있는 것은 아닙니다.

수집된 데이터는 보통 원본 시스템의 모양을 그대로 가지고 있습니다.

- 컬럼 이름이 분석하기 불편할 수 있다.
- 시간대가 UTC일 수 있다.
- 중복 데이터가 있을 수 있다.
- 필요한 테이블끼리 조인이 필요할 수 있다.
- 이벤트 로그를 세션 단위로 묶어야 할 수 있다.
- 비즈니스 지표에 맞게 집계해야 할 수 있다.

즉 수집은 입구이고, 그 다음에는 가공이 필요합니다.

```text
Source
  -> Ingestion
  -> Storage
  -> Processing
```

다음 글에서는 이 Processing 영역을 볼 수 있습니다.

질문은 이것입니다.

> 저장된 데이터는 왜 바로 쓸 수 없을까?

이 질문을 따라가면 `ETL`, `ELT`, `Batch`, `Streaming`, `정제`, `집계`, `세션화` 같은 개념이 자연스럽게 이어집니다.

## 마무리

이번 글에서는 Ingestion을 봤습니다.

Ingestion은 여러 Source에서 생긴 데이터를 분석 환경으로 가져오는 단계입니다.

중요한 것은 도구 이름을 먼저 외우는 것이 아니라, 데이터가 어떤 성격을 가지고 있고 어떤 방식으로 흘러와야 하는지 보는 것입니다.

정리하면 이렇게 볼 수 있습니다.

```text
배치 수집
  = 일정한 간격으로 모아서 가져오기

이벤트 수집
  = 발생하는 데이터를 계속 흘려보내기

CDC
  = 운영 DB의 변경 사항을 따라가기

파일 수집
  = 외부에서 전달된 파일을 원천 데이터로 가져오기
```

수집 방식은 데이터의 성격, 필요한 속도, 복구 방식, 원본 시스템의 부담에 따라 달라집니다.

그리고 좋은 수집 구조는 처음 한 번 성공하는 것보다, 실패했을 때 다시 실행할 수 있는지를 중요하게 봅니다.

이제 데이터는 분석 환경으로 들어왔습니다.

하지만 아직 바로 쓸 수 있는 데이터는 아닐 수 있습니다.

다음 글에서는 그 이유를 보겠습니다.

> 저장된 데이터는 왜 바로 쓸 수 없을까?
