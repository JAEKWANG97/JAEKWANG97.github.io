## 들어가며

요즘 AI 도구를 쓰다 보면 이런 말을 자주 보게 됩니다.

“이제는 프롬프트 엔지니어링이 아니라 루프 엔지니어링의 시대다.”

처음 들으면 조금 과장된 말처럼 느껴집니다. AI 업계에는 새로운 이름이 자주 생기고, 그중에는 기존 개념에 이름만 새로 붙인 것들도 많으니까요. 저도 처음에는 “또 새로운 용어가 나온 건가?” 정도로 봤습니다.

그런데 자료를 찾아보고, Hermes 같은 에이전트 도구를 직접 쓰는 관점에서 다시 생각해보니 이 말이 완전히 허무맹랑한 유행어만은 아니었습니다.

핵심은 단순합니다.

AI에게 일을 맡긴다는 것은 더 이상 “좋은 프롬프트를 한 번 쓰는 일”만으로 끝나지 않습니다. 이제는 AI가 목표를 향해 움직이고, 결과를 확인하고, 실패하면 다시 고치고, 필요하면 멈추게 만드는 반복 구조를 설계해야 합니다.

이 글에서는 제가 이해한 Loop Engineering을 너무 거창한 이론이 아니라, 실제로 AI를 작업 도구로 쓰는 사람의 관점에서 정리해보려고 합니다.

## 프롬프트를 잘 쓰는 것만으로는 부족해졌다

예전에는 AI를 잘 쓴다는 말이 대부분 “프롬프트를 잘 쓴다”는 말과 비슷했습니다.

예를 들면 이런 식입니다.

```text
너는 시니어 백엔드 개발자야.
아래 에러 로그를 보고 원인을 분석해줘.
```

물론 이런 프롬프트는 여전히 중요합니다. 역할을 정해주고, 맥락을 주고, 원하는 출력 형식을 알려주면 결과가 훨씬 좋아집니다.

그런데 실제 작업에서는 한 번의 좋은 답변보다 더 중요한 순간이 자주 생깁니다.

코드를 고친다고 해보겠습니다. AI가 코드를 한 번 수정했습니다. 그런데 테스트를 돌려보니 실패합니다. 그러면 다시 로그를 보고, 원인을 추정하고, 코드를 고치고, 다시 테스트를 돌려야 합니다.

이 과정은 한 번의 프롬프트로 끝나지 않습니다.

```text
코드 수정
→ 테스트 실행
→ 실패 로그 확인
→ 원인 추정
→ 다시 수정
→ 다시 테스트
→ 통과 여부 확인
```

사람 개발자도 원래 이렇게 일합니다. 처음부터 완벽한 코드를 쓰는 것이 아니라, 실행해보고, 깨지는 지점을 보고, 다시 고칩니다.

AI 코딩 에이전트가 실제로 유용해지는 지점도 여기에 있습니다. 코드를 한 번 생성하는 능력보다, 실패를 보고 다시 시도하는 능력이 중요해지는 것입니다.

그래서 요즘 말하는 Loop Engineering은 “프롬프트를 더 멋지게 쓰자”가 아닙니다. 오히려 질문이 바뀝니다.

```text
AI에게 뭐라고 말할까?
```

에서

```text
AI가 어떤 순서로 일하고, 무엇으로 검증하고, 언제 멈추게 할까?
```

로 바뀌는 것입니다.

## Loop Engineering은 무엇인가

제가 이해한 Loop Engineering은 이렇게 정리할 수 있습니다.

> AI가 목표를 향해 실행하고, 관찰하고, 검증하고, 수정하고, 다시 시도하도록 만드는 반복 시스템 설계.

조금 더 풀면 이런 질문들입니다.

```text
목표는 무엇인가?
AI가 봐야 할 정보는 무엇인가?
어떤 도구를 쓸 수 있는가?
행동한 뒤 무엇을 관찰할 것인가?
성공 여부는 무엇으로 판단할 것인가?
실패하면 어떻게 다른 시도를 할 것인가?
언제 멈출 것인가?
어디까지는 사람 승인을 받을 것인가?
```

여기서 중요한 단어는 “반복”보다 “설계”입니다.

그냥 AI에게 “될 때까지 계속 해”라고 말하는 것은 좋은 루프가 아닙니다. 그건 비용이 많이 들고, 같은 실패를 반복하고, 나중에는 무엇을 했는지도 알기 어려운 자동화가 될 수 있습니다.

좋은 루프는 오히려 멈출 줄 압니다.

예를 들어 이런 지시가 더 좋습니다.

```text
이 repo의 failing test를 고쳐줘.
먼저 실패를 재현하고, 관련 파일만 최소 수정해.
수정 후 같은 테스트를 다시 실행해.
같은 에러가 3번 반복되면 멈추고 원인 후보를 보고해.
의존성 추가나 대규모 리팩터링은 승인 없이 하지 마.
완료하면 변경 파일, 실행한 명령, 실제 테스트 결과, 남은 리스크를 요약해.
```

이 프롬프트가 좋은 이유는 길어서가 아닙니다. 루프의 구성요소가 들어 있기 때문입니다.

- 목표: failing test 통과
- 관찰: 테스트 실행 결과
- 행동: 관련 파일 최소 수정
- 검증: 같은 테스트 재실행
- 중단 조건: 같은 에러 3회 반복
- 안전장치: 의존성 추가와 대규모 리팩터링 금지
- 완료 보고: 변경 파일, 명령, 결과, 리스크

이 정도가 되어야 AI에게 “계속 일해줘”라고 말할 수 있습니다.

## 왜 갑자기 이 말이 유행할까

자료를 찾아보면 Loop Engineering이라는 말은 2026년 들어 AI 코딩 에이전트 쪽에서 많이 언급되고 있습니다. Addy Osmani의 글, MindStudio의 글, Business Insider 기사, TechTalks 글에서도 비슷한 흐름을 설명합니다.

핵심 배경은 AI 도구의 사용 방식이 바뀌고 있다는 점입니다.

초기에는 사람이 대화창에 질문을 입력하고, AI가 답변했습니다. 사용자는 답을 복사해서 어딘가에 붙여넣었습니다.

하지만 지금의 코딩 에이전트들은 파일을 읽고, 코드를 수정하고, 터미널을 실행하고, 테스트 결과를 보고 다시 작업합니다. 사람은 매번 다음 프롬프트를 입력하기보다, 목표와 검증 기준을 정하는 쪽으로 이동합니다.

이 변화는 작아 보이지만 실제 사용감은 꽤 다릅니다.

예전 역할:

```text
사람 = 매번 다음 지시를 입력하는 사람
AI = 답변하는 도구
```

바뀌는 역할:

```text
사람 = 목표, 검증 기준, 중단 조건을 설계하는 사람
AI = 루프 안에서 실행하는 작업자
```

이 관점에서 보면 “좋은 프롬프트를 쓰는 능력”보다 “좋은 작업 루프를 설계하는 능력”이 더 중요해질 수 있습니다.

특히 코딩에서는 이 차이가 큽니다. 코드는 실행할 수 있고, 테스트할 수 있고, 실패 로그가 남습니다. 즉 AI가 자기 결과를 말로만 평가하지 않아도 됩니다. 외부 검증기가 있는 셈입니다.

이 점 때문에 Anthropic의 agent 관련 글에서도 코딩 에이전트가 효과적인 이유로 “자동 테스트로 검증 가능하고, 테스트 결과를 피드백으로 삼아 반복할 수 있다”는 점을 이야기합니다.

## 실제로는 어떻게 쓰고 있을까

처음에는 저도 이게 그냥 말뿐인 유행어인지 궁금했습니다. 그래서 “실제로 이걸 적용한 사람이 있나?”를 조금 더 찾아봤습니다.

결론부터 말하면, 있습니다. 다만 아직은 정리된 산업 표준이라기보다, 빠르게 실험하는 개발자와 도구 제작자들의 실무 패턴에 가깝습니다. 그리고 생각보다 공통점이 분명했습니다.

가장 많이 인용되는 사례 중 하나는 Claude Code를 만든 Boris Cherny의 말입니다. 그는 “이제 Claude에게 직접 프롬프트하지 않고, Claude를 프롬프트하는 루프를 쓴다. 내 일은 루프를 쓰는 것이다”라는 취지로 말했습니다.

이 말은 처음 들으면 조금 과장처럼 들립니다. 그런데 구조를 뜯어보면 그렇게 신비한 이야기는 아닙니다.

```text
사람이 매번 지시한다
→ AI가 답한다
→ 사람이 결과를 확인한다
→ 사람이 다음 지시를 한다
```

이 방식에서 사람은 계속 키보드 앞에 있어야 합니다. 반대로 루프를 설계한다는 것은 다음 구조에 가깝습니다.

```text
목표를 준다
→ 에이전트가 작업한다
→ 별도 판단기나 테스트가 확인한다
→ 완료 전이면 다시 작업한다
→ 막히면 사람에게 넘긴다
```

여기서 사람은 매번 다음 프롬프트를 치는 사람이 아니라, 목표와 검증 기준과 중단 조건을 설계하는 사람이 됩니다.

Peter Steinberger의 사례도 비슷합니다. 공개적으로 인용된 예시를 보면, Codex에게 repo를 관리하게 하고, 5분마다 깨어나서 작업 thread로 일을 분배하게 한다는 식의 루프를 사용한다고 합니다.

제가 이해한 구조는 대략 이렇습니다.

```text
5분마다 실행
→ repo 상태 확인
→ issue, PR, CI, TODO 탐색
→ 할 일이 있으면 작업 thread 생성
→ triage/autoreview skill로 우선순위와 결과 확인
→ 사람에게 필요한 것만 보고
```

여기서 중요한 건 “AI가 전부 알아서 개발한다”가 아닙니다. 오히려 반대에 가깝습니다. 자동화하는 부분과 사람이 봐야 하는 부분을 나누는 것입니다.

또 하나 흥미로웠던 사례는 `loop-engineering`이라는 GitHub repo입니다. 이 repo는 loop engineering을 아예 패턴과 도구로 정리합니다.

예를 들어 이런 패턴들이 있습니다.

- Daily Triage: 매일 아침 issue, PR, CI 상태를 보고 오늘 볼 일을 정리한다.
- Issue Triage: 새 issue를 읽고 라벨이나 우선순위 후보를 제안한다.
- PR Babysitter: PR이 CI 실패, 리뷰 대기, rebase 필요 상태인지 지켜본다.
- CI Sweeper: CI 실패를 감지하고 로그를 읽어 원인 후보를 정리한다.
- Dependency Sweeper: dependency update 중 patch 수준의 안전한 변경만 제안한다.
- Changelog Drafter: release note나 changelog 초안을 만든다.

이 패턴들이 현실적으로 느껴졌던 이유는, 처음부터 “자동 수정하고 자동 merge하자”가 아니었기 때문입니다. 오히려 대부분은 report-only부터 시작하라고 말합니다.

```text
L1: 보고만 한다.
L2: 작은 수정 제안까지 한다.
L3: 검증과 승인 구조가 있을 때만 더 자동화한다.
```

이 단계가 중요하다고 느꼈습니다. AI 루프를 만든다고 해서 바로 운영 권한을 넘기는 게 아닙니다. 처음에는 “알려주는 루프”로 시작하고, 검증 가능한 작은 부분만 “수정하는 루프”로 올리는 방식이 더 안전합니다.

실제 적용 사례들을 보면 공통적으로 이런 구조가 보입니다.

```text
자동 실행보다 자동 발견
자동 수정보다 자동 검증
자동 merge보다 사람 승인
무한 반복보다 중단 조건
단일 agent보다 maker/checker 분리
대화 기록보다 STATE.md 같은 외부 상태
```

예를 들어 CI Sweeper 루프라면 이렇게 설계할 수 있습니다.

```text
CI 실패 감지
→ 실패 로그 읽기
→ flaky test인지 실제 regression인지 분류
→ 간단한 수정은 worktree에서 시도
→ verifier가 테스트 재실행
→ 최대 3회 실패하면 사람에게 넘김
```

PR Babysitter라면 이런 식입니다.

```text
주기적으로 PR 확인
→ CI 실패, 리뷰 대기, 충돌 여부 확인
→ 단순 rebase나 작은 수정 후보 제안
→ 테스트 통과 여부 확인
→ merge는 사람 승인 후 진행
```

이런 사례를 보면 Loop Engineering의 핵심은 “AI에게 더 많이 맡기는 것”이 아니라는 생각이 듭니다. 오히려 AI가 맡아도 되는 범위를 작게 자르고, 확인 가능한 기준을 붙이고, 위험한 순간에는 멈추게 하는 쪽에 가깝습니다.

그래서 실제 적용의 시작점도 거창할 필요가 없습니다. 개인 작업에서는 이런 정도가 현실적입니다.

```text
매일 아침 GitHub/Linear/Obsidian 상태를 보고 오늘 볼 일만 요약한다.
자동 수정은 하지 않는다.
근거와 다음 행동만 남긴다.
```

또는 코딩 프로젝트에서는 이렇게 시작할 수 있습니다.

```text
테스트 실패를 감지한다.
로그를 요약한다.
원인 후보를 정리한다.
수정은 사람 승인 후 진행한다.
```

이 정도만 해도 이미 루프입니다. 핵심은 “AI가 나 대신 모든 걸 한다”가 아니라, “내가 매번 확인하던 반복적인 관찰과 정리를 AI가 대신 수행하고, 나는 판단이 필요한 지점에 집중한다”는 것입니다.

## 좋은 루프는 검증기를 가진다

Loop Engineering에서 제가 가장 중요하게 느낀 부분은 “검증”입니다.

AI는 꽤 그럴듯하게 말합니다. 문제는 그럴듯한 말과 실제로 맞는 결과가 다를 수 있다는 점입니다.

예를 들어 AI가 이렇게 말할 수 있습니다.

```text
수정이 완료되었습니다. 이제 정상적으로 동작할 것입니다.
```

하지만 실제 테스트를 돌리지 않았다면, 이 말은 아직 확인된 사실이 아닙니다. 그냥 모델의 추정에 가깝습니다.

그래서 좋은 루프는 AI의 자기평가에만 의존하지 않습니다.

코딩에서는 다음과 같은 검증기가 있습니다.

- unit test
- integration test
- type check
- lint
- build
- API smoke test
- CI 결과

글쓰기나 문서 작업에서는 기계적 테스트가 어렵지만, 그래도 검증 기준을 만들 수 있습니다.

- 독자가 처음 읽어도 흐름이 보이는가?
- 제목이 실제 질문처럼 보이는가?
- 너무 추상적인 주장만 있지 않은가?
- 예시가 있는가?
- 과장된 표현은 없는가?
- 공개 글로 나가도 위험한 내용은 없는가?

중요한 것은 “AI가 스스로 잘했다고 말하는 것”과 “외부 기준으로 확인되는 것”을 구분하는 일입니다.

저는 이 부분이 AI를 포트폴리오나 취업 준비에 쓸 때도 중요하다고 생각합니다. 결과물이 좋아 보이는 것보다, 내가 어떤 기준으로 확인했는지를 설명할 수 있어야 하기 때문입니다.

## Hermes에서 보면 더 구체적으로 보인다

Hermes를 쓰다 보면 Loop Engineering이 그냥 추상적인 말이 아니라는 걸 느낄 수 있습니다.

Hermes에는 이미 루프를 구성하는 여러 부품이 있습니다.

가장 먼저 `/goal`이 있습니다. `/goal`은 Hermes가 여러 턴에 걸쳐 하나의 목표를 계속 추적하게 하는 기능입니다. 예를 들어 테스트를 통과시킬 때까지 작업하게 하거나, 특정 문서 정리가 끝날 때까지 이어가게 할 수 있습니다.

하지만 `/goal` 자체가 Loop Engineering은 아닙니다.

비유하면 `/goal`은 러닝머신이고, Loop Engineering은 운동 프로그램에 가깝습니다. 러닝머신이 있다고 해서 자동으로 좋은 운동이 되지는 않습니다. 속도, 시간, 인터벌, 멈추는 기준을 정해야 합니다.

마찬가지로 `/goal`도 이렇게 쓰면 위험합니다.

```text
/goal 이 프로젝트를 개선해줘
```

너무 넓고, 성공 기준도 없고, 언제 멈출지도 알 수 없습니다.

반대로 이렇게 쓰면 루프가 됩니다.

```text
/goal 이 repo의 failing test를 통과시켜.
먼저 실패를 재현하고, 관련 파일만 최소 수정해.
수정 후 테스트를 다시 실행해.
같은 실패가 3번 반복되면 멈추고 원인 후보를 보고해.
완료하면 변경 파일, 실행 명령, 실제 테스트 결과, 남은 리스크를 요약해.
```

Hermes의 todo는 루프의 상태판이 될 수 있습니다. 지금 실패 재현 단계인지, 수정 단계인지, 검증 단계인지 보이게 해줍니다.

terminal과 process는 관찰 장치입니다. 실제 테스트를 돌리고, 로그를 보고, 서버 상태를 확인할 수 있습니다.

delegate_task는 작성자와 검토자를 분리하는 데 쓸 수 있습니다. 한 에이전트는 원인을 분석하고, 다른 에이전트는 기존 코드 패턴을 조사하고, 메인 에이전트가 최종 판단을 하는 식입니다.

cronjob은 주기적 루프에 맞습니다. 매일 채용 공고를 확인하거나, GitHub 이슈를 살펴보거나, 서버 상태를 점검하는 일은 매번 대화창에서 요청하기보다 예약 루프로 두는 편이 자연스럽습니다.

skills는 반복 절차를 저장하는 장치입니다. 자소서 작성 루프, 블로그 초안 개선 루프, 코드 리뷰 루프처럼 자주 반복하는 방식은 skill로 남겨둘 수 있습니다.

memory는 사용자 선호나 환경 조건을 기억합니다. 예를 들어 “자소서는 한 문항씩 진행하는 것을 선호한다”는 memory에 가깝고, “자소서 작업은 공고 분석 → 소재 확인 → 초안 → 검토 → 승인 후 파일 반영 순서로 한다”는 skill에 가깝습니다.

이렇게 보면 Hermes에서의 Loop Engineering은 단순히 `/goal`을 쓰는 것이 아닙니다.

```text
/goal = 루프 엔진
todo = 상태판
terminal/process = 관찰 장치
delegate_task = 병렬 분석/리뷰
cronjob = 주기적 실행
skills = 반복 절차 기억
memory = 기본 조건 기억
worktree/checkpoint = 격리와 롤백
```

이 부품들을 작업 성격에 맞게 조합하는 것이 Hermes식 Loop Engineering에 가깝습니다.

## 루프를 설계할 때 조심해야 할 것

Loop Engineering이 유용하다고 해서 모든 일을 AI에게 계속 돌리면 되는 것은 아닙니다.

오히려 루프는 잘못 만들면 더 위험합니다.

첫 번째 위험은 비용 폭주입니다. 목표가 모호하고 중단 조건이 없으면 AI는 계속 시도합니다. 특히 “더 개선해줘”, “더 좋게 만들어줘” 같은 요청은 끝이 없습니다.

두 번째 위험은 허위 완료입니다. AI가 실제 검증 없이 완료했다고 말할 수 있습니다. 그래서 최종 보고에는 가능하면 실행한 명령과 실제 결과가 있어야 합니다.

세 번째 위험은 잘못된 목표의 자동화입니다. 목표가 틀렸다면 루프는 틀린 방향으로 더 빠르게 갑니다. 그래서 위험한 작업에는 승인 지점을 둬야 합니다. 의존성 추가, DB 마이그레이션, 대규모 삭제, 배포 같은 작업은 자동으로 넘기면 안 됩니다.

네 번째 위험은 같은 실패 반복입니다. 같은 에러를 계속 보고도 같은 방식으로 수정한다면, 그건 학습하는 루프가 아니라 토큰을 태우는 반복입니다.

그래서 좋은 루프에는 항상 브레이크가 있어야 합니다.

```text
같은 오류가 3번 반복되면 멈춘다.
최대 5회 수정 후에도 실패하면 보고한다.
권한이나 비밀키가 필요하면 중단한다.
공개 API 변경은 승인 없이 하지 않는다.
```

자동화의 실력은 많이 돌리는 데 있지 않고, 안전하게 멈추는 데 있다고 생각합니다.

## 내가 앞으로 AI를 쓸 때 바꿔야 할 점

이 개념을 보면서 저는 AI에게 일을 맡기는 문장을 조금 바꿔야겠다고 느꼈습니다.

이전에는 이렇게 말하기 쉬웠습니다.

```text
이거 고쳐줘.
이 글 다듬어줘.
이 프로젝트 정리해줘.
```

앞으로는 조금 더 루프에 가깝게 말하는 편이 좋겠습니다.

```text
목표는 이것이고,
먼저 현재 상태를 확인하고,
수정한 뒤 이 기준으로 검증하고,
실패하면 이 범위 안에서 다시 시도하고,
이 조건에서는 멈추고 보고해줘.
```

이렇게 말하면 AI가 더 말을 잘 듣는다는 차원을 넘어서, 작업이 더 안전해집니다. 무엇을 했는지, 무엇으로 확인했는지, 어디서 막혔는지가 남기 때문입니다.

취업 준비나 포트폴리오 관점에서도 이건 꽤 중요합니다.

AI를 썼다는 사실 자체보다 중요한 것은 “AI를 어떤 검증 루프 안에서 썼는가”입니다. 프로젝트를 만들 때도, 블로그 글을 쓸 때도, 자소서를 다듬을 때도 마찬가지입니다.

단순히 AI가 만들어준 결과물을 제출하는 것과, 내가 목표를 정의하고, AI에게 초안을 맡기고, 테스트하거나 검토하고, 다시 수정하면서 결과를 만든 것은 다릅니다.

면접에서 설명해야 하는 것도 결국 이 차이에 가까울 것 같습니다.

```text
AI를 썼습니다.
```

보다

```text
AI를 초안 생성과 검토 보조에 사용했고,
최종 판단은 테스트 결과와 요구사항 기준으로 확인했습니다.
```

가 더 설득력 있습니다.

Loop Engineering은 이런 설명을 가능하게 만드는 작업 방식이기도 합니다.

## 마무리

Loop Engineering이라는 말은 분명 유행어의 느낌이 있습니다. 기존에 있던 자동화, 테스트, 에이전트 루프, CI, human-in-the-loop 같은 개념을 새 이름으로 부르는 면도 있습니다.

하지만 유행어라고 해서 무시할 필요는 없다고 생각합니다. 이름이 붙었다는 것은 그만큼 많은 사람이 비슷한 변화를 느끼고 있다는 뜻이기도 하니까요.

제가 이해한 핵심은 이렇습니다.

AI에게 일을 맡긴다는 것은 더 이상 “좋은 질문을 던지는 일”만이 아닙니다.

이제는 작은 작업 시스템을 만드는 일에 가깝습니다.

```text
목표를 정하고,
도구를 주고,
결과를 관찰하고,
검증 기준을 세우고,
실패하면 다시 시도하게 하고,
위험하면 멈추게 하고,
과정을 기록으로 남기는 것.
```

이게 제가 이해한 Loop Engineering입니다.

앞으로 AI를 쓸 때는 “프롬프트를 어떻게 쓰지?”만 생각하기보다, “이 작업은 어떤 루프로 돌아야 안전하게 끝날까?”를 먼저 생각해보려고 합니다.

특히 Hermes 같은 에이전트 도구를 쓸 때는 더 그렇습니다. `/goal`을 쓰든, cronjob을 쓰든, skill을 만들든, 결국 중요한 것은 기능 자체가 아니라 그 기능이 어떤 루프 안에서 돌아가느냐입니다.

AI에게 일을 맡기는 능력은 점점 “질문을 잘하는 능력”에서 “검증 가능한 반복 구조를 설계하는 능력”으로 옮겨가고 있는 것 같습니다.
