> 이 글은 실제 배포 설정을 바탕으로 쓴 1차 초안입니다. 프로젝트명과 브랜치명 등 식별 가능한 정보는 일반화했으며, 세부 표현은 이후 실제 운영 결과와 제 판단을 보충해 다듬을 예정입니다.

## staging 이미지를 추가하면 끝이라고 생각했다

기존에는 운영 브랜치에서만 Docker 이미지를 빌드해 AWS ECR에 올리고 있었습니다. 배포 파이프라인도 단순했습니다.

```text
운영 브랜치 push
→ Docker 이미지 빌드
→ ECR push
→ EC2에서 이미지 pull
→ 운영 컨테이너 실행
```

여기에 staging 환경을 추가하게 됐습니다. 처음에는 staging 브랜치에서도 같은 이미지를 빌드하고, 운영과 다른 컨테이너 이름과 포트를 사용하면 끝이라고 생각했습니다.

그런데 ECR에 올릴 이미지 태그를 확인하다가 한 가지가 걸렸습니다. 기존 빌드에서는 모든 이미지에 `latest`를 붙이고 있었습니다.

```bash
docker build \
  -t "${IMAGE}:${IMAGE_TAG}" \
  -t "${IMAGE}:latest" .
```

기존에는 운영 브랜치만 이 명령을 실행했기 때문에 별문제가 없었습니다. `latest`는 자연스럽게 최근 운영 이미지를 가리켰습니다.

하지만 staging 브랜치도 같은 ECR 저장소에 `latest`를 push하면 이야기가 달라집니다.

```text
운영 파이프라인 완료
latest → 운영 이미지 A

staging 파이프라인 완료
latest → staging 이미지 B
```

이제 `latest`는 최근 운영 이미지가 아니라 **가장 마지막에 끝난 파이프라인의 이미지**가 됩니다.

여기서 이번 작업의 중심 질문이 생겼습니다.

> 운영과 staging이 같은 ECR 저장소를 사용할 때, 각 이미지 태그에는 어떤 역할을 맡겨야 할까?

## `latest`는 최신 이미지를 찾아주는 기능이 아니었다

처음 Docker를 배울 때 `latest`라는 이름은 조금 특별해 보입니다. 저장소에서 가장 최신 이미지를 Docker가 알아서 찾아 가리키는 것처럼 느껴지기도 합니다.

하지만 `latest`는 특별한 계산 결과가 아니라 **이름이 `latest`인 일반 태그**입니다. 누군가 새 이미지에 그 태그를 붙여 push해야 가리키는 대상이 바뀝니다.

```bash
docker tag app:abc123 app:latest
docker push app:latest
```

이 명령이 실행되면 `latest`는 `abc123` 이미지와 같은 대상을 가리킵니다. 다음에 다른 이미지로 같은 작업을 하면 다시 그 이미지로 이동합니다.

```text
app:abc123 ─┐
app:latest ─┘ 같은 이미지
```

즉 `latest`의 실제 의미는 태그 이름만으로 결정되지 않습니다. **어떤 브랜치가 언제 이 태그를 갱신하도록 파이프라인을 구성했는지**에 따라 달라집니다.

기존에는 운영 브랜치만 갱신했기 때문에 `latest = 최근 운영 이미지`라는 암묵적인 약속이 성립했습니다. staging이 추가되면서 그 약속이 더 이상 자동으로 유지되지 않게 된 것입니다.

## 먼저 실제 배포가 어떤 태그를 쓰는지 확인했다

`latest`가 staging 이미지로 바뀔 수 있다는 사실만 보면 곧바로 운영 장애가 날 것처럼 느껴집니다. 하지만 실제 영향도를 판단하려면 EC2가 어떤 태그를 pull하는지 먼저 봐야 했습니다.

현재 배포는 `latest`가 아니라 커밋 SHA를 사용하고 있었습니다.

```bash
IMAGE="${ECR_REGISTRY}/${ECR_REPOSITORY}:${IMAGE_TAG}"
docker pull "${IMAGE}"
```

예를 들어 파이프라인의 커밋 SHA가 `abc123`이라면 실제 배포 이미지는 다음과 같습니다.

```text
app:abc123
```

이 태그는 다음 파이프라인이 실행돼도 다른 이미지를 가리키도록 덮어쓰지 않습니다. 따라서 staging 파이프라인이 `latest`를 갱신하더라도, 이미 SHA를 기준으로 실행되는 운영 배포가 즉시 staging 이미지로 교체되지는 않습니다.

여기서 두 문제를 분리할 수 있었습니다.

```text
1. 실제 배포와 롤백은 무엇을 기준으로 할 것인가?
2. 사람이 현재 환경의 이미지를 확인할 때 어떤 별칭을 쓸 것인가?
```

첫 번째에는 고정된 식별자가 필요하고, 두 번째에는 읽기 쉬운 이름이 필요합니다. 하나의 태그로 두 목적을 모두 해결하려 했기 때문에 `latest`의 역할이 애매해졌던 셈입니다.

## SHA와 환경 태그의 역할을 나눴다

최종적으로 태그를 세 가지 역할로 나눴습니다.

| 태그 종류 | 예시                            | 역할                              |
| --------- | ------------------------------- | --------------------------------- |
| 커밋 SHA  | `app:abc123`                    | 실제 배포·재배포·롤백 기준        |
| 환경 태그 | `app:production`, `app:staging` | 각 환경의 현재 이미지 확인용 별칭 |
| 호환 태그 | `app:latest`                    | 기존 운영 참조와의 호환           |

브랜치별로 ECR에 올리는 태그는 다음과 같이 정리했습니다.

| 브랜치  | 발행하는 태그               | 실제 배포 태그 |
| ------- | --------------------------- | -------------- |
| 운영    | SHA, `production`, `latest` | SHA            |
| staging | SHA, `staging`              | SHA            |

이 구성에서 `production`과 `staging`은 움직이는 태그입니다. 새 배포가 발생할 때마다 해당 환경의 최근 이미지를 가리킵니다. 사람이 ECR에서 현재 상태를 확인할 때는 편리하지만, 과거의 정확한 이미지를 다시 지정하기에는 적합하지 않습니다.

반면 SHA 태그는 특정 커밋의 빌드 결과를 가리킵니다. 그래서 실제 배포와 롤백 기준으로 사용했습니다.

```text
SHA 태그       → 기계가 정확히 배포할 대상
환경 태그      → 사람이 현재 환경을 확인할 별칭
latest 태그    → 기존 사용자를 위한 호환 별칭
```

핵심은 태그를 많이 붙이는 것이 아니라 **각 태그가 어떤 질문에 답해야 하는지 나누는 것**이었습니다.

## `latest`를 없애지 않고 운영에만 남긴 이유

가장 단순한 방법은 `latest`를 완전히 없애고 SHA와 환경 태그만 사용하는 것입니다. 실제 배포가 이미 SHA를 사용하고 있으니 내부 실행 경로만 보면 가능한 선택이었습니다.

다만 ECR 저장소 밖에서 누가 `app:latest`를 참조하는지 바로 확인하기 어려웠습니다.

```bash
docker pull app:latest
```

기존 사용자가 이 명령을 `최근 운영 이미지`라는 의미로 사용하고 있었다면, `latest`를 즉시 제거하는 것도 호환성을 깨뜨릴 수 있습니다. 반대로 staging에서도 계속 갱신하면 같은 이름이 더 이상 운영 이미지를 보장하지 못합니다.

그래서 당장은 중간 선택을 했습니다.

- 운영 브랜치만 `latest`를 갱신한다.
- staging은 `staging` 환경 태그를 사용한다.
- 실제 배포는 두 환경 모두 SHA를 사용한다.

이 선택은 `latest`가 좋은 배포 기준이라는 뜻이 아닙니다. 기존 약속을 한 번에 없애지 않으면서 의미가 staging 이미지로 오염되는 것을 막는 호환성 처리에 가깝습니다.

## 빌드할 때 붙일까, 나중에 붙일까?

구현 방식에서도 선택지가 있었습니다.

첫 번째는 브랜치에 따라 빌드 명령을 나누는 방식입니다.

```bash
if [ "$CI_COMMIT_BRANCH" = "main" ]; then
  docker build --pull \
    -t "${IMAGE}:${IMAGE_TAG}" \
    -t "${IMAGE}:${IMAGE_CHANNEL}" \
    -t "${IMAGE}:latest" .
else
  docker build --pull \
    -t "${IMAGE}:${IMAGE_TAG}" \
    -t "${IMAGE}:${IMAGE_CHANNEL}" .
fi
```

`latest`가 빌드 시점부터 붙는다는 점은 직관적입니다. 하지만 긴 `docker build` 명령이 두 군데에 중복됩니다.

두 번째는 공통 빌드를 한 뒤 운영 브랜치에서만 별칭을 추가하는 방식입니다.

```bash
docker build --pull \
  -t "${IMAGE}:${IMAGE_TAG}" \
  -t "${IMAGE}:${IMAGE_CHANNEL}" .

docker push "${IMAGE}:${IMAGE_TAG}"
docker push "${IMAGE}:${IMAGE_CHANNEL}"

if [ "$CI_COMMIT_BRANCH" = "main" ]; then
  docker tag "${IMAGE}:${IMAGE_TAG}" "${IMAGE}:latest"
  docker push "${IMAGE}:latest"
fi
```

`docker tag`는 이미지를 다시 빌드하거나 복사하지 않습니다. 기존 로컬 이미지에 다른 이름을 붙이는 작업입니다. 따라서 빌드 명령을 분기하는 방식이 성능상 더 효율적인 것은 아닙니다.

결국 선택 기준은 성능보다 중복과 가독성이었습니다. 공통 빌드는 한 번만 작성하고, 운영에만 필요한 호환 태그 처리를 그 뒤에서 분기했습니다.

## 여러 줄 블록에서는 중간 실패도 생각해야 했다

한 줄짜리 조건문은 짧지만 읽기 어려워서 여러 줄 블록으로 풀었습니다.

```yaml
- |
  set -e
  if [ "$CI_COMMIT_BRANCH" = "main" ]; then
    docker tag "${IMAGE}:${IMAGE_TAG}" "${IMAGE}:latest"
    docker push "${IMAGE}:latest"
  fi
```

여기서 `set -e`는 명령이 실패하면 블록 실행을 즉시 중단하라는 뜻입니다.

예를 들어 SHA 이미지에 `latest`를 붙이는 작업이 실패했는데 다음 push가 계속 실행된다면, runner에 우연히 남아 있던 과거의 `latest`를 밀어 올리는 상황을 이론적으로 생각할 수 있습니다.

```text
docker tag 실패
→ 즉시 종료
→ docker push latest는 실행하지 않음
```

작은 조건문이지만 배포용 스크립트에서는 실패를 성공처럼 지나가게 하지 않는 것이 중요하다고 판단했습니다.

## 이번 선택에서 얻은 것과 남은 한계

최종 전략을 트레이드오프로 정리하면 다음과 같습니다.

| 선택                       | 얻은 것                                    | 감수한 것                              |
| -------------------------- | ------------------------------------------ | -------------------------------------- |
| SHA로 실제 배포            | 배포 대상을 재현하고 롤백하기 쉬움         | 사람이 SHA와 커밋을 연결해 확인해야 함 |
| 환경 태그 사용             | 현재 production·staging 이미지 확인이 쉬움 | 새 배포 때 가리키는 대상이 바뀜        |
| `latest`를 운영에서만 갱신 | 기존 운영 참조와 호환                      | `latest`의 가변성 자체는 남음          |
| 빌드 후 `docker tag`       | 빌드 명령 중복을 줄임                      | 태그 처리 단계가 하나 추가됨           |

이 구성이 모든 환경에 대한 정답이라고 생각하지는 않습니다. `latest`를 사용하는 외부 소비자가 없다는 사실을 확인할 수 있다면 아예 제거하는 편이 더 단순할 수 있습니다. 이미지 태그 변경을 막아야 한다면 ECR의 태그 불변성 정책도 함께 검토할 수 있습니다.

또한 같은 SHA를 붙였다는 사실만으로 완전한 재현성이 자동 보장되는 것은 아닙니다. 같은 태그를 다시 push할 수 있는 정책, 빌드 시점의 베이스 이미지와 의존성, ECR lifecycle 정책도 함께 영향을 줍니다.

이번 작업에서는 우선 실제 배포 경로를 SHA로 고정하고, 환경별 이동 태그와 기존 호환 태그의 역할을 분리하는 데 집중했습니다.

## 마무리

처음에는 “staging도 `latest`를 push하면 운영 이미지가 덮이는 것 아닌가?”라는 걱정에서 시작했습니다. 그 질문 자체는 맞았지만, 바로 조건문부터 추가했다면 왜 필요한 코드인지 제대로 설명하기 어려웠을 것 같습니다.

실제 배포 흐름을 따라가 보니 판단 순서는 다음과 같았습니다.

```text
EC2가 실제로 pull하는 태그 확인
→ SHA와 가변 태그의 역할 구분
→ 환경별 별칭 정의
→ 기존 latest 사용 가능성 검토
→ main에서만 latest 갱신
```

이번 경험에서 가장 크게 배운 것은 `latest`를 쓰면 안 된다는 단순한 규칙이 아니었습니다.

> 실제 배포를 식별하는 태그와 사람이 현재 상태를 확인하는 태그, 기존 시스템과의 호환을 위한 태그는 서로 다른 역할을 가질 수 있다.

staging 환경 하나를 추가하면서 태그 하나의 의미가 흔들렸고, 그 덕분에 기존 배포에서 암묵적으로 사용하던 약속을 명시적인 정책으로 바꿀 수 있었습니다.
