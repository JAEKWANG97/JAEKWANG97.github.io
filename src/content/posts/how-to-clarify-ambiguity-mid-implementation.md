AI 코딩 도구를 쓰다 보면 처음부터 요구사항이 완벽하지 않아도 구현은 시작됩니다.

```text
가격 비교 API를 만들어줘.
공식 API만 사용하고 테스트도 추가해줘.
```

이 정도면 출발하기에는 충분해 보입니다. 그런데 코드를 작성하다 보면 처음에는 보이지 않던 질문이 나타납니다.

- 상품명은 같은데 용량이 다르면 같은 상품일까?
- 외부 API 하나가 실패하면 전체 요청도 실패해야 할까?
- 매칭 결과가 없을 때 빈 목록과 오류 중 무엇을 반환해야 할까?

이럴 때 저는 두 선택지만 떠올렸습니다.

```text
1. 에이전트가 적당히 가정하고 계속 구현한다.
2. 작업을 멈추고 전체 요구사항을 처음부터 다시 정리한다.
```

첫 번째는 빠르지만 엉뚱한 결과를 만들 수 있습니다. 두 번째는 안전하지만, 이미 진행 중인 작은 작업에는 너무 무겁습니다.

그래서 그 사이에 들어갈 작은 장치가 필요했습니다.

> 지금까지 한 작업은 유지하되, 현재 구현을 갈라놓는 모호함만 하나씩 없앨 수 없을까?

이번에는 이 역할을 하는 Hermes 스킬인 `clarify-work`를 직접 만들어봤습니다.

## 왜 전체 명세 도구만으로는 부족했을까

앞서 [Ouroboros의 명세·평가 루프](/posts/how-ouroboros-uses-results/)를 살펴보면서, 모호한 목표를 Interview와 Seed로 구체화하는 방식이 꽤 인상적이었습니다.

```text
Interview → Seed → Execute → Evaluate → Evolve
```

프로젝트를 시작하거나 큰 기능을 착수하기 전이라면 이런 흐름이 잘 맞습니다. 목표와 제약, 인수 조건을 먼저 정하고 실행과 평가가 같은 계약을 보게 만들 수 있기 때문입니다.

그런데 이미 작은 기능을 구현하는 중이라면 상황이 조금 다릅니다.

```text
구현 시작
  ↓
코드와 테스트 일부 작성
  ↓
예상하지 못한 정책 질문 발견
  ↓
현재 작업만 잠깐 멈추고 결정 필요
```

이 지점에서 프로젝트 전체 Seed를 다시 만드는 것은 과할 수 있습니다. 그렇다고 에이전트가 임의로 결정하게 두기도 어렵습니다.

`clarify-work`는 전체 프로젝트를 다시 설계하는 도구가 아니라 **작업 중간의 판단 체크포인트**로 범위를 좁혔습니다.

## 핵심 규칙은 질문을 하나씩 하는 것이다

처음에는 모호한 항목을 목록으로 뽑아 한꺼번에 물어보면 효율적일 거라고 생각할 수 있습니다.

```text
동일 상품 기준은 무엇인가요?
옵션 차이는 어떻게 처리하나요?
매칭 실패 시 무엇을 반환하나요?
캐시는 얼마나 유지하나요?
```

하지만 이렇게 질문을 몰아서 받으면 각 답변의 영향이 섞입니다. 앞 질문의 답 때문에 뒤 질문 자체가 필요 없어질 수도 있고, 사용자는 여러 결정을 한 번에 내려야 합니다.

그래서 스킬의 가장 강한 규칙을 다음처럼 정했습니다.

```text
한 번에 질문 하나
→ 답변 반영
→ 남은 모호함 다시 평가
→ 가장 영향이 큰 질문 하나
→ 반복
```

질문을 세 개나 다섯 개로 제한하지도 않았습니다. 정해진 횟수를 채우는 것이 목적이 아니라, **서로 다른 구현을 만들 수 있는 중요한 모호함이 없어지는 것**이 종료 조건이기 때문입니다.

## 사용자에게 묻기 전에 코드가 답할 수 있는지 확인한다

질문을 하나씩 한다고 해서 모든 것을 사용자에게 물어보는 것은 아닙니다.

예를 들어 다음 질문은 저장소를 읽으면 답할 수 있습니다.

- 현재 인증 방식은 무엇인가?
- 실패 응답은 어떤 공통 형식을 사용하는가?
- 기존 테스트는 빈 결과를 어떻게 검증하는가?
- 외부 API 호출에 이미 타임아웃이 설정되어 있는가?

이런 내용까지 사용자에게 묻기 시작하면 인터뷰가 길어집니다. 더 큰 문제는 이미 코드에 존재하는 계약과 다른 답을 받을 수도 있다는 점입니다.

그래서 `clarify-work`는 모호한 내용을 네 종류로 나눕니다.

| 구분 | 처리 방식                                       |
| ---- | ----------------------------------------------- |
| 사실 | 코드·설정·문서에서 직접 확인한다                |
| 가정 | 임시 해석임을 드러내고 위험도를 판단한다        |
| 결정 | 제품이나 사용자의 판단이 필요하므로 질문한다    |
| 실험 | 작은 일회용 스파이크로 기술적 가능성을 확인한다 |

예를 들어 현재 코드가 매칭 실패를 빈 목록으로 반환한다면, 이렇게 물을 수 있습니다.

> 현재 API는 매칭 실패를 빈 목록으로 반환합니다. 새 비교 기능도 이 계약을 유지할까요?

“실패하면 어떻게 할까요?”라고 처음부터 묻는 것보다 현재 문맥이 보이고, 사용자가 결정해야 할 부분도 하나로 줄어듭니다.

## 어떤 질문부터 해야 할까

모호함이 여러 개라면 단순히 발견한 순서대로 묻지 않습니다. 다음 세 기준이 큰 질문부터 고릅니다.

```text
영향도 × 되돌리기 어려움 × 불확실성
```

예를 들어 상품 비교 기능에서 변수명보다 동일 상품 판정 기준을 먼저 물어야 합니다. 동일 상품 기준은 데이터 모델, 필터링, 테스트 결과를 모두 바꿀 수 있기 때문입니다.

반대로 저장소의 기존 규칙으로 정할 수 있는 이름이나 포맷은 질문하지 않습니다. 쉽게 되돌릴 수 있고 외부 동작도 바꾸지 않는 세부 사항까지 모두 확인받으면, 모호함을 줄이는 과정이 오히려 개발을 막게 됩니다.

## 언제 모호함이 없어졌다고 판단할까

“충분히 대화한 것 같다”는 느낌만으로 구현을 재개하면 같은 문제가 반복됩니다. 그래서 스킬에는 종료 전에 확인하는 조건을 넣었습니다.

- 합리적인 두 답이 서로 다른 외부 동작이나 테스트를 만들지 않는가?
- 이번 작업에 포함되는 것과 제외되는 것이 분명한가?
- 중요한 실패와 예외 상황의 동작이 정해졌는가?
- 남아 있는 가정이 낮은 위험이고 명시되어 있는가?
- 인수 조건을 관찰하거나 테스트할 수 있는가?
- 실제 검증 방법을 알고 있는가?

이 조건을 통과하면 다음과 같은 작은 결정 묶음을 남깁니다.

```text
결정
- 상품명, 브랜드, 용량이 모두 같아야 동일 상품이다.
- 색상 차이는 같은 상품의 옵션으로 취급한다.

제외
- 이미지 유사도 매칭은 이번 작업에 포함하지 않는다.

인수 조건
- 용량이 다르면 서로 다른 상품으로 분류된다.
- 매칭 기준을 충족하지 못한 후보는 결과에서 제외된다.

검증
- 동일 이름·다른 용량 테스트
- 동일 상품·다른 색상 테스트
- 매칭 실패 응답 테스트
```

이제 에이전트와 사람 모두 무엇을 구현하고 무엇으로 완료를 판단할지 알 수 있습니다.

## Hermes에서는 이렇게 사용한다

Hermes의 스킬은 `~/.hermes/skills/` 아래에 저장되는 필요 시 로드되는 지침 문서입니다. 설치된 스킬은 슬래시 명령이나 자연어로 호출할 수 있습니다. 자세한 구조는 [Hermes Skills System 공식 문서](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills)에서 확인할 수 있습니다.

이번에 만든 스킬은 다음처럼 사용합니다.

```text
/clarify-work 가격 비교 API를 구현 중인데 동일 상품 기준이 애매해
```

또는 자연어로 요청해도 됩니다.

```text
지금 구현을 멈추고 clarify-work 방식으로 모호함부터 없애줘.
```

그러면 에이전트는 바로 다음 코드를 작성하지 않습니다.

```text
현재 코드·diff·테스트·이슈 확인
→ 사실·가정·결정·실험 분리
→ 영향이 가장 큰 질문 하나
→ 답변 반영 후 전체 모호함 재평가
→ 중요한 모호함이 없어질 때까지 반복
→ 결정·제외 범위·인수 조건·검증 방법 정리
→ 구현 재개
```

새로 만든 스킬은 현재 로컬 Hermes 프로필에서 로드 검증까지 마쳤습니다. 다만 아직 여러 실제 프로젝트에서 장기간 사용해 본 것은 아닙니다. 질문이 너무 길어지거나 반대로 중요한 예외를 일찍 닫는 문제는 실제 작업에서 더 확인해야 합니다.

## 자동 훅보다 수동 체크포인트를 선택한 이유

처음에는 에이전트가 모호함을 감지하면 자동으로 질문하게 만드는 훅도 생각했습니다.

그런데 “지금 모호한가?”는 단순한 명령 패턴이 아니라 의미 판단에 가깝습니다. 자동 훅으로 만들면 다음과 같은 문제가 생길 수 있습니다.

- 저장소 규칙으로 해결 가능한 세부 사항에도 계속 개입한다.
- 구현 흐름을 너무 자주 끊는다.
- 사용자가 이미 허용한 자율적 판단까지 다시 묻는다.

그래서 지금은 사람이 필요할 때 호출하는 방식이 더 낫다고 판단했습니다.

```text
큰 기능 시작 전 명세가 필요하다 → 전체 Interview·Seed 흐름
구현 중 특정 판단이 막혔다       → clarify-work 체크포인트
원인이 불명확한 기술 문제다       → 디버깅 또는 작은 spike
```

도구 하나로 모든 모호함을 해결하려 하기보다, 모호함이 나타난 시점과 크기에 따라 다른 방법을 쓰는 편이 자연스럽습니다.

## 마무리

AI 코딩에서 위험한 순간은 에이전트가 코드를 못 쓰는 때만은 아닙니다. 오히려 요구사항의 빈칸을 아주 자연스럽게 채우며 계속 진행할 때가 더 알아차리기 어렵습니다.

그렇다고 작은 모호함이 생길 때마다 프로젝트 전체를 다시 명세할 필요는 없습니다.

제가 이번에 정리한 방식은 단순합니다.

```text
멈춘다.
코드가 답할 수 있는 사실은 먼저 확인한다.
사람이 결정할 질문은 하나씩 묻는다.
답변마다 남은 모호함을 다시 계산한다.
테스트 가능한 기준이 생기면 다시 구현한다.
```

아직 이 스킬이 모든 상황에 맞는다고 말할 수는 없습니다. 하지만 AI에게 구현 속도만 요구하기보다, **언제 멈추고 무엇을 물어야 하는지**도 작업 흐름의 일부로 만들었다는 점에서 의미가 있었습니다.
